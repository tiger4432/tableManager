## 1. 판정

# 🔴 NO-GO (병합 차단 1건)

**근거 한 줄:** B2가 **닫히지 않았다.** 수정은 "조회가 계속 실패하는" 경우만 막고, `saveDoeToServer`의 **회복 재시도가 성공하는 경로**에서는 `S.doe`가 서버본을 한 번도 담지 않은 채 `S.doeServerLoaded=true`가 되어 — **원래의 전량 삭제 + 형제 결함인 덮어쓰기가 둘 다 그대로 재현된다.** 라이브 브라우저에서 2회 재현했다(쓰기는 가로채 실 데이터 무접촉).

## 2. 확인된 결함

### 🔴 C1 [차단·심각도 높음] B2 미해소 — 회복 재시도 경로에서 전량 삭제 + 덮어쓰기가 그대로 재현
`client2/src/transfer_plan.js:927-942` (회복 재시도) · `:1153-1156` (전역 상태 선언) · `:988-1005` (keep/prune 호출) · `:1043-1078` (`pruneScoped`)

**뿌리.** `loadDoeFromServer`는 성공하면 **함수 안에서** `S.serverKeys`와 `S.doeServerLoaded=true`를 전역으로 세운다(`:1154-1156`). 그런데 `saveDoeToServer`의 회복 재시도는 반환값의 `retry.doe`를 **의도적으로 버린다**:

```js
if (!S.doeServerLoaded) {
  const retry = await loadDoeFromServer();
  if (!retry.ok) { …저장 보류 후 return; }   // ← 여기만 테스트됨
  S.saveError = null;                        // ← retry.doe 는 버려진다
}
```
주석은 *"사용자가 그 사이 편집한 내용이 정본이다"* 라고 정당화하지만, 그 편집은 **서버 상태를 한 번도 보지 못한 화면 위에서** 이뤄진 것이다. 결과적으로
- `S.doeServerLoaded` = **true** (= "서버를 안다") 인데
- `S.doe` = **최초 로드 실패 당시의 빈/낡은 초안 상태**

라는 모순 상태가 만들어지고, 이후 `keep`은 화면 기준으로, `candidates = serverKeys − keep`는 서버 기준으로 계산되어 **차이 전부가 삭제 대상**이 된다.

**라이브 재현 ①(강제 500, 1회만).** `map_doe` GET을 **딱 1회** 500으로 주입 → 이후 회복. 맵 `bonding_map / AAA` 열기 → 헤더 `⚠ 서버 상태 미확인` + 경고 토스트(여기까지는 수정대로) → DOE 패널에서 값 `F`에 `[+ 구간]` **한 번** 클릭. 1.7초 뒤 클라가 시도한 서버 쓰기:

```
PUT  map_doe/data/updates        → bonding_map|AAA|F|1  stack_band=""  qty_total=0
                                   (서버 실제값: GOLD-1 / 100 → 파괴)
POST map_doe/rows/batch_delete   → row 019f9dfb-651c-…  (= bonding_map|AAA|F|2, GOLD-2/90)
POST map_doe_source/rows/batch_delete → 4행 전량
헤더: "자동 저장 19:58"   ·   토스트: 0건
```

**라이브 재현 ②(절단 응답 + 낡은 초안).** 하드 에러조차 필요 없다. `map_doe` 응답을 `total=9 / rows=2`로 절단 위장(= 실제로 500행 초과 시 발생) + 7월 1일자 로컬 초안 존재. 맵 열기 → `응답 절단 (9 > 2)` 경고(정상) → `need` 필드 1회 수정:

```
PUT  map_doe/data/updates        → bonding_map|AAA|F|1  stack_band="STALE-DRAFT"  qty_total=8
POST map_doe/rows/batch_delete   → 1행     POST map_doe_source/rows/batch_delete → 4행
헤더: "자동 저장 20:07"   ·   토스트: 0건
```
즉 **3주 묵은 로컬 초안이 다른 세션의 최신 계획을 통째로 대체**한다. 요구 ⓒ가 정상 경로에서만 지켜지고 실패 경로에서 뒤집힌다.

**두 재현 모두 쓰기 요청을 `fetch` 셰임으로 가로채 실제 DB는 무접촉이다** — 검수 전후 `map_doe` 2행·`map_doe_source` 4행의 `updated_at`이 `2026-07-26 19:34:51`로 불변임을 확인했다.

**왜 구현자 검증이 통과했는가.** 보고서 §6-c-1 ⓓ의 공격은 GET을 **지속적으로** 막았다(`차단된 GET: 2회` = 최초 로드 + 재시도). 즉 재시도가 **실패하는** 분기만 실증했고, **재시도를 추가한 바로 그 이유인 "일시 장애 후 회복" 분기는 한 번도 실행되지 않았다.** 그 상태에서 "해소"·"서버 행 전부 바이트 동일"로 결론지었다.

**최소 발현 조건 (전부 평범하다).**
1. 열린 맵에 서버 DOE 행이 있다 · 2. 맵 열 때 `map_doe`/`map_doe_source` GET이 **1회** 실패하거나 500행을 넘겨 절단된다 · 3. 다음 저장 전에 네트워크가 회복된다 · 4. 사용자가 DOE를 **한 번** 편집한다.

**권장 조치 (택1, ①이 정본).**
① 재시도가 성공하면 **서버본을 반영**한다 — 최초 로드(`:1230-1240`)와 동일하게 `S.doe = retry.doe` + `renderAll()` + 고지 토스트. 사용자의 미반영 편집은 서버본 위에 다시 얹는 병합 규칙을 명시하거나, 최소한 "서버본으로 갱신했다"를 알리고 이번 저장을 건너뛴다.
② 또는 **"서버 상태를 안다"의 정의를 좁힌다**: `S.doeServerLoaded`는 *"`S.doe`가 서버본에서 유래했다"*는 의미여야 한다. 재시도 성공만으로 참이 되면 안 되고, `S.doe`를 서버본으로 세운 경로에서만 참이 되게 한다.
③ 방어선 추가(위 둘과 병행 권장): `serverKeys`에는 있는데 `S.doe`에 흔적조차 없는 `doe_value`가 나오면 prune 대신 **사용자 확인**을 요구한다. 계획 전량 삭제는 확인 없이 일어날 일이 아니다.

### 🟠 C2 [심각도 중] `loadDoeFromServer`가 `loadSeq` 검사 없이 전역 상태를 세운다 — 맵 전환 레이스
`client2/src/transfer_plan.js:1154-1156` vs 호출부 가드 `:1223`

호출부는 `if (seq !== S.loadSeq) return;`로 늦게 도착한 응답을 버리지만, **함수 내부는 이미 `S.serverKeys`·`S.doeServerLoaded`를 세운 뒤다.** 맵 A의 느린 응답이 맵 B 전환 이후 도착하면:
- `S.ctx` = B · `S.doe` = B의 초안 · `S.serverKeys` = **A의 키** · `S.doeServerLoaded` = **true**

삭제 방향은 안전하다(키에 `map_key`가 박혀 있어 교집합이 공집합 → 과삭제 없음). 그러나 **쓰기 방향은 안전하지 않다**: B의 로드가 실패했더라도 늦은 A 응답이 `doeServerLoaded=true`로 만들어 §C1의 보류 장치를 우회하고, B의 서버 행을 재번호된 `band_seq`로 덮어쓴다. 부수적으로 B의 잔재 정리도 조용히 무력화된다(과소 삭제).

**권장 조치.** `loadDoeFromServer`에 `seq`(또는 `S.ctx` 스냅샷)를 넘기고 전역 상태 기록 직전에 재확인한다.

### 🟠 C3 [심각도 중] 500행 초과 계획은 **영구히 저장 불가**가 된다 — 절단 강등의 부작용
`client2/src/transfer_plan.js:1090` (`limit=500`) · `:1105-1108` · `:1136-1138`

절단 응답을 로드 실패로 강등한 것 자체는 옳다(§3-S2에서 실측 확인). 그러나 `map_doe`와 `map_doe_source`가 **같은 `limit=500`** 을 쓰므로, 자재 행이 500을 넘는 계획은 **매번** 절단 → 매번 `ok:false` → 저장이 **영구 보류**된다. 사용자가 볼 수 있는 것은 경고 토스트 하나뿐이고 회복 수단이 없다.

`map_doe_source` 1행 = (값, 구간, 자재)이므로 20값 × 3구간 × 10자재 = 600행으로 도달 가능하다. 확장성 규율("1000만행에서도 동작") 대비 500은 지나치게 낮다.

**권장 조치.** 페이지네이션으로 전량 수집하거나, 서버 캡(`MAX_DOE_PER_PLAN`)과 정합하는 상한을 쓰고 상한 초과 시 **사용자에게 조치 가능한 안내**를 준다.

### 🟡 C4 [심각도 낮음] 페인트 잠금 콜드 스타트는 여전히 fail-open (다만 조용하지 않다)
`client2/src/map_editor.js:38` · `:95-103`

`degrade()`는 *직전 값*을 유지하는데, 페이지 로드 후 **첫 조회가 실패하면 직전 값이 `{enabled:false}`(기본값)** 이라 8개 강제 지점이 전부 열린 채 시작한다. 칩(`⚠ 잠금 규칙 미확인`)이 뜨므로 M2가 요구한 "조용한 fail-open 제거"는 충족되나, 잠금 자체는 걸리지 않는다.
부수 관찰: 테이블 전환 시 실패하면 **이전 테이블의 잠금 값**을 새 테이블에 계속 적용한다(실측: `bonding_map`의 `F` 잠금이 `sample_map`에 유지됨). fail-closed 방향이라 안전하지만 의미상 부정확하다.

## 4. 런타임 검증 필요 (코드·자동화로 단정 불가)

1. **캔버스 페인팅 육안 확인** — 합성 마우스 이벤트로는 페인팅이 발화하지 않아 잠금 셀 위 덮어쓰기 차단을 실증하지 못했다. 실제 마우스로 `F` 셀 위에 다른 브러시를 칠해 거부되는지 확인 필요.
2. **더티 가드(프레임 뒤로가기)** — 자재 프레임 진입/복귀가 필요해 미실증. 편집 후 프레임 back에서 확인창이 뜨는지 육안 확인.
3. **C7 실증** — 오버레이를 올린 상태에서 `phys_offset_x`만 바꾸고 `[적용]` → 오버레이가 따라 움직이는지. 어긋나면 C7 확정.
4. **C3 임계** — `map_doe_source` 500행 초과 계획을 만들어 저장이 영구 보류되는지 확인(현재 라이브는 4행이라 미발현).
5. **C1 수정 후 재검** — §5의 재현 절차를 그대로 다시 돌려 쓰기·삭제 시도가 0건인지 확인할 것. *지속 실패*가 아니라 **1회 실패 후 회복**으로 돌려야 한다.

## 8. 교훈 제안 (`agent_workspace/memory/qa-reviewer.md` — 총괄 검수 후 반영)

- **함정**: "실패를 감지하고 회복을 재시도한다"는 수정은 **실패 분기**만 시험해도 통과한 것처럼 보인다. 정작 재시도를 도입한 이유인 **회복 성공 분기**가 미검증으로 남고, 거기서 원 결함이 그대로 재현되는 일이 잦다.
  **올바른 방법**: 재시도·폴백·자가치유 코드를 볼 때는 항상 **실패(지속) / 회복(1회 실패 후 성공) / 부분 성공** 세 분기를 각각 돌린다. 구현자가 "주입 N회"를 보고하면 **N이 재시도 횟수 이상인지**를 먼저 확인한다 — 같으면 회복 분기는 시험되지 않은 것이다.
- **함정**: 조회 함수가 반환값과 **전역 상태**를 동시에 세우면, 호출부의 시퀀스 가드(`if (seq !== S.loadSeq) return`)를 통과해도 전역은 이미 오염돼 있다.
  **올바른 방법**: "이 함수가 반환 전에 무엇을 전역에 썼는가"를 먼저 세고, 호출부의 모든 조기 return 지점에서 그 전역이 롤백되는지 확인한다.
- **함정**: "안다/모른다"를 나타내는 플래그는 이름이 아니라 **세워지는 지점**으로 의미가 결정된다. `doeServerLoaded`는 이름상 "서버본을 로드했다"지만 실제로는 "서버에 요청이 한 번 성공했다"였고, 그 간극이 차단 결함이 됐다.
  **올바른 방법**: 안전 플래그를 만나면 *세워지는 모든 지점*을 열거하고, 각 지점에서 **플래그가 보증한다고 주장하는 불변식이 실제로 성립하는지** 하나씩 대조한다.
- **함정**: 삭제 대상을 `A − B` 차집합으로 계산하는 코드는, 두 집합이 **서로 다른 시점·다른 출처**에서 오면 조용히 "전부 삭제"가 된다(여기서는 `serverKeys`=회복 후 서버, `keep`=회복 전 화면).
  **올바른 방법**: 차집합 삭제를 보면 두 피연산자의 **출처와 시점이 같은지** 묻는다. 다르면 그 자체가 결함이다.
