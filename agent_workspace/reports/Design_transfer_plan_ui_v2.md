## 0. 요약 (4줄)

1. **「전사 계획」이라는 개체를 없앤다.** stage 선택·타깃 입력·`plan_id`·모드 A/B·페인팅 진입/이탈 버튼이 전부 사라진다. 남는 것은 ⓐ *무슨 맵을 열었나*(좌) ⓑ *그 맵의 값이 무슨 뜻인가*(우) 둘뿐.
2. **우측 패널 = 세로 두 목록.** 위 **DOE LIST**(값 정의 + 브러시 팔레트), 아래 **사용 자재 리스트**(**DOE별로 그 DOE가 쓰는 자재 전부를 나열** — 자재 맵으로 가는 유일한 허브).
3. **맵에 층 차원은 없다.** 층 차이는 DOE의 **STACK 구간 행**이 표현한다. **소스는 묶음(pool)** 이며, 묶음의 나열·수량·맵 구축은 DOE 행이 아니라 **자재 리스트**가 진다 — 그래서 DOE 표가 짧고 좁게 유지된다.
4. **실맵 직접 편집의 대가로** 로드 정체성 핀 + 키 기본 잠금 + 델타 표시 Push 모달 3중 가드를 세운다.

**전체 UI 추가량: 목록 하나(자재) + 브레드크럼 한 줄 + 뒤로가기 버튼 하나.** 그 외는 전부 삭감이다.

## 1. 진단 — "왜 따로 노는가" (코드 근거)

사용자 원문: *"bonding_map을 열어서 편집하면 그게 BONDING PLAN이고 DT_MAP을 열어서 편집하면 그게 DT PLAN이 되어야 하는데, MAP SEARCH & LOAD 이거랑 전사 계획 이거랑 다 따로 논다."*

현행 코드에는 **맵 정체성이 두 벌** 존재한다.

| | 좌측「1. Map Search & Load」 | 우측「2. 전사 계획」 |
|---|---|---|
| 무엇을 가리키나 | `selectedTable` + `meta-input-*` (맵 키) | `S.stage` + `S.target` |
| 식별자 | `getMapIdFromMeta()` → `BASE-77` | `buildPlanId()` → `bonding__BASE-77` (`transfer_plan.js:122`) |
| 저장처 | 실 맵 테이블 (`bonding_map` / `dt_map`) | `transfer_plan_map` (**사본**) |
| 입력 방식 | 스키마 유도 필드(`map_key_columns`) | 자유 텍스트 + 그래프 노드 자동완성 |

두 정체성은 **어디서도 동기화되지 않는다.** `enterPlanPaint()`(`map_editor.js:3543`)는 진입 시 `selectedTable`을 `transfer_plan_map`으로 **바꿔치기**하고 좌측 패널을 통째로 잠근다(`el.tableSelect.disabled = true`, `lockPlanMetaInputs(true)`). 현행 설계는 "계획 페인팅 중에는 좌측 패널이 없는 것으로 친다"는 회피책이며, 사용자가 느낀 이질감의 정확한 출처다.

**이미 서버 config에 답이 있다.** `server/config/transfer_plan_config.json`:

```
stages.dt.target_map.table       = "dt_map"
stages.bonding.target_map.table  = "bonding_map"
```

stage → 테이블 매핑이 **선언되어 있다.** 역방향 조회 한 줄이면 `stage = stageOf(selectedTable)`. **stage 선택 UI는 처음부터 불필요했다** — 새 계약이 아니라 기존 선언의 역인덱스일 뿐이다.

## 2. 새 모델 — 정체성 하나

```
편집 정체성 = (selectedTable, mapKey)          ← 좌측 패널이 단일 원천
                     ↓ 유도 (config 역인덱스, 새 계약 없음)
stage        = stageOf(selectedTable)          ← dt_map→dt / bonding_map→bonding / 그 외→null
                     ↓
DOE 집합     = legend(ref_table=selectedTable, map_key=mapKey) + 전사 확장 필드
                     ↓ 자동 집계 (중복 제거 + 소요 합산)
사용 자재    = ⋃ DOE.materials
```

**핵심 귀결 4가지**

- **`plan_id` 소멸.** DOE 키가 `plan_id|doe_value` → **`ref_table|map_key|doe_value`** (`map_split_registry`의 composite key 관례 `ref_table|map_key|value`와 동일).
- **`transfer_plan_map` 소멸.** 계획 맵이 곧 `bonding_map`/`dt_map`이므로 사본 불필요.
- **legend와 DOE가 한 행의 두 얼굴.** `split_desc` = DOE 설명, `color` = DOE 색, `value` = DOE value. 전사 대상이 아닌 맵에서는 확장 필드가 안 뜨고 순수 legend로 동작 — **같은 컴포넌트, 점진적 공개**.
- **사용 자재는 입력이 아니라 집계다.** 사용자가 별도로 관리하지 않는다. DOE들이 참조한 자재를 중복 제거·소요 합산해 자동으로 목록이 선다.

폭 변화: 좌 350→**330**, 우 620→**430** → 캔버스 **+210px**.

### 3.2 우측 패널 4층 + 이중 스크롤

| 층 | 높이 | 내용 |
|---|---|---|
| **계획 헤더** | 고정 | stage 배지 + `테이블 · 맵 키` + 소스종류/값컬럼 + 자동저장 시각. **입력이 아니라 "유도된 사실"의 표시** |
| **요약** | 고정 (sticky) | 검증 스킵 배너 → 배지 4종 → STACK 커버리지 스트립 |
| **DOE LIST** | `flex: 1`, 최소 180px | 아코디언 행. **자체 스크롤** |
| **사용 자재** | 고정 240px | DOE별 그룹 목록. **자체 스크롤** (그룹 헤더는 스크롤 중 sticky) |

**이중 스크롤을 쓰는 이유:** 자재 리스트는 *이동 허브*다. DOE를 아무리 아래로 스크롤해도 **허브는 항상 화면에 있어야** 왕복 동선이 성립한다. 단일 스크롤이면 DOE 10개만 넘어가도 허브가 화면 밖으로 사라진다.

각 목록 컨테이너는 `flex` + `min-height: 0` + `overflow-y: auto`. 자재 0건이면 자재 영역은 **접혀서 자리를 차지하지 않는다**(계획 대상 아닌 맵에서 자동 소멸).

### 3.3 DOE LIST — 값 정의 + 브러시 팔레트

```
접힘   ▶ ●D1  1       DT-A 외 3매      120 / 120        ✓
       ▶ ●D2  2-11    DT-A 외 3매      200 / 180        [확인 불가]
       ▶ ●D3  12      DT-E             90 / 0           [부족 30]
                └ STACK   └ 자재(요약, 비대화형)  └ 소요/칠함

펼침   ▼ ●D2  고압 본딩 · 30N 조건군  [브러시]         [확인 불가]
       ├ STACK 구간 [2-11    ]      총 소요 [200]
       ├ 사용 자재  (DT-A ✕)(DT-B ✕)(DT-C ✕)(DT-D ✕)(＋)
       │            ※ 여기서는 "무엇을 쓴다"만 선언. 수량·맵 구축은 아래 자재 목록.
       ├ knob 계획  force=30N  temp=180℃  time=2.5s        [+ knob]
       └ 설명       [2~11층은 DT-A~D 4매 묶음 투입 …]
                    ※ 이 서술이 곧 map_split_registry.split_desc
```

- 행 클릭 = ① 선택 ② 브러시 전환 ③ 펼침 — **한 동작으로 셋 다.** 한 번에 하나만 펼친다.
- 접힌 행의 자재 열은 **`DT-A 외 3매` 요약 텍스트**(비대화형). 칩을 여기 나열하면 행이 세로로 자란다.
- 펼침 안에서만 칩으로 편집: 칩 `✕` = 제거(1동작), `＋` = 그 자리에 인라인 자동완성이 열림(1동작). **새 모달 없음.**
- **소스 맵으로 가는 버튼은 DOE 행에 없다.** 이동은 자재 목록 전담(§3.4).
- 소요는 "층당 × 층수"가 아니라 **구간 총 소요 1칸**. 층별 정밀 배정이 불가능하다는 사용자 확정에 따라 입력이 하나 줄었다.

### 3.4 사용 자재 리스트 — **DOE별 그룹** + 이동 허브

계획 전체의 평평한 집계가 아니라 **DOE 단위로 묶인 목록**이다. 각 DOE가 쓰는 자재 전부가 그 DOE 아래 나열된다.

```
┌ 사용 자재  (DOE별) ─────────────── [↻ 가용 재조회] ┐
│ ●D2  2-11 · 소요 200                              │  ← 그룹 헤더 = DOE (색 칩 재사용)
│   ├ DT-A    480 / 50        [맵 ✓]                │
│   ├ DT-B    372 / 50        [맵 ✓]                │
│   ├ DT-C    미상 / 50    ⚠  [맵 ✓]                │
│   └ DT-D    279 / 50        [맵 ✓]                │
│ ●D3  12 · 소요 90                                 │
│   ├ DT-A    480 / 90   [↔ 2 DOE ⚠ 140/480]  [맵 ✓]│  ← 같은 자재 재등장
│   └ WF-05     — / 90        [맵 없음]             │  ← 미구축
│                                                   │
│ 행 클릭 = 그 자재의 맵을 엽니다 (뒤로가기로 복귀)     │
└───────────────────────────────────────────────────┘
```

**그룹 헤더 = DOE.** 위 DOE LIST와 **같은 색 스와치·같은 value 표기**를 쓴다 — 두 목록이 한 몸으로 읽히게 하는 유일한 장치이며, 별도 범례나 연결선을 추가하지 않는다.

**자재 행은 3요소로 못 박는다** (그 이상 금지):

| 요소 | 표시 | 비고 |
|---|---|---|
| 식별자 | `DT-A` (mono) | lot\|slot |
| 가용 / 소요 | `480 / 50` | 가용 = 자재 실측. 소요 = **그룹 총 소요의 균등 배분**(200÷4매) |
| 상태 | `맵 ✓` / `맵 없음` | 자재 맵 존재 여부 |

> **소요가 균등 배분인 이유**: 사용자 확정대로 *"몇 층에 뭐가 들어갈지 정확히 예측할 수 없어 4매 묶어서 투입"* 하므로, 매별 소요는 **애초에 지정 대상이 아니다.** 정본 수량은 **그룹 헤더의 `소요 200`** 이고 행의 숫자는 파생 표시다. 파생임이 드러나도록 헤더에 소요를 두고 행에는 배분값만 둔다.

**DOE LIST ↔ 자재 그룹 연동 (필터 금지 — 전체가 보여야 한다):**
위 DOE 행을 선택하면 아래의 해당 그룹이 ① 좌측 액센트 바 점등 ② `scrollIntoView({block:'nearest'})` 로 시야 확보. **숨김 없음, 상태 없음.** 반대 방향(자재 → DOE 강조)은 넣지 않는다 — 양방향 하이라이트는 밀도 대비 이득이 적다.

**교차 초과배정 (같은 자재가 여러 DOE에 쓰일 때) — 서버 F4 판정과 직결**

같은 자재는 **양쪽 그룹에 다 보인다**(요구사항). 대신 그 행에 공유 칩을 하나 붙인다:

| 상태 | 칩 | 색 |
|---|---|---|
| 공유 중 · 합계 여유 | `↔ 2 DOE` | 중립(회색) |
| 공유 중 · **합계 초과** | `↔ 2 DOE ⚠ 140/480` (총소요/가용) | 적색 + 해당 자재의 **모든 행**이 동시에 적색 테두리 |
| 공유 중 · 가용 미상 | `↔ 2 DOE · 판정 불가` | 앰버 (초과 아님이라 단정하지 않음) |

- 칩 클릭 = 같은 자재의 **다른 그룹 행들이 동시에 깜빡임**(형제 하이라이트). 새 패널·모달 없이 "어디서 겹쳤는지"를 보여주는 최소 장치.
- 요약 배지에 `교차 초과배정 N건` 추가 — 서버 `source_overallocated` 경고와 같은 사건이므로, **서버가 그 경고를 주면 그것을 정본으로 표시**하고 클라 계산은 서버 응답 전 잠정치로만 쓴다(`잠정` 표기). 서버가 `미검증`이면 이 배지도 초록이 되지 않는다.

**⭐ 왕복의 보상 — 돌아왔을 때 수량이 갱신되어 보이는 지점**

이 워크플로의 핵심 보상이므로 명시적으로 설계한다.

```
자재 행 클릭
  → 편집 프레임 push (현재 맵 상태·오버레이·스크롤 스냅샷)
  → dt_map · DT-C 로드   [맵 없음이면 빈 격자 + 자재 규격 프리셋 자동 적용]
  → 사용자가 맵을 만들고 [⚡ Push]
  → 뒤로가기 (브레드크럼)
  → 프레임 pop + 복원
  → ★ 그 자재의 가용을 자동 재조회 (전체가 아니라 해당 자재만)
  → ★ 자재 행: `가용 미상 → 345` 로 갱신 + 1회성 하이라이트 + [맵 없음] → [맵 ✓]
       (같은 자재가 여러 그룹에 있으면 **모든 그룹의 그 행이 함께 갱신**된다)
  → ★ 상단 요약 배지 재계산 (부족 3 → 부족 2, 교차 초과배정 재판정)
```

- **자동 재조회는 해당 자재 1건만.** 전체 재조회는 느리고, 사용자가 방금 한 일과 무관한 값까지 흔들려 "무엇이 바뀐 건지" 읽기 어렵다.
- **하이라이트는 `opacity` 페이드만** — 행 위에 절대 배치된 오버레이 레이어의 `opacity`를 1→0으로 800ms. `background-color` 트랜지션은 페인트를 유발하므로 쓰지 않는다.
- **값이 안 바뀌었으면 하이라이트도 안 뜬다.** 매번 번쩍이면 신호가 죽는다.
- 재조회 실패 시 `가용 미상`으로 되돌리고 `[↻]` 노출 — **성공으로 위장하지 않는다.**

### 3.5 STACK 구간 표기 — 자유 입력, 강제 없음

**맵에 층 차원은 없다**(§8-① 확정). 층 차이는 **DOE의 STACK 구간 행**이 표현한다:

```
값 A ─┬─ H1~H2   (자재: DT-A, DT-B, DT-C, DT-D)
      └─ H2~H3   (자재: DT-E)        ← 한 value 안에 구간 행이 여러 개
값 B ─── H1~H3   (자재: DT-F, DT-G)
```

**표기는 강제하지 않는다.** 입력칸 하나에 자유 텍스트: `1` / `2-11` / `12` / `H1~H2` 어느 쪽이든 쓰던 대로 받는다. 층 번호 구간인지 바닥·중간·꼭대기 3티어인지가 미확정이므로 **UI가 먼저 어휘를 못 박지 않는다.**

> **선택적 편의 기능(제안만)**: 입력칸 옆 `[바닥][중간][꼭대기]` 프리셋 칩 — 각각 `1` / `2-N-1` / `N`을 채워 넣는 단축키. 사용자의 *"1층이랑 꼭대기만 다르고 이외 층은 거의 유사"* 를 3클릭으로 세팅할 수 있다. **다만 총 층수 N을 알아야 동작하고**(§8-② 미해결), 칩이 행마다 붙으면 밀도가 오른다 — **"절대 복잡하면 안 된다"에 걸리면 빼는 것이 맞다.** 자유 입력만으로 기능은 완결된다.

## 4. 다섯 질문에 대한 답

### Q1. 별도 "계획" 영역이 필요한가? → **아니다. legend가 곧 DOE 편집기다.**

**답: 행 확장(아코디언) + 아래 자재 목록.** 별도 계획 영역·별도 상세 컬럼 모두 폐기.

근거:

- **의미론적으로 같은 행이다.** `map_split_registry`는 이미 `(ref_table, map_key, value) → (split_desc, color)`이고 DOE는 여기에 `(STACK 구간, 자재, 수량, knobs)`가 붙은 것. ontology_mapping.json 서술 그대로 — *"페인팅 value 하나가 곧 하나의 실험 조건군"*.
- **브러시가 곧 DOE다.** 페인팅 중 "이 값이 무슨 조건인지"를 보려면 팔레트와 정의가 같은 자리에 있어야 한다.
- **점진적 공개로 일반 맵까지 커버.** `stage == null`이면 확장 필드와 자재 목록이 렌더되지 않고 순수 legend. 「원시 범례 & 브러시」 details를 따로 둘 필요가 사라진다.

**담는 방법:** 반복 항목(자재)을 DOE 행 밖으로 빼낸 것이 이번 구조의 핵심이다. DOE 행은 `VALUE | STACK | 자재 요약 | 소요/칠함` 4열로 짧게 유지되고, 폭발할 수 있는 축(자재 N개)은 아래 목록이 흡수한다.

### Q2. 소스 사용 영역 지정 왕복 → **모드가 아니라 "편집 스택", 진입점은 자재 목록 하나**

**핵심 전환:** 현행 `S.mode = 'B'` + 좌/우열 렌더러 교체 + 「저장하고 base로」 = **모드**. 새 안은 *맵을 하나 더 연 것*이고, 유일한 새 크롬은 **브레드크럼 한 줄**이다.

```
[← bonding_map · BASE-77]  ›  dt_map · DT-C
                              돌아가면 BASE-77의 편집 상태·오버레이·스크롤이 복원됩니다
```

- **진입점은 자재 목록 행 하나뿐.** DOE 표 셀에 흩어져 있지 않다. 하는 일은 좌측 패널이 하는 일과 동일하다 — 테이블·맵 키를 세팅하고 로드. 다른 점은 *현재 프레임을 스택에 push*하는 것뿐. 모달 없음, 모드 배너 없음.
- **미구축 자재도 같은 동선.** `[맵 없음]` 행을 클릭하면 빈 격자 + 자재 규격 프리셋이 적용된 상태로 열린다 — "맵을 만들러 간다"와 "맵을 고치러 간다"가 같은 동작이다.
- **자재 맵의 legend**: 그 자재를 쓰는 DOE들이 legend로 선다(색 그대로). 한 테이프가 여러 DOE에 공급하는 것이 정상이므로 영역 분할을 한 화면에서 끝낸다.
- **복귀:** 브레드크럼 부모 크럼 클릭. 더티면 인라인 3지선다(`💾 저장하고 돌아가기` / `← 버리고 돌아가기` / 취소). `confirm()` 대신 패널 하단 인라인 버튼.
- **상태 보존:** 기존 `snapshotEditorState()`/`restoreEditorState()`(`map_editor.js:3206`/`3241`)가 이미 깊이 1의 스택이다. 스택 배열로 일반화하면 그대로 재사용.

**⚠️ 보존 누락 2건 (로직 — Client PM 이관):**

| 항목 | 현행 | 필요 |
|---|---|---|
| `overlayLayers` | `enterCorePaint`에서 `clearOverlayLayers()`, `finishCorePaint`에서도 clear — **돌아오면 오버레이 전멸** | 스택 프레임에 포함해 복원 |
| 캔버스 스크롤/줌 | 스냅샷에 없음 | `#map-workspace`의 `scrollLeft/Top` 저장·복원 |

### Q3. 오버레이 — **「1. Map Search & Load」에 존치, 표현을 강화**

오버레이는 *"캔버스에 무엇이 겹쳐 있는가"* = 로딩의 결과이므로 로딩 패널에 있는 것이 맞다. 계획 패널의 모드 B 전용 오버레이 컬럼(`renderLeftCoreMode`)은 **폐기**하고, 그 기능(defect/EDS 원클릭)은 같은 박스 안 **"추천" 칩 줄**로 흡수한다(열린 맵에 `fail_sources`가 선언돼 있을 때만 등장).

```
🗂 오버레이 (3)                                   [모두 해제]
● core_defect_map / LOT-A_05     1,204칩  [aligned 0°]     👁 ✕
● eds_fail_map    / LOT-A_05       312칩  [aligned 180°]   🚫 ✕   ← 숨김(50% 투명)
● dt_map          / TP-7_02      2,000칩  [일부만·상한2000] 👁 ✕   ← 절단 경고(앰버)
✕ dt_map          / TP-9_01      정렬 불가 [align_unavailable] ↻ ✕ ← 실패 잔존(적색)
추천(선언된 fail 원천):  [＋ defect]  [＋ EDS fail]
```

**설계 판단 4가지**

1. **정렬 상태는 칩으로 항상 노출** — `aligned 180°` / `identity 0°` / `align_unavailable`. 현행은 `alignApplied`일 때만 표기해 **"정렬 안 함"과 "정렬 실패"가 구분되지 않는다.** PROJECT_STATUS의 align 3규율을 3칩으로 직역.
2. **실패한 오버레이도 목록에 남긴다(신규).** 현행 `addOverlayLayer()`는 실패 시 토스트만 띄우고 끝 — **왜 안 겹쳤는지가 화면에서 증발한다.** 적색 행 + `[↻ 다시 시도]`.
3. **절단(`truncated`)은 앰버 경고 등급.** "2,000칩"만 보이면 전량으로 오독한다.
4. **툴바에 `🗂 오버레이 N 표시중` 칩(신규).** 캔버스에 남의 데이터가 겹쳐 있다는 사실이 사이드바를 스크롤해야만 보이면, 오버레이를 실맵으로 착각한 채 페인팅할 위험이 있다.

### Q4. 수량·경고의 위치 — **3층 분산 + 어휘 4단 고정**

| 층 | 위치 | 담는 것 |
|---|---|---|
| **1. 스캔** | DOE 접힌 행 | `소요 200 / 칠함 180` + 판정 배지 1개 |
| **1'. 자재** | 자재 그룹(DOE별) | 헤더 = `소요 200`(정본) · 행 = `가용 480 / 배분 50` + 공유 칩 + 상태 — **가용 수치의 출처는 여기다** |
| **2. 상세** | 자재 행 펼침(선택) | 산식 `총 500 − defect 35 − EDS 20 − 기사용 100 = 345` + fail_breakdown + by_core |
| **3. 전역** | sticky 요약 | 검증 스킵 배너 → 배지 5종(+`교차 초과배정`) → STACK 커버리지 스트립 |

**가용의 출처를 자재 행으로 옮긴 것이 이번 구조의 부수 이득이다.** 묶음 합산을 DOE 행에서 계산해 보여주면 "합계가 왜 이 숫자인지" 추적할 곳이 없다. 자재별로 `가용`을 보여주면 부족의 **출처가 곧 행**이고, 그 행을 클릭하면 곧바로 그 자재를 손보러 갈 수 있다 — **진단과 처치가 같은 자리**다.

**신뢰 어휘 4단 — 초록의 조건을 못 박는다**

| 표기 | 색 | 조건 |
|---|---|---|
| `미상` | 회색 + 점선 밑줄 | `remaining === null` (서버가 모른다고 말함) |
| `확인 불가` | 앰버 | 값은 있으나 `remaining_reliable === false`, 또는 `unverified` / `availability_checked === false` |
| `부족 N` | 적색 | 값이 있고 **신뢰 가능**하고 **검증됨** + `가용 < 소요` |
| `충족` | **초록** | `known && reliable && verified` **3조건 동시** — 하나라도 빠지면 초록 금지 |

- **묶음 판정 규칙**: DOE가 쓰는 자재 중 **하나라도 `미상`이면 그 DOE는 `확인 불가`**. 알려진 것만 더해 `≥1,540 (1매 미상)` 형태의 **하한**으로 표기하고, 절대 확정 숫자로 쓰지 않는다.
- **신규 배지 `신뢰: 통과 / 미검증 / 실패`** 를 요약에 상시 배치. 다른 배지가 우연히 0건이어도 이 배지가 계속 "미검증"을 말한다.
- **`remaining_upper_bound`는 숫자 자리에 넣지 않는다.** 별도 칩 `≤ 240 (실제는 이보다 작음)`로만.
- 판정 로직은 현행 `layerStats`/`doeStats`/`remainingReliability`/`renderValidation`(`transfer_plan.js:509–704`)을 **1비트도 바꾸지 않고** 표현만 재배치한다.

### Q5. 위험 가드 — **실맵 직접 편집의 대가**

새 모델은 격리된 `transfer_plan_map`이 아니라 **실운영 `bonding_map`/`dt_map`에 직접 칠한다.** `pushMapData()`는 `replace_map: true`로 **맵 키 일치 행을 전량 삭제 후 재기록**한다(`map_editor.js:2742–2750`). 맵 키를 한 글자 잘못 고친 채 Push하면 **남의 실맵이 전량 삭제된다.** 현행 C5 가드(`lockPlanMetaInputs`)는 "계획 페인팅 모드 중"에만 걸리는데 새 모델엔 그 모드가 없다 → **가드를 상시화해야 한다.** 자재 맵 왕복이 잦아져 맵 전환 횟수가 늘어나므로 위험 노출도 함께 오른다.

**5중 가드 (위험도 비례 마찰)**

1. **로드 정체성 핀 — 핵심.** 로드 순간 `loadedIdentity = {table, mapKey}` 고정, 좌측 상단 초록 핀으로 상시 표시. 입력이 달라지면 **적색 전환 + Push 비활성 + 우측 배너**. PROJECT_STATUS 초점 #2가 요구한 *"맵 키가 로드한 맵과 달라졌으면 Push 차단"* 의 UI 구현체.
2. **키 필드 기본 잠금.** 로드 후 `readOnly` + 🔒. 변경은 명시적 `[🔓 다른 맵으로 전환]`으로만 — **몰래 키만 바꾸는 경로를 UI에서 없앤다.**
3. **Push 확인 = 전용 모달 + 델타 + type-to-confirm.**
   ```
   서버 현재 1,536셀 → 적재 1,180셀
   삭제 1,536 · 재기록 1,180 · 순감 356셀 (−23%)
   [ ] 기존 셀이 전부 삭제됨을 이해합니다
   확인을 위해 맵 키를 입력: [________]   (BASE-77)
   ```
   **순감이 임계 초과일 때만 타이핑 확인을 요구.** 일상적 소폭 수정에는 체크 1회 — 마찰을 위험에 비례시켜 확인 피로로 인한 무의식 승인을 막는다.
4. **대량 축소 감지.** 서버 현재 셀 수와 대조. 조회 실패 시 델타를 `미상`으로 표시하고 **타이핑 확인 강제**(모르면 더 조심).
5. **자재 맵에서의 Push는 정상 허용하되 정체성 핀이 따라간다.** 자재 맵도 실맵(`dt_map`)이므로 같은 가드를 그대로 적용한다 — 브레드크럼 자식 프레임에서도 핀·잠금·모달이 동일하게 작동해야 한다.

추가 존치: split 서술 누락 경고(`getMissingDescValues`)는 **"DOE 미정의 value 경고"**로 의미 승격해 유지.

## 7. 1안 vs 2안 (DOE 목록 레이아웃)

자재 목록이 하단에 확정된 상태에서, 위쪽 DOE 목록의 상세 편집 방식만 비교한다.

| | **1안 · 아코디언 (추천)** | 2안 · 좌 리스트 / 우 상세 |
|---|---|---|
| 폭 | 430px | 620px |
| 캔버스 | +190px | 변화 없음 |
| 자재 목록과의 공존 | 세로 3분할(요약/DOE/자재)로 자연스럽게 쌓임 | **2열 상세 + 하단 자재 = 3분할이 2차원으로** — 복잡도 급증 |
| 장점 | 스캔 열이 하나 / 브러시 팔레트 상시 노출 / 선택·편집이 같은 행 | 상세가 길어도 목록이 안 밀림 / 현행 구조 재사용 |
| 단점 | 펼친 행이 길면 다음 DOE가 밀림 → **하나만 펼침**으로 완화 | 1280px에서 캔버스가 950px로 눌림 / 목록↔상세 선택 동기화가 또 하나의 상태 |

**추천: 1안.** 자재 목록이 하단 밴드를 차지하는 순간 2안은 "좌우 2열 + 상하 2단" 격자가 되어 **"절대 복잡하면 안 된다" 제약과 정면 충돌**한다. 1안은 세로 스택 하나로 끝난다.

## 8. 미해결 / 확정 사항

### ① ~~`bonding_map` 층 차원~~ — **해소됨 (사용자 확정 2026-07-26)**

> 사용자 원문: *"실제 공정은 **1층이랑 꼭대기만 다르고 이외 층은 거의 유사**해."*

**결론: 맵에 층 차원을 추가하지 않는다.** `bonding_map`은 현행 `(base, x, y)` 2D 스키마로 충분하고 **캔버스 층 스텝퍼는 넣지 않는다.**

- 층에 따라 달라지는 것은 **어느 자재를 쓰는가**이지 **어느 좌표를 쓰는가**가 아니다.
- 층 차이는 **DOE의 STACK 구간 행**이 이미 표현한다(§3.5).
- 특정 구간에서 쓰는 좌표가 다른 예외가 있더라도 **별도 value로 칠하면 표현된다** — 그 value의 STACK 구간이 곧 *"이 셀은 이 구간에서만 쓰인다"* 는 뜻이므로.

`leg` 컬럼은 값 컬럼(=DOE value 저장처)으로 사용한다. **설계 귀결: 툴바가 `[편집 대상][stage][오버레이][FRONT][Brush]` 5칩으로 확정**되고 화면이 한 겹 더 단순해졌다.

### ② ~~소스가 단일인가~~ — **해소됨 (사용자 확정 2026-07-26)**

> 사용자 원문: *"실제 몇 층에 뭐가 들어갈지 **정확히 예측할 수 없어** 여러 개의 DT 군을 지정할 수도 있어 (한 매당 500칩이면 그냥 **4매 묶어서 투입**)."*

**결론: 소스는 묶음(pool)이고, 층별 정밀 배정은 하지 않는다.** 계획의 단위는 *"이 STACK 구간에는 이 묶음에서 총 N칩"*. 이것이 오히려 UI를 단순하게 만든다 — 층마다 소스를 지정하는 정밀 입력이 사라지고 `층당 수량` 칸이 `총 소요` 한 칸으로 줄었다. 묶음의 나열·수량·맵 구축은 **자재 목록**이 흡수한다(§3.4).

### ③ 총 층수(`total_layers`)의 소속 — **미해결**

현행은 `transfer_plan`에 컬럼이 없어 **브라우저 초안에만** 보관(`:1662` 주석). `plan_id`가 사라지면 주인이 없어진다. 후보: ⓐ `wafer_map_metadata`의 base 맵 속성 ⓑ base 노드 속성 ⓒ stage config의 target 속성. **STACK 티어 프리셋(§3.5)과 커버리지 검증이 이 값에 의존**하므로, 미정인 동안은 커버리지 스트립이 "총 층수 미입력" 상태로 남는다.

### ④ 자재 맵의 "사용 영역" 저장 키 — **미해결(스텁이라 지금이 적기)**

`transfer_plan_source_map`의 현행 키 `plan_id|doe_value|source_lot|source_slot|x|y` → `target_table|target_key|doe_value|source_lot|source_slot|x|y`로 이동 필요.

## 11. 교훈 제안 (ui-designer 메모리 — 총괄 승인 후 반영)

- **함정**: 같은 대상을 가리키는 식별자를 화면 두 곳에서 각각 입력받으면(좌 패널 맵 키 + 우 패널 타깃), 코드가 동기화를 포기하고 "한쪽을 비활성화"로 회피하게 되며 사용자는 이를 "따로 논다"로 체감한다.
  **올바른 방법**: 정체성 입력구는 화면당 **하나**. 나머지는 유도해 **읽기 전용으로 표시**한다. 유도 규칙이 이미 서버 config에 선언돼 있는지 먼저 확인할 것(본 건은 `transfer_plan_config.stages.*.target_map.table`에 이미 있었다).
- **함정**: 파괴적 조작(replace_map)의 범위를 정하는 입력이 편집 가능한 상태로 상시 노출될 때, 모드 기반 잠금은 그 모드가 사라지는 순간 함께 증발한다.
  **올바른 방법**: 위험 입력은 **로드 시점에 값을 고정(pin)하고 기본 잠금**, 해제는 명시적 전환 동작으로만. 확인 마찰은 **위험도에 비례**시켜 확인 피로를 막는다.
- **함정**: 개수가 예측 불가한 축(자재 N매)을 표의 한 셀 안에 넣으면 행이 세로로 자라 목록의 스캔성이 무너진다.
  **올바른 방법**: 폭발하는 축은 **별도 목록으로 분리**하고 원래 행에는 요약 텍스트(`DT-A 외 3매`)만 남긴다. 분리된 목록은 그 축에 대한 **작업 허브**(이동·수량·상태)로 재활용하면 화면이 늘지 않고 오히려 동선이 모인다.
