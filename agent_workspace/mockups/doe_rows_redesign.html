현재 쪽 빨간 번호 = 사용자가 지목한 곳

  • 1끝 층 칸이 작다 — 74px인데 그중 17px을 숫자 스피너가 먹습니다.
  • 2자재 추가 버튼 — 누르면 아래에 인풋이 열립니다.
  • 3그 인풋 + [추가] — 자재 1개당 이 왕복을 반복합니다.
  • 4knob 추가 버튼 — 누르면 빈 칸 2개가 생깁니다.

포커스가 풀리는 것은 이 넷의 결과입니다 — 아래 마지막 카드 참조.

없앤 것

  • ＋ 자재 버튼 + 인풋 상자 + 추가 버튼 — 구간마다 3개
  • ✕ 자재 칩 삭제 버튼 — 자재 1개당 1개
  • + knob 버튼과 knob마다 인풋 2개 + ✕
  • k / v 쌍 자체 — 태그 한 줄로
  • 구간 아래 별도 계산 줄 — 파생값을 각자 출처 칸 밑으로
  • TO의 숫자 스피너 — 화살표가 먹던 폭을 타이핑에

구간 3개 · 자재 6개 · 태그 4개 기준 클릭 대상 22개 → 5개.

모음 필드 하나 — 자재와 태그가 같은 물건

둘 다 정체 없는 문자열 목록이라 칸도 똑같이 만들었습니다. 사용자는 한 가지 조작만 배웁니다.

평소엔 칩으로 빽빽하게 읽히고, 누르면 원문 텍스트(한 줄에 하나)로 바뀝니다. 전환은 :focus-within + opacity뿐 — JS 재렌더가 없어서 포커스가 풀릴 수가 없습니다. 상자 높이는 고정이라 태그가 4개든 12개든 행 높이가 변하지 않습니다.

칩이라서 가로로 채워집니다. 같은 폭에 줄글이면 9개가 9줄이지만 칩은 3줄입니다 — 나중에 공정 추적이 태그를 자동으로 달아도 모양이 무너지지 않습니다(B1 참고).

자재 칩은 색이 곧 보고입니다: 맵 있음 맵 없음 — 기존 자재 pane의 맵 ✓ / 맵 없음 어휘 그대로입니다. 못 찾은 ID는 이름을 대서 보고하고 고쳐 주지 않습니다.

TO 세 상태

15정상 — 숫자 + 아래 15층·소요
미정미정 — 빈 칸 + 회색 이탤릭. 오류 아님
0x10읽을 수 없음 — 원문 그대로 + 빨강 + 행 왼쪽 띠

차이가 세 채널로 동시에 옵니다 — 칸 내용(숫자 / 빈칸 / 원문), 색(기본 / 회색 / 빨강), 아래 파생줄(15층·소요 / 아직 정하지 않음 / 읽을 수 없음). 미정도 읽을 수 없음도 절대 0으로 보이지 않습니다.

type=number를 버리는 것이 핵심입니다. 지금은 0x10을 숫자 칸에 못 넣어 화면에 빈 칸으로 나옵니다 — 미정과 구분이 안 됩니다. type=text여야 원문이 보입니다.

FROM은 칸을 안 씁니다. 테두리 있는 것은 입력, 맨 글자는 계산값 — 아이콘보다 강한 신호입니다. 구간 2·3이 둘 다 16층인 것은 정상입니다: 가운데가 0층이라 다음 구간이 같은 자리에서 시작합니다.

가장 약한 곳 ① 태그 칸이 146px

사용자가 "첫째 행은 VALUE · DESCRIPTION · KNOB"이라 했는데, 380px 안에 셋을 넣으면 설명이 180px, 태그가 146px밖에 안 됩니다. 태그 4개까지는 좋지만 9개면 B1처럼 아래가 잘립니다(흐림 처리로 더 있다고만 말합니다). 자동 부착이 12개를 달면 절반은 눌러야 보입니다 — 읽기 무마찰이 깨집니다.

대안은 하나뿐입니다: 태그를 VALUE·DESCRIPTION 아래 전폭 한 줄로 내리는 것. 380px이면 같은 높이에 9개가 다 보입니다. 새 영역이 생기는 게 아니라 첫째 행이 두 줄짜리 한 덩어리가 됩니다. 다만 사용자가 말한 "한 행"과는 어긋납니다. 태그가 보통 몇 개나 붙을지를 사용자에게 물어보고 정하는 게 맞습니다 — 3~5개면 지금 그대로 두면 됩니다.

가장 약한 곳 ② 자재 자동완성이 사라짐

텍스트 칸으로 접으면 자동완성이 없어집니다. 자재 ID는 불투명 문자열이라 지금은 그게 사실상 유일한 탐색 수단인데, 하필 「사용 자재」 pane도 절반이 됩니다 — 발견 수단 둘이 동시에 얇아집니다.

칩 색깔이 사후 확인은 해 주지만 사전 탐색은 아닙니다. 엑셀에서 8개를 붙여넣는 건 확실히 빨라지고, 맨손으로 ID를 떠올려 치는 사용자에게는 느려집니다. 사용자에게 물어볼 것: 자재 ID를 보통 어디서 가져오는가 — 외워서 치는가, 어디선가 복사하는가.

포커스는 표현이 아니라 로직 (Client PM 이관)

원인은 칸 모양이 아닙니다. 값 하나를 고칠 때마다 commitBands/commitKnobs → updateLegendRow → renderDoeList()가 돌고 그 안에서 box.innerHTML = …로 목록 전체를 다시 그립니다. 포커스를 쥔 DOM 노드가 통째로 사라지니 포커스가 풀립니다.

이 시안이 그 문제를 구조적으로 줄입니다 — 모음이 필드 하나라 자재·태그 편집이 더 이상 노드를 추가·삭제하지 않기 때문입니다. 확정을 change(칸을 떠날 때)로 두면 타이핑 중 재렌더가 아예 없습니다. 다만 재렌더를 건너뛰는 것 자체는 코드 변경이라 디자인 범위 밖입니다.

구간(band)은 텍스트로 접지 않았습니다. 구간은 seq라는 정체를 들고 있고 자재가 거기 매달려 있습니다. 텍스트는 정체를 실을 수 없어서, 다시 파싱할 때마다 seq를 새로 매기게 되고 자재가 남의 구간으로 따라갑니다. 모음을 필드로 접는 규칙은 정체 없는 값에만 적용했습니다.
