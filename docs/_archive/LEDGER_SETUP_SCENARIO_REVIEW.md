## 0. 셋업이 걸치는 파일 지도 (오늘 실측 기준)

| 단계 | 파일/코드 | 성격 |
|---|---|---|
| 테이블 정의 | `table_config.json` | 선언 |
| 테이블 생성·유입 | 파일 인제션 + `chain_rules.json` + mapper 스크립트 | 선언+코드 |
| 소스→원장 | `ledger_config.json` `sources` | 선언 |
| 어휘(술어) | `ledger/vocabulary.py`(코드 v0) + config 확장(R-M) | 코드+선언 |
| 주어 타입 | `ledger/vocabulary.py` `ENTITY_TYPES` | **코드만** |
| 불량 종류 | `finding_kinds.py` | **코드만** |
| 읽기 기하·축 | `siblings_axes.json` (`geometry`·`ledger_subject`·`attribution`) | 선언 |
| 물리 온톨로지 | `mechanism_models.json` (모델·엣지·bindings) | 선언 |
| 이름·구간 | `ledger_journey.json` (`segments`·labels 3종) | 선언 |
| 파생·확정 | `enrichment_rules.json` | 선언 |
| 가동 | `python -m ledger.backfill --source X` + reload-configs | **수동 CLI** |

한 기능이 서려면 **최소 3개, 보통 5개 파일**이 같은 철자에 합의해야 한다.
이 사실 자체가 최상위 난점이다(§7-①).

## 1. 시나리오 A — 신규 관측 테이블 (불량 검사 결과)

1. `table_config`에 표 선언 → business_key 결정(시트에 없음, §7-④).
2. `sources`에 `kind: observation` — 여기는 순수 컬럼 매칭이라 **가장 순한 길**.
3. 🔴 **불량 종류(kind)가 코드다.** `finding_kinds.py`에 없는 종류면 Python 수정
   없이는 등재 불가 — 「admin만으로」의 첫 구멍.
4. 🔴 **검사 이력(run) 테이블을 요구하는 걸 아무도 말해주지 않는다.** run 없이도
   원자는 쌓이지만 분모가 없어 발생률·대조가 전부 `undeterminable`로 나온다.
   엔지니어는 「됐는데 왜 아무것도 안 나오지」 상태에 빠진다. 필요조건(관측
   테이블 + run 테이블 + method 합의)이 어디에도 순서로 안내되지 않는다.

## 2. 시나리오 B — 공정 이력 테이블 (`process_event` 류)

1. 전용 번역기 kind가 없다 → **선언형 번역기**(R-M ⑤)의 `emit` 블록으로 감.
2. 🔴 **중첩 payload 조립.** `processed_with`의 계약은 `{step, recipe}`이고
   `recipe`는 `{id, rev}` **객체**다. 평평한 두 컬럼(`rcp_id`, `rcp_rev`)을 객체
   하나로 접는 문법을 emit 템플릿이 지원하는지, 철자는 뭔지 — 예시가 없다.
   틀리면 게이트 거절문으로 «사후에» 배운다.
3. 🔴 **서명 불일치의 발견 시점이 늦다.** 술어가 요구하는 required 필드를
   매핑 «작성 시점»에 보여주는 것이 없다. vocabulary.py의 영어 docstring을
   읽는 것이 현재의 유일한 사전이다 — 소유자가 말한 「어휘에 뭐가 있는지
   모르겠다」의 실체.

## 3. 시나리오 C — 랏 계보 테이블 (split/merge)

1. `lot_event` kind + `vocabulary` 블록(event_type → 문법 사상).
2. 🔴 **event_type의 실제 값 목록을 알아야 쓸 수 있는데, 열거해 주는 것이 없다.**
   `SPLIT`(대문자)로 오면 소문자 `split` 선언과 안 맞고, 미선언 유형은 거절된다
   (거절은 정직하나, 사전 열거가 없어 왕복이 잦다).
3. 🔴 **두 줄 문법·리스트 짝짓기.** 스플릿 1건 = 2행, `slot_numbers`×`wafer_ids`
   위치 짝짓기 — 선언형 번역기 범위 밖(전용 번역기 필요)임을 엔지니어가 미리
   알 방법이 없다. 축 7 실사고: 같은 시각 두 스플릿이 business key에서 붕괴.
4. 새 테이블의 컬럼명이 다르면(`slotnumbers` vs `slot_numbers`) columns 매핑으로
   해소 — 이 부분은 잘 설계돼 있다.

## 4. 시나리오 D — 대장/참조 맵 (DOE 레지스트리, `bonding_map`)

1. R-N 판정대로 「맵을 주어로, 전개 금지」 — 그런데 **맵을 주어로 세우려면
   그 주어 타입이 `ENTITY_TYPES`에 있어야 하고, 주어 타입은 코드다**(§7-⑤).
   R-M이 술어는 열었지만 주어 타입은 안 열었다 — 두 번째 구멍.
2. 계획 vs 실행 분리(R-N ④)를 지키려면 술어 둘 + emit 둘 — 가능하나, «이렇게
   하는 게 맞다»는 안내가 판정문에만 있고 도구에는 없다.

## 5. 시나리오 E — 계측(MI) 테이블

1. `measured` 술어의 4상태 계약(recorded/missing/not_performed/unknown, 비기록
   상태는 value 금지) — 옳은 문법이지만, **평평한 소스 행에서 state를 어떻게
   «계산»해 넣는가?** NULL 패턴→상태 사상 같은 조건 로직을 선언형 번역기가
   지원하지 않으면 이 술어는 선언만으로 채울 수 없다.
2. `run_uid` 필수(recorded일 때) — run 테이블 합의 문제(시나리오 A-4)와 동일.

## 6. 시나리오 F — 장비·PM 이벤트 (창 앵커의 재료)

1. Equipment 주어는 어휘에 이미 허용 — 선언형 번역기로 가능해 보임.
2. 🔴 **등재 ≠ 소비.** 술어를 만들어 원자가 쌓여도, `siblings_axes`의 축이나
   journey `segments`·labels·bindings 어디에도 연결하지 않으면 **화면 어디에도
   안 나타난다.** 「landed is not wired」의 셋업판 — 다음에 뭘 선언해야 보이는지
   말해주는 것이 없다.

## 7. 관통 난점 (시나리오 공통 — 이것이 UI 계획의 요구사항이다)

① **다섯 파일 철자 합의.** `base_wafer_id`라는 철자가 table_config·sources·
   siblings_axes(geometry/join)·bindings·labels에 걸쳐 반복된다. 합의 검사기가
   없다 — `config/resolve`는 「읽혔는가」만 답하지 「서로 맞는가」는 안 답한다.

② **실패의 발견 시점이 제각각이고, 최악은 «영원히 조용»이다.**
   - 저장 시점: 식별자·참조 검증 (좋음)
   - 번역 시점: 게이트 거절 (정직하나 늦음)
   - 읽기 시점: 걷기 불가·undeterminable (더 늦음)
   - **영원히 조용: bindings·labels의 점경로 오타.** 바인딩은 후보를 좁히지
     않는 설계라 틀린 경로는 오류가 아니라 «영원한 unknown»이다. 선언 자체가
     죽어 있는지 살아 있는지 알 길이 없다 — 「영원히 거짓인 필터」 계열.

③ **순서 의존이 문서에만 있다.** 표 → (kind/술어) → 소스 → 백필 → 축/기하 →
   온톨로지 → 확인. 어느 단계가 어느 단계를 전제하는지 아는 사람이 없으면
   각 단계의 오류만 만나며 역순으로 배운다.

④ **실물이 안 보인다.** 매핑을 쓰는 동안 (a) 소스의 실제 행 (b) 어휘가 요구하는
   서명 (c) 나올 원자 — 셋 다 화면에 없다. 드라이런이 있지만 «저장 직전 확인»
   이지 «작성 중 참조»가 아니다.

⑤ **여전히 코드인 것들** (「admin만으로」의 남은 구멍 목록):
   - 불량 종류(`finding_kinds.py`)
   - 주어 타입(`ENTITY_TYPES`)
   - 리스트 짝짓기류 구조 변환 번역기
   - **백필 실행 자체** (CLI 수동 — 저장하고 나서 원자가 «저절로» 생기지 않는다)

⑥ **은퇴 유산의 혼동.** `ontology_mapping.json`(구 그래프 시대, 13KB)이
   `mechanism_models.json` 옆에 나란히 있다. 「온톨로지 설정」을 찾는 엔지니어가
   먼저 여는 파일이 죽은 파일일 확률이 절반이다.

## 8. 계획으로 넘기는 요구사항 (처방의 골자만)

1. **어휘 사전 화면** — 술어·주어 타입·종류를 한국어로: 뜻, 서명(required),
   실제 원자 예시 1개, 사용량, origin(code/config). §7-④(b)의 해소.
2. **3열 워크벤치** — 왼쪽 실제 소스 행 / 가운데 매핑(서명이 슬롯으로 펼쳐짐) /
   오른쪽 **타이핑 중 갱신되는 드라이런 원자**. §7-④(a)(c).
3. **합의 검사기** — 다섯 파일을 가로질러 철자·경로를 대조하고, **bindings·labels의
   점경로를 라이브 원자 잎에 실측 대조**(「이 바인딩에 걸리는 원자 0개」를 말하는
   것이 핵심 — §7-②의 «영원히 조용»을 죽이는 유일한 방법).
4. **파이프라인 지도 + 다음 단계 안내** — 표→소스→백필→축→온톨로지 단계별
   상태(예: 「원자 0 — 백필 미실행」)와 그 자리에서 실행 버튼. §7-③⑤.
5. **코드 구멍 셋 등재** — 종류·주어 타입의 선언화, 백필 라우트화는 각각 판정
   후 별도 라운드.
