## 1. 왜 지금 안 되는가 — 정리(theorem)

이미 저장소에 적혀 있다. `server/trace_fixture/frames.py` 헤더:

> 두 후보 프레임은 **하나에 다른 하나의 역을 합성한 것이 점유 집합을 자기 자신으로 보낼 때** 정확히 구별 불가능하다. **원은 여덟 프레임 모두에 불변**이므로 아무것도 기여하지 못한다. **점유 부분집합만이 동점을 깬다.**

사용자 진술 「맵도 좌표계와 같이 돌아가므로 어떤 미지의 회전인지 알 수 없음」은 **이 정리의 경험적 관측**이다.

**기제**(`map_editor.js:3350-3356`): 셀 값과 마스크 판정이 **같은 키**로, **같은 변환**(`getDieIndex`)으로, **같은 캔버스 칸**에서 조회된다. 회전은 표시에만 걸리는 전단사이므로 **두 집합에 동시에** 적용된다 — **답을 바꿀 수 없다.**

🔴 **그러므로 이것은 클라 결함이 아니다. 어떤 UI로도 「회전 버튼을 돌려 본다」는 제스처는 정보를 낼 수 없다.**

**노치도 증거가 아니다**(`map_editor.js:3651-3654`): `currentRotation`에서 **그려진다.** 가설의 렌더링이므로 가설과 모순될 수 없다.

## 2. 탐색 공간 — 16이 아니라 8

**실측**(비대칭 376다이 마스크, 이방성 칩 12×16, `side=back`, 오프셋 0.1):

| 튜플 | 개수 |
|---|---|
| `4 회전 × 2 면 × 2 y반전` | 16 |
| **서로 다른 격자 변환** | **8 (D4)** — 각 변환에 정확히 두 튜플이 대응 |

- `grid_y_invert`는 **완전 잉여**다. 모든 `true` 튜플이 `false` 튜플과 별칭이고, 실제로 **668행 중 666행이 false**다. **후보 목록에 넣지 않는다** — 16개를 보여 주면 모든 답이 두 번 나온다.
- `rot=180`은 새 매핑을 하나도 안 만든다(180/front ≡ 0/back).
- 이 붕괴는 **강건하다**: 이방성·등방성·오프셋 0·정확히 반피치(6.0)·6.5·8.5 전부 8을 낸다.

### start는 탐색 대상이 아니라 **풀리는 값**

```
phys(dbX, dbY | start=(sx,sy)) == phys(dbX, dbY | start=(0,0)) + (-sx, -sy)
```

567다이 × 10개 start × 16개 방위에서 **불일치 0**으로 확인. 후보마다 겹침을 최대화하는 정수 시프트를 계산하면 된다.

🟩 **연속 부분은 지배적이지 않다. 존재하지 않는다.** 공간은 **이산 8 + 후보별 해석 가능한 평행이동**이다.

## 3. 무엇으로 채점하는가 — 지표 둘, 그리고 그 한계

두 렌즈가 서로 다른 답을 냈고, **모순이 아니라 기준 맵에 달렸다.**

| 지표 | 실측 | 유효 조건 |
|---|---|---|
| **발자국 겹침**(점유 다이 집합 차분) | 임의 두 방위가 **567 중 540다이(95.24%) 이상** 불일치, 구별 불가 쌍 **0** | 기준 발자국이 **비대칭**일 때 |
| **점유**(다른 맵 상대) | **평평함** — 8개가 4점 안에(63.5 vs 61.2 등) | 둘 다 꽉 찬 웨이퍼면 무용 |
| **값 일치** | **100% 유일 승자 4/4**, 차점 92.5~93.9, 격차 **6.1~7.5pp** | 두 맵의 **어휘가 비교 가능**할 때 |
| **총 개수** | 8개 매핑에 대해 **1~2개 값** | 🔴 **절대 쓰지 말 것** |

🔴 **적합도 퍼센트를 순위 근거로 쓰면 안 된다.** 실측: 비대칭 376다이 마스크에서 **방향이 맞고 한 칸 밀린 후보(94%)가 방향이 틀린 후보 셋(98·97·95%)보다 아래**로 갔다. 근사 대칭 웨이퍼에서 값이 좁은 구간에 뭉치고 **순위가 뒤집힌다.**

### 그래서 규칙

1. **두 지표를 다 계산하고 각각의 「2위와의 격차」를 함께 낸다.**
2. **격차가 작으면 순위를 매기지 않는다** — `이 기준으로는 구별되지 않습니다 — 후보 N개`.
3. **판별 부분집합으로 정규화**한다. 후보들이 실제로 갈리는 다이만 센다 — 대칭 코어 셀은 정보량 0이다.
4. **1차 채널은 숫자가 아니라 형태**다. 빗나간 19개가 비대칭 특징에 **뭉쳤는지** 한쪽 가장자리에 **초승달**로 늘어섰는지가 즉시 보이고, **초승달은 어느 쪽으로 밀지 알려 주는 방향 벡터**다. 「가까움」이 가장 값진 상태이고 오늘 화면엔 그 정보가 없다.
5. **절단된 레이어는 채점 자체를 거절**한다(`OVERLAY_CELL_LIMIT = 2000`). 잘린 집합의 점수는 **불완전한 모집단에서 나온 자신 있는 숫자**다.

🔴 **항상 순위를 내는 도구는 무능을 인정하는 도구보다 나쁘다.** 세 렌즈가 독립적으로 같은 결론에 왔다.

## 4. 기준(reference)은 꽂아 넣는 것 — 유효 다이로 못 박지 말 것

| 하는 일 | 유효 다이 필요? |
|---|---|
| 좌표를 칸에 앉히기 | **아니오** |
| 격자 밖 판정 | 아니오 (원으로도 됨) |
| **방위 구별** | **비대칭 기준이 필요** ― 유효 다이는 그중 **하나** |
| 값 기반 구별 | 아니오 ― **다른 맵의 값**으로 |

```
decide(cells, frame, physSpec, reference)
    reference = 유효 다이 맵 | 다른 맵(셀+값) | 없음
```

**기준이 없으면 계산은 되고 순위는 안 낸다** — `기준이 원 기하뿐입니다 — 8개 중 6개를 구별할 수 없습니다`.

🔴 **「기준이 부족하다」와 「후보가 진짜 비슷하다」는 다른 사실**이다. 둘 다 순위 없음으로 끝나지만 **고치는 방법이 다르다.**

⚠️ **대상 320개 맵에는 유효 다이가 대개 없다** — 그게 아무도 방위를 잰 적 없는 맵들이다. 하지만 **같은 웨이퍼의 다른 맵은 있을 수 있다**(실측이 푼 것이 정확히 그 경우: `dt_log` 대 `core_wafer_map`). **기준을 유효 다이로 고정하면 그 320개를 못 푼다.**

## 5. 이것은 인리치먼트다 — 규칙이 이미 선언돼 있다

```
rule        : dt_log → eqp_frame_attribution
decision_key: ['dt_eqp', 'product']
target      : ['core_frame', 'dt_frame']
reference   : 4개 (그중 하나가 「좌표 분포 — 비대칭이면 …, 대칭이면 알 수 없음」)
auto_confirm: False
```

**4행 전부 NULL — 0% 채워져 있다.**

| 새로 만들 뻔한 것 | 이미 있는 것 |
|---|---|
| 확정 → 메타 쓰기 경로 | **인리치먼트 확정이 그 쓰기** |
| `orientation_basis` 필드 | **인리치먼트 출처**(`source=user` vs 자동) |
| 진행률·백로그 | **인리치먼트 진행률** |
| 증거 저장 테이블 | **참조뷰가 곧 그 계산**(요청 시 계산, 저장 안 함) |
| 후보 목록 화면 | **인리치먼트 화면이 이미 그 모양** |

🟩 **남는 것은 하나뿐: 참조뷰가 후보를 실제로 채점하게 만드는 것.** 지금 참조뷰 4개는 **사람이 눈으로 보라고 데이터를 보여 주는데, 사람이 눈으로 못 본다** — 그게 문제 전체였다.

🟩 **판단키가 이미 맞다.** `(dt_eqp, product)` — 맵 하나가 아니라 설비+제품 단위. 실측이 뒷받침한다: **웨이퍼별 증거가 서로 모순**됐고(같은 설비·제품인데 3장이 `rot270_back`, 1장이 `rot0_front`) **풀링이 필요**하다.

⚠️ `auto_confirm`은 **참조뷰가 채점을 시작한 뒤**에 켠다. 격차 7.5pp는 기준을 세울 만한 분리다.

🟩 **그리고 이게 `dt_map` 파생을 푼다** — `HOLD_FRAME_MISSING`으로 8,700행이 막혀 있는데 **그 4행을 채우면 풀린다.** 그 거절은 옳았고, 이제 채울 방법이 생긴다.

## 6. 순수 판정 층 — 첫 산출물

```
① 판정 (순수, 캔버스 없음)
     어느 다이가 존재하는가 · 저장 좌표가 어느 칸에 앉는가 · 무엇이 격자 밖인가
② 그리기
     ①의 결과를 칠한다
```

🔴 **지금은 한 패스이고, 그래서 렌더가 데이터에 권한을 갖는다.** `renderGridCanvas`의 **캔버스 밖 `continue`가 셀 등록보다 앞에** 있어서:

- 선언된 셀이 캔버스 밖으로 밀리면 등록조차 안 되고 **Push 페이로드에서 조용히 빠진다** — 실측 **1,600칸 중 480칸**
- 반대로 **격자 밖 셀이 등록돼 칠해지고 세어지고 저장**됐다 — 실측 36칸 전부 `inside`

**같은 뿌리다: 그리는 루프가 등록도 한다.** 그리기 순서가 데이터를 정하면 그리기를 바꿀 때마다 데이터가 바뀐다.

①이 순수해지면 **하네스가 캔버스 없이 채점**한다 — 오늘은 기록 캔버스를 만들어 그리기를 가로채야 한다. 그리고 그것이 R7/R8 게이트(**하네스를 텍스트 슬라이싱에서 해방**)를 첫 단계에서 충족한다.

## 8. 재개발의 조건

1. **불변식을 먼저 옮긴다**(§7). 설계 레인 산출 30개 이상(E1~E8·C1~C11·D1~D6·W1~W8·S1~S7)은 `agent_workspace/reports/Map_editor_decomposition_plan.md` §13.
2. **옆에 세운다.** 옛 에디터가 매일 돌고 운영 사고도 났다. 새것이 정렬을 해내기 전까지 옛것이 산다.
3. **전환 기준은 측정이다**: **맵 8개 · 조작 4회 이하 · 30초 이하 · DB 쓰기 0.** 현재 에디터는 **조작 수 무한대에서도 0/8**. 숫자가 없으면 「거의 다 됐다」가 끝없이 이어진다.
4. **`contracts/map_seam/`은 살아남는다** — 클라 구현의 테스트가 아니라 **양쪽이 같은 답을 내야 한다는 계약**이라 클라를 새로 써도 오라클로 쓴다. ⚠️ 다만 **마스크 경계를 안 재는 구멍은 물려받지 말 것**.
5. **서버·온톨로지·계획 데이터 모델은 안 건드린다.** 새 클라가 바꾸지 않고 계속 말해야 하는 것.

## 9. 승인 대기 중인 판정

| | 무엇 |
|---|---|
| **ⓐ 320개 잠금 해제** | 합성 규격(`chip 1x1`) 맵이 오버레이 경로에서 거절된다 — **정확히 그 맵들이 방위를 잰 적 없는 맵**이다. 소스·타깃이 **같은 명목 피치**면 mm 왕복이 다이 인덱스에 항등이라 같은 함수로 된다. ⚠️ **`동일 격자 가정`으로 표시하고 피치 선언으로는 쓸 수 없게** 해야 한다 — 안 그러면 합성 규격 문제를 다시 만든다 |
| **ⓑ 온톨로지 `CoreCellClaim`** | `ontology_mapping.json`이 lot/slot 축은 `DtCellClaim`으로 정확히 갈라 놓고(「아무도 확립하지 않은 링크를 확정처럼 주장하면 화면은 멀쩡해 보인다」고 자기가 적어 놓음), **좌표 축은 원시 좌표 동일성으로 하드 링크**한다. 같은 파일이 세 줄 위에서 「두 좌표는 서로 독립인 미지 프레임에 있다」고 적는다. **설정 한 줄이면 정직해진다** |
| **ⓒ 방위 출처를 스키마가 말할 수 있게** | `grid_metadata` 키 15개 중 확신·출처·근거·비교대상을 표현하는 것이 **하나도 없다**. `_rotation_of`가 **키 부재·파싱 실패·명시적 0을 전부 0으로** 삼키고, `rotation: 0`이 **668행 중 516행(77.2%)** — 가장 흔한 값이 판독 실패와 구별되지 않는다. `auto_registered`는 `PHYS_KEYS` 여섯 개만 덮고 **`rotation`·`side`는 그 밖**이다 |
