## ✅ 해소 — B1 · B2 (2026-07-27, 커밋 `8117456`)

### B1(해소). 프로세스 감시 — `server/process_supervisor.py`
런처의 `while True: time.sleep(1)`이 **`Supervisor.run()`으로 교체**됐다(`run_decoupled_app.py`). 자식 5~6개를 1초 주기로 폴링하고, 죽으면 재시작하고, 재시작 사실을 남긴다.

- **재시작 예산**: 연속 실패 n회째 `min(2·2^(n-1), 60)`초 후 재시작 → **2/4/8/16/32초**. **6번째 연속 실패에서 `FAILED`로 확정**하고 다시는 살리지 않는다(배너 로그 + `/health` 비정상). 무한 재시작은 "감시가 도는 것처럼 보이면서 고장을 숨기는" 최악의 실패라 일부러 막았다.
- **예산 회복**: 60초 이상 살아 있었으면 크래시 루프가 아니므로 연속 카운터가 리셋된다. 이게 없으면 한 달에 한 번 재기동하는 시스템이 결국 아무것도 재시작하지 않게 된다.
- **재시작해도 안전한 근거**: P2 체크포인트 재개 드릴(실제 `taskkill /F`, 10만 행 중 3만 행 지점) — 유실·중복 0.
- **데스크톱 셸은 `restartable=False`**다. 창을 닫는 것은 "전체 종료"지 "나를 살려라"가 아니다.
- 상태는 `<DATA_ROOT>/config/supervisor_status.json`에 기록되며 `updated_at`이 **감시자 자신의 생존 신호**다.

### B2(해소). `/health` — `server/health.py` + `GET /health`
JSON을 반환하고 **비정상이면 503**을 낸다. 판정 대상은 DB·워커·outbox·감시자 4종.

- **워커는 pid가 아니라 진행 박동으로 판정한다**(`server/utils/heartbeat.py`). 우리가 실제로 겪은 장애는 프로세스가 살아 있는 채 멈춘 이벤트 루프 동결이었고, pid 검사로는 안 보인다. 감시자의 프로세스 관점과 워커 자신의 진행 관점을 **조인**해 실패를 명명한다 — `down`(프로세스 없음) / `wedged`(살아 있는데 진행 없음) / `starting`(기동 유예 60초) / `ok`.
- **정체 임계 60초**는 측정에서 나왔다. 워커별 박동 간격 p50이 각자의 설계 주기와 일치했고(chain 2.04s · watcher 3.07s · scheduler 5.11s) 최악 단일 간격이 10.26초 — 즉 60초는 **연속 12회 이상 누락**을 뜻한다. 한 번 놓쳤다고 우는 헬스체크는 곧 무시당한다.
- **backlog은 크기가 아니라 나이로 본다.** 정상적인 10만 행 적재 하나가 outbox 약 11.6만 행을 만들기 때문에, 멈춘 워커를 잡을 만큼 낮은 크기 임계는 **큰 파일마다 오경보**한다. 큐가 빠지고 있으면 가장 오래된 미처리 행은 젊게 유지된다 — 나이가 신호고 크기는 참고값이다(5분 degraded / 15분 unhealthy).
- **박동은 감시자가 띄운 pid의 것만 인정한다.** 같은 역할의 유령 프로세스(손으로 띄운 워커, 같은 data root를 공유하는 두 번째 스택)가 정체된 워커를 가리는 사례가 드릴에서 실제로 관측됐다.

> 검증: 워처를 `psutil`로 정지시킨 드릴에서 `tasklist`·`psutil.status()`·감시자 모두 "running"이었고 **박동만이 알아챘다**(58.7초에 503, 같은 pid로 0.03초 만에 복구). 스위트 540 passed / 0 failed.

## 🔴 차단 — 프로덕션 전 필수

### ✅ B3(해소, `d56e7e2`). 무음 데이터 손실 경고가 워처 로그에 남는다
`crud.py`의 미선언 컬럼 경고(방금 추가)는 워처 프로세스에서 `logging.lastResort`로 떨어진다 — **핸들러가 비어 있어 워처 로그 파일에 안 남는다.** 10만 행 파일이 컬럼을 통째로 잃어도 진단 기록이 없다.

- **필요**: `server/utils/logger.py`의 핸들러 배선 수정. (현재 다른 작업이 같은 파일에 있어 대기 중)

### B4. 롤백 절차가 없다
배포가 잘못됐을 때 되돌리는 문서화된 절차가 없다. 스키마 변경(`table_config.json`)은 **ALTER 경로가 `config_watcher` 단독**이고 원자적 쓰기를 감지 못한다(이슈 #9) — 즉 되돌리기가 더 어렵다.

- **필요**: 코드 롤백 + config 롤백 + "이미 CREATE된 테이블은 어떻게 하나"에 대한 답.

**실제 사례로 확보됨 (2026-07-27, M2.6 `0f8d35f`)** — 절차가 왜 필요한지가 추상론이 아니라 관측으로 남았다.

- 계획 계열 config는 **요청마다 디스크 재읽기**, 코드는 **재기동까지 고정**이라 한 배포 안에서 반영 시점이 갈린다. 라이브 `transfer_plan_config.json`을 새 바인딩으로 바꾼 뒤 웹서버가 옛 모듈을 들고 있어 `GET /api/transfer-plan/validate`가 **404**가 됐다.
- **여기서 코드만 되돌리면 복구되지 않는다** — config가 이미 새 형태라 옛 코드도 못 읽는다. 롤백 대상 목록에 **config가 코드와 함께** 들어가야 하고, 순서는 배포의 역순이어야 한다.
- 같은 배포에서 `table_config.json` 컬럼 추가는 `config_watcher`가 **재기동 없이** ALTER를 실행했다 → 한 배포의 반영 시점이 **컬럼(즉시)·config(즉시)·코드(재기동 후)** 셋으로 갈린다.
- ⚠️ 그 ALTER는 `sync_dynamic_tables_schema`가 `print()`로 내보내 **어느 로그 파일에도 남지 않았다**(B3와 같은 계열). 롤백 판단의 입력이 되는 "무엇이 언제 바뀌었나"가 사후 감사 불가다.
- 운영자 관점 요약은 [DEPLOY_SETUP §7](../guide/DEPLOY_SETUP.md).

## 🟡 조건부 — 전제에 따라 필요

### C1. 접근 통제 (사내망 팀 공유 · 2~5명)
**인증이 전혀 없다.** 신뢰된 사내망이라 즉시 차단은 아니지만, 아래 둘은 성격이 다르다:

| 엔드포인트 | 위험 |
|---|---|
| `POST /admin/scripts/code` | **임의 코드 파일 쓰기** (파서·매퍼·수집기) |
| `POST /admin/auto-update/run-now` | **그 스크립트 실행** |

둘을 합치면 서버에서 임의 코드 실행이다. 팀 5명이면 악의가 아니라 **실수 한 번**으로 충분하다.

- **최소**: bind 주소를 명시 고정하고, 위 두 라우트만이라도 분리하거나 잠글 것.
- **권장**: admin 화면 전체를 별도 인증 뒤로.

### C2. 동시 편집 (2~5명)
같은 맵을 둘이 열어 편집하는 상황이 실제로 가능하다.

- **있는 것**: Push 시 맵 키 불일치 가드(로드한 맵과 달라지면 차단).
- **없는 것**: 마지막 저장이 이김. 누가 언제 덮었는지 화면에 없음. DOE 자동 저장은 디바운스라 **두 사람이 같은 값을 편집하면 늦게 끝난 쪽이 이긴다.**
- **판단 필요**: 이 정도로 충분한가, 아니면 편집 중 표시나 낙관적 잠금이 필요한가. 실제 작업 흐름을 아는 쪽은 사용자다.

### C3. 백업 — git이 안전망이 아니기 때문에 필요하다

`server/config/`와 `server/ingestion_workspace/`가 gitignored인 것은 **의도된 설계다**(사용자 확정): 운영 서버에 코드를 패치할 때 현장 자산이 딸려 들어가 오염되는 것을 막는다. 오늘 정리한 **제품 소유 / 현장 소유** 구분이 바로 이 경계다.

> ⚠️ **이 두 디렉터리를 git에 넣지 마라.** 배포 안전을 위해 일부러 뺀 것이지 누락이 아니다. 제품이 정의하는 테이블은 `.sample`과 설치 스크립트로 배포되고, 현장 자산은 현장에 남는다.

대가는 명확하다 — **git이 복구 경로가 아니다.** 그래서 별도 백업이 필수다.

- **필요**: 두 디렉터리 + PostgreSQL 정기 백업. **복원을 실제로 한 번 해볼 것**(백업은 복원해 보기 전까지 백업이 아니다).
- 오늘 이 자산 2건이 실수로 덮어써졌고 **git에 없어서 원본을 복구할 수 없었다.** 하나는 `.pyc`·해시 매니페스트·폐기 전 커밋 blob 세 경로를 조합해 겨우 되살렸고, 다른 하나(`inventory_master/config/config.json`)는 **원본 내용을 끝내 알 수 없다.**
