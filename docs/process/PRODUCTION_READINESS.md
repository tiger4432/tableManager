## 판정

**조건부 가능.** 데이터 무결성과 인제션 안정성은 게이트를 통과했다. 막는 것은 기능이 아니라 **운영 체계**다 — "무중단에 가깝게"라는 요구에 대해 지금 시스템은 **죽어도 아무도 모른다.**

| 영역 | 상태 |
|---|---|
| 데이터 무결성 | 🟢 통과 (실측 근거 있음) |
| 인제션 안정성 | 🟢 통과 (드릴 PASS) |
| 배포·설정 | 🟢 통과 |
| **운영 가시성·복원력** | 🔴 **차단** |

| 동시 편집 | 🟡 조건부 |

## 🔴 차단 — 프로덕션 전 필수

### B1. 프로세스가 죽어도 아무도 모른다
`run_decoupled_app.py:111` — 런처는 `while True: time.sleep(1)`이 전부다. 5개 프로세스 중 워처나 체인 워커가 죽으면 **감지도 재시작도 없다.** 웹서버만 살아 있으면 화면은 멀쩡한데 **데이터 유입이 조용히 멈춘다.**

- **필요**: 자식 프로세스 생존 감시 + 자동 재시작 + 재시작 사실의 기록.
- **왜 차단인가**: "무중단에 가깝게"의 최소 조건이다. 지금은 무중단이 아니라 **무감지**다.

### B2. 헬스체크 엔드포인트가 없다
`/health`는 존재하지 않고, 없는 경로는 **정적 catch-all이 HTML을 200으로** 반환한다. 즉 외부 모니터링을 붙이면 **죽은 서버도 200으로 보인다.**

- **필요**: JSON을 반환하는 실제 헬스 라우트. 최소한 DB 연결·각 워커 하트비트·outbox 적체를 담을 것.
- 워커 하트비트가 없으면 B1을 밖에서 확인할 방법이 없다.

### B3. 무음 데이터 손실 경고가 정작 워처에서 안 보인다
`crud.py`의 미선언 컬럼 경고(방금 추가)는 워처 프로세스에서 `logging.lastResort`로 떨어진다 — **핸들러가 비어 있어 워처 로그 파일에 안 남는다.** 10만 행 파일이 컬럼을 통째로 잃어도 진단 기록이 없다.

- **필요**: `server/utils/logger.py`의 핸들러 배선 수정. (현재 다른 작업이 같은 파일에 있어 대기 중)

### B4. 롤백 절차가 없다
배포가 잘못됐을 때 되돌리는 문서화된 절차가 없다. 스키마 변경(`table_config.json`)은 **ALTER 경로가 `config_watcher` 단독**이고 원자적 쓰기를 감지 못한다(이슈 #9) — 즉 되돌리기가 더 어렵다.

- **필요**: 코드 롤백 + config 롤백 + "이미 CREATE된 테이블은 어떻게 하나"에 대한 답.

## 🟡 조건부 — 전제에 따라 필요

### C1. 접근 통제 (사내망 팀 공유 · 2~5명)
**인증이 전혀 없다.** 신뢰된 사내망이라 즉시 차단은 아니지만, 아래 둘은 성격이 다르다:

| 엔드포인트 | 위험 |
|---|---|
| `POST /admin/scripts/code` | **임의 코드 파일 쓰기** (파서·매퍼·수집기) |
| `POST /admin/auto-update/run-now` | **그 스크립트 실행** |

둘을 합치면 서버에서 임의 코드 실행이다. 팀 5명이면 악의가 아니라 **실수 한 번**으로 충분하다.

- **최소**: bind 주소를 명시 고정하고, 위 두 라우트만이라도 분리하거나 잠글 것.
- **권장**: admin 화면 전체를 별도 인증 뒤로.

### C2. 동시 편집 (2~5명)
같은 맵을 둘이 열어 편집하는 상황이 실제로 가능하다.

- **있는 것**: Push 시 맵 키 불일치 가드(로드한 맵과 달라지면 차단).
- **없는 것**: 마지막 저장이 이김. 누가 언제 덮었는지 화면에 없음. DOE 자동 저장은 디바운스라 **두 사람이 같은 값을 편집하면 늦게 끝난 쪽이 이긴다.**
- **판단 필요**: 이 정도로 충분한가, 아니면 편집 중 표시나 낙관적 잠금이 필요한가. 실제 작업 흐름을 아는 쪽은 사용자다.

### C3. 백업
`server/config/`와 `server/ingestion_workspace/`는 **git에 없다**(gitignored). 스키마 선언·매퍼·수집기 스크립트가 전부 여기 있다.

- **필요**: 이 두 디렉터리 + PostgreSQL 정기 백업. 복원을 실제로 한 번 해볼 것.
- 오늘 이 자산 2건이 실수로 덮어써졌고 **원본을 복구할 수 없었다.**

## 🟢 통과 — 근거 있음

### 데이터 무결성
| 항목 | 근거 |
|---|---|
| 계획 저장이 서버 상태를 모른 채 전량 삭제 | 해소 — 권한 획득 지점을 채택 지점으로 일원화. 라이브 재현 2종에서 쓰기 0건 |
| 좌표 오정렬로 잘못된 셀에 기록 | 해소 — 25,760 순서쌍 SILENT-WRONG 0, 재기동 후 REST 실측 격자 밖 0건 |
| 테이블 전환 시 남의 테이블에 값 유입 | 해소 — 전환 시 오버레이 해제 |
| 정렬 구현 중복(A1 미적용 사본) | 해소 — 셋 → 둘. 가용량 8개 질의 중 7개 동일, 1개는 **바로잡힘** |
| 미선언 컬럼 무음 손실 | 경고 추가(핫패스 비용 0.0039%). ⚠️ 단 B3 미해결로 워처에서는 안 보임 |

### 인제션 안정성
| 항목 | 근거 |
|---|---|
| 대형 파일이 소형 파일을 막음(HOL) | P1 heavy 레인 — 비차단 **180배** 실측 |
| 재기동 시 전체 재처리 | P2 체크포인트 — 실제 `taskkill /F` 후 재개, 유실·중복 0, 건너뛰기 275ms vs 219s |
| 동일 파일 재적재 | P2 dedup — **1,383배** 분리 |
| 대형 tx가 이벤트 루프 동결 | 해소 — 발신 측 절단. 라이브 p50 16ms, 스파이크 0 |
| 파일 규모(수십 MB) | P1/P2로 충분 — **P3는 백로그 유지** |

### 배포·설정
- [DEPLOY_SETUP](../guide/DEPLOY_SETUP.md) — 무엇을 직접 채워야 하는지
- 제품 소유 테이블 **자동 설치 스크립트** — 병합 안전(dry run 기본, 백업, 현장 항목 무접촉)
- `.sample` config 정정 — 신규 환경이 실제로 뜬다(이전에는 계획 저장이 조용히 손실됐다)

### 검증 체계
- 스위트 **498 passed / 0 failed** — 허용 실패 0건
- 테스트가 라이브 자산에 쓰지 않음(바이트·mtime 동일성으로 증명)
- **격리 개발 환경** — 스냅샷 DB + 별도 포트 + 워처·스케줄러 없음. ⚠️ 로그 누수 수정 중

## ⏭️ 장기 트랙 (게이트 제외)

- **온톨로지/그래프** — 사용자 지시로 장기 개발. G2.5 탐색 정책 엔진, 이슈 #15(`Wafer` label 정체 혼입) 포함.
- **M3 맵 메타 자동 등록** — 현재 맵 키 39만 vs 메타 9건. 정렬이 9개 맵에서만 실제로 일한다. 미등록은 화면에 `화면기준` 칩으로 노출된다.
- **P3** — backpressure · PG COPY · audit 값 길이 상한. 파일 규모가 커지면 재평가.

## 착수 순서 (권고)

1. **B1 + B2** — 프로세스 감시 + 헬스 라우트. 하나로 묶어야 의미가 있다(감시 결과를 밖에서 볼 수 있어야 한다).
2. **C3 백업** — 코드가 아니라 절차다. 오늘 실제로 자산을 잃었다.
3. **B3** — 로그 배선(진행 중인 작업과 같은 파일).
4. **C1** — 최소한 코드 쓰기·실행 두 라우트.
5. **B4** — 롤백 절차 문서화.
6. C2는 사용자 판단 후.
