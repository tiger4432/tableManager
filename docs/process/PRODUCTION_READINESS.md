## ✅ 해소 — B1 · B2 (2026-07-27, 커밋 `8117456`)

### B1(해소). 프로세스 감시 — `server/process_supervisor.py`
런처의 `while True: time.sleep(1)`이 **`Supervisor.run()`으로 교체**됐다(`run_decoupled_app.py`). 자식 5~6개를 1초 주기로 폴링하고, 죽으면 재시작하고, 재시작 사실을 남긴다.

- **재시작 예산**: 연속 실패 n회째 `min(2·2^(n-1), 60)`초 후 재시작 → **2/4/8/16/32초**. **6번째 연속 실패에서 `FAILED`로 확정**하고 다시는 살리지 않는다(배너 로그 + `/health` 비정상). 무한 재시작은 "감시가 도는 것처럼 보이면서 고장을 숨기는" 최악의 실패라 일부러 막았다.
- **예산 회복**: 60초 이상 살아 있었으면 크래시 루프가 아니므로 연속 카운터가 리셋된다. 이게 없으면 한 달에 한 번 재기동하는 시스템이 결국 아무것도 재시작하지 않게 된다.
- **재시작해도 안전한 근거**: P2 체크포인트 재개 드릴(실제 `taskkill /F`, 10만 행 중 3만 행 지점) — 유실·중복 0.
- **데스크톱 셸은 `restartable=False`**다. 창을 닫는 것은 "전체 종료"지 "나를 살려라"가 아니다.
- 상태는 `<DATA_ROOT>/config/supervisor_status.json`에 기록되며 `updated_at`이 **감시자 자신의 생존 신호**다.

### B2(해소). `/health` — `server/health.py` + `GET /health`
JSON을 반환하고 **비정상이면 503**을 낸다. 판정 대상은 DB·워커·outbox·감시자 4종.

- **워커는 pid가 아니라 진행 박동으로 판정한다**(`server/utils/heartbeat.py`). 우리가 실제로 겪은 장애는 프로세스가 살아 있는 채 멈춘 이벤트 루프 동결이었고, pid 검사로는 안 보인다. 감시자의 프로세스 관점과 워커 자신의 진행 관점을 **조인**해 실패를 명명한다 — 상태값 **8종**: `down`(프로세스 없음) / `starting`(기동 유예 60초) / `missing`(도는데 박동 이력 없음) / `foreign_beat`(다른 pid의 박동) / `wedged`(살아 있는데 진행 없음) / `stale`(감시자 관점 없음) / `stalled`(박동은 하는데 **claim한 작업**이 300초 무진행) / `ok`. 전수·판정 조건은 [backend §1.3](../architecture/backend.md).
- **정체 임계 60초**는 측정에서 나왔다. 워커별 박동 간격 p50이 각자의 설계 주기와 일치했고(chain 2.04s · watcher 3.07s · scheduler 5.11s) 최악 단일 간격이 10.26초 — 즉 60초는 **연속 12회 이상 누락**을 뜻한다. 한 번 놓쳤다고 우는 헬스체크는 곧 무시당한다.
- **backlog은 크기가 아니라 나이로 본다.** 정상적인 10만 행 적재 하나가 outbox 약 11.6만 행을 만들기 때문에, 멈춘 워커를 잡을 만큼 낮은 크기 임계는 **큰 파일마다 오경보**한다. 큐가 빠지고 있으면 가장 오래된 미처리 행은 젊게 유지된다 — 나이가 신호고 크기는 참고값이다(5분 degraded / 15분 unhealthy).
- **박동은 감시자가 띄운 pid의 것만 인정한다.** 같은 역할의 유령 프로세스(손으로 띄운 워커, 같은 data root를 공유하는 두 번째 스택)가 정체된 워커를 가리는 사례가 드릴에서 실제로 관측됐다.

> 검증: 워처를 `psutil`로 정지시킨 드릴에서 `tasklist`·`psutil.status()`·감시자 모두 "running"이었고 **박동만이 알아챘다**(58.7초에 503, 같은 pid로 0.03초 만에 복구). 스위트 540 passed / 0 failed.

### ✅ B4(해소, 2026-07-28). 롤백 절차 — **문서 + 드릴 통과**

절차는 [guide/ROLLBACK_PROCEDURE](../guide/ROLLBACK_PROCEDURE.md)이고, **격리 스택에서 전 구간을 실제로 돌렸다.** 문서만 있고 아무도 실행해 본 적 없는 롤백은 롤백 능력이 아니므로, 판정 근거는 문서의 존재가 아니라 **드릴 결과**다.

**드릴 조건** — 전용 데이터 루트(`ASSY_DATA_ROOT`), `assy_qa` 스냅샷, API :8082 / 그래프 :8092, 런처(`run_decoupled_app.py --server-only`)로 **당시 5개 프로세스 전부**. ⚠️ **[2026-08-14] 이 드릴 기록의 구성입니다** — 그래프 워커 은퇴로 오늘은 하나 적습니다. 운영은 손대지 않았다(운영 런처가 동시에 :8080에서 가동 중이었고 읽기 전용으로 유지).

**시나리오** — 계획 config의 바인딩 키를 새 형태로 바꾸고 그 형태만 읽는 코드를 함께 배포(**비하위호환**), 동시에 `table_config.json`에 테이블 1개 + 기존 테이블 컬럼 1개 추가. 즉 M2.6 인시던트와 `map_band_registry` 잔여물을 **한 배포 안에서** 재현했다.

| 관측 | 실측값 |
|---|---|
| 코드 파일만 교체(재기동 전) | API는 **여전히 옛 동작** — 코드는 재기동까지 고정 |
| 런처 통째 재기동 | **5.6~5.7초** (정지 2.5 + `/health` 응답까지 3.2) |
| 계획 config 되돌리기 | **0.01초** — 다음 요청부터. 재기동 불필요 |
| `table_config` 제자리 쓰기 → 물리 DDL | **약 5초** 뒤 `CREATE TABLE` + `ALTER TABLE ADD COLUMN` |
| **코드만 되돌리고 재기동**(잘못된 순서) | `target_map: {}` — **여전히 깨짐**. 그리고 **`/health`는 `ok`, `problems: []`** |
| **올바른 순서** 전 구간 | **총 30초** (증거 8 → config 10 → 코드 0 → 재기동 11) |
| 사용자 체감 장애(0.25초 폴링) | **16초** (응답 저하 13 + 연결 거부 3) |
| 롤백 후 검증 | 옛 응답 형태 복귀, `/health` ok |

**핵심 정정 3건** — 기존 서술이 부정확하거나 부족했던 부분:

1. **순서는 "배포의 역순"이 아니다.** 배포는 `코드 → 재기동 → config`, 롤백은 `config → 코드 → 재기동`이다. 거꾸로 읽으면 `config → 재기동 → 코드`가 되는데 그 재기동은 아직 새 코드로 올라간다. **재기동이 배포에서는 가운데, 롤백에서는 맨 마지막**이라는 것이 차이의 전부다.
2. **`/health`로 롤백 성공을 판정하면 안 된다.** 코드/config 형태 불일치는 `/health`의 판정 대상(DB·박동·outbox·감시자)이 아니다. 드릴에서 완전히 깨진 상태가 `status: ok`로 보고됐다. 검증은 **그 배포가 건드린 도메인 엔드포인트**로 해야 한다.
3. **전진 배포에도 창이 있다.** "코드 먼저, config 나중"은 **새 코드가 옛 config를 읽을 수 있을 때만** 무중단이다. 비하위호환 변경은 재기동 직후 `새 코드 + 옛 config` 상태에서 같은 방식으로 깨진다(드릴에서 관측). 그 경우 config를 미리 준비해 창을 초 단위로 줄이거나 콜드 배포를 택해야 한다.

**"이미 CREATE된 테이블은 어떻게 하나"에 대한 답** — 스키마는 **한 방향**이다. 선언을 되돌려도 물리 테이블·컬럼은 남는다(드릴에서 재현). 그래서 **찾는 도구**를 만들었다:

```bash
conda run -n assy_manager python server/scripts/list_undeclared_tables.py
```

읽기 전용이다(DDL 없음). 미선언 테이블(행 수로 "되돌린 선언의 잔여물" vs "레거시 데이터" 구분) · 미선언 컬럼 · 선언됐지만 없는 테이블을 보고하고 `DROP` 문을 **출력만** 한다. **지우는 판단은 사람이 한다** — 새벽 2시에 스크립트가 내릴 결정이 아니다. 드릴에서 검출 → 제거 → 재검출(깨끗함) 왕복을 격리 DB에서 확인했다.

> **드릴에서 실행하지 않은 부분**(문서 §8에 표로 명시): `git revert`의 **커밋 객체** 조작(파일 복원만 실행), `client2/dist/` 해시 변경 왕복(없는 해시가 404를 낸다는 것만 실측 — `client2/**`는 map-pm 동시 작업 중이라 접근 금지), `ASSY_ADMIN_TOKEN` 부분 재기동 → `/internal` 401.

### C1. 접근 통제 (사내망 팀 공유 · 2~5명) — 🟡 **부분 해소 2026-07-27**

**과거 상태**: 인증이 전혀 없었다. `main.py`의 admin 라우트 **16개 전부** 무인증이었고(모든 `Depends`가 `get_db`), 아래 둘을 합치면 사내망 누구나 서버에서 임의 코드를 실행할 수 있었다.

| 엔드포인트 | 위험 |
|---|---|
| `POST /admin/scripts/code` | **임의 코드 파일 쓰기** (파서·매퍼·수집기) |
| `POST /admin/auto-update/run-now` | **그 스크립트 실행** |

**조치**: 공유 토큰 헤더 게이트(`server/admin_auth.py`). 로그인 화면·사용자 관리는 **의도적으로 도입하지 않았다**(2~5명 사내 공유).

- 토큰 = `ASSY_ADMIN_TOKEN` 환경변수, 헤더 = `X-Admin-Token`, 비교 = `secrets.compare_digest`.
- **설정 시**: `/admin/*` 16개 전부 필수(조회 포함 — 소스 코드 반환도 유출이다).
- **미설정 시**: 위험한 2개는 **503**(fail closed), 나머지는 열어 둠 — 첫 재기동에 운영자가 어드민 전체에서 잠기는 사고 방지. 기동 로그가 `WARNING`으로 무엇이 꺼졌고 어떤 변수를 설정해야 하는지 알린다.
- `GET /health`는 **무인증 유지** — 잠그면 B2(모니터링)가 무의미해진다.

### C4. 감사 이력 인덱스 — 없으면 오늘의 성능 수리가 배포되지 않은 것과 같다 (2026-08-11 신설)

`dab9152`(행/셀 이력 keyset 페이징)와 `2630790`(`/audit_logs/recent` bounded scan)이 `audit_logs`를 훑는 세 경로의 비용을 68x~468x 줄였는데, 그 개선의 물리적 근거가 **세 인덱스**(`idx_audit_recent_groups` · `idx_audit_row_history` · `idx_audit_cell_history`)다. `models.py`에 선언돼 있어 **신규 설치는 `create_all`이 자동으로 만들지만**, `create_all`은 **이미 있는 테이블에 인덱스를 추가하지 않는다** — D3(업무 키 UNIQUE 인덱스, §6 8-bis)와 정확히 같은 계급의 함정이다.

- **차단이 아닌 이유**: 인덱스가 없어도 쿼리는 정확한 답을 낸다 — 순차 스캔 + 디스크 정렬로 느리게 낼 뿐이다. 데이터 무결성·기능 정확성 축에는 영향이 없다.
- **조건부인 이유**: `audit_history_config.json`의 상한(`recent_max_scan_rows` 등)을 아무리 낮춰도 **각 청크의 스캔 자체는 테이블 전체에 비례해 자란다** — config만 배포하고 인덱스를 건너뛴 프로덕션 박스는 "오늘 배포했다"는 사실과 무관하게 **2026-08-11 이전과 같은 지연**을 겪는다. 대량 인제션 직후 첫 `/audit_logs/recent` 호출이 실측 31.7초였던 것이 이 항목의 동기다.
- **반영 절차**: [DEPLOY_SETUP §6 단계 8-ter](../guide/DEPLOY_SETUP.md). `CONCURRENTLY`라 쓰기 락 없이 라이브에 돌릴 수 있다.
- **점검**: `--preflight-only`는 컬럼 드리프트만 보고 **인덱스 존재는 보지 않는다**(8-bis와 같은 사각). 확인은 `psql`로 `pg_indexes`에서 세 이름을 직접 조회하거나, 대량 인제션 직후 `/audit_logs/recent` 응답 시간을 재는 것이 정직하다.

### C5. 동적 테이블 인덱스가 선언과 어긋난 채로 배포된다 (2026-08-14 신설 — F6, 판정 `R-2026-08-14-B`)

`models.init_dynamic_models`가 인덱스를 하드코딩 목록이 아니라 `table_config.json`의 **선언**에서 파생하게 됐고(`idx_<표>_declared_key`), 동시에 스캔 0으로 실측된 `ix_<표>_created_at`·`idx_<표>_bk` 두 가족이 은퇴했다. 그런데 `create_all`은 **기존 테이블에 인덱스를 추가하지 않고 어떤 인덱스도 지우지 않는다** — C4·D3와 **정확히 같은 계급**의 함정이고, 이 함정이 이미 개발 두 사본의 수동 인덱스 집합을 **교집합 공집합**으로 갈라놨다.

- **차단이 아닌 이유**: 인덱스가 어긋나도 답은 정확하다. 읽기가 느리고 쓰기가 비쌀 뿐이다.
- **조건부인 이유**: 미루면 **양쪽으로** 손해다 — 선언 키 인덱스가 없어 맵 조회가 순차 스캔으로 떨어지고(예: `bonding_log`의 `(bond_lot, bond_slot)`는 오늘 어느 DB에도 없다), 동시에 아무도 안 읽는 인덱스 둘에 **매 insert마다** 값을 계속 치른다. 🔴 **순비용이 음수라 미룰 이유가 성능 쪽에는 없다** — `assy_qa` 실측 −80.9 B/행 WAL(−10.9%), insert 시간 −11.8%(2칸 키 형태).
- **반영 절차**: [DEPLOY_SETUP §6 단계 8-quinquies](../guide/DEPLOY_SETUP.md). 기본 읽기 전용, `--apply`로만 쓰고 `--reverse --apply`로 원복(`assy_qa`에서 표별 개수까지 원상 복귀 실측). 정책·표별 근거는 [architecture/INDEX_POLICY](../architecture/INDEX_POLICY.md).
- **점검**: `--preflight-only`는 여기서도 눈이 없다(컬럼만 본다). 정직한 확인은 **마이그레이션을 읽기 전용으로 한 번 돌려 보는 것**이다 — 아무것도 쓰지 않고 표별 before/after 개수와 거절 사유를 전부 찍는다.
- ⚠️ **거절은 실패가 아니다.** 모든 은퇴는 대상 DB에서 다시 증명되며, 그 표의 인덱스가 전부 스캔 0이면(신선 복원·통계 리셋) **거절한다** — 그 0은 증거의 부재이지 부재의 증거가 아니기 때문이다. 종료 코드 1은 「이 박스에서 아직 증명 안 된 항목이 있다」는 뜻이다.

### C3. 백업 — git이 안전망이 아니기 때문에 필요하다

`server/config/`와 `server/ingestion_workspace/`가 gitignored인 것은 **의도된 설계다**(사용자 확정): 운영 서버에 코드를 패치할 때 현장 자산이 딸려 들어가 오염되는 것을 막는다. 오늘 정리한 **제품 소유 / 현장 소유** 구분이 바로 이 경계다.

> ⚠️ **이 두 디렉터리를 git에 넣지 마라.** 배포 안전을 위해 일부러 뺀 것이지 누락이 아니다. 제품이 정의하는 테이블은 `.sample`과 설치 스크립트로 배포되고, 현장 자산은 현장에 남는다.

대가는 명확하다 — **git이 복구 경로가 아니다.** 그래서 별도 백업이 필수다.

- **필요**: 두 디렉터리 + PostgreSQL 정기 백업. **복원을 실제로 한 번 해볼 것**(백업은 복원해 보기 전까지 백업이 아니다).
- 오늘 이 자산 2건이 실수로 덮어써졌고 **git에 없어서 원본을 복구할 수 없었다.** 하나는 `.pyc`·해시 매니페스트·폐기 전 커밋 blob 세 경로를 조합해 겨우 되살렸고, 다른 하나(`inventory_master/config/config.json`)는 **원본 내용을 끝내 알 수 없다.**

#### ✅ config 트리 — 해소 (2026-07-28)

주 1회 `server/config/*.json` 전량 스냅샷(`<이름>_<yymmdd>.json.bak`, 1개월 FIFO). Auto-Update 스케줄러 프로세스가 유지보수 작업으로 돌린다. 상세는 [ROLLBACK_PROCEDURE §3.1-bis](../guide/ROLLBACK_PROCEDURE.md).

**이 항목이 통과인 이유는 스크립트가 생겼기 때문이 아니라 복원을 실제로 했기 때문이다.** 격리 스택에서 스냅샷 → 라이브 config 파손 → 복원 → **시스템이 옛 동작을 실제로 서빙하는 것까지** 확인했다:

| 대상 | 파손 시 관측 | 복원 후 | 총 소요 |
|---|---|---|---|
| `transfer_plan_config.json` | `dt.target_map.table` = `None` | `'dt_map'` 복귀 | **0.17초** |
| `table_config.json` | `/tables/test/schema`에서 `leg` 소실 | `leg` 복귀(watcher 재읽기) | **0.33초** |

드릴이 **새로 찾아낸 함정 1건** — ✅ **2026-07-29 해소(H2)**: `config_watcher.py`의 1초 디바운스가 **리딩 엣지**라 연속 두 번째 쓰기를 통째로 버렸다. 파일은 옳은데 시스템이 옛 선언을 서빙하고 로그에는 아무 줄도 남지 않았다. 이슈 #9(원자적 rename)와 증상이 같았고, **원인도 같은 계급**이었다 — 파일이 시스템에 도달하는 경로가 하나 막혀 있는데 그 사실이 아무 데도 안 남는다. 지금은 트레일링 엣지(이벤트마다 재무장, 마지막 이벤트 후 1초 발화)라 버려지는 저장이 없다. 남은 것은 **약 1초의 반영 지연**뿐이며 ROLLBACK_PROCEDURE 단계 2에 기재.

**멈추면 보인다**: `/health`의 `checks.config_backup`이 `missing`/`stale`이면 `problems`에 뜨고 `degraded`가 된다(HTTP 200 유지). 판정 근거는 작업이 스스로 쓴 "마지막 실행" 필드가 아니라 **디스크의 스냅샷 파일** — 조용히 죽은 작업은 자기 성공 기록을 그대로 들고 있기 때문이다.

> ⚠️ **운영에는 아직 스냅샷이 없다**(드릴은 격리 환경에서만 했고 운영은 읽기 전용이었다). 따라서 이 코드가 배포되고 **런처가 재기동될 때까지 운영 `/health`는 `config backup: ... never been taken`으로 degraded**다. 그 줄이 사라지는 것이 곧 첫 백업이 돌았다는 증거다.

#### 🟡 남은 것 — PostgreSQL과 `ingestion_workspace/`

- **PostgreSQL 정기 백업**: 없다. config만 해결됐다. 데이터베이스는 §5(스키마는 한 방향)의 이유로 롤백 대상이 아니지만, **소실**에 대한 방어는 여전히 없다.
- **`server/ingestion_workspace/`**: 스냅샷 대상이 아니다. 매퍼·수집기 스크립트가 여기 있고, 실제로 원본을 잃은 2건 중 하나가 이 트리였다.

- 🔗 **B4 의존성은 해소됐다.** 롤백 단계 2가 이제 실재하는 복원 원본을 가리킨다. `install_product_tables.py`의 `table_config.json.bak.<ts>`가 **배포 이력이 아니라 "제품 테이블 설치 이력"**이라는 판단은 그대로 유효하며([ROLLBACK_PROCEDURE §3.1](../guide/ROLLBACK_PROCEDURE.md)), 주간 스냅샷은 **날짜를 확장자 앞에 두어** 그 둘이 `ls`만으로 구분되게 했다.
