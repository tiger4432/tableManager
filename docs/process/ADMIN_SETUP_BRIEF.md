# ADMIN 셋업 레인 지시서 — 「소스 테이블 하나를 내 손으로 원장에 잇고 어휘까지 추가한다」

> 소유자 목표(2026-08-15, 1순위): **「내가 소스 테이블 하나 새로 만들어서 어휘
> 추가까지 하는 것.」** 코드 0줄·재기동 0회로. 판정 정본은 `LEDGER_RULINGS.md`
> **R-2026-08-15-M**. UI 전략이 바뀌어(소비자=Spotfire) 콘솔 재작성은 보류이고,
> 이 레인이 오늘의 본체다.

## 0. 완주 여정 (이걸로 합격/반려를 가른다)

소유자가 **admin 화면만으로** 다음을 끝낸다:

1. 이미 존재하는(또는 파일 인제션으로 방금 생긴) 테이블 하나를 고른다.
2. 그 테이블을 **원장 소스로 선언**한다 — kind 선택, 컬럼 매핑, 시각 컬럼·타임존,
   주어 타입, 워터마크.
3. 필요하면 **ontology 층 술어를 새로 등재**한다(서명 완결 필수).
4. **드라이런**으로 「이 선언이 낳을 원자」를 쓰기 0으로 미리 본다.
5. 저장 → 자동 reload → **「먹었는가」 문장** 확인.
6. 백필을 돌리면 그 테이블의 행이 원자가 되고, `/api/ledger/structure`에
   **새 술어·새 엣지가 «선언 출처: config»로 뜬다.**

## 1. 기존 재료부터 (새로 짓기 전에 반드시 확인)

- `POST /admin/reload-configs` — 캐시 교체. **재기동 불필요**의 근거.
- `GET /admin/config/resolve` — 「내 config가 먹었는가」 보고 조립기. 새 화면도
  이걸 재사용한다(두 번째 판정기를 만들지 말 것).
- `GET/POST /admin/scripts/code` — 파일 읽기·쓰기 + strict 토큰 + Monaco 전례.
  저장 경로는 이 규율을 그대로 따른다.
- `server/config/ledger_config.json`의 `sources` — 이미 **컬럼 매핑·이벤트 유형별
  술어 방출**까지 선언이다. 새 스키마를 발명하지 말고 **이 파일을 편집 대상으로**
  삼는다.
- 파일 인제션·워크스페이스 화면 — 테이블 생성은 그쪽 소관. 이 레인은 «잇기»부터.

## 2. 편집 표면 셋

### 층 1 — 소스 → 원장 (`ledger_config.json` / `sources`)
노코드 폼: 테이블 선택(실재 확인) → **kind 선택**(`observation` / `transfer` /
`lot_event` / `derivation`) → kind가 요구하는 필수 매핑만 폼이 물어본다 →
`occurred_at` 컬럼·포맷·타임존 → `subject_types`·`register_entity_types` →
워터마크 컬럼. **어느 kind 모양에도 안 맞으면 화면이 그렇게 말하고 멈춘다**
(억지로 밀어 넣지 말 것 — 그건 새 kind 판정 사안이다).

### 층 2 — 어휘 (ontology 층만)
- canonical(`register`/`pin`/`same_as`)은 **읽기 전용**으로 표시.
- ontology 술어 추가 폼: `label_ko` · `subject[]` · `object{kind, required[]}` ·
  **`traversable` 삼상태 명시 선택**(True 재귀 / False 도달만 / None 미수집) ·
  `direction` · `since`. 하나라도 비면 저장 거절(R-M ②).
- 삭제 버튼 없음. `status: retired` + `superseded_by`만(R-M ③).
- 코드가 싣는 v0 집합과 config 확장분을 **출처로 구분해 표시**(R-M ④). 어휘
  로더는 두 출처를 합치되 각 항목에 `origin: code|config`를 붙인다. 게이트의
  서명 검사는 합쳐진 집합을 그대로 쓴다(자동으로 따라온다).

### 층 3 — 온톨로지(물리·이름)
- `mechanism_models.json`: 모델·노드·엣지(from→to, dir)·**bindings(필드→물리량)**.
- `ledger_journey.json`: `step_labels` / `family_labels` / `field_labels`.
- 둘 다 폼 편집 + 원본 JSON 보기(Monaco) 병행. 여기 편집은 즉시 관문·화면 문구에
  반영된다.

## 3. 저장은 항상 3단 (R-M ⑥ — 예외 없음)

1. **문법 검증**: 서명 완결성, SQL 식별자 규칙(관계·컬럼명은 문자열 보간 자리),
   참조 무결(존재하는 테이블·컬럼·주어 타입인가), 어휘 중복.
2. **드라이런 — 쓰기 0**: 소스 N행(예: 20행)을 실제 번역기에 태워
   「나올 원자 N개」를 **원자 봉투 그대로** 보여 준다. `derivation` 규칙이면
   「이 규칙에 걸리는 대상 M개」와 근거 원자. 게이트 거절이 나면 그 사유도 그대로.
3. **저장 → `reload-configs` → `/admin/config/resolve`**로 「먹었는가」 한 문장.
   드라이런 없는 저장 버튼은 만들지 않는다.

## 4. 경계 (하지 말 것)

- canonical 어휘를 화면에서 늘리는 문 만들기 금지.
- 술어 삭제 경로 금지(은퇴만).
- 드라이런을 «샘플 미리보기»로 대충 하지 말 것 — **실제 번역기를 태운다**.
  가짜 미리보기는 조용한 거짓말이다.
- 콘솔(ledger.html) 화면에 투자 금지 — 이번 레인은 admin과 서버뿐.
- API 응답 모양 변경 금지 — 소유자와 논의 중인 별개 레인이다.

## 5. 착지·검수

- 착지는 **한 라운드로**(중간 착지 금지, 재기동 1회), 완료 시 「admin 셋업 착지」
  한 줄.
- 포크 검수: 위 §0 여정을 포크가 직접 admin에서 끝까지 수행한다. 특히 ③(어휘
  추가) → ⑥(구조 뷰에 `origin: config`로 등장)이 이어지는지가 이 레인의 심장이다.
- 막히는 항목은 빼고 착지하되 **뺀 것을 목록으로 말할 것**(무언 누락 금지).

## 6. 개정 (2026-08-15, 소유자 관찰·판정 반영)

### 6-1. 새 화면을 짓지 말 것 — **구조 뷰가 편집 표면이 된다**
소유자 관찰: 「구조 뷰에 소스→원장, 원장→온톨로지 구조 다 있네.」 맞다. 구조 뷰는
이미 번역기·축·해소기·종류·기전 **선언 패널**을 싣고 각 행이 자기 엣지 id를 물고
있다. 그러므로 admin은 별도 화면이 아니라 **그 지도의 «편집 모드»**다 — 같은 행에
편집 버튼, 저장 3단(검증→드라이런→저장+핫리로드)이 그 자리에서. 지도와 편집기가
따로 서면 「내가 고친 게 저 지도의 어디인가」를 사람이 머리로 이어야 하고, 그
이음이 이 레인 목표의 절반이다.

### 6-2. 넷째 kind = **선언형 번역기** (오늘 목표의 심장)
번역기는 소스마다가 아니라 **모양(kind)마다** 하나다(`void_obs`·`delam_obs`가 같은
번역기를 공유하는 것이 증거). 문제는 새 «모양»이고, 그래서 행→원자 사상 자체를
선언으로 받는 범용 번역기 하나를 넣는다:

```jsonc
"emit": [{ "predicate": "...", "subject": {"type":"...","keys":{"...":"$col"}},
           "object": {"kind":"value","payload":{"...":"$col"}},
           "when": {"$event_type":"..."} }]
```

**첫 판은 «단순 사상」만 좁게** — 한 행이 1~N 원자, 값 사상, 열 값 분기까지. 리스트
열 분해·짝짓기 같은 **구조 변환은 범위 밖**이다(실측 근거: `lot_event` 한 행이
`slot_numbers`/`wafer_ids` 두 리스트를 위치로 짝지어 `derived_from` 1 + `has_wafer`
19를 낳는다 — 이건 선언으로 표현하면 작은 프로그래밍 언어가 된다). 안전망은 게이트다:
선언이 잘못된 원자를 만들면 저장이 아니라 **거절**로 끝난다.

### 6-3. 첫 시험 케이스는 `bonding_map` — **소유자가 직접 수행한다**
판정 R-2026-08-15-N에 따라, 이 레인의 완주 시연은 이것으로 한다:
① `bonding_map`(1,181행 · `pkg_id·base·x·y·leg`)을 소스로 선언 ② 「좌표별 레그
배정」을 말할 ontology 층 술어 하나를 admin에서 등재 ③ **맵을 주어로** 세우고
웨이퍼에는 「이 맵을 썼다」 주장 하나만 — **전개 금지** ④ 드라이런으로 나올 원자
확인 → 저장 → 구조 뷰에 `origin: config`로 등장.
**이 시연은 소유자가 직접 한다**(소유자: 「admin 되면 내가 직접 이거 해볼게」).
구현자는 길만 깔고 미리 넣어 두지 말 것.

### 6-4. 같이 고칠 것 — 읽기 롤업 (판정 R-2026-08-15-O)
지금 `WaferLeg` 주어 원자 42개가 웨이퍼 스코프 조회에서 보이지 않는다(본딩 조건이
화면에서 사라진다). 읽기를 `subject_type` 고정이 아니라 **뿌리 키 롤업**으로 —
파생 주어 타입은 자기 뿌리 키를 선언해야 등재되게(R-M 서명 요건에 추가).
이 한 건은 API 응답 «모양»을 바꾸는 게 아니라 «누락을 메우는» 수리라 이번 라운드에
포함한다.
