# The frame lookup borrowed the bonding slot for every axis

**Date:** 2026-08-14 13:43 · **Domain:** Server (원장 — 랏 맵 프레임 해소) · **Status:** 착지 — `29a82ea`

---

## 배경 — 코어 데이터가 오는 순간 터질 잠복 결함 둘

병렬 레인이 바로 그 코어 데이터를 짓고 있었다. 오늘은 코어 축이 unreachable이라
안 보이고, 내일은 그럴듯한 틀린 격자가 된다 — 이 모듈 자신의 주석이 경고하던
바로 그 실패다.

## 변경 내용

**결함 1**: 프레임 조회가 요청된 슬롯을 모든 축에 썼다 — 코어 축이
`{core_lot}_{bond_slot}`을 찾게 된다. 오버라이드는 중요한 곳에서 틀렸고 안
중요한 곳에선 중복이었다(WHERE 절이 이미 행을 좁히므로 필터된 축의 관측 슬롯이
이미 그 값, 그것도 컬럼 자신의 철자로) — 삭제가 순이익.

**결함 2**: `_slot_column_for`가 docstring은 「축마다 자기 계열」이라면서 모든
축에 `bond_slot`을 반환했다.

```python
# 이전: source 인자를 받고 안 읽으며, 루프 안에서 무조건 return —
#       조회처럼 생긴 루프. 모든 행 축에 bond_slot을 답했다.
slot_column = _slot_column_for(source)
# 이후: 행 축 자신의 계열, 없으면 None — None은 공백이 아니라 답이다
slot_column = _slot_column_for(axis)
```

docstring이 이겼는데 취향이 아니라 근거로: "3"은 세 슬롯 공간(bond 3 · dt 7 ·
core 21)에서 서로 다른 물리 객체라, `by=dt_lot` 행을 `bond_slot`으로 거르면 그
DT 랏의 임의 단면을 한 프레임치라고 부르며 넘기게 된다.

## 증명은 미끼다

분리 단언만으로는 아무것도 판정 못 한다 — 전부 거절하는 구현도 통과하므로.
그래서 **틀린 프레임을 등록했다**: `CORE-A_3`을 4×4로, `DT-A_3`을 5×5로. 두 규칙
다 `ready`를 답하니 판정이 「어느 프레임인가」로 강제된다: 수리 전 코어는
`CORE-A_3` 4×4로 해소됐고, 수리 후 `CORE-A_21` 13×13.

레인은 자기 계측기도 잡았다: 첫 주입이 `slot_column` 마커 단언에서 멈춰 행 집합
단언에 못 닿았다 — 아무것도 검사 안 됐는데 잡힌 것처럼 보였다. 순서를 뒤집어
**질의가 한 일**을 응답이 말하는 것보다 먼저 채점하자 `{5} == {1}`이 울렸다.

응답엔 `slot_column` 필드가 가산으로 추가됐다 — `slot`만 되돌려주면 안 좁혀진
행 집합이 슬롯 제목 아래 렌더되고, 우연히 한 슬롯이면 `ready`까지 보고하는데
읽는 사람이 구별할 길이 없다.
