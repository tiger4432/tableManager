# wafer_id was the right key all along

**Date:** 2026-08-14 09:32 / 09:33 · **Domain:** 보드 + 프로세스(소유자 판정) · **Status:** 기록만 — `acbcef2`, `57ecd8e`

## 소유자 판정 — 청소 문제가 config 문제의 옷을 입고 있었다

**`core_wafer_map`의 키는 `wafer_id`가 맞다. 9,674개의 빈 행은 레거시 쓰레기이지
선언에 대한 증거가 아니다.** 이것이 총괄이 아침 내내 이 축을 서술한 방식을 뒤집었다:
「대부분 NULL인 컬럼으로 조회하는 config」가 아니라 — 선언은 옳았고 데이터가 백필된
적이 없었다. 전날 `272da5b`가 그 빈 행들을 근거로 선언을 복합키로 되돌렸는데, 그
추론도 판정 아래 살아남지 못한다.

판정은 오늘 상태를 **놔두는 것**이다: 복합키가 소유자 화면에 209층을 내놓은 그것이고
유지된다 — 수리랍시고 되돌리지 못하게 기록됐다.

## 그리고 아침에 은퇴시킨 도구가 바로 그 방향을 섬겼다 (`57ecd8e`)

`migrate_map_meta_to_wafer_id.py`는 같은 날 아침 F1(`614a2ab`)에서 「기각된 방향을
구현한 도구」라는 근거로 은퇴됐다 — **그런데 방향은 기각된 적이 없었다.** 은퇴
자체는 살아남는다(전제조건이 없는 도구는 돌면 안 된다). 파일은 git에 있고
RETIRED.md가 부활 조건을 드므로 잃은 것은 없다 — 적어야 했던 것은 **순서**다:
마커의 자기 순서대로 선언을 먼저 하면 그날 아침의 11층 화면으로 걸어 돌아간다.
레거시 행 청소와 `wafer_id` 백필이 먼저, 선언이 둘째, 도구 부활이 마지막.

## 그때 남아 있던 것

- 이 판정 시점에 실행된 것은 없다 — 청소도 백필도 미착수. RETIRED.md의 부활 조건에
  순서가 보강된 상태로 남았다.
