# 개수가 «첫 그림»을 떠났다 — 그러려면 `null` 이 «0 으로 그려지는 것»부터 멈춰야 했다

> **측정 상자:** 이 워크스테이션. **운영이 아니다.**

## 배경 — 첫 그림의 비용 중 «개수»가 얼마인지 먼저 쟀다

```
이 상자, 워밍업 후, 행 1,000 이상인 «모든 표»
   count 가 첫 페이지 비용의 «66% ~ 95%» 이고, «표와 함께 커지는 쪽»이 그것이다
   bonding_log 380,353 행:  세는 데 123.7ms  ·  페이지 가져오는 데 6.7ms
```
⚠️ 이 수는 **이 상자의 표**에서 잰 것이다.

## 🔴 ① 이름이 정해지기 «전»에 클라가 먼저 간 이유

`07068feb`. 총괄이 **서버보다 앞서 도는 것을 승인**했다 — 그 절반이
**«파라미터 이름과 무관»**하기 때문이다.

```
지금까지 화면이 아는 상태   숫자 · 0
개수가 늦게 오면 생기는 상태  «아직 모른다»   <- 화면이 «한 번도 가진 적 없는» 상태
그것을 Matches: 0 으로 그리면
   운영자는 「필터가 아무것도 안 맞췄다」고 읽고 «좁지도 않았던 필터를 넓힌다»
```

개수가 **다섯 자리**에 철자돼 있었다 — `api.js` 둘, `timeline.js` 둘, `main.js` 하나.
**한 곳에서 null 을 처리하면 나머지 넷이 「Matches: null」을 찍는다** — 0 도 빈칸도 아니면서
「세는 중」도 아닌 **세 번째 거짓말**이다.

```js
/** 「아직 모른다」의 표기. 0 과도 빈칸과도 달라야 합니다. */
export const COUNTING = '…';

/** 센 수인가. `null`·`undefined`·NaN 은 «아닙니다». */
export function isCounted(total) {
  return typeof total === 'number' && Number.isFinite(total);
}
```
🔴 요소에 **클래스**로 표시한다 — **참/거짓 검사로는 «진짜 0» 을 「세는 중」으로 찍고**,
운영자가 **영원히 안 오는 수를 기다린다.**

**여섯째 자리는 마크업에 있었다** — `<span id="total-rows">Matches: 0</span>` 이 하드코딩된
첫 그림이었다. **아무것도 묻기 «전»에 화면이 「0건」이라고 주장하고 있었다** —
이 라운드가 다루는 바로 그 순간의 같은 거짓말이다.

## 🔴 ② 페이징은 «반대 방향으로, 조용히» 틀린다

```
Math.ceil(null / limit) || 1  ==  1
=> 안 센 표가 «한 페이지»로 읽힌다
   currentPage >= totalPages 가 참이 되고  ->  NEXT 가 «회색»
   운영자는 개수가 오는 동안 «1페이지를 벗어날 수 없다»
   그리고 회색은 «마지막 페이지»의 모습이기도 하다
```
판단을 같은 모듈의 **숫자만 받는 순수 함수**로 옮겨 **DOM 없이 채점**되게 했다 —
모르면 페이지 수가 null, 「1」이 아니라 «세는 중» 표시, next 는 **살아 있다**.

새 하니스 **20 checks · 변이 7 · 통제 2**. **쌍이 요점**이다 —
문구·요소 표시·페이징 각각에서 **0 과 unknown 을 짝지어** 본다. 한쪽만 보면
**결함이 있어도 통과**한다.

## ③ 서버 — 두 라우트가 «하나의 조립»을 읽는다

`f7a3c372`. `?defer_total=true` 는 `total: null` 을 보내고 `count()` 를 **0회** 부른다.
`GET /tables/{t}/data/count` 가 **같은 필터로** 같은 수를 답한다.

```
개수가 «덜 정확해지지» 않는다 — 근사치 없음 · TTL 확장 없음 · 무효화 규칙 «불변»
바뀌는 것은 «언제 오는가» 뿐이다
```
`null` 은 `0` 이 아니다. **0 은 「어느 행도 안 맞았다」이고 화면이 그렇게 읽는다** —
그래서 둘을 **어느 `or` 가 먼저 도느냐에 맡기지 않고 «따로» 단언**한다.

🔴 **두 라우트가 조립을 «공유»한다는 것이 정돈이 아니라 요점이다.**
```
`?filters=` 를 «두 번째로 해석»하면
   그리드가 «푸터가 없다는 행»을 그린다
   그리고 «어느 쪽이 틀렸는지» 말해 주는 것이 두 응답 어디에도 없다
narrowed_table_query 가 «질의»와 «캐시 키»를 «둘 다» 돌려준다
   -> count 라우트가 어느 쪽도 자기 철자로 못 쓴다
      자기 키를 쓰면 캐시가 «반»으로 갈리고 «한쪽 무효화에서 살아남는다»
```
그리고 `defer_total` 이면 **캐시도 안 본다** — 히트를 먼저 보면 「보통은 빠르고 가끔 느린」
동작이 되고, 그게 이 라운드가 없애려는 것이다.

**제외되는 것 하나가 «논증이 아니라 측정»으로 남았다** — `target_row_id` 점프.
그 경로는 **행 id 를 오프셋으로 바꾸려고 자기 `count()`** 를 돌린다. 그 히트 경로에는
**시험이 하나도 없었고**(미스 경로만 있었다), 이제 공유 조립이 만든 질의를 쓴다.
**오프셋은 총계가 아니라서 count 라우트에서 올 수 없다.**
둘 다 보내는 호출자는 **점프를 뺀 모든 요청에서** 빠른 첫 그림을 얻는다.

변이 다섯: 미루면서 **여전히 세기** · 0 을 돌려주기 · **자기 조립을 쓰는 count 라우트**
(이름 붙은 큐 술어를 떨어뜨린다) · **자기 캐시 키를 쓰는** count 라우트 ·
`?filters=` 를 **무시하는** count 라우트. 각각이 **정확히 하나의 시험**을 빨갛게 만든다.

## ④ 클라 나머지 반쪽 — 늦게 온 개수는 «칠하지 않고 버린다»

`d0be1928`. 좁히기(narrowing)를 **한 번** 조립한다.
`skip`·`limit`·`order_by` 는 **거기 없다** — count 라우트가 그것을 거절하는 것과 같은 이유로,
그것들은 **어느 행을 보일지**를 고르지 **몇 개인지**를 고르지 않는다.

```
늦은 개수    표를 바꾸거나 필터를 고치면 «다른 질문의 답»이 된다
            -> 세대(generation)와 표 이름을 «싣고», 둘 다 여전히 맞아야 칠한다
아예 못 받으면  화면은 «세는 중»에 머문다 — 요청이 실패해도 「모른다」는 «여전히 참»이고
                0 은 그렇지 않다
캐시된 페이지  개수가 도착하면 «채워진다». 좁히기가 바뀌면 캐시가 비워지므로 하나를 공유한다
              -> 안 하면 캐시된 페이지가 «영원히 세는 중»으로 남는다
```

측정(빌드된 번들, 라이브):
```
요청 «둘» — data?defer_total=true · 그다음 /data/count
행이 «개수보다 먼저» 화면에 있다
개수 응답을 «일부러 붙들어» 중간 상태를 봤다:
   33 행 그려짐 · `Matches: …` + 표시 · 총 페이지가 「1」이 아니라 «같은 말» ·
   페이지 입력에 max 안 걸림 · NEXT 가 «내내 활성»
개수 요청이 데이터 요청의 필터를 «그대로» 나른다 (URL 로 확인)
16 행 맞추는 필터 -> 16 · 아무것도 안 맞추는 필터 -> Matches: 0, «세는 중» 표시 꺼짐
```

## 🔴 ⑤ 맵 에디터 — 셋을 «일부러» 남겼고, 안 남겼으면 «조용히 꺼졌을» 것이다


## 아키텍처 영향

- 표 데이터 라우트가 **`?defer_total=true`** 를 받고 `total: null` 을 보낸다.
  **`GET /tables/{t}/data/count`** 가 같은 필터·같은 캐시 키로 그 수를 답한다.
- **두 라우트가 `narrowed_table_query` 하나**를 읽는다 — 질의와 캐시 키를 둘 다 거기서 받는다.
- 개수 표기가 **`match_count.js` 한 곳**이고 **세 상태**(숫자 · 진짜 0 · 모름)를 답한다.
  페이징 판단이 **DOM 없는 순수 함수**다.
- 맵 에디터의 `/data` 호출 여덟 중 **다섯이 미루고 셋이 센다**. 세는 셋은 그 수를 **읽는다.**
