# 아웃박스가 행을 통째로 실어 나르고 있었고, 「업무 키당 한 행」은 불변식이 아니라 가정이었다

**레인:** 서버(인제션·아웃박스·마이그레이션) + QA
**측정 상자:** 이 워크스테이션의 시뮬레이션. **운영이 아니다.**

## 배경 — 서로 다른 두 문제가 한 커밋에 묶인 이유

`4738d84`가 남긴 배포 제약(`20260807_042352`)이 둘째 절반을 강제했다. 첫째 절반은 별개의
용량 문제다. 둘을 한 커밋에 담은 것은 **둘 다 인제션의 쓰기 경로 한 곳**을 지나기 때문이다.

## 1. 아웃박스 붕괴 — 이벤트가 행을 **가리키게** 했다

인제션은 **데이터 행 하나당 아웃박스 행 하나**를 쌓았고, 그 행은 컬럼 전체를 덤프로 실었다 —
**2,113.5 B/행**. 1,000만 행짜리 파일이면 **19.7 GiB**이고, 배수기(drain)의 지속 상한은
**하루 120만 행**이다.

이제 이벤트는 **트리거 행의 `row_id` 목록과 테이블 이름**만 싣고, 파생은 그 행을 다시 읽는다.

- **20,000행 → 이벤트 20건**, **36.0 B/행**.
- 다시 읽는 비용은 오히려 싸다 — **0.29~0.69배**. 🔴 이 숫자에는 기록해 둘 경로가 있다:
  **레인의 첫 측정은 반대 결론을 냈고**, 레인이 그 이유가 계측 쪽에 있다고 **스스로 신고한
  뒤** QA가 독립적으로 다시 쟀다.
- 새 페이로드 모양을 셋째로 만들지 않았다. `chain_replay`가 **이미 하던 재구성**을 확장기가
  그대로 재사용한다.

**사람 경로는 행 단위로 남긴다.** `request_outbox_mode` 기본값이 `per_row`인 이유는
`request_source`가 파일명이라서 **사람의 맵 Push 수천 행과 자동 인제션을 구분할 수 없기**
때문이다. 붕괴된 청크가 실패하면 **행 단위로 다시 펼치되 각자 새 트랜잭션 id**를 받는다 —
워커의 실패 단위는 이벤트가 아니라 그룹이라, 원래 id로 다시 펼치면 그 행들이 **다시 함께
실패하도록 묶이기** 때문이다.

🔴 그리고 두 워커의 상한은 **한 심볼에서 유도하면 안 된다.** `GRAPH_BATCH_LIMIT`은 이벤트
수로 세고 체인 워커의 상한은 행 수로 센다 — 애초에 같은 수였던 적이 없다. 하나로 합쳤다가
**그래프 배치가 20배로 커진 것을 QA가 잡았다.**

## 2. 유니크 업무 키 — 가정을 불변식으로

`business_key_val`을 덮는 인덱스는 **25개 테이블에 50개**였고 **유니크는 0개**였다. 그런데
데이터는 이미 그 조건을 어디서나 만족하고 있었다 — **52,725행, 잉여 0**. 즉 D2가 막지 않는다.

```
uq_bk_*  (UNIQUE on business_key_val)
```

`apply_batch_updates`는 이제 `uq_bk_*` 위반을 잡으면 **새 스냅샷에 대고 병합으로 다시
재생한다.** 이것이 `4738d84`가 벌려 놓은 프로세스 간 경쟁을 **살아남을 수 있게** 만드는
부분이고, 실제 프로세스 둘로 실측됐다 — **인덱스 없으면 행 두 개와 침묵, 인덱스 있으면 행
하나와 이름 붙은 복구 한 건.**

## 3. 잉여 인덱스 29개 / 382.3 MB

`primary_key` 컬럼에 `index=True`가 함께 선언된 자리 **다섯 곳**에서 나왔다. 그중 하나가
동적 테이블이 **공유하는** `row_id`인데, **그 하나가 26개를 만든다.**

집합은 목록으로 적어 두지 않고 **실행할 때마다 `pg_index`에서 다시 발견한다** — 적어 둔
목록은 스키마가 바뀌는 날 조용히 틀려진다.

## 4. 경계 계약 하나

해소되지 않은 충돌이 **500이 아니라 409**를 돌려준다. 이 시점에 **그것을 읽는 클라이언트는
없다** — 그래도 경계 계약이라 커밋에 넣었다.

## 리빙 문서 쪽에서 드러난 표류 (`cc602ed`)

- 운영 가이드가 마이그레이션 판정 문자열을 `refused_invalid_leftover`로 인용하고 있었는데
  코드가 내보내는 것은 `refused_invalid_index`였다. **인시던트 도중에 문서의 낱말로 grep해서
  아무것도 못 찾는** 형태의 표류다.
- `data_model` §3.2가 「선언은 넷이었고」라 써 놓고 다섯을 나열했다. **이 수는 세 번 틀린
  뒤에야 실측됐다.** 고친 줄은 숫자만 바꾸지 않고 **왜 29인지**(선언 다섯, 그중 하나가 26)를
  적었다.
- 아웃박스 이벤트의 문서 초안이 **두 워커에 하나의 예산**을 주장하고 있었다 — 위에서 QA가
  코드에서 잡은 결함의 **산문판**이다.
