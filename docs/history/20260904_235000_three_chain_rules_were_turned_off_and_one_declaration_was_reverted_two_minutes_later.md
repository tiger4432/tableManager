## 배경 — 「안 도니까 둬도 된다」가 «비용에 대한 주장»이었다

네 편집 모두 `server/config/sample/chain_rules.json.sample` 의 `enabled` 한 낱말 뒤집기와
`__comment` 앞의 `DISABLED 2026-09-04 by lead: …` 다. **사유가 설정 파일 «안»에 산다.**

🔴 **공유 기제 — 이것이 이 항목 전체의 하중을 받는 사실이다:**

```
체인 «그룹»은 «그룹 전체가 성공할 때만» 커밋한다
=> 던지는 규칙 «하나»가 «같은 그룹에서 형제가 쓴 것을 지운다»
```

## ① 한 번도 안 돌던 규칙이, 도는 규칙의 쓰기를 지우고 있었다 (`f78b8362`)

`dt_inventory_to_core_usage_map` 은 **모든** `dt_inventory` 이벤트에서 거절한다
(`trigger_job_column` 미선언 + `dt_inventory` 의 비즈니스 키가 복합). 그러니
**한 번도 돈 적이 없다.** 그런데 `dt_inventory_to_standard_dt_map` 과 «트리거 그룹을
공유»해서, 그 던짐이 **저 규칙의 쓰기를 롤백한다** — 그것이 «3번 규칙만 고쳤는데도
여전히 0행» 이었던 이유다.

```
구현자의 맵퍼 로그가 그 순서를 그대로 보여 줬다:
   규칙 #3 END rows_out=5,  그다음 규칙 #5 RAISED,  그리고 «그룹이 사라짐»
```

🔴 **칸을 채우는 것은 «안전한 고침»이 아니다:**

```
core_usage_map 의 맵 키는 core_wafer
dt_inventory 에는 core_wafer 가 «없다»
core_usage_mapper.py:84 가 replace_map 을  scope={'core_wafer': wafer} 로 내는데
   wafer 는 getattr(row, 'core_wafer', None)
=> 풀리게 만들면 «null 스코프의 맵 전체 소거»가 깨어난다
```

## ② 「파괴만 할 수 있는」 둘 — 그리고 «통제된 쌍»으로 증명했다 (`7b89f538`)

`dt_log_to_primary_core_frame` 과 `dt_log_to_core_usage_map`. 둘 다 모든 이벤트에서
거절하고(`dt_inventory` 에 대한 `resolve_column`), 둘 다 **통과하는**
`dt_log_to_dt_alignment_metadata` 와 `dt_log` 트리거를 공유한다.

```
=> 그 둘은 «기여할 수 없고 파괴만 할 수 있다»
   따라서 이것은 «쓰기를 지키는» 변경이고, 상설 게이트가 기능 작업보다 먼저 통과시킨다
```

🔴 **논증이 아니라 «통제된 쌍»으로 쟀다** (이 상자):

```
같은 규칙 · 같은 입력
   던지는 형제가 «있을 때»   0 행
   그 형제를 «끈 뒤»        5 행
```

⚠️ **이 시점에 «일부러 켜 둔 것» 하나** — `dt_metadata_to_dt_inventory`. 그것도
거절하지만 **트리거 그룹에 «혼자»** 라서, 끄면 **아무것도 안 지키면서 선언에 주장만
써 넣는 것**이 된다.

## 🔴 ③ 두 시간 뒤 그 문장을 «자기가» 반쯤 뒤집었다 (`57ee3dfd`)

커밋이 스스로 적었다 — 「두 시간 전에 이것을 켜 둔 근거는 «트리거 그룹에 혼자라 형제의
쓰기를 안 지운다»였다. **그건 참이었고 질문의 «절반»이었다.**」

```
거절은 «재시도»된다  ->  거절이 «실패»로 끝나지 않고 «큐를 곱한다»
```

**실측 (🔴 전부 «이 상자», 재기동한 로컬 워커 — 보고 `91d5e871`):**

| 양 | 값 |
|---|---|
| 입력 행 | **50** (맵퍼 호출 한 번, `rows_out=50`) |
| 만들어진 아웃박스 이벤트 | **101** (내 것 50 + 파생 메타데이터 **51**) |
| 파생 51 에서 나온 거절 그룹 | **153** (51 × **재시도 3**) |
| 배수 속도 | 그룹당 **2.5~3.5초** |
| 진짜 맵퍼 자기 비용 | **0.500초** |
| 끝에서 끝까지 | **약 3.5분** |

```
🔴 「그래서 배수는 «체인이 느린 것의 부작용»이 아니라
   «체인이 안 돈다»가 «만들어진 재료» 자체다」
```

⚠️ **200행·1000행을 «안 돌린» 이유가 적혔다** — 거절 그룹이 대략 600·3000 이 되고,
세 레인이 공유하는 DB 에 수십 분의 재시도 트래픽이 가며, **새 정보가 없다**
(배수와 배수 속도는 이미 쟀다). 2번 규칙이 풀린 «뒤»에는 값어치가 있다 —
그때는 «거절 소용돌이»가 아니라 «맵퍼 비용»을 재게 된다.

그 실행에서 같이 나온 것: **`database_outbox.processed_at` 을 «아무도 안 쓴다»** —
선언돼 있고, `/admin/outbox/failed` 가 «항상 null» 로 보고하고, 마이그레이션이
coalesce 로 지워 버린다. **네 번째 구간에 관측점이 «아예 없다».**
(같은 밤 `bd01209c` 가 고쳤다.)

## 🔴 ④ 되돌린 것 — 한 줄 선언이 «검증기가 못 보는 고리»를 닫았다

`41024df7` 이 `dt_metadata_to_dt_inventory` 에 정확히 한 줄을 더했다:

```json
      "name": "dt_metadata_to_dt_inventory",
+     "target_job_column": "dt_job",
```

**왜 시도했나:** `dt_log → dt_map` 은 세 홉이다. 첫째와 셋째는 됐고 **가운데가 거절**했으며,
`dt_inventory` 에 쓸 수 있는 두 규칙이 다 죽어 있어서 체인이 자기를 먹일 수 없었다 —
그날 저녁 마지막 홉을 고친 것이 **닫힌 문 뒤에 앉아 있었다.** 빠진 선언은 이미 고친 것과
**같은 표의 같은 컬럼**이고, `dt_inventory` 의 `column_types` 가 그것을 들고 있었다.

⚠️ 그리고 방법 하나가 기록됐다 — **«파일 텍스트»가 아니라 «파싱된 규칙»에 대고 확인했다.
텍스트 확인이 «다음 규칙의 주석»에서 거짓 양성을 냈기 때문이다.**

**2분 뒤 되돌린 이유:**

```
🔴 그 홉을 풀면 «순환 검증기가 못 보는 고리»가 닫힌다
   규칙 #3 은 target 을 dt_map 이라 «선언»하지만
      allow_map_metadata_upsert 로 «wafer_map_metadata 에도 쓴다»
   규칙 #2 는 그 메타데이터를 다시 dt_inventory 로 바꾼다
   규칙 #3 은 체인이 만든 dt_inventory 이벤트를 «소비한다»
=> 검증기는 «선언된 target_table» 로 그래프를 만든다.
   그 메타데이터 쓰기는 «그래프에 없는 엣지»다
```
「가드는 규칙 #2 가 거절하는 «동안» 옳았고, **내가 그것을 도달 가능하게 만들었다**.」

**되돌리기의 비용이 0 이었다** — 재기동 이후 맵퍼 줄이 0 이었고, 아무것도 안 돌았고,
**행이 하나도 안 써졌다.** 끝에서 끝까지의 단절은 소유자 판단 사항으로 보드에 남았다 —
「이제 «그 고리가 질문의 일부»로, «예라고 말할 사람을 기다리는 놀람»이 아니라」.

## 아키텍처 영향

- 출하 샘플에서 규칙 **셋이 꺼져 있다**. 사유가 각 규칙의 `__comment` 안에 산다.
- 「거절이 큐를 곱한다」가 **수로** 기록돼 있다 — 거절은 «비용 0»이 아니다.
- **순환 검증기의 한계가 이름을 얻었다**: 그래프를 «선언된 target_table» 로 만들어서,
  `allow_map_metadata_upsert` 같은 부수 쓰기는 엣지로 «안 보인다».
