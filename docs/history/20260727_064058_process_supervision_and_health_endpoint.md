## 배경

`run_decoupled_app.py`가 프로세스 다섯을 띄우고 `while True: time.sleep(1)`을 돌았다.
워처나 체인 워커가 죽어도 **아무것도 감지하지 않고 아무것도 되살리지 않았다.**
웹 서버는 살아 있으니 UI는 멀쩡해 보이고, 데이터만 조용히 멈춘다.

> 준연속 운영 요구에 대고 이것은 가동률이 아니라 **감지되지 않은 다운타임**이다.

### health 전제는 총괄이 말한 것보다 나빴다

먼저 측정했다 — `/health`, `/healthz`, **아무 엉터리 경로** 셋 다 **HTML + 200**을 반환했다.
라우트가 없어서 SPA catch-all로 떨어진 것이다. 외부 모니터는 **모든 가능한 상태에서** 죽은 서버를 살아 있다고 불렀을 것이다.

## 변경 내용

### 살아 있음(liveness)만으로는 도움이 안 됐을 것이다

이 시스템의 **실제 인시던트는 이벤트 루프 프리즈**였다 — 프로세스는 내내 살아 있었고
수십 초간 아무것도 서빙하지 않았다. pid 확인은 healthy라고 답했을 것이다.

그래서 워커별 신호를 **진행 기반**으로 잡았다. 비트를 워커 **자기 작업 루프 안에서** 찍는다.

```
supervisor: 안 돌고 있음                -> down     (재기동 대상)
supervisor: 돌고 있음 + 비트 stale      -> wedged   (살아 있는데 진행 없음)
supervisor: 돌고 있음 + 비트 아직 없음  -> starting (유예, 경보 아님)
supervisor: 돌고 있음 + 비트 신선       -> ok
```

두 사실이 **다른 소유자에게서** 오는 것이 의도다. supervisor는 프로세스 핸들을 쥐므로 **존재**에 권위가 있고,
**진행**에 권위가 있는 것은 워커 자신뿐이다. 하나의 출처로는 두 실패를 구분할 수 없고, 둘은 대응이 다르다.

### 결정적 드릴 — `psutil`로 워처를 서스펜드

| 관측 도구 | 판정 |
|---|---|
| `tasklist` (샘플 10회) | 살아 있음 |
| `psutil.status()` | running |
| supervisor | running, 재기동 0회 |
| **얼어붙은 비트** | **58.7초에 503** |

복구는 **같은 pid로 0.03초**. 즉 프로세스를 보는 어떤 도구도 못 봤고, 진행을 보는 것만 봤다.

### 60초 임계값은 측정에서 나왔다

워커별 비트 간격 p50이 **각 워커의 설계 루프 주기에 그대로 떨어졌다**
(chain 2.04s · watcher 3.07s · scheduler 5.11s) — 이것 자체가 비트가 루프에서 나온다는 증거다.
단일 최악 간격은 10.26초로 **5.8배 여유**, 그러고도 경보까지 **연속 12회 결손**이 필요하다.

> 한 번 놓친 비트로 경보가 울리면 안 된다. GC 정지·느린 디스크·잠깐 바쁜 DB가 그렇게 만든다.
> **거짓 경보를 내는 health check는 뮤트되고, 뮤트된 것은 없는 것보다 나쁘다.**

### 백로그는 크기가 아니라 **나이**로 판정한다

정상적인 10만 행 인제션 하나가 outbox 행 약 11.6만 개를 만든다.
막힌 워커를 잡을 만큼 낮은 **크기** 임계값은 큰 파일마다 발화한다.
**바쁨과 막힘을 가르는 것은 큐가 빠지는가**이고, 그건 나이가 답한다.

### 드릴이 설계 아닌 결함 둘을 뱉었다

**ⓐ 같은 역할의 유령 프로세스가 wedge된 워커를 92초간 가렸다.** 하트비트 파일이 역할 이름으로 키잉되기 때문이다.
운영 유사 사례가 있다 — **재기동 직후에는 죽은 전임자의 비트가 아직 신선하므로,
루프에 도달하기 전에 죽는 후임자가 한 창(window) 내내 healthy로 보인다.**

```python
# server/health.py — 비트는 "감시되는 pid"가 쓴 것만 인정한다
if (hb is not None and cinfo is not None
        and cinfo.get("pid") is not None
        and hb.get("pid") is not None
        and hb.get("pid") != cinfo.get("pid")):
    entry["beat_pid"] = hb.get("pid")
    entry["detail_beat"] = (...)
    hb = None          # pid가 어긋난 비트는 "비트 없음"으로 취급
```

**ⓑ `stop_all()`이 손자 프로세스를 고아로 남겼다.** Windows의 `terminate()`는 트리를 걷지 않고,
스케줄러는 수집기를 서브프로세스로 돌린다. 종료 전에 자손 pid를 **미리 수집**해야 한다 —
부모가 나가면 손자에서 부모로 가는 링크가 사라져 더는 찾을 수 없다.

> Ctrl+Break 드릴로는 이걸 **찾을 수 없었다** — 콘솔 이벤트는 그룹 전체를 죽이므로 어느 쪽이든 깨끗해 보인다.
> 드릴 방식이 결함을 가릴 수 있다는 사례로 기록해 둔다.

### 재기동 예산 — 영원히 재시도하지 않는다

연속 실패 n회째의 대기는 `min(2 × 2^(n-1), 60)`초 — 즉 **2/4/8/16/32초**까지가 예산이고,
`MAX_CONSECUTIVE_FAILURES = 5`를 넘는 **6회째에 FAILED로 고정해 다시는 띄우지 않는다.**
FAILED인 동안 `/health`는 계속 non-200이다.

> 영원히 재기동하면 CPU를 태우고 로그를 넘치게 하고, **무엇보다 감시가 작동하는 것처럼 보인다.**
> 영구 고장 자식을 숨기는 supervisor는 supervisor가 없는 것보다 나쁘다.

`HEALTHY_UPTIME_SEC`(60초) 이상 살아 있던 자식은 연속 카운터가 0으로 돌아간다 —
이게 없으면 **한 달에 한 번 재기동하는 시스템이 결국 아무것도 재기동하지 않게 된다.**

### 라우트 등록 순서가 계약이다

```python
# server/main.py — SPA catch-all `@app.get("/{file_name:path}")` 보다 한참 위에 등록한다.
# FastAPI는 등록 순서로 매칭하므로, 이 라우트가 없던 시절 /health는 catch-all로 떨어져
# index.html + 200을 반환했다. 테스트가 양쪽을 단언한다 — /health는 JSON, 엉터리 경로는 여전히 HTML.
```

DB 프로브는 **2초로 시간 제한**하고, 진행 중 프로브는 **동시에 하나만** 둔다 —
10초마다 폴링하는 모니터가 폴링마다 멈춘 스레드를 쌓지 못하게. (막힌 health check는 두 번째 장애다.)

## 아키텍처 영향

- 하트비트 저장은 `<DATA_ROOT>/config/worker_heartbeats/`의 워커당 작은 JSON —
  `scheduler_status.json` 패턴 **재사용**이고, 그 덕에 `ASSY_DATA_ROOT`가 이미 격리해 준다.
  DB에 두지 않은 이유: **DB 장애 시 모든 워커의 비트가 동시에 stale이 되어
  "DB가 죽었다"와 "워커가 막혔다"가 뒤섞인다.** `/health`에서 별개 행인 이유가 그것이다.
- 자동 재기동은 P2의 체크포인트 재개가 실증됐기 때문에만 허용된다 —
  10만 행 중 3만 행에서 실제 `taskkill /F` 드릴, 커밋된 오프셋이 실제 행수와 정확히 일치,
  275ms 재개, 손실·중복 0.

## 다음 단계

  자손 정리는 `psutil` 부재 시 예외가 아니라 **"자손 정리 없음"으로 조용히 강등**된다 —
  의도된 강등이지만, 선언되지 않은 의존성에 기대는 상태는 해소된 것이 아니다.
- health는 워커의 **진행**과 outbox **나이**를 본다. 진행하면서 틀린 일을 하는 경우는 범위 밖이다.
- 재기동은 자식 프로세스에 한정된다. supervisor 자신이 죽으면 `updated_at`이 멈추는 것으로 드러날 뿐,
  되살리는 주체는 없다.
