## 배경 — 화면은 멀쩡했고 서버는 빈 계획을 검증하고 있었다

`cdcddee`가 DOE 저장 모델을 세 테이블에서 한 테이블로 접었지만 **착지한 것은 클라 절반뿐**이었다.
그 항목이 스스로 남긴 "아직 되지 않은 것" 4건 중 ①(ALTER)과 ②(서버 재바인딩)가 이 커밋의 범위다.

라이브에서 고장은 한 겹이 아니라 **세 겹**이었고, 셋이 서로를 가리고 있었다.

1. 서버 `plan_store`가 퇴역한 `map_doe`/`map_doe_source`를 계속 바인딩했다 → `validate`는 **빈 계획**을 읽었다.
2. 라이브 `table_config`가 `knobs`·`bands`를 선언하지 않았다 → 패널이 보낸 쓰기가 **200과 함께 조용히 드롭**됐다.
   `08d2b12`가 로그만 붙여 두고 동작은 일부러 바꾸지 않았던 [미선언 컬럼 드롭](./20260727_053850_undeclared_column_silent_drop.md) 경로가 정확히 이것이다 —
   계측을 붙여 놓은 덕에 원인 추적이 아니라 확인으로 끝났다.
3. 수량이 여전히 저장에서 읽혔다.

결과적으로 **DOE 패널은 라이브에서 한 번도 동작한 적이 없었다.** 화면은 값을 보여 주고 저장 토스트도 떴다.
라이브 registry 102행 중 `bands`를 가진 행은 **0**이었다 — 옮길 데이터가 없다는 뜻이기도 해서,
마이그레이션 대신 사용자가 패널에서 다시 입력하는 것으로 정리됐다.

## 변경 내용

### 수량은 이제 어디에도 저장돼 있지 않다

서버가 `qty_total`/`qty`를 읽던 자리에 클라와 같은 뺄셈이 들어갔다. 규칙은 네 줄이다.

```
layers = to − prevTo(i)        # prevTo = 앞쪽에서 `to`가 정해진 가장 가까운 구간, 첫 구간 앞은 0
total  = painted(값) × layers
share  = ceil(total / 자재 수)
```

순서를 지는 것은 **배열 위치**이고 `seq`는 정체일 뿐이라 정렬에 쓰지 않는다.
자재 ID는 불투명하게 두고, `(lot, slot)`으로 푸는 규칙은 `plan_store.material_identity` 선언에서 읽는다 —
못 풀면 **보고하고 조회하지 않는다**(추측하지 않는다).

유도가 연속성을 구조적으로 보장하므로 `layer_coverage_gap` 경고는 **표현 자체가 불가능해져** 제거했고,
`layer_range_invalid`는 "층 수를 낼 수 없는 구간 구조"로 용도를 바꿔 `reason`(`unreadable`·`incomplete`·`not_increasing`)을 달았다.

### 검수가 막은 첫 번째 — 라벨 하나가 두 가지 일을 하고 있었다

초과배정 검사(F4)의 게이트가 **사람이 읽는 라벨 목록의 크기**였다.
`seq`가 중복되면 두 수요가 한 라벨로 접히고, `len < 2`가 되어 **검사가 통째로 꺼졌다** — 그런데 `required`는 이미 둘 다 합산돼 있었다.
소스 하나에 60칩이 남았는데 100칩을 요구하는 계획이 **경고 0건 + `status: ok`**를 반환했다.

```python
# server/transfer_plan.py — 이 커밋 시점
acc["required"] += required
acc["demands"] += 1                       # 세는 것은 항목 수
if label not in acc["labels"]:
    acc["labels"].append(label)           # 라벨은 표시 전용

# ...
if acc["demands"] < 2 or acc["required"] <= acc["available"]:
    continue                              # 게이트는 건수. 라벨 수로 세면 seq 중복 하나가 검사를 끈다
```

**왜 이게 자명하지 않았나가 이 결함의 요점이다.** 구 모델에서 `seq`는 복합 business key의 일부였다 —
중복이 **구조적으로 불가능**했고, 그래서 라벨 유일성에 기대는 코드가 오랫동안 옳게 동작했다.
같은 필드가 브라우저가 쓰는 자유 텍스트 JSON 블롭 안으로 내려오면서 DB가 강제하던 유일성이 사라졌는데,
**그 유일성에 기대던 판정은 조용히 꺼졌을 뿐 아무 소리도 내지 않았다.**
파싱 시점에 `seq`를 유일하게 만드는 수리도 함께 넣었지만, 게이트를 건수로 바꾸는 쪽이 본 수정이다 —
제네릭 그리드와 `/tables/.../data/updates`도 같은 컬럼에 쓸 수 있어 **패널의 정규화는 패널을 통과한 쓰기만 지킨다.**

### 검수가 막은 두 번째 — 읽기 실패가 모든 수량을 0으로 만들었다

수량을 저장에서 읽던 시절, `painted` 조회는 값-맵 정합 경고에만 쓰이는 **무해한 읽기**였다.
유도로 바꾸면서 그 읽기가 하중을 지게 됐는데 **가드는 따라오지 않았다.**
group-by가 실패하거나 상한에 잘리면 모든 `required`가 0으로 내려가고, `0 > available`은 영원히 거짓이라
**부족 경고가 하나도 발화하지 않으면서 `availability_checked`는 여전히 true**를 주장했다.

```python
painted_reliable = (painted_status == "connected") and not painted_truncated
# ...
if painted_reliable:
    # 페인팅을 못 읽었으면 이 두 경고는 사실을 주장할 수 없다 — "칠해졌는데 정의가 없다"도
    # "정의됐는데 안 칠해졌다"도 모두 painted를 근거로 하는 단정이다.
```

`painted_reliable`이 유도 전체를 게이트하고, 못 읽었을 때는 `painted_unavailable` 경고 + `unverified`로 내려간다.
그리고 **`undefined_doe_value`·`doe_value_unpainted`를 억제한다** — 셀 수를 모르는 상태에서 페인팅에 관한 단정을 내보내면 그 경고가 거짓말을 한다.

이 두 건은 **저장 → 유도 전환이 만든 새 의존**이며, 전환 자체의 비용이었다.
같은 계열의 결함을 다음에 찾으려면 물어야 할 질문은 "이 읽기는 원래 무엇에만 쓰였나"다.

### 발산은 고치지 않고 **계열을 없앴다**

같은 JSON에서 클라와 서버가 다른 수를 냈다. `Number("  ")`는 `0`이라 `prevTo` 걷기를 **거기서 멈추고**,
`float("  ")`는 예외라 **건너뛴다.** `[10, "  ", 20]`이 화면에서는 20층, 서버에서는 10층이었다.

JS 강제변환을 파이썬으로 이식하면 버그가 스펙으로 승격된다. 대신 `to`를 **`blank | ok | invalid` 셋으로 좁히고,
걷기에서 blank와 invalid를 동일하게 건너뛰게** 했다 — 패리티를 쫓는 대신 **분기가 생길 자리 자체를 없앴다.**

```js
// client2/src/transfer_plan.js — 이 커밋 시점. 서버 `_band_to`와 한 줄씩 대응한다.
if (typeof raw === 'string') {
  const s = raw.trim();
  if (s === '') return { value: null, state: 'blank' };
  if (!/^[+-]?[0-9]+$/.test(s)) return { value: null, state: 'invalid' };
  // Number('9007199254740993')은 검사가 돌기 전에 2^53으로 접혀 경계를 통과시킨다 — BigInt로 정확히 판정.
  ...
}
```

그 과정에서 **아무도 찾고 있지 않던 것**이 나왔다. `normalizeBands`(읽기-수정-쓰기 정규화기)가
자기 나름의 `Number()`를 한 번 더 돌리고 있어서, 컬럼의 `"0x10"`이 **`16`으로 바뀌어 저장되고 있었다.**
표시 함수는 전부 옳았다 — **화면에 오류가 안 보인 이유는 오류가 이미 데이터가 됐기 때문이다.**
정규화기는 파서이고, 파서가 둘이면 그 필드의 의미가 둘이다.

### 계약을 파일 하나로 만들고, 그 파일이 조용히 통과하지 못하게 했다

`contracts/band_arithmetic/vectors.json`이 정본이다. pytest가 읽고, node 하네스가 **클라 소스에서 함수 본문을 떼어내
샌드박스에서 평가**한다(클라 코드는 건드리지 않는다). 하네스는 함수가 개명되면 exit 2로 죽고,
**채점되지 않은 벡터가 하나라도 있으면 실행이 실패한다** — 초록인데 단언을 건너뛴 결과가 이 하네스가 막으려는 실패 형태다.

## 검수 — 렌즈를 다르게 해서 병렬로 돌렸다

기록해 둘 값이 있는 것은 결함이 아니라 **찾은 방법**이다.

- 적대 검수 **둘을 병렬로, 서로 다른 렌즈**로 돌렸다 — 하나는 *유도 충실도*(클라와 같은 수가 나오는가),
  하나는 *조용한 통과 위험*(검사가 꺼졌는데 ok가 나오는 경로가 있는가). 둘 다 NO-GO를 냈고,
  **각자 상대가 놓친 HIGH를 하나씩 찾았다.** 한 렌즈만 썼으면 둘 중 하나는 병합됐다.
- 두 블로킹 결함 모두 **코드를 읽어서가 아니라 구성한 입력에 대고 실행해서** 나왔다.
  지면에서 `float(raw)`와 `Number(b.to)`는 같아 보인다. `seq` 중복이 게이트를 끄는 것도,
  `painted` 실패가 부족을 침묵시키는 것도 **그 입력을 실제로 넣어 봐야** 보인다.

클라 쪽은 **변이 테스트**로 하네스 자신을 검증했다 — 고친 결함을 하나씩 사본에 되돌려 넣고 하네스가 빨개지는지 봤다.
**10건 중 8건 검출, 2건은 구멍**이었다. 정직하게 남길 것은 그 구멍 쪽이다.

- 초록 하네스는 **빨개지는 것을 본 적이 있기 전까지** 아무것도 증명하지 않는다. 실제로 첫 실행에서
  `normalizeBands`의 `to` 출력에 **단언이 아예 없다는 것**이 드러났다 — 조용한 저장 손상이 살던 바로 그 자리다.
- 남은 구멍 중 하나(2^53 경계를 문자열로 통과하는 축)는 벡터를 **10진 문자열로 고쳐** 닫았다.
  다른 하나(`seq`가 `"2"`·`true`로 오는 축)는 **아직 열려 있다** — 코드는 양쪽 다 맞췄지만 계약이 그 축을 고정하지 않는다.

구현자 스스로 보고한 두 가지도 함께 남긴다. 새로 넣은 상한 테스트가 **자기 수정의 구멍**(수요 상한이 구간 단위로만 검사돼 한 구간이 상한을 넘길 수 있었다)을
첫 실행에서 잡았고, B1 테스트 초안에 `... or True`가 들어가 **실패할 수 없는 단언**이 될 뻔했다.
후자는 이번 라운드가 다루던 결함 계열 그 자체다 — 만들어지기 쉬운 패턴이라 검수 항목으로 볼 값이 있다.

## 아키텍처 영향

- **`PRIMITIVES.md`에 두 항목이 등록됐다.** 하나는 `_` 분해 관례가 **셋** 공존한다는 사실(bk 파싱은 마지막 필드가,
  자재 ID 해석은 첫 필드가 여분 분리자를 흡수한다 — `LOT_A_01`에서 갈린다), 하나는
  **"키에서 JSON 블롭으로 내려온 정체는 더 이상 유일하지 않다"**. 후자는 이번 B1의 일반형이고, 스키마를 접을 때마다 다시 물어야 하는 질문이다.
- **자재 해석은 서버 내부 일관성이 아니라 화면과의 일치를 택했다.** 패널과 `validate`가 같은 자재로 같은 엔드포인트를 묻기 때문에,
  분해가 다르면 한 화면에 가용치가 둘 생긴다. 대신 서버 내부에서 bk 파싱과 다르다는 것이 남았고, 코드 주석과 위 카탈로그에 명시했다.
- **`availability_checked`가 한 식으로 줄었다.** 미선언 stage·빈 계획·전부 해석 불가·절단이 모두 그 한 줄을 통해 `unverified`로 모인다.
  **조임이다** — 종전에는 빈 계획이 `status: ok`를 반환했다.
- **배포 순서가 롤백 위험을 만들었다.** config(`knobs`/`bands` 선언)가 먼저 적용됐고 코드는 재기동 대기다.
  이 순서에서는 **코드만 되돌려도 복구되지 않는다.**

## 아직 되지 않은 것 — 이 커밋으로 패널이 살아나지 않는다

1. **웹서버 재기동 전까지 `/api/transfer-plan/validate`는 404다.** 물리 컬럼은 설정 워처가 재기동 없이 ALTER를 적용해 이미 존재하지만,
   구동 중인 uvicorn은 변경 전 모듈을 쥐고 있다. 컬럼과 코드의 답이 다르다는 점이 이 항목의 요지다.
2. `dev_env/config/*`는 옛 바인딩 그대로다 — 격리 환경은 재스냅샷 전까지 계속 404다.
3. **`validate`에 살아 있는 클라 소비자가 없다.** 이를 읽던 클라 코드는 전부 보류(`__held_*`)이고 어떤 번들에도 들어 있지 않다.
   새로 생긴 `reason` 필드를 렌더할 곳이 아직 없다 — 다시 연결하는 사람에게 전달돼야 한다.
4. `docs/guide/CONFIG_GUIDE.md`가 아직 `plan_store.{doe,doe_source}`를 문서화한다(doc-keeper 소관, 이 커밋은 손대지 않았다).
5. `map_doe`(9행)/`map_doe_source`(8행) 물리 DROP은 승인 대기이며, 그 내용은 **이제 코드로 도달 불가**다.
6. `seq: 2.0` 발산은 **클라에서 수정 불가**다 — `JSON.parse('{"seq":2.0}')`는 `2`와 구별되지 않는데 파이썬은 float로 본다.
   실무 위험은 낮지만 전송 한계이지 결함이 아니라는 점을 적어 둔다(다시 발견되지 않도록).
7. 클라는 여전히 `lastIndexOf('_')`를 하드코딩하고 서버는 선언에서 규칙을 유도한다 — **같은 계열의 다음 갈림**이다.
   단일 필드 랏을 쓰는 현장은 모든 자재가 `미상`으로 보이는데, 이는 의도된 대가(신뢰할 수 없던 숫자를 없앤 것)이지만 처음 보는 사람에게는 퇴행으로 읽힌다.
8. **관측 공백**: 설정 워처의 로그가 웹서버 로그에 남지 않고, `sync_dynamic_tables_schema`는 로거가 아니라 `print()`를 쓴다.
   **프로덕션이 의존하는 DDL이 사후에 아무 데도 보이지 않는다.**

## 다음 단계

  `2.0`은 닫히지 않는다 — **벡터 파일에 "여기는 고정할 수 없다"를 남기는 편이 낫다.**
