# 읽기 시점 조인 선언이 «이름으로» 거절되고, 구 선언 파일은 «그대로 돈다»

> **커밋:** `6580c30f`(은퇴 1/5 · 판정 440 ④) — 구현자
> **일자:** 2026-09-16 (밤 23:04)
> **레인:** 구현자 · 검수는 응용(Q-22)
> **측정 상자:** 이 워크스테이션. **운영이 아니다.**
> **이 항목의 앵커는 blob 에서 다시 쟀다** — 커밋 메시지의 줄 번호를 옮기지 않았다

## 무엇이 일어났나

소유자 판정: 운영은 조인 값을 **«표에 써서»** 쓴다(`into.table`). 그래서 통합 체인 선언의
`derive.kind: join` + `into: {read: true}` — 즉 「읽기 시점 조인」 — 이 **은퇴**했다.

**은퇴는 삭제가 아니다.** 엔진(`virtual_join/executor.py`)도 검증기(`_validate_join`)도
어댑터도 그대로 서 있고, 이 커밋 하나만 되물리면 되돌아온다. 이번에 바뀐 것은 **선언이 거절된다**는
것뿐이다. 총 다섯 단계의 첫 단계다 — 은퇴 → 좌석 둘 이동 → 삭제.

```
server/chain/rule_shape.py                                     +28 −0 (순증)
server/virtual_join/config.py                                  +13 −0
server/tests/test_a_read_time_join_is_retired_by_name.py       +147 (신설)
server/tests/…a_read_time_join_can_be_declared_in_the_unified_file.py  −165 (은퇴와 «같이» 죽음)
```

## 🔴 좌석이 «둘»이고, 둘이 «한 문장»을 읽는다

```
server/chain/rule_shape.py:82   READ_TIME_RETIRED = ( … )        <- 정본 «한 상수»
                          :479  expand_declaration 이 그 문장으로 거절
server/virtual_join/config.py:576  _read_time_joins_from_unified
                             :605-613  같은 상수로 로그 + `_record` 뒤 «continue»
```

**왜 둘 다여야 하나** — 코드가 스스로 적어 두었다: 로더만 거절하면 **수집기가 여전히 그것을
돌린다**. 즉 「거절된 선언이 도는」 모양이 된다. 이것이 이 밤에 반복해서 잡힌 **문 가르기**의
같은 부류이고, 이번에는 **거절 쪽**에서 갈라질 뻔한 것이다.

## `read` 를 문법에서 «빼지 않았다» — 그것이 이 커밋의 판단이다

```
server/chain/rule_shape.py:67   INTO_KINDS = ("table", "read")   <- 「read」가 «남는다»
                          :70   주석: 이름으로 거절하려면 문법이 그 낱말을 «알아야» 한다
```

빼면 은퇴한 선언이 **「모르는 칸」**으로 돌아와, 운영자가 **자기가 안 낸 오타**를 찾게 된다.
그것이 정확히 S-251 이 닫았던 구멍(옳은 선언이 `unresolvable_mapper` 로 버려짐)이고,
**은퇴가 자기 도착으로 닫은 구멍을 다시 열지 않는다**는 규율이 여기 서 있다.

## 거절이 «다음 행동»을 싣는다 — 대안이 우회로가 아니기 때문이다

```
「읽기 시점 조인(into.read)은 은퇴했습니다 — 조인 값을 «표에 써서» 씁니다.
 → 다음: 이 선언의 `into` 를 `{"table": "<대상 표>"}` 로 바꾸십시오」
```

그리고 그 문장이 운영자에게 **두 곳**에서 닿는다 — 로더가 규칙마다 ERROR 한 줄
(「한 규칙만, 이름 대고」 — 문서째 죽지 않는다), 그리고 `ledger/admin.py` 의 저장 게이트가
`declaration_refused` 로 **저장 시점**에. 어드민 UI 에서 선언을 고치는 사람은 부팅을 기다리지
않는다.

`enabled: false` 는 여전히 **조용하다**(판정 399 ③′) — 내려놓은 선언을 은퇴가 새로 나무라지 않는다.

## ⚠️ 이 커밋이 «닫지 않은 문» — 구 선언 파일 (응용 Q-22 ②)

```
거절되는 것   «통합 선언»의 into.read      (_read_time_joins_from_unified)
안 건드린 것   server/virtual_join/config.py:531  load_virtual_join_rules
              (:113  VIRTUAL_JOIN_RULES_PATH = … "virtual_join_rules.json")
              이 diff 에 그 이름 «0회»
```

🔴 **그래서 은퇴는 오늘 «절반»이다.** `virtual_join_rules.json` 에 적은 읽기 시점 조인은
**그대로 돈다**. 운영은 `into.table` 만 쓴다는 소유자 판정 아래서 이것은 운영에 무해하지만,
**3단계(삭제)의 입장 조건을 하나 만든다**:

```
① 구 파일의 선언도 «같이 은퇴»한다   -> 그 선언들이 그날 멈춘다 (그것이 은퇴의 정의라면 옳다)
② 구 파일은 «대상 밖»이다            -> 그러면 엔진을 «못 지운다» — 그 선언이 엔진을 부른다
🔴 ①②가 다른 답이고, 안 정하면 삭제 단계에서 「지웠는데 도나/안 도나」가 «우연»으로 갈린다
```

## 시험이 «능력과 같이» 죽고, «은퇴를 재는» 시험이 대신 섰다

능력을 증명하던 파일(`…a_read_time_join_can_be_declared_in_the_unified_file.py`, 165줄)이
그 능력과 **같은 커밋에서** 죽었다 — 「시험은 자기가 재던 코드와 같은 커밋에서 죽는다」 그대로다.
그 자리에 147줄이 서서 **은퇴를 잰다**: 좌석 «둘 다» 거절하는지, 문장의 «내용»(다음 행동)이
실리는지, `enabled: false` 가 여전히 조용한지.
