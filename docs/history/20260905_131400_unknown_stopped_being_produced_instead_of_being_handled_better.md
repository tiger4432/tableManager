## 배경 — 소유자의 신고는 한 문장이었다: 「큐에 넣으면 아무 일도 안 일어난다」

그 한 문장이 **세 가지 다른 세계**를 가리키고 있었고, 화면은 셋을 **같은 값**으로 그리고
있었다.

```
「곧」          «금방» 시작된다
「늦음」        기다리고 있다
「아무도 안 집음」  집을 사람이 «죽었다»
=> 셋 다 화면에서 «빈 대기 목록»이었다. 그리고 셋째가 소유자가 신고한 것이다
```

## 🔴 ② 진행 중인지 «이미 알고 있었는데» 답을 버리고 있었다 (부재의 모양 ③)

`5b427a28`. `in_flight` 는 그 실행이 «진행 중인가·멈췄나·보고가 없나»를 **이미 계산하고
있었고** — 그리고 **그 답을 떨어뜨렸다.** 응답은 「실행 중」만 말했다.

```
「곧 끝난다」와 「멈췄고 뒤의 전부가 기다린다」가  ->  «같은 값»
그것이 소유자의 신고를 한 문장으로 옮긴 것이다
=> gate_blocked 가 그것을 나른다
```

그리고 **행 어디에도 「어느 프로세스가 이걸 들고 있나」가 없었다.** 실행 행은 자기 세션에
써져서 그 작업의 트랜잭션보다 오래 산다 — 그 말은 **프로세스보다도 오래 산다**는 뜻이다.

```
스케줄러가 실행 중에 죽으면  ->  running 이 «영원히» 남고 게이트가 «다시 안 열린다»
runner = host/pid,  «실행이 시작될 때» 읽는다 (import 시점이 아니라)
   -> 포크된 프로세스가 «물려받을 수 있는» 정체는 없느니만 못하다. «구체적으로 보이기» 때문이다
```

⛔ **이 커밋은 아무것도 «판정하지» 않는다.** 자동 회수는 «일부러» 안 만들었다 — 정체가
없는 상태에서 회수하면 「영원히 안 끝남」이 「«둘이 동시에» 돎」이 되고, 그게 더 나쁘다.
**이건 그 결정의 «재료»이지 결정이 아니다.**

### ⛔ 한 가지 합침은 «금지»됐다

```
하트비트가 답하는 것   그 «프로세스»가 사는가
하트비트가 답 «못»하는 것  그 «실행»이 진행되는가
=> 방금 뛴 심장 + 진행 없음  =  gate_blocked. «회수하면 안 된다»
   그 둘을 접는 것이 «이날 하루가 없애려던 바로 그 병»이다
```

그리고 회수는 **기록된다** — 상태를 조용히 뒤집지 않는다. 우리 판단으로 한 «쓰기»이고
이력은 핵심 가치라서.

### 셋 중 «셋째»가 옳았던 이유 (`6614c001`)

구현자가 하트비트에 묻는 방법 셋을 늘어놓고 **아무것도 안 바꾸고 올렸다.**

```
①  아끼는 게 없거나 규칙을 깬다 — 셋째와 같은 스탬프 변경이 필요하거나,
    아니면 «코드»가 「재실행은 스케줄러 것」임을 알아야 한다
    -> 그날 아침 로스터 판정이 이미 「어느 프로세스를 돌리나는 «운영자»의 사실」이라 못 박았다
②  보이는 것보다 나쁘다 — pid 를 «싱싱한 하트비트»에 맞춰 보면
    «우연히 겹친 남의 pid» 가 조용히 「소유됨」이 된다
    -> 모름을 «없애는» 게 아니라 «이름만 바꾼다»
    -> 「회수 안 하는 쪽으로 틀리는 건 괜찮다」는 «확신 있게 틀린 문장을 지우던 날»엔 변명이 못 된다
③  ✅ 맞고, 타이밍 논증도 맞다 — 그 컬럼이 «그날 아침» 착지했고 «쓰인 행이 0» 이다
    지금 바꾸면 «필드 하나», 나중에 바꾸면 «마이그레이션»
    그리고 스탬프할 이름이 런처 ChildSpec 이 «이미 주는» 이름이다 — 한 이름, 두 소비자
```

## 🔴 ④ 로스터의 «넷째 상태» — 총괄이 «같은 방식으로 두 번» 빠뜨렸다

`729d25a0`·`a7f003b3`. 클라 레인이 닫힌 목록의 세 상태 규칙을 «넷»으로 쪼갰고
(도착 안 한 목록 ≠ 멤버 없는 목록), **같은 구멍이 그날 아침 총괄이 쓴 로스터 지시서에
그대로 있었다.**

```
선언+살아있음 · 선언+죽음 · 미선언   ->  «선언됐는데 아직 안 뛰는 것»이 빠졌다
```

가정이 아니다. 프로세스는 **첫 박동 전까지 하트비트 파일을 안 쓴다.**

```
프로세스 시작 ~ 첫 박동 사이에는 하트비트 파일이 «아예 없다»
그것을 「선언됐는데 안 돎」으로 읽으면  ->  «매 재기동마다» /health 가 503
   그리고 이 프로젝트의 규칙은 착지할 때마다 «재기동»을 요구한다
   -> 재기동마다 빨개지는 계기는 «아무도 안 읽는다». 반대편에서 본 같은 병이다
```

```python
ROSTER_RUNNING = "running"        # declared, beating
ROSTER_STARTING = "starting"      # declared, no beat YET
ROSTER_DOWN = "down"              # declared, no beat and long past the point one was due
ROSTER_OFF_ROSTER = "off_roster"  # beating, but nothing declares it
```

두 가지가 «일부러» 이렇게 됐다:

```
낡은 박동은 «유예 안»이라도 down 이다
   — «있었다가 멈춘» 박동은 «아직 안 써진» 박동과 «다른 사실»이다. 그 구분이 넷째 상태의 전부다
시작 시각이 없는 로스터 항목은 «나이를 못 재므로» starting 으로 «남는다» — 짐작으로 down 이라 안 한다
유예값은 heartbeat.DEFAULT_STALE_AFTER_SEC — «새 수를 안 만들었다»
   이 시스템에는 「침묵이 뜻을 갖기에 충분히 긴 시간」의 답이 «이미» 있고,
   미배달 쓸기가 «젊은 행을 그냥 둔다»는 «같은 모양»을 이미 쓴다
```

### 로스터는 «선언»이지 코드가 정할 것이 아니다 (`75004fa1`)

구현자가 「워처와 수퍼바이저가 이 시스템의 정상 모습인가」에서 멈추고 소유자 질문으로
올리려 했다. **아니다.** 어느 프로세스를 돌리는지는 **그 배치의 운영자가 가진 사실**이고
운영자마다 다르다 — 그러니 **코드가 그걸 정하는 것 자체가 결함**이고, 여기서의 답이
무엇이든 상관없다.

### 그래서 런처가 «이미 가진 것»을 게시했다 (`f450871e`)

`/health` 는 **찾아낸 모든 하트비트 파일**을 「살아 있어야 하는 워커」로 취급했다 —
한 번이라도 돈 것은 **영원히 명부에 남았다.**

```

못 읽었던 이유    그 파일이 저장소 «루트»에 있고, 모듈 본문이 import 시점에 «런처를 돌린다»
```

🔴 **시작 시각이 요점이다.** 그게 없으면 「아직 박동 없음」과 「박동이 아예 없던 것」이

```
실패는 «중요한 방향»으로 비치명적이다:
   로스터를 못 쓰는 런처도 «자식은 시작하고», 그 사실을 «말한다»
   없거나 깨진 로스터는 «빈 것»으로 읽힌다
   🔴 빈 것은 「아무도 안 말했다」이지 「아무것도 안 돈다」가 아니다
      읽는 쪽이 그것을 「모든 하트비트가 미선언」으로 바꾸면 «건강한 시스템»을 미선언이라 부른다
```

## 그때 남아 있던 것

- 🔴 **자동 회수는 안 만들어졌다.** `b2943749` 가 「확실한 것만」을 판정했지만,
  «자동으로» 하는 것은 **데이터로 행동하는 것**이라 소유자께 올라갔다. 금지의 «전제»는
  그날 아침 host·pid 가 착지하면서 **소멸했다**고 기록돼 있다.
- 🔴 **최상위 취약점은 «세 번째 층»만 고쳐졌다** — 집는 것이 «하나»이고, 그것이 죽으면
  행이 영원히 기다리며, 화면이 그 둘 «내내» 「실행 중」이라고 말했다. 화면 쪽만 고쳐졌다.
