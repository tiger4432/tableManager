## 배경 — 전제가 셋 중 둘만 맞았고, 셋째는 「없음」보다 나빴다

정렬 규칙을 고르면 대상 테이블과 좌표 바인딩이 맵 오버레이에서 정해지고 작업목록이 그 규칙으로
좁혀진다 — 그것이 목표였다. 총괄의 전제는 「서버는 세 반쪽을 다 답하고 있고 클라 배선만
없다」였다. **둘은 맞았다.**

셋째는 없는 것이 아니었다. **`selection.map_tables`는 그 라우트가 착지한 이래 모든 작업목록
응답에 실려 왔고**, `normaliseWorklist`가 세션으로 정규화하고 있었고, 클라이언트 자신의
헤더가 그것을 「부트스트랩 3단계」라고 서술하고 있었다 — **소비자 0개로.** 피커는 대신
부트스트랩 discovery에서 채워지고 있었다: `map_key_columns`를 선언한 모든 테이블, 즉 **어떤
규칙 아래에서든 같은 아홉 테이블.**

## 그 대가는 「데이터가 나쁘다」로 읽힌다

격리 `assy_qa` 실측: `core_frame_review`(소스 `dt_core_view`)에 `dt_map`을 고르면 라우트가
**200**을 답하고 **150 유닛 중 150이 `unscorable / map_keys_unavailable`**이다. 그리고 **그
거절 중 어느 하나도 데이터에 대한 사실이 아니다.** 라우트는 거절하지 않는다. 아무것도 없는
화면을 돌려주고, 그것은 **「네 데이터가 나쁘다」로 읽히지 「이 규칙이 못 쓰는 테이블을
골랐다」로 읽히지 않는다.**

```js
// 🔴 고를 수 없는 테이블은 선택지가 아니고, 그것을 채택하는 것이 이 기능이 고장 나
//    보이던 방식이다. ... `selectable !== false`라서 첫 작업목록 이전에 지어진 카탈로그는
//    — 아직 아무도 아무 말도 안 한 상태 — 고를 수 있는 채로 남는다.
const choosable = tables.filter(t => t && t.selectable !== false).map(t => t.table);
```

아홉 개 선택지는 이제 disabled 플래그와 **서버의 사유 문장을 그대로** 달고 있다.
사유는 줄이지 않는다 — 잘라내면 `선택 불가`만 남고, 그것이 이 라운드가 없애려던
**사유 없는 「없음」**이다.

## 지나가다 찾은 것이 체인의 «첫» 컨트롤이었다

🔴 **규칙 피커가 규칙을 고르는 순간 `규칙 선택`으로 되돌아갔다.**

핸들러가 `options: null`을 넘기면서 **제안 플래그만** 다시 표시하고 선택 상태는 손대지
않았다. 그런데 이 배포에서는 규칙 둘이 `alignment`를 선언해서 `found.declaration`이 null이고,
그래서 선택지가 **플레이스홀더가 선택된 채로** 지어진다. `fillSelect`는 매 리페인트마다 그
불리언에서 `node.value`를 쓴다.

```js
const ruleOptions = (name) =>
  [{ value: '', label: WORDS_PICK_RULE, selected: !name }].concat(
    found.rules.map(r => ({ value: r.name, label: r.name, selected: r.name === name })));
...
// 손으로 고르는 것은 선택이므로 제안 표식은 떨어진다 — 그리고 «고른 것이 표시된다».
app.setRules({ options: ruleOptions(picked ? picked.name : null), proposed: false });
```

테이블도 컬럼도 작업목록도 **밑에서는 전부 올바르게 채워지고 있었다.** 손대지 않은 것처럼
읽히는 컨트롤 아래에서. **기능이 돌았고 안 돈 것처럼 보였다.**

## 좁은 구멍 셋

- `derived`가 `fallback_guess`로 접혀 있었다. 접힘은 라우트가 애써 그리는 구별 하나를
  화면에서 지웠다 — `fallback_guess`는 **값 컬럼이 지어냈다**는 뜻이고 데이터 경로가 그대로
  거절하는 반면, `derived`는 `table_config`에서의 평범한 상속이다. 둘 다 아무도 합의하지
  않은 짝이지만 **추측인 것은 하나뿐**이고, 그 하나만 그렇게 말하는 단어를 받는다.
- 규칙을 바꿔도 카탈로그 재구축이 끝날 때까지 **이전 규칙의 행이 그대로 떠 있었고**,
  재구축이 실패하면 **영구히** 그랬다.
- 선언된 컬럼의 override가 선언 자체와 구별되지 않았다.

## 꾸미지 않고 보고한 것

두 규칙은 **동일한 유닛 목록**을 만든다(둘 다 `derived_table: dt_inventory`,
`decision_key: ['dt_job']`). 그래서 **「작업목록이 규칙에 따라 바뀐다」는 이 데이터에서
다른 유닛 집합으로 시연할 수 없다.** 실제로 바뀌는 것 — 테이블 선택지, 바인딩, 유닛별
사유 코드, 와이어의 `?rule=` — 만 보였다.

## 아키텍처 영향

- 클라이언트는 어느 테이블을 고를 수 있는지를 **다시 결정하지 않는다.** 서버가 규칙별로
  답하고 이쪽은 따른다. `selectable` 필드의 **부재는 거절이 아니라 「고를 수 있음」**이다 —
  부트스트랩 카탈로그는 어떤 작업목록도 답하기 전에 지어지기 때문이다.
- 복잡도 예산 **순증 0** — 새 패널·모드·모달·버튼 없음.
