## 배경 — 잘린 순위가 «전체 순위»로 읽히고 있었다

walk 이 예산에 걸려 끊기면 화면은 그것을 말하지 않았다. `29475a5c`가 **잘렸다는 사실을 화면이
말하게** 했다 — 부분 순위가 전체 순위로 읽히면 그 다음 판단이 전부 그 위에 선다.

🔴 **그런데 그 커밋은 표시만 넣고 «필드가 없었다».** `subgraphModel`이 `truncated`를 안 실어서
**32분 동안 아무것도 안 찍혔다.** `3f6a27c4`가 이음매를 건너게 만들었다 — **거짓을 지어내지 않고
이름으로**:

```js
// client2/src/rnd_board/api.js
function truncationNames(raw) {
  if (!raw || typeof raw !== 'object') return null;
  return Object.keys(raw).filter((key) => raw[key] === true);
}
```

서버는 **불리언 플래그 객체** `truncated`(+`reason`)를 보내고, 클라는 그것을 **이름 배열**
`model.truncated`와 `model.truncationReason`으로 바꾼다. 그리고 `9fbf1f09`이 **예산을 함께
실었다** — 잘림을 읽는 부품이 그것을 «들어 올릴» 수도 있어야 하기 때문에 `node_limit`과
`hops`가 질의 인자로, 부품마다 `options.nodeLimit`으로 선언된다.

## 🔴 벽은 내 프로브였다

`701fa9f6`. 「깊이 벽이 있다」는 판단의 근거는 **내가 직접 던진 `hops=2` 요청**이었다.
그 파라미터에서 walk 이 깊이로 잘렸고, 그 `truncated: ['depth']`를 **화면을 제약하는 벽**으로
읽었다. 다시 재 보니:

```
보드는 hops 를 «아예 안 보낸다»
ranked 는 깊이 2~20 «전 구간에서 208»
hops=12 에서 그래프가 닫힌다 — truncated=none, 노드 801

```

같은 커밋이 유지한 컷(소스 이벤트 잎 버리기, 801 → 541 노드)은 **벽을 피하려던 게 아니라
payload 때문에** 남았다 — 소스 이벤트는 provenance 이므로 순위 walk 은 그것을 건너뛴다.

## 예산이 선언이 되자, 늘 거기 있던 것이 나타났다

```

node_limit 1000  -> 후보 21, 최상위 void · void_formation
```

「후보가 없다」가 **없음이 아니라 예산**이었다. 같은 커밋이 `complete`를 세 상태로 갈랐다 —
`null`(모름)과 `false`(불완전)가 같은 값이 아니게 됐고, 두 패널이 `!m.complete`에서
`m.complete === false`로 옮겼다.

🔴 **`9fbf1f09`(14:42)은 같은 씨앗에서 「상한을 올리면 잘림은 사라지는데 개수는 여전히 0」이라고

쪽이 원인인지 증명하지 않는다.** 확실한 것은 **앞 문장이 살아남지 못했다**는 것이다.
