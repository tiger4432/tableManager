# A narrower request cost more, and the row that did not move is what caught the gate

**Date:** 2026-08-12 11:43 · **Domain:** Server (정렬 뷰 / 참조 카탈로그) · **Status:** 착지 — `b510df2`

> ⚠️ **모든 수치는 격리 `assy_qa`와 이 개발 워크스테이션 실측이다. 운영 수치가 아니다.**

---

## 먼저 정정 — 지시서의 두 수가 둘 다 틀렸다

정정을 앞에 놓는 이유는 **다음 사람이 인용할 것이 그 수이기 때문**이다.

- 워크리스트는 **3.17 s가 아니라 1.72 s**다. 서베이가 지목했던 config 드리프트는 **그
  사이 다른 사람이 이미 고쳤고**, 823 statements는 벌써 623이다. **3.17 s는 다시 인용하면
  안 된다.**
- `/view`는 **3.46 s가 아니다.** 결정 단위 하나에 **4.17 s**, 파라미터 없이 **4.33 s**,
  그리고 `map_table=core_wafer_map`에서 **29.26 s** — **마지막 것은 아무도 재 본 적이
  없었다.**

지시서가 「시간이 «어디»로 가는가」에 대해 한 정정은 정확히 맞았다: 맵당 소스 셀 읽기가
151회 × 23.48 ms인데 `load_map_meta`는 **한 문장 1.54 ms**다.

## 새로 나온 것 — 좁은 요청이 맵당 더 비쌌다

**동등 조건 셋을 걸면 플래너의 행 추정이 1로 떨어지고, 그러면 워커 둘짜리 `Gather`가
뜬다.** 그 워커 기동이 **~72 ms**인데 실제 스캔은 **9 ms**다.

| 조건 수 | 맵당 |
|---|---|
| 1개 | 23.48 ms |
| 3개 | **99.28 ms** |

**엔드포인트가 운영자가 가장 구체적으로 물을 때 가장 느렸다.** 좁히면 빨라진다는 직관과
반대 방향이고, 이건 인덱스 문제가 아니라 **추정치가 병렬 계획을 사는 문제**다.

## 결과 — 교대 실행, 라운드마다 갈래 순서를 뒤집었다

| | before | after |
|---|---|---|
| 단위 클릭 | 4.166 s | **0.071 s (58.3x)**, 42 statements → 3 |
| `/view`, 파라미터 없음 | 4.328 s | 0.893 s |
| `/view`, `core_wafer_map` | 29.259 s | 4.035 s |
| 워크리스트 | 1.716 s | 0.801 s, 630 statements → 425 |

수리는 두 자리다 — 요청당 소스 셀을 **한 번** 읽는 것(`_source_rows_by_map`), 그리고
후보마다 돌던 `COUNT(*)`를 **하나의 `GROUP BY`**로 접는 것(`_count_cells_bulk`). 후자는
워크리스트 1.73 s 중 **200후보 × 3.9 ms = 0.78 s**였다. 바닥 표들이 맵 키 컬럼에 인덱스를
안 갖고 있어 **후보마다 전량 주사**였고, 비용이 `후보수 × 바닥행수`로 **양쪽에서** 나빠졌다.

## 이 항목의 중심 — 하마터면 착지할 뻔한 판, 그리고 그것을 잡은 것

**첫 게이트는 «요청» 단위였다.** 분해되지 않는 맵 id가 하나만 있어도 배치 전체가 거절됐다.

실데이터에서 `core_lot` 값 **1,443개 중 170개**가 구분자를 품고 있다(`CL_2601_005_A5`).
그래서 **29 s 케이스가 29 s 그대로 남았고 A/B 표에 «1.0x»로 찍혔다.**

> **안 움직인 행 하나가 있는 속도 향상 표는 반올림 오차가 아니라 발견이다.**

숫자가 좋아진 세 행이 아니라 **좋아지지 않은 한 행**이 게이트의 입도가 틀렸다고 말하고
있었다. 표를 「평균 몇 배」로 접었으면 사라졌을 신호다.

## 게이트는 이제 맵 단위이고, 그것은 최적화가 아니라 판정이다

```python
🔴 **The gate is per map, not per request.** It has to be: `core_lot` values
   on this data look like `CL_2601_005_A5`, so `compose_map_id` produces an
   id the loop's `split('_')` cannot take apart - measured, 170 of 1,443
   key tuples on `assy_qa`. Those maps read zero cells today (that is what
   `_no_cell_refusal`'s `key_ambiguous` is for), and serving them from the
   batch would quietly *change the answer*, which is a ruling and not an
   optimisation. Failing the whole request instead would have surrendered
   the other 1,273.
```

그 170개 맵은 **오늘 셀을 0개 읽는다.** 배치에서 서빙하면 **엔드포인트가 지금은 안 보여주는
셀을 운영자에게 보여주게 된다.** 그건 화면이 무엇을 뜻하느냐에 대한 결정이지 성능 작업이
내릴 결정이 아니다.

그리고 커버되지 않는 것과 셀이 없는 것을 **절대 섞지 않는다.**

```python
🔴 `servable` is the set of map ids this answer **covers**, and a map id
   missing from it means "read this one the old way", never "this map has no
   cells". Those two are opposite answers: an empty list read as data seats
   the map on the `no_cells` exclusion, a refusal the operator would then be
   shown for a map that is perfectly fine.
```

`_count_cells_bulk`도 같은 규율을 갖는다 — `complete=False`는 **거절**이지 「전부 0」이
아니다. 여기서 지어낸 0은 운영자에게 **빈 바닥**으로 읽히고, 그건 이 필드가 구별하려고
존재하는 두 상태 중 하나다.

## 가장 강한 증거는 속도가 아니라 해시다

`map_table=core_wafer_map`이 **해시 동일**인데 그 안에서 **1,272개 맵은 새 배치에서,
171개는 옛 루프에서** 왔다. 게이트가 어느 방향으로든 틀렸으면 — 루프가 못 다루는 맵을
서빙했거나, 다룰 수 있는 맵을 떨궜거나 — **그 해시가 달라진다.**

요청 모양 19개를 해시해 18개 동일. `cell_count`는 총계가 아니라 **후보별로** 대조했다 —
**207후보, 불일치 0.**

## 열아홉째는 이 커밋이 만들지 않은 결함이다

`cell_cap=50`은 **양쪽 갈래에서 불안정**하다. 그리고 이 모듈을 프로세스에서 **아예 빼고**
HEAD만 8회 연속 돌려도 **서로 다른 페이로드 둘**이 나오는데, `cell_cap=20000`은 하나만
나온다.

**상한이 걸린 읽기는 어느 셀이 상한을 넘어 살아남는지에 대해 비결정적이다.** 운영자가
새로고침하면 다른 셀을 본다. 여기서 생긴 것이 아니고 여기서 안 고쳤고 보드에 적혔다.

## 검증 — 공유 트리를 쓰지 않고 잰다

스위트 **72 failed / 395 passed, 양쪽 갈래 동일**, 실패 집합도 **이름 단위로 동일**.
그리고 그것을 **HEAD의 모듈을 pytest 플러그인으로 주입해서** 세웠다 — **공유 트리에는 한
번도 쓰지 않았다.** 같은 날 아침 다른 레인이 바이트 스냅샷·교체 방식의 하네스를 공유
파일에 걸었다가 옆 레인의 쓰기와 충돌해 80건 넘는 가짜 빨강을 냈던 것과 대조된다.

그 **72**라는 수는 같은 날 32분 전에 다른 레인이 스위트 기준선 105를 분해하며 얻은 수와
**같다** —
[PostgreSQL 픽스처 항목](./20260812_111113_the_postgresql_fixture_a_commit_of_mine_called_impossible.md).
두 레인이 서로 모른 채 같은 술어에 도달했다.

## 남은 것을 이름으로 적었다

- `dt_map`에서 `/view`는 이제 **파이썬 바운드**다 — 0.95 s 중 **0.80 s.**
- `core_wafer_map`에서 남은 4.0 s의 **74%가 그 170개 분해 불가 맵**이다. **규모 문제가
  아니라 이름 문제**이고, 이름이 바뀌면 그 요청은 코드 변경 없이 약 1.1 s가 된다(측정).

## 그때 남아 있던 것

- **테스트와 리빙 문서는 다른 레인 소관이라 이 커밋에 없다.** 제안된 테스트 6개와 문서
  델타는 보고서에만 있다. 그중 **「분해 불가 맵 id를 서빙한다」 가드는 기존 테스트를 하나도
  울리지 않는다** — 위에서 안 움직인 행이 잡아낸 바로 그 갈래이고, 이 시점에 그것을 지켜
  주는 것은 없다.
- **`cell_cap=50`의 비결정성은 열려 있다.** 이 커밋 이전부터 있었고 이 커밋이 안 고쳤다.
- **170개 분해 불가 맵은 여전히 셀을 0개 읽는다.** 게이트는 그 상태를 «보존»했지 해소하지
  않았다.
- 커밋 본문은 그 수를 **두 자리에서 다르게 적는다** — 구분자 스캔은 「1,443 중 170」이고,
  실제 서빙 분할은 「배치 1,272 / 루프 171」이다. 합은 둘 다 1,443이고 **한 건 차이가
  이 커밋 안에서 조정되지 않았다.**
- 워크리스트의 3.17 s를 낳은 config 드리프트는 **다른 사람이 이미 고쳤다.** 이 레인이 한
  일이 아니고, 그래서 워크리스트의 1.72→0.80은 그 수리 «위에서» 잰 것이다.
