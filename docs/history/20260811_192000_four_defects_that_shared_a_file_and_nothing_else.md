# Four defects that shared a file and nothing else

**Date:** 2026-08-11 19:20 · **Domain:** Server (read path — 감사 이력 / 트랜잭션 상세 / CSV 추출 / count 캐시) · **Status:** 착지 — `721b175`

> 한 파일(`server/main.py`)에 있다는 것 말고는 공통 원인이 없는 네 건이다. 각각 따로 읽으십시오.

## ① 셀 이력 탭이 감사 94%에서 비어 있었다 — 그리고 복원하면 안 되는 자리였다

**현상.** `GET .../cells/{col}/history`는 `column_name == col_name`으로 거른다. 기계
쓰기(파서·체인·스크립트)는 셀마다가 아니라 **행마다 한 줄**을, 컬럼명 자리에 리터럴
`ROW_UPDATE`를 넣어 적는다. **영원히 안 맞는다.**

실측(`assy_qa`, 2026-08-11): 감사 **239,786행 중 225,586행(94.08%)**이 `ROW_UPDATE`.
그리고 **225,101개 행**은 기계 이력만 갖고 컬럼별 기록이 **하나도 없다** — 그 행들에서는
**모든** 셀 탭이 비고 행 탭은 차 있다. 이력이 없었던 게 아니라 **한쪽 화면에서만 없었고**,
그래서 아무도 신고하지 않았다.

**복원하지 않은 이유.** 요약 문자열은 데이터가 아니라 **렌더된 문장**이다
(`f"{col}: {val}"`을 `", "`로 이어 붙이고 NULL은 한국어 `비어있음`, 정수 `0`과 문자열
`"0"`이 구별 불가). 게다가 **값 자체가 쉼표·콜론을 가진 JSON인 경우가 실재한다** —
`wafer_map_metadata`의 산 기록이 이렇다:

```
신규 데이터 생성: target_table: dt_log, map_id: ZZQA-…,
grid_metadata: {"grid_cols": 2, "grid_rows": 2, "grid_start_x": 0, …}
```

`", "`로 자르면 **`"grid_rows"`라는 없는 컬럼이 생긴다.** 표현을 데이터로 되돌리면
「이력 없음」이 아니라 **자신 있게 틀린 이력**이 나온다. 진짜 수리는 쓰기 경로에 있고
이 라운드에서 `crud.py`는 잠겨 있었다.

**한 것 — 복원이 아니라 공시.** 셀 라우트 응답에 두 필드가 붙었다.

| 필드 | 뜻 |
|---|---|
| `row_history_total` | 그 **행**의 감사 건수(= 행 탭이 페이징할 모집단). 행 라우트에선 `None` |
| `row_history_truncated` | 위 수가 정확값이 아니라 **하한**이라는 표시 |

이 하나의 수가 두 상태를 가른다 — `returned == 0 && total == 0`은 「이 행엔 정말 이력이
없다」, `returned == 0 && total > 0`은 「기록은 있는데 이 화면이 못 보여준다」. **둘을
똑같이 「기록 없음」으로 그리는 것이 결함이었다.**

계측은 `audit_history.count_row_history` — `cap + 1`만 읽는 capped probe이고
`fetch_page`가 `truncated`를 얻는 것과 **같은 수법**이다. 300,019행짜리 행이 이 프로젝트에
실재했으므로 공시 한 줄이 O(depth) 스캔이 되면 안 된다. `idx_audit_row_history` 위에서
Index Only Scan이라 실측 비용은 정확 count와 **같다**(0.32ms 대 0.39ms/5회) — 상한이 공짜다.

🔴 **화면은 아직 안 바뀌었다.** `client2`는 이 라운드에서 읽기 전용이었고,
`timeline.js:410`은 여전히 `No change history recorded.`를 그린다. **사실은 선에 실렸고
화면은 아직 아니다.** 클라 할 일은 [backend §이력/감사](../architecture/backend.md)에.

## ② `/audit_logs/transaction/{tx}`가 벌크 원시를 700줄 옆에 두고 N+1을 돌고 있었다

`get_deleted_row_business_key`(호출당 최대 2문장)를 **로그별 루프 안에서** 불렀고, 이
라우트의 기본 `limit`은 20,000이다. **분기가 둘이고 둘 다 그랬다** — 캐시 분기(먼저
검사되는 흔한 경로)와 DB 분기. 한쪽만 고쳤으면 산 라우트는 그대로였다.

수리는 `batch_delete`가 이미 쓰던 `get_deleted_rows_business_keys_bulk`를 테이블별로 묶어
부르는 것뿐이다(`resolve_missing_business_keys`). 한 트랜잭션의 로그는 여러 테이블에 걸칠
수 있어서(체인) 그루핑이 필요하다.

⚠️ **비용 귀속을 정정한다.** 이 스냅샷의 실제 큰 트랜잭션들은 `business_key`를 전부
갖고 있어서 **조회 분기 자체가 발화하지 않는다**(전 DB에서 조건을 만족하는 감사 행이 **1개**).
실측 A/B에서 구·신 코드가 같았다(100,000-로그 tx: 1.63s 대 1.60s). 서베이의 3.4–6.8초는
**실재하지만 N+1이 낸 비용이 아니다** — 20,000 로그 직렬화 비용이다.

결함 축을 실제로 활성화한 통제 실험(삭제된 행 2,000개 + `business_key` NULL, 측정 후 제거):

| | 구코드 :8081 | 신코드 :8082 |
|---|---|---|
| 벽시계 | 3.47s / 3.71s | **0.145s / 0.197s** |
| business_key 해석 | — | 2,000/2,000 정확 |

## ③ 추출의 「최대 100만 행」이 응답 헤더에만 걸려 있었다

`total_count = min(total_count, 1000000)`이 **크기 추산만** 깎았고 스트리밍 쿼리엔
`.limit()`이 없었다. 200만 행 테이블은 상한을 광고하면서 200만 행을 다 내보내고, 덤으로
진행률을 100% 너머로 밀었다(추산 분모가 깎였으므로).

**자르지 않고 거절(413)을 골랐다.** 잘린 CSV는 엑셀에서 **멀쩡히 열리고 숫자만 모자란**
파일이라 「잘렸다」를 적을 자리가 파일 안에 없고, 다운로드가 시작된 뒤엔 헤더도 사용자에게
안 보인다. 거절은 `query.count()` 직후 **첫 바이트 이전**이라 반쯤 쓰인 파일이 남지 않는다.
같은 라우트가 이미 컬럼 밀린 CSV를 500으로 거절한다 — 같은 계급, 같은 판단.

상한은 `main.EXPORT_MAX_ROWS` **한 곳**에서만 선언되고 헤더 추산과 거절 판정이 그 하나를
읽는다. `min()`은 사라졌으므로 `X-Total-Rows`는 이제 **진짜 행수**다.

## ④ `invalidate_table_cache`의 호출 지점 여덟 개가 전부 죽어 있었다

키는 `"|".join(...)`으로 쓰였는데 무효화는 `k == t or k.startswith(f"{t}_")`로 찾았다.
구분자가 안 맞아 **여덟 지점 전부가 키를 0개 지웠다.**

결과가 둘이고 **둘째가 더 나쁘다**:

1. 쓰기 뒤 무효화된 줄 알았던 count가 TTL 내내 살아남았다.
2. 키에 사용자가 타이핑한 `?q=`/`?filters=`가 들어가므로 이 dict이 **서로 다른 검색어
   하나당 한 칸씩, 프로세스 수명 내내** 자랐다. **상한이 전혀 없었다.**

산 A/B(같은 DB, 프로세스별 캐시):

| | 쓰기 전 | 쓰기 후 |
|---|---|---|
| 구코드 :8081 | 43 | **43** (자기 무효화를 살아남음) |
| 신코드 :8082 | 44 | **45** |

수리는 철자를 한 곳으로 모은 것이다 — `build_count_cache_key`(구분자의 유일한 소유자)
↔ `count_cache_table_of`(그 역연산). 판정이 **첫 구획 정확 일치**라 이름이 겹치는
테이블을 오탐/누락하지 않는다. 상한은 `COUNT_CACHE_MAX_ENTRIES`(2,000)이고
`store_table_count`이 **만료분부터** 회수한다(TTL 지난 엔트리는 정의상 죽은 값이다).

곁다리로 `server/scripts/diagnose_slow_after_ingest.py`의 낡은 서술을 고쳤다 — TTL을
2초라 적고 있었고(실제 5.0), 「인제션 완료가 이 캐시를 비운다」고 적고 있었는데 그건
**이 라운드 전에는 거짓**이었다(무효화가 죽어 있었으므로). 지금은 참이다.

## 검증

- **변이 채점 8건, 전부 각자의 테스트만 죽였다** — 셀 공시 off / cap 미고지 / 캐시 분기
  N+1 복원 / DB 분기 N+1 복원 / 테이블 그루핑 제거 / 무효화 구분자 원복 / 캐시 상한 제거 /
  추출 헤더-온리 캡 원복. ⚠️ 그 중 한 번은 **패턴 오타로 변이가 안 먹은 채 초록이 나왔다** —
  다시 앵커를 잡아 적용을 확인하고 재측정했다. 안 먹은 변이의 초록은 아무것도 증명하지 않는다.
- **산 경로 3종 전부 실행**: 브라우저 셀 편집(:8082, 실제 쓰기 + 탭 육안 확인) · 인제션
  트리거(격리 watcher, CSV 3행 적재 후 정지) · 체인 트리거(`production_plan → inventory_master`,
  `chain_2619816e…` 발화 확인). **dt_log 체인은 일부러 안 건드렸다** — 그 캐스케이드는 같은 시각
  가동 중인 정렬 레인의 측정과 충돌한다.
- 프로브 데이터는 전부 회수했다(테이블 행수 원복 확인). 감사 행은 append-only라 남는다(설계대로).
