## ① 장애 넷 — 셋은 한 부류, 넷째는 «다른 주어»

```
① 파일 인제션 전량 실패    S-226 이 평키를 채움 -> 잠자던 uq_bk 가 «처음 살아남» -> 23505 -> rollback -> Detached
② 운영 규칙이 «사라짐»     S-152 가 「모르는 칸」을 경고->거절로 바꿨고, 적재 루프가 거절된 규칙을 «버렸다»
③ 로그가 장애가 됨        한 건용 로그가 수만 행에서 행마다 전문을 찍음
```
🔴 **셋의 부류가 한 줄이다 — 「어제까지 «관대»하던 것이 오늘 «엄»해졌고, 그 엄함이 «이미 돌던 것»을
무효로 만들었다」.** 셋 다 게이트가 「내 변경이 «의도대로» 되나」만 물었고,
**「내 변경이 «어제까지 되던 것»을 못 되게 만드나」를 안 물었다.**
📌 그래서 상설이 하나 늘었다: 제품을 더 엄하게 만드는 변경의 게이트에는 «호환성 한 줄»이 있어야 하고,
**규칙을 «버리는» 거절은 거절이 아니라 «삭제»다.**

### 🔴 넷째는 부류가 달랐고, 그것이 이 항목에서 제일 값진 줄이다

```
증상   체인을 «전부» 끄고 파생까지 꺼도 로그 폭주가 안 멎음
원인   virtual_join/executor 의 검증 캐시 TTL 5초 — 만료마다 재로그
      즉 유일 인덱스 없는 조인 «하나»가 5초마다 영원히 찍고 있었고 «체인은 한 번도 관여 안 했다»
조치   `015bfb38` — 서 있는 거절은 «바뀔 때만» 로그
```
🔴 소유자가 「체인 다 껐는데 난다」로 가설을 죽였는데도 체인 «안»에서 두 라운드를 더 팠다.
📌 판별식: **로그를 진단할 때 «왜»보다 «누가 찍나»가 먼저다** — 그 문자열을 내는 자리를 전수로 세고,
자리마다 «호출 주기»(TTL·타이머·행당)를 본 다음에 원인을 말한다.
