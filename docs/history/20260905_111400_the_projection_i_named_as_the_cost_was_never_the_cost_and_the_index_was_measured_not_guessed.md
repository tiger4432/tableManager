## 🔴 ① 진단이 틀렸고, 그 커밋이 «자기 안에서» 그것을 적었다 (`df64d53f`)

ORM 의 `.count()` 가 행 선택 질의를 서브쿼리로 감싸서, **수 하나를 얻으려고 감사 컬럼
열한 개를 전부 나열하는 SQL** 을 냈다. 그것을
`SELECT count(audit_logs.id) FROM audit_logs WHERE timestamp >= ?` 로 바꿨고,
**코드를 읽어서가 아니라 «핸들러가 실제로 내는 문장»에 대고** 확인했다.

```
🔴 그런데 «두 번째 것»은 못 산다. 그리고 내 직전 보고는 그럴 것처럼 적었다
   같은 표에 대고 연달아 재면  0.585s  vs  0.544s  —  «편차 안의 7%»
   EXPLAIN 이 이유를 말한다: 390만 행 전체에 대한 Parallel Seq Scan
                            timestamp 에 «인덱스가 없다»
   플래너가 이미 서브쿼리를 «평탄화»하고 있었다
   -> 내가 «비용»이라 이름 붙인 투영은 «한 번도 비용이 아니었다»
   「SQL 의 «모양»에서 추론하고 «설명하지 않았다» — 남에게 하지 말라고 해 온 바로 그 실수다」
```
변경은 **남는다** — 맞고, 읽기 싸고, 같은 핸들러의 표별 개수와 «이미 같은 방식»이라서.
움직일 지렛대는 «인덱스»이고, **이 라운드가 그것을 금지**하며 **세 레인이 공유하는 DB**에
대한 총괄 판단 사항이다.

## ② 그래서 소유자가 「인덱스 만들어라」 했고, «어느 것인지»는 쟀다 (`d331afca` → `38090fdb`)

```
지시 전에 «먼저» 잰 것:
   이미 있는 timestamp 인덱스는 «부분»이다 — source_name = 'user' 로 제한
   -> 기계 쓰기를 포함하는 개수는 그것을 «못 쓴다»
   timestamp 상관계수 0.995
후보 «둘»을 라이브 표에 CONCURRENTLY 로 «둘 다» 만들고 진짜 질의로 EXPLAIN ANALYZE
```

```
                     계획              시간        크기
before   Parallel Seq Scan   cost 218,016   468.8 ms
BRIN     Bitmap Heap Scan    cost   9,284     1.2 ms     72 kB
btree    Index Scan                            0.7 ms     71 MB
```
🔴 **「BRIN 이 «잡음이 아닌 축»에서 이긴다.**
둘 사이의 0.5ms 는 469ms 스캔 앞에서 «아무것도 아니고», **천 배의 크기 차이는 아니다** —
btree 는 **이 시스템이 가장 많이 쓰는 표**에 대해 «모든 감사 쓰기가 유지해야 하는 71MB»
이고, 그건 `models.py` 의 `[C-3]` 주석이 인덱스를 은퇴시킬 때 쓰는 «같은 논증»이다.」
BRIN 이 맞는 이유는 컬럼이 «물리적으로 거의 정렬»돼 있어서다(감사 행은 시간 순으로
덧붙여지고 «갱신되지 않는다»). **btree 는 다시 지웠다.**

⚠️ **`CONCURRENTLY` 가 세 레인 한 DB 에서 하중을 받고, «가정이 아니라 확인»됐다** —
빌드 내내 `pg_locks` 를 표집해 `audit_logs` 에 `ShareUpdateExclusiveLock` «만» 있는 것을
봤고, 그것은 INSERT 를 막지 않는다.

**양쪽에 선언됐다** — 신규 DB 용 `models.py` 와 기존 DB 용 마이그레이션 파일
(create_all 은 기존 표에 인덱스를 «안 더한다»). **중단된 빌드의 복구 절차**가
마이그레이션 머리말에 적혔다.

## 🔴 ③ 총괄의 게이트가 «총괄 자기 수»를 잡았다 (`f8e2d099`)

총괄은 `table_stats` 와 `uncounted` **둘만** 사라진다고 썼다. **레인이 멈추고 보여 줬다** —
**한 루프가 «셋»을 만들어서**, `table_stats` 만 지우면 39개 개수가 그대로 남고
라운드가 «67%» 가 아니라 «20%» 를 번다.

```
나머지 둘을 «총괄이 직접» 셌다:
   total_tables · total_global_rows   독자 «아예 없음»
   total_rows                         클라에 «여덟 번» 나오는데 «전부 다른 객체»다 —
                                      적재 진행 항목 자기 총계, «처리/총계»로 그려진다
🔴 리터럴 훑기였으면 그것을 «소비자 여덟»으로 읽고 필드를 남겼을 것이다.
   «멈춰서 확인한 것»이 그 둘을 갈랐다
```

## ④ 그리고 «부산물 하나»가 이 변경의 유일한 조심이었다 (`471f66f7`)

```
wall           1.063 s -> 0.488 s
문장 수             80 -> 41
문장 합계      0.721 s -> 0.262 s
응답은 «통째로» 대조 — 정확히 그 세 키만 사라지고 더해진 것 없음.
              effort · recorrection · system_health · today_updates 동일
```

🔴 **`uncounted_tables` 가 살아남았고, 그것이 조심이 필요한 자리다.**

```
그것은 «지워지는 질의들의 부산물»이었다 —
   물리 모양이 표류한 «선언된 표»가 «개수가 실패하면서» 발견됐다
질의를 그냥 지웠으면 그 목록이 «조용히 비었을» 것이다 — 오늘 «아홉 개»
   그리고 「아무것도 안 깨졌다」는 「내가 안 봤다」와 «같은 사실이 아니다»
=> 같은 세 컬럼을 «LIMIT 0» 로 여전히 풀어 낸다 —
   DB 가 문장을 계획하고, 행을 «안» 돌려주고, «똑같은 UndefinedColumn» 을 던진다
확인: «같은 아홉 표, 같은 사유 문구»
```

## 아키텍처 영향

- `audit_logs.timestamp` 에 **BRIN 인덱스**가 있다 — `models.py` 와 마이그레이션 «양쪽»에
  선언됐다. 기존의 부분 인덱스(`source_name = 'user'`)는 **이 질의를 못 받친다.**
- 대시보드 요약에서 **표별 개수 루프가 사라졌다.** `table_stats`·`total_rows`
  ·`total_tables`·`total_global_rows` **넷**이 나갔다.
- **`uncounted_tables` 는 남았고 «LIMIT 0» 로 같은 예외를 계속 받는다** — 그 목록이
  «부산물»이었다는 사실이 코드에 남았다.
