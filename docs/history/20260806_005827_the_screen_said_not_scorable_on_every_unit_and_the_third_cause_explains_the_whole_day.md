## 배경 — 서버는 이미 답을 냈고 화면이 다른 말을 했다

서버는 **결정했다** — 메트릭 index, 승자 `rot0_front`, 마진 87. 화면은 그 아래에
**점유(occupancy) 수치를 「채점 불가」 표제와 함께** 그렸다.

> **축 하나만 고쳤어도 화면은 움직이지 않았을 것이다. 원인이 셋 쌓여 있었고
> 내가 지시한 것은 그중 첫째뿐이었다.**

## ① 디코더가 점유 쌍을 **무조건** 읽었다

이제 서버 자신의 선택을 **함수 단위로** 비춘다 — **폴백까지 포함해서.** 모르는
메트릭은 점유를 읽고, 그것이 **서버의 `else` 가지가 하는 일**이다.

## ② 서버는 **미채점 후보의 카운트에 0을 쓴다** — 자리표시자가 측정치로 도착했다

디코더가 이제 **상태를 먼저 읽고**, 미채점 후보를 **null 카운트와 서버 자신의 사유**로
나른다 — **목록에 유지하고 절대 버리지 않는다.**

**null-as-zero 함정 둘을 같이 닫아야 했다.**

```js
-    && Number.isFinite(Number(s.agree))
-    && Number.isFinite(Number(s.discriminating))
+    && finiteOrNull(s.agree) !== null
+    && finiteOrNull(s.discriminating) !== null
```

> **`Number(null) === 0`이다.** 두 채점 가능성 검사가 입력을 `Number()`에 통과시키고
> 있었으므로, **null 카운트 후보가 「0점으로 채점된 후보」로 순위에 들어가서
> 승자의 마진을 정하는 차점자가 됐을 것이다.**

## 🔴 ③ 한 번도 들여다본 적 없는 셋째 — **클라에는 임계값이 아예 없다**

**config 라우트가 `null`이고 그 로더는 무조건 거절한다.** 그래서 판정 모듈은
**no-thresholds**를 받고 **축·데이터·단위와 무관하게 순위 매기기를 거부했다.**

> **이것이 모든 단위가 모든 라이브 실행에서 「채점 불가」로 읽힌 이유다.**
> 서버 임계값을 20에서 1로 내려도 아무것도 바뀌지 않았다 — **화면은 그것을 한 번도
> 읽은 적이 없다.**

판정은 **자기가 적용한 쌍을 이미 나르고 있다**(서버가 축마다 골라서 싣는다).
그래서 클라가 **그것을 먼저 읽고 세션 config로 폴백한다.**

```js
    const thresholds = session.payload.ruling_thresholds || session.config || null;
```

**발명한 기본값이 아니다** — **둘 다이거나 둘 다 아니거나**이고, **임계값이 없으면
여전히 거부한다.** 임계값이 축마다 다른 이유는 각 축이 다른 질문을 재기 때문이고,
그래서 서버가 `index_thresholds`와 `thresholds` 중 하나를 건넨다.
