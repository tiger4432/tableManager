## 소유자 지시 (2026-09-23)

> 「작은 소급은 바로 아웃박스에 트리거와 같은 형태로 꽂히게」
> 「체인트리거든 소급이든 같은 로직으로 돌려」

## 무엇이 일어났나

소급이 «체인의 둘째 벌»이기를 그만뒀다. 행을 고르고, 그 행들에 대한 «평범한 편집»이
남겼을 사건을 stage 한다. 워커가 그것을 «같은» 맵퍼 좌석 · «같은» 쓰기 문 ·
«같은» 키 게이트 · «같은» 봉투로 비운다.

## 새 기제를 «안» 지었다 — 있던 좌석을 넓혔다

```
「이 규칙만」을 읽는 좌석은 «이미» 있었다. 쓰는 쪽이 없었을 뿐이다
   only_rule_of 를 ingestion_worker.fires 가 한 번 묻고, outbox_expand 는 그 키를 확장 «너머»로 나른다
그래서 stage_collapsed_event 가 그 칸을 «채우는 인자»를 얻었다 — 옆에 둘째 stager 를 안 지었다
```

## 루프와 «같이» 간 것

```
쓰기 배치 · 그것이 들고 있던 키 게이트 «사본» · 페이로드 빌더
그리고 소유자 판정 「ㄷ」(미리보기 없음)로 «드라이런» — 규칙을 돌려 「무엇을 쓸지」 세던 사본
   -> 그건 「이게 무엇을 쓰나」의 «둘째 저자»였다. 쓰는 곳과 «다른 파일»에서 답하고 있었다
```
⚠️ CLI 의 드라이런은 «그대로»다(`chain_replay_cli` — 「Dry-run everywhere by default」).
없어진 것은 «어드민 operation» 쪽이다. 응용이 뒤에 확인했고, guide 의 R1 줄에 «어느 문»인지를 달았다.

## 이름 붙여 남긴 것 — 찾아지기 전에 (구현자 실측)

```
crud.can_mean_emptied 가 chain_ingestion 에 «참»이다
   -> 라이브 경로는 소급의 SKIP_BLANK 가 «거절»하던 자리에 빈 값을 쓴다
   -> 문 둘이 «리포트»가 아니라 «셀의 값»에 대해 어긋나 있었다
   -> 값이 안 나오는 규칙을 소급하면 이제 그 컬럼이 «지워진다». 되돌리는 길은 R2 withdraw 다
트랜잭션 id 는 실행당 «한 번» 고정된다 — 아니면 쪽마다 워커 스레드에서 새로 찍혀
   한 번의 행동이 N 개의 실행으로 도착한다
replay_<run> 으로 stage 되어, 감사 로그에 닿는 라벨이 이 라운드 «전»에 소급이 쓰던
   chain_replay_<run> 과 «정확히 같다»
```

## 죽은 줄 하나

`RETROACTIVE_RUN` 깨움 행이 체인 소유 op 에 대해 더는 안 써진다. 그 행은 스케줄러가 집어
한 줄 찍고 표시하던 것이었다 — 운영 로그에서 그 줄을 찾던 사람은 이제 «못 찾는다».
