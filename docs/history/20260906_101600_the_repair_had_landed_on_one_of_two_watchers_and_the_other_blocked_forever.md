# 같은 모양의 감시자 «둘» 중 «한쪽에만» 수리가 있었고, 다른 쪽은 «영원히» 막고 있었다

> **커밋:** `92d1c1ff` (10:16)
> | **일자:** 2026-09-06
> **레인:** 구현자(서버)
> **측정 상자:** 이 워크스테이션. **운영이 아니다.**

## 무엇이 일어났나

`SCHEDULER_RUN_NOW` 감시자는 «처리 안 된» 아웃박스 행 중 `order_by(id.asc()).first()` 로
«머리»를 고른다. 처리하다 예외가 나면 **로그만 찍고 멈췄다** — 롤백도, `status` 도 없고
`processed_chain` 은 False 로 남았다.

```
그래서   «같은 행»이 매 틱 다시 뽑힌다 — 영원히
결과     그 뒤에 줄 선 요청이 «하나도» 안 돈다
증상     아무것도 raise 하지 않고, 화면에 아무 표시가 없고, «재시작해도 안 풀린다»
         (고장이 «프로세스»가 아니라 «행»에 있다)
```

## 🔴 수리는 «이미 있었다» — 형제 감시자에

같은 파일의 `handle_retroactive_trigger` 가 그 수리를 들고 있었고, 그 주석이 사유를
낱말 그대로 적어 두었다: **예외가 난 요청은 «끝난» 것이지 «대기 중»이 아니고, 표시를
안 남기면 생산이 멈춘다.** 즉 수리가 «둘 중 하나»에만 착지해 있었다.

## 🔴 그리고 부류가 «갈린다» — 그래서 한 곳만 고쳤다

처리 안 된 아웃박스 행을 고르는 핸들러는 «넷»인데 모양이 둘이다:

```
SCHEDULER_RUN_NOW   id.asc() + FIFO 머리   <- 이 모양. 여기서 고쳤다
RETROACTIVE_RUN     id.asc() + FIFO 머리   <- 이미 수리를 들고 있었다
SYSTEM_RELOAD ×2    id.desc() + 메모리 고수위
```
뒤의 둘은 **다시 못 뽑고 머리를 막을 수도 없다** — 그쪽의 실패 모양은 「낡은 규칙으로
조용히 도는 것」이라, `FAILED` 로 표시하는 것은 **없는 결함을 고치는 일**이 된다.
그래서 손대지 않았고, 대신 **그 둘이 여전히 최신순으로 읽는지**를 시험이 못 박는다.

## 확인한 것 (diff 실측)

```
+ db.rollback()
+ latest_trigger.status = "FAILED"
+ latest_trigger.processed_chain = True
+ (시험) 두 reload 감시자의 소스에서 `id.desc()` 가 사라지면 빨개진다
```
