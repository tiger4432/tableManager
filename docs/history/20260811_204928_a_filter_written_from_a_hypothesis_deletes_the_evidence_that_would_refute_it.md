# A filter written from a hypothesis deletes the evidence that would refute it

**Date:** 2026-08-11 20:49 · **Domain:** Server (운영 인시던트 / `server/scripts`) · **Status:** 착지 — `dc69928` `f39af06` `bf5671a` `79cab93` `62cfaa3` `1214868` `2d7da86` `ecb78df` `c4d1b5b`

> 아홉 커밋이 **한 이야기**다. 운영에서 올라온 중복 업무키 인시던트를 수리할 도구 둘을
> 만드는 과정이고, 뒤 일곱 개는 **만들면서 낸 정정**이다. 그 정정이 이 항목의 본문이다.
>
> ⚠️ **숫자의 출처를 구분한다.** 370,000 / 90,000 / 170,000 은 **운영 실측이고 제품
> 소유자가 보고한 것**이다. 이 워크스테이션에서 잰 것이 아니다. 반대로 이 저장소의
> 다른 항목들이 인용하는 `assy_qa` 수치는 운영이 아니다. 두 세계를 섞지 않는다.

## 배경 — 경합이면 2가 나온다

`add_business_key_unique_index.py`가 운영의 한 표에서 **중복 키 90,000 · 잉여 행
170,000 · 전체 370,000**을 보고했다. 중복 그룹 안에 있는 행이 전체의 70%, 키당 평균
**2.89행**이다.

이 평균이 원인을 하나 지운다. 두 프로세스가 같은 창에서 부딪히는 경합은 **정확히 2**를
만든다. 2.89는 경합이 아니라 **같은 논리적 행이 세 번쯤 다시 들어왔다**는 뜻이다.

제품 소유자가 기전을 지목했다 — `818c9c0` 이전, 키 컬럼이 비어 있으면 조립된 키에 빈
컴포넌트가 들어가던 시절의 잔재다. 키를 잃은 행은 업서트가 **찾지 못해 새 행으로 다시
들어오고**, 그래서 한 그룹은 서로 다른 행이 아니라 **같은 행의 재입고**다. 신규 발생은
`818c9c0`이 이미 막았다.

그리고 두 번째 관측이 이 일을 「정리」가 아니라 「스크립트」로 만들었다 — **키 재료가 행에
아직 남아 있다.** 그러니 병합하지도 삭제하지도 않는다. **각 행의 원본 컬럼에서 키를 다시
조립하면 중복이 스스로 풀린다.**

그래서 도구가 둘이고, 순서가 있다.

| | 스크립트 | 하는 일 |
|---|---|---|
| ① | `rebuild_blank_business_keys.py` | 원본 컬럼에서 키를 **재조립** |
| ② | `dedupe_business_key_rows.py` | ①로도 안 풀린 그룹을 **한 행으로 접음** |

순서를 뒤집으면 **틀린 줄 아는 키를 근거로 「같다」고 판정**하게 된다. 그 제약은 ②의
독스트링에 박혀 있다.

## 정정 다섯 — 이 항목의 본문

### ① 관문이 손상의 «모양»을 맞히려 했다 (`dc69928` → `f39af06`)

첫 판은 「옛 조합기가 빈 컴포넌트를 **남겼을** 것」이라고 가정하고, 키를 구분자로 쪼개
빈 조각이 있는 행만 통과시켰다.

운영에서 읽기 전용으로 돌리자 `scanned`는 표 전체인데 **`blank`이 0**으로 나왔다.
데이터가 아니라 **관문이 틀렸다.** 빈 조각을 남기지 않고 **아예 빼고** 이었다면
`a_b`는 그냥 `a`가 되고, 거기엔 빈 조각이 하나도 없다.

관문을 지웠다. 전부 재조립해서 **저장된 것과 다른 것**을 찾는다.

```python
for r in rows:
    # 🔴 관문 없이 전부 재조립한다. 손상의 모양을 미리 맞히려 들면
    #    (예: "빈 컴포넌트가 남았을 것") 그 모양이 아닌 손상을 통째로 놓친다.
    if _blank_parts(r["business_key_val"], sep):
        stat["blank_shape"] += 1          # 참고용 표시일 뿐 관문이 아니다
    new = _compose(table, r, sources)
```

같은 커밋이 `no_material`에 **컬럼 이름**을 붙였다. 「370,000행은 못 만든다」만 내놓으면
운영자가 손에 쥐는 것은 다음 행동이 없는 수 하나다.

### ② `WHERE business_key_val IS NOT NULL` — 고쳐야 할 행만 빼고 읽었다 (`bf5671a`)

키가 NULL인 행이 대상인데 질의가 NULL을 걸렀다. 그 필터는 **중복 키 인구조사에서
그대로 가져온 것**이고, 거기서는 옳다 — NULL은 중복이 될 수 없으니까. 그러나 이건 다른
결함이다. PostgreSQL은 UNIQUE 인덱스에 NULL을 **몇 개든** 받으므로 NULL 키는 인덱스를
막지도 않는다. 별개의 문제인데 **수리가 같을 뿐**이다.

```python
# 🔴 NULL 키도 대상이다. 처음엔 `WHERE business_key_val IS NOT NULL` 로 걸렀는데
#    그것이 정확히 고쳐야 할 행들을 빼고 있었다 — 제품 소유자가 운영에서 확인.
rows = conn.execute(text(f'SELECT {cols} FROM public."{table}"')).mappings().all()

# NULL 은 넣지 않는다 - 여러 행이 공유하므로 주인을 정할 수 없고, 애초에
# 유니크 제약의 대상이 아니다.
owner = {r["business_key_val"]: r["row_id"]
         for r in rows if r["business_key_val"] is not None}
```

`null_key`·`blank_shape` 둘 다 **세기만 하고 관문으로 쓰지 않는다.**

### ③ 비교가 config가 선언한 컬럼만 봤다 (`2d7da86`)

②의 「그룹이 정말 같은가」 판정이 `column_types`에 적힌 컬럼만 읽었다. 선언 밖 컬럼이
달라도 **`identical`로 나왔다.** 무손실 판정의 근거가 무손실을 반증할 컬럼을 애초에
안 읽고 있었다.

```python
# 🔴 `SELECT *`. 처음엔 `column_types` 선언한 컬럼만 떠서 비교했는데, 그러면
#    **선언 밖 컬럼이 달라도 identical 로 나온다.** 비교 모집단을 선언으로 좁히는
#    것 자체가 가설이고, 그 가설이 반증을 먼저 지운다. 전부 떠서 분류한다.
rows = conn.execute(text(
    f'SELECT * FROM public."{table}" WHERE business_key_val IS NOT NULL'
)).mappings().all()
```

거르지 않고 **분류**한 것이 수리의 절반이다. 「선언 컬럼은 같은데 타임스탬프만 다르다」와
「데이터가 다르다」는 다른 판정이라 `system_only`가 자기 계수기를 갖는다. 접어도 데이터는
안 잃지만 **그 시스템 값은 잃는다** — 판단 전에 운영자가 읽을 문장이다.

### ④ 동적 모델이 초기화된 적이 없었다 — 점검은 초록, 위험한 쪽만 죽었다 (`62cfaa3`)

`crud.delete_rows_batch`가 `Table model ... is not initialized`로 죽었다. 동적 테이블
모델은 서버 기동 때 `table_config.json`에서 만들어지고 단독 스크립트엔 없다.

**실패의 모양이 실패보다 나쁘다.** 읽기 전용 패스는 생 SQL이라 모델이 필요 없어 **멀쩡히
통과했고 `--apply`에서만 죽었다.** 사전 점검이 절대 가져서는 안 되는 배치다.

```python
models.init_dynamic_models(crud.TABLE_CONFIG)
if models.DYNAMIC_TABLES.get(table) is None:
    print(f"!! '{table}' 모델이 만들어지지 않았다 - table_config.json 에 선언이 있는지 "
          f"먼저 볼 것. 읽기 전용 패스에서 미리 막는다(그래야 --apply 에서만 죽는 일이 없다)")
    return {"skipped": True}
```

가드를 **읽기 전용 패스**에 뒀다. 아직 되돌릴 수 있는 쪽에서 답이 나와야 한다.
①에도 같은 줄을 넣었다 — 오늘은 생 SQL과 config만 쓰지만 조합기가 언젠가 모델을 보게
되면 두 스크립트가 조용히 갈린다.

### ⑤ `continue`가 수집보다 위에 앉아 있었다 (`1214868` → `ecb78df` → `c4d1b5b`)

`--dump`가 **0군을 저장하는데 콘솔은 그 그룹들을 찍고 있었다.** differing 그룹을 삭제
대상에서 빼는 `continue`가 덤프 수집 **위에** 있어서, 기본 플래그로는 그룹이 세어지고,
찍히고, 파일에 닿기 전에 루프를 빠져나갔다.

한 보고서의 두 출력이 **같은 루프의 서로 다른 지점**에서 채워지고 있었다는 것이 결함
전체다. 구조를 뒤집어 남길 행 선정과 두 출력을 **먼저** 채우고, 그다음에 삭제 여부를
정한다.

```python
# 🔴 `keep` 계산과 덤프 수집은 **삭제 여부를 정하기 «전»**이다.
#    처음엔 이 아래에 있었고, `not allow_differing` 의 `continue` 가 그 위에서
#    빠져나가는 바람에 **콘솔에는 differing 이 뜨는데 파일은 0건**이었다.
keep = sorted(g, key=lambda r: (-srccount.get(r["row_id"], 0), r["row_id"]))[0]
drop = [r["row_id"] for r in g if r["row_id"] != keep["row_id"]]
...
# 삭제 대상에 넣는 것은 **여기서** 정한다. 덤프·콘솔은 위에서 이미 담았으므로
# 「안 지우기로 한 그룹」도 보고에는 남는다 - 그것이 보고의 목적이다.
if differing_cols and not allow_differing:
    continue
victims.extend(drop)
```

**안 건드리기로 한 그룹이야말로 운영자가 봐야 할 그룹이다.** 삭제에서 빼는 것은 보고에서
빼는 이유가 아니다.

## 관통선

①②③은 **같은 실수의 다른 옷**이다 — 어떤 행이 흥미로운지를 **미리** 정하고, 그 필터가
자기를 반증할 증거를 먼저 지웠다. `2d7da86` 커밋 본문이 그것을 스스로 센다: 그날 **네
번째**였고(나머지 하나는 `grep | head`로 함수의 부재를 단정한 건), **세 번째 뒤에 적어
둔 규칙을 네 번째에서 깼다**고 적혀 있다.

⑤는 다른 계급이다. 필터가 아니라 **제어 흐름**이 두 출력을 갈랐고, 그 불일치는 데이터
질문처럼 보였다.

## 만들면서 지킨 것 — 새로 만들지 않은 자리

- **조합은 `crud.assemble_composite_business_key`가 정본이다.** SQL로 `a || '_' || b`를
  쓰면 그것이 조합 규칙의 **두 번째 철자**가 되고, 규칙이 바뀌는 날 이 스크립트만 옛
  규칙으로 남는다. 형제인 `check_missing_business_key.py`가 같은 이유로 조합을 거부하고
  독스트링에 그 이유를 적어 두었다.
- **삭제는 `crud.delete_rows_batch` 경유.** 생 `DELETE`는 `cell_sources`·`cell_overwrites`를
  고아로 남기고 DELETE 감사 로그를 안 남긴다 — 행이 사라진 **기록 자체**가 없어진다.
- **`None`과 `''`를 비교에서 같게 보지 않는다.** 같게 보면 실제 손실이 무손실로 보고된다.
  덤프가 TSV가 아니라 **JSON**인 이유도 이것이다(TSV는 둘 다 빈 칸으로 찍는다). 콘솔도
  `repr`로 찍는다.
- **읽기 전용을 관례가 아니라 구조로 강제한다.** 세션에 `default_transaction_read_only`를
  걸고, 끝나면 `close()`가 아니라 `invalidate()`로 커넥션을 버린다 — 풀로 돌려보내면
  다음 사용자가 그 플래그를 물려받는다. 형제 스크립트가 실제로 그 사고를 겪었다.
- **남길 행 규칙이 페이로드에 실린다** — `_keep`·`_cell_sources`. 규칙을 산문으로만
  적으면 파일을 여는 사람이 머릿속에서 규칙을 다시 적용해야 한다.

## 아키텍처 영향 — 인시던트가 드러낸 순환

이 인시던트는 세 조각이 서로를 막고 있었다는 것을 드러냈다.

```
apply_batch_updates 의 충돌 복구  ──필요──▶  IntegrityError
       (_is_business_key_unique_violation + 재프리페치·병합)
                                                   │
                                              발생 조건
                                                   ▼
                                        UNIQUE 업무키 인덱스
                                                   │
                                       중복이 하나라도 있으면
                                        CREATE 가 실패한다
                                                   ▼
                                            중복 90,000
                                                   │
                                        인덱스가 «없어서» 생겼다
```

즉 **복구 장치는 인덱스가 있어야 발화하고, 인덱스는 복구 장치가 없어서 생긴 중복 때문에
설치할 수 없었다.** `add_business_key_unique_index.py`가 표마다 미리 재고 못 받는 표를
**이름으로 거절하고 계속 진행**하는 것도 그래서다.

이 두 스크립트가 그 고리를 끊는 도구다. 그리고 보드의 2026-08-12 운영 항목에 **사용자
보고로** 「유니크 인덱스가 켜졌다」가 올라와 있다 — 정리와 설치가 끝났다는 뜻이고,
`apply_batch_updates`의 충돌 복구가 **처음으로 무장된 상태**가 됐다. 대가도 같이
적혀 있다: 전에 조용히 중복으로 들어가던 쓰기가 **이제 거절로 보인다.** 새 결함이 아니라
전부터 있던 결함이 드디어 보이는 것이다.

⚠️ 운영 카탈로그를 이 레인이 직접 조회한 것은 아니다. 위 문장의 출처는 커밋 흔적과
사용자 보고다.

## 검증 — 그리고 스위트가 없다는 사실

**스위트는 돌지 않았다.** 아홉 커밋이 만진 것은 `server/scripts/` 두 파일뿐이고
(`git show --stat`으로 확인), 이 스크립트들에는 테스트가 없다. 검증은 **운영에서 돌린
읽기 전용 패스의 카운터**였고, 그 카운터가 정정 ①②를 낳았다. ④는 `--apply`가 죽으면서
드러났고, ⑤는 덤프 파일과 콘솔이 어긋나면서 드러났다.

## 그때 남아 있던 것

- **두 스크립트 모두 이 레인에서는 `--apply`로 돌지 않았다.** 아홉 커밋 전부가 본문에
  그렇게 적고 있다. 운영 정리는 그 뒤에 사용자 몫으로 진행됐다.
- **`differing` 그룹은 아무것도 접히지 않았다.** `--allow-differing`이 존재하고 꺼져
  있으며, 이 시점에 켠 적이 없다. 값이 다른 그룹을 접을지는 **덤프를 열어 보고 사람이
  정하는 판정**으로 남았다.
- `no_material` — 원본 컬럼까지 비어 있는 행은 **어떤 스크립트도 못 만든다.** 컬럼
  이름과 건수까지만 내놓고 끝난다.
- `dedupe_business_key_rows.py`의 `SAMPLE = 5` 상수는 `ecb78df`가 `--show-diff`로
  대체한 뒤 **아무도 안 읽는 채로 파일에 남았다.**
- ②의 그룹 수집은 여전히 `WHERE business_key_val IS NOT NULL`이다 — ③에서 고친 것은
  **컬럼 축**이지 행 축이 아니다. NULL 키는 ①의 소관이고 유니크 제약의 대상도 아니라
  그쪽에서는 의도된 필터다.
