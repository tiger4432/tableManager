## 이 라운드가 딛고 선 것 — 사용자가 확정한 네 판정

커밋이 네 문장을 받은 순서 그대로 적었고, 코드가 지금 네 개를 전부 말한다.

> ① **화면이 정본이다** — 저장은 화면을 따라가고, 결함은 화면을 **조용히 움직이는** 것이다
> ② **표시 = 원점 + DB 값**
> ③ **`start_x/start_y` = 유효 다이 영역의 최소 열/행**
> ④ **원점 = start를 놓았을 때 (0,0)으로 읽히는 지점**

저장 좌표는 **원점 기준 칸수**이지 mm 주소가 아니다.

그리고 사용자가 이 라운드에 준 스킴 문장이 하나 더 있다.

> 「유효 다이 로드 시 유효 다이 맵을 중심으로 회전, 반전 적용. Y INVERT 여부 맞추어서
> 유효 다이 영역 X,Y 최솟값이 START X,Y가 되게 좌표계 및 ORIGIN CELL 설정.
> **유효 다이 맵이 원 기하 중심이 되는 스킴.**」

## 결함이 셋 겹쳐 있었다 — 위를 걷어내야 아래가 보였다

### ① 원점이 **웨이퍼 원**에 앵커돼 있었다

`getWaferBoundingBox`는 원 기하만 훑었다. 그 상자가 `getVisualCoords`의
`xv = c − box.minC + startX`를 통해 **화면 표기이자 DB에 저장되는 x/y**를 만들고,
`getCellFromVisualCoords`가 정확한 역함수로 로드 배치를 한다. 상자 하나가 좌표계 전부다.

**원 bbox는 회전에 거의 불변인데 유효 다이 영역은 그렇지 않다.** 그래서 회전할 때마다
마스크의 최소 열이 `startX`가 놓인 칸에서 멀어졌다 — 「회전 할때마다 origin이 틀어지네」의 정체다.

수리는 **같은 루프 안에서 두 상자를 함께 누적**하고, 해석된 참조가 실효 중일 때 마스크의 상자를
돌려주는 것이다. 판정을 새로 쓰지 않는다 — 원은 `isCellInsideWaferFast`, 마스크는
`isValidDieAt`, **렌더 루프가 부르는 바로 그 두 함수**를 같은 인자·같은 순서로 부른다.

```js
const circleInside = isCellInsideWaferFast(c, r, visualCols, visualRows, physConfig, width, height);
if (circleInside) { /* 원 상자 누적 */ }
if (useMask) {
  const p = getPhysicalCoords(c, r, cols, rows, rotation, side);
  if (isValidDieAt(p.x, p.y, circleInside)) { /* 마스크 상자 누적 */ }
}
```

⚠️ **마스크가 이 격자 안에 한 칸도 없으면 원 상자로 돌아간다.** `{0,0,0,0}`은 좌표계 전체를
조용히 평행이동시킨다 — **미상은 0이 아니다.** 사용자 판정 「밀리게 그냥 보여주기」는 밀린
마스크를 보이라는 것이지 좌표계를 무너뜨리라는 뜻이 아니다.

원으로 남는 자리를 명시적으로 갈랐다: **프레임 창 안**(창 안의 계산은 소스 맵의 좌표계를 푸는
중이고 거기에 타깃 마스크를 먹이면 다른 맵의 마스크로 소스를 재단한다) · **저작 캔버스**(저작 중
마스크는 격자 전체라 저작 모드 진입만으로 모든 좌표가 다시 매겨진다) · **`refused`**(해석 못 한
선언으로 좌표계를 바꾸지 않는다) · **노치**(`computeNotchCell`이 `{circleOnly:true}`로 묻는다 —
노치 칸은 클립보드의 프레임 지문이라, 참조 해석이 한 번 실패한 세션에서 지문이 달라지면 정상
붙여넣기가 「회전·면이 다릅니다」라는 무관한 사유로 거절된다).

### ② `projectCellsToPhys`가 **프레임마다 자기 격자 중심**으로 물리 키를 만든다

그 함수의 물리 인덱스 원점은 `(cols−1)/2`다. 참조 23×23은 **11**, 이 맵 45×45는 **22**.
**두 인덱스 공간이 달라서 같은 키가 같은 다이가 아니었다** — 마스크가 좌상단으로 약 11칸 밀려
앉고 오리진 셀만 중앙에 남은 실측 화면의 원인이다.

수리는 회전·반전의 중심을 **마스크 자신**으로 옮기는 것이다. 마스크 집합의 중심이 이 격자의
중심에 오도록 통째로 평행이동하면 두 인덱스 공간이 마스크 위에서 만나고, 격자 중심을 축으로
도는 기존 회전이 곧 마스크를 축으로 도는 회전이 된다. **새 기하식은 없다 — 결과에 정수
평행이동 하나를 얹을 뿐이다.**

```js
const maskCx = (Math.min(...pxs) + Math.max(...pxs)) / 2;
const gridCx = (hereCols - 1) / 2;
const shiftX = Math.round(gridCx - maskCx);
const keys = new Set(rawKeys.map(k => { … `${px + shiftX}_${py + shiftY}` }));
```

### ③ 캐시 태그의 세대 번호가 **진입에서** 오르고 대입에서 오르지 않았다

`getWaferBoundingBox`의 캐시 태그는 `V<validDieResolveSeq>`인데, 그 카운터는
`resolveValidDie` **진입 시** 오른다(`const mySeq = ++validDieResolveSeq`). `validDie`가
교체되는 것은 그보다 한참 뒤다.

> 그 창 안에서 상자를 한 번이라도 물으면, **새 키에 옛 마스크로 만든 상자가 실린다.**
> 그다음부터 모든 렌더가 마스크 B를 마스크 A의 상자에 대고 그린다.

**이것은 아무도 밟은 적 없는 선행 함정이다.** 그 창 안에서 상자를 묻는 코드가 종전에는 없었다 —
아래 ④의 재배치 패스가 정확히 그 질문을 하면서 처음 밟았다. 수리는 **대입 지점에서 캐시를
비우는 것**이다. 세대 번호를 셀 **개수**로 바꾸지 않은 이유도 코드에 적혀 있다: 같은 크기의 다른
참조가 서로의 상자를 덮어써서 지정을 바꿔도 좌표계가 이전 참조 그대로 남는다.

## 마지막 결함을 지목한 것은 사용자의 관찰이다

> 「**캔버스 좌표를 보존하고 있어 셀이**」

셀들이 **틀린 수량을 붙들고 있었다.** 근거가 바뀌면 `box.minC`가 셀 밑에서 움직이는데
셀은 자기 캔버스 칸을 붙들고 있어서 **읽는 번호가 바뀌었다** — `bonding_map` 4E → DT에서
`5,5`가 조용히 `2,3`이 됐다. ①이 금지하는 「화면이 동의 없이 움직이는 것」의 정확한 사례다.

붙들 것은 **번호**이고 칸은 **파생**이다. 근거를 바꾸기 전에 각 셀이 지금 말하는 저장 좌표를
되찾아 두고, 바꾼 뒤 각 셀을 **자기 저장 좌표에서** 새 좌표계가 주는 칸에 다시 앉힌다.
`serverCellKeys`도 함께 옮긴다 — 안 옮기면 서버에서 온 셀이 「보낸 적 없음」으로 읽혀
정리 경로가 실재하는 행을 지우자고 제안한다.

**수리 후 실측: 725셀, 좌표 드리프트 0, `5,5`로 표시된 셀이 `5,5`가 가리키는 다이에 앉는다.**

⚠️ **로드 경로에서는 이 재배치가 아무 일도 하지 않는다.** `loadExistingMap`이 `gridData`·
`loadedFCells`·`serverCellKeys`를 `resolveValidDie`보다 먼저 비우므로 집합이 비어 무비용이다.
이 코드가 고치는 것은 **화면에 이미 앉아 있는 셀** — 지정·해제·변경뿐이다.

같은 이유로 `resolveValidDie` 호출이 **셀 배치 약 200줄 앞**으로 올라갔다. 마스크가 셀 배치 뒤에
앉으면 배치는 원 기준으로, 표기와 Push는 유효 다이 기준으로 계산되어 저장 좌표가 조용히 옮겨간다.
사용자 지시의 순서 그대로다 — **유효 다이맵 → 오리진 → 셀 위치.**

## 기각된 설계 하나 — 기록해 둘 값이 있다

어느 빌드는 **참조 자신의 최솟값을 `grid_start_x/y` 컨트롤에 대입**했다. ③을 문자 그대로
만족시키는 형태다. **사용자가 기각했다.**

> 「**START X,Y는 바뀌면 안됨**」

그래서 편집기는 그 컨트롤을 **결코 쓰지 않는다.** `start_x/start_y`는 운영자의 선언이고,
대신 **유효 다이 최솟값이 그 선언된 값으로 *읽히도록* 좌표계를 배치한다.**
`loadExistingMap`에 잠시 있던 「START를 컨트롤에서 되읽는 줄」도 그 기각된 안의 잔재라 삭제됐다.

## 경보가 내내 다른 수량을 찍고 있었다

`[F8]` 경보는 **프레임 정렬 사실**(참조는 자기 최소 다이를 1,1이라 부르는데 이 맵은 START 0,0을
선언한다)을 찍고 그것을 「어긋남」이라고 이름 붙였다. 그래서 그 수가 **사용자가 화면에서 본
이동량과 한 번도 맞지 않았다.** 실측 4E → DT에서 전자는 (1,1)인데 후자는 (−3,−2)였다.

지금은 두 수를 **따로 재고 따로 이름 붙인다.**

| | 무엇을 재는가 | 데이터를 움직이는가 |
|---|---|---|
| `originDiffer` | 참조가 부르는 최솟값 vs 이 맵의 선언된 START | **아니다** |
| `screenShift` | 이번 지정으로 셀과 마스크가 화면에서 실제로 움직인 칸 수 | 화면만 |

이동량은 **재배치를 수행하는 바로 그 함수**가 잰다. 종전 원점 비교(`projectCellsToPhys`를 두
프레임으로 돌려 물리 다이를 비교)는 **마스크를 격자 중심으로 다시 앉히기 전**의 인덱스 공간에서
이뤄져 화면과 무관한 수를 냈다 — 실측: 화면은 중앙에 맞아 있는데 「31칸·8행 어긋남」을 찍었다.

## (0,0)을 손으로 다시 유도하던 사본이 둘 있었고, 실제로 갈려 있었다

`getGridCellObject`와 `renderGridCanvas`가 각자 (0,0) 칸을 재유도했다. **`renderGridCanvas`의
사본에는 `getVisualCoords`에 없는 x/y 미러 항이 있었다**(`isXMirrored`/`isYMirrored`).
원 bbox가 대칭인 동안만 우연히 같은 답이 나왔고, 마우스 경로는 이미 미러 항 없이 계산하고 있어
**두 경로가 실제로 갈려 있었다.** 원점 상자가 유효 다이 기준이 되면 그 우연은 성립하지 않는다.

둘 다 `getCellFromVisualCoords(0, 0, …)`로 바뀌었다 — **역함수가 답한다.**

## cp949 — 진단이 존재 이유인 QA 동안 화면에 도착한 적이 없었다

`[F8]` 콘솔 줄에 em dash(U+2014)가 들어 있었다. **cp949에 없는 글자다.**
한국어 운영 콘솔에서 로깅 핸들러가 **그 줄 전체를 버린다.**

> 그 줄은 쓰인 이래로 사용자 화면에 **한 번도 도착한 적이 없다** — 그것을 뒷받침하려고 존재하는
> 바로 그 QA 동안에.

새로 붙인 7줄짜리 유도 추적 로그(참조 · 이 맵 메타 · 회전 중심 · 반전 축 · 마스크의 캔버스 범위 ·
오리진 캔버스 칸 · 재배치)는 **모든 글자가 cp949로 인코딩 가능**하다. em dash 대신 U+2015(―)를 쓴다.
