# 적용 순서, 그리고 선언이 **조용히 먹히지 않는** 세 가지 방식

> **일자:** 2026-08-02 새벽 | **관련 커밋:** `8f5cb57`(CONFIG_ROLLOUT_GUIDE 신설) · `558a4af`(라이브 시뮬 config 스냅샷) · `31ac9e9`(런북↔스냅샷 연결, 낡은 경고 하나 제거) · `5d9eb59`(라이브보다 뒤처졌던 샘플 넷 갱신)

## 배경 — 아무도 답하지 않던 질문

`CONFIG_GUIDE`는 **무엇을 설정해야 하는가**의 지도이고 `config/`는 **파일별 키
사전**이다. 둘 다 운영이 실제로 갖는 질문에 답하지 않는다 —
**이 선언 집합을 어떤 순서로 적용하고, 각 단계가 먹혔다는 것을 어떻게 증명하는가.**

새 런북이 `table_config` → 맵 바인딩 → 체인 → enrichment → 가상 조인 → 온톨로지를
걷는다. **문서화된 모든 키는 `.sample`이나 로더 소스에서 읽어 냈다** —
라이브 config는 gitignore돼 있어 **출처로 쓰지 않았다.** 그래야 독자가 저장소 안에서
모든 모양을 검증할 수 있다.

## 그것이 존재하는 이유인 조용한 실패 셋 — 전부 실측된 것

1. **규칙이 디스크에서는 유효한데 워커에서는 불활성일 수 있다.** 체인 워커가
   **자기 `TABLE_CONFIG`가 다시 로드되기 전에** 새 enrichment 규칙을 읽고
   「`source_table` is not registered」로 둘 다 버린 뒤 **다시 시도하지 않았다.**
   → **테이블을 먼저 선언하고 착지하게 두라. 그다음 `chain_worker.logs`에서 검증하라.**
2. **스키마 라우트의 200은 config 싱글턴을 읽은 것이고 증거가 아니다.**
3. **다른 config가 아직 가리키고 있는 선언을 지우면 조용히 강등된다.**

> **이 셋이 없는 파일 목록은 가이드가 아니다.**

## 스냅샷 — 모양이 아니라 **실제로 선언돼 돌고 있는 것**

`558a4af`가 라이브 시뮬레이션 config 10개 파일의 읽기 좋은 스냅샷을 낸다.
샘플은 **모양**을 보여 주고, 이것은 **실제로 무엇이 선언돼 돌고 있는지**를 보여 준다 —
운영에서 그 셋업을 재현하려는 사람에게 필요한 것.

**복사 전에 스캔했다**: 10개 파일 어디에도 자격증명 모양의 키, 절대 경로, 호스트가
없다. 런타임 상태 파일은 제외했다 — **그것은 설정이 아니라 상태다.**

## 샘플 넷 — 하나가 실제로 중요했다

`5d9eb59`. `auto_update_control`이 문제였다 — **어느 수집기가 도는지를 소유**하므로,
라이브보다 낡은 샘플은 **데이터를 계속 생산하는 법도, 옛 데모 수집기 중 무엇이
꺼졌는지도** 독자에게 보여 줄 수 없다. `maps`·`bonding_plan_config`·
`transfer_plan_config`도 같은 이유로 낡아 있었다.

**이제 모든 라이브 config에는 그것보다 낡지 않은 샘플이 있다.**
