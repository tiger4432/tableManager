## 배경

직전 연구 라운드(`c723585`)가 남긴 진단 도구(`diagnose_slow_after_ingest.py`)로 사용자
신고 「html 띄우는 것부터 느려짐」을 추적한 결과를 보드에 올린 커밋이다. `PROJECT_STATUS.md`

**서술만** 하고 파일 자체는 건드리지 않는다.

## 진범 ① — 페이지 로드마다 부르는 호출 하나

```
GET /audit_logs/recent?limit_groups=100  →  31,737 ms  (65 KB)
두 번째 →  243 ms      세 번째 →  130 ms
```

`switchTable → loadHistory()`(`client2/src/timeline.js:14`)가 테이블 전환마다·초기
로드 포함 호출된다. `audit_cache.load_initial`이 5,000행 청크를 커지는 OFFSET으로,
서로 다른 `transaction_id` 100개를 모을 때까지 훑는데, 대량 적재는 **파일 하나 =
트랜잭션 하나**라 최근 20만 행에 트랜잭션이 93개뿐이었다. `timestamp` 선두 인덱스가
없어 청크마다 전체 재스캔 + 디스크 정렬(46 MB). `refresh_if_stale`은 워터마크 위 전부를
`LIMIT` 없이 pydantic으로 모델링했다. `/internal/events/batch-refresh`가 이걸 못 막은
이유도 여기서 확인됐다 — `add_logs_batch`가 워터마크(`_db_max_id`)를 못 올려 이미 병합한
행을 두 번 읽고 있었다.

## 진범 ② — 안 사라지는 바닥: `cell_sources` 셀당 1행

실측(10만 행 × 16컬럼): `cell_sources` +1,600,098행 = 행당 정확히 **16.00**,
제안서 예측과 일치. `cell_sources` 388 MB → 1,072 MB(인덱스 증가가 힙의 2.3배).
**11.7 MB CSV 하나가 DB를 ~1.0 GB 늘린다(85배).** 같은 값 재적재도 셀당 1행을 영구히
더한다 — `cell_sources` 키에 파일명(`source_name`)이 들어가서다.

## 총괄이 틀린 것 셋, 레인이 바로잡음

1. **「`wafer_id` NULL 9,674행(40%)이 정체성 없는 행」 — 아니다.** `trace_fixture/world.py:297`
   의 `rng.random() < 0.40`, **픽스처 파라미터**였다. 소스 CSV의 공란도 같은 9,674로
   일치하고, `table_config`에는 「`wafer_id`는 일부러 희소하다」고 이미 적혀 있었다 —
   **자신이 만든 픽스처를 운영 사실로 인용한** 사례다.
2. **「그래프엔 교차검증이 없다」 — 있다.** `ontology_config.py:256-271`이 로드 시점에
   컬럼 존재를 `table_config`와 대조해 어긋나면 그 테이블 매핑을 통째로 거절한다. 총괄이
   든 loud/silent 대비표가 뒤집혀 있었다 — 로드 시점 대조의 참조 구현은 `map_overlay`가
   아니라 온톨로지 쪽이었다. 진짜 이유는 따로였다: identity 이동이 조용했던 건 검사가
   없어서가 아니라 **그 변경이 컬럼을 없애지 않았기 때문**이다(`core_lot`/`core_slot`은
   여전히 존재해 존재 검사를 통과한다).
3. **「죽은 선언 셋을 지워라」 — 하나만 맞았다.** `bin_map.x/y`만 삭제 대상이었다.
   `bin_map.bin`(`c_bn`)은 지우면 안 된다 — 파생이 `dt_index`를 답해 **옳은 답을 틀린
   답으로** 바꾸기 때문이다. `lot`/`slot`은 파생이 설계상 `None`이라 유지.
