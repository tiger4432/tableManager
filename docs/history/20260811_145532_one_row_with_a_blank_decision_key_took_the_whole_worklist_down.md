# 신원 없는 행 하나가 워크리스트 전체를 500으로 데려갔다 — 침묵 네 겹의 사슬

**날짜:** 2026-08-11 13:14~14:55 · **커밋:** `5b09d69` `3d43a6c` `347de78` `2fb1c44` `c4a3159` `99a4fe6`
· **레인:** 서버(체인/정렬) + 클라(map2) + 문서
**측정 상자:** 이 워크스테이션의 격리 DB `assy_qa`. **운영이 아니다** — 신고는 운영에서 왔지만
이 항목의 모든 수치는 격리 상자에서 잰 것이다. 운영 DB는 이 라운드에서 한 번도 읽지 않았다.

## 배경

오전은 config 상속과 프레임/체인 작업이었다. 오후는 **살아 있는 운영 인시던트**였다.

앞 절반(fetch 1초 초과 → 인덱스 부재 + 감사 전수 스캔)은 이미 이름이 붙어 있었다
(`20260811_082334`, `20260811_083951`). 뒤 절반이 이 항목이다 —
`GET /api/maps/alignment/worklist`가 운영에서 **500**을 답하고 있었다.

원인은 하나가 아니라 **네 겹의 침묵이 이어 붙은 사슬**이었고, 어느 고리도 실패를 보고하지
않았다. 하루가 걸렸고 결국 사람이 화면에서 봤다.

```
운영 dt_log의 실제 컬럼: dt_job_id   |   config와 매퍼 여섯 곳이 말한 이름: dt_job
  ① 매퍼가 없는 이름을 읽는다 -> _value(payload, "dt_job")가 None -> 그 행 스킵
       -> 빈 배치 반환 -> 워커는 SUCCESS를 기록
  ② crud.apply_batch_updates가 column_types에 없는 updates 키를 드롭
       -> (테이블, 컬럼)당 프로세스 1회만 경고 -> 200 SUCCESS 반환
  ③ dt_inventory에 결정키가 빈 행이 착지 (신원 없는 파생 행)
  ④ 워크리스트가 그 행에서 compose_unit_key를 부른다 -> ConfirmationRefused
       -> 그 예외는 ValueError가 아니라 라우트의 except가 못 잡는다
       -> 요청 전체 500. 건강한 단위 다섯이 나쁜 행 하나에 같이 사라졌다.
```

## 무엇을 했나

### `5b09d69` — 잡 컬럼 이름이 config에서 온다

리터럴 기본값(`rule.get("job_column", "dt_job")`)을 전부 지우고
`server/chain_bindings.py`를 신설해 `선언 > table_config 유도 > 이름을 대고 거절`
하나로 통일했다. **기본값 삭제가 하중을 받는 절반이다** — 개발 박스에서만 맞는 기본값은
아무도 진짜 이름을 선언할 이유를 주지 않으므로 불일치가 영원히 드러나지 않는다.

설계 상세는 이 커밋이 착지하기 **전에** 쓰인 `20260811_131004` 항목에 있다. 그 항목은
`Status: implemented, not committed`으로 시작하고 **해시를 달고 있지 않다** — 여기서 묶는다.

그리고 아무도 이것을 몰랐던 이유가 기록할 값이 있다: **이 트리의 모든 픽스처가 `dt_job`을
쓴다.** 고친 코드와 안 고친 코드가 같은 초록을 냈다.

### `3d43a6c` — 확정 키가 규칙의 선언을 따른다, 그리고 채택 실패가 말을 한다

두 결함이 한 화면에 있었고 둘째가 첫째를 가리고 있었다.

- `keyFrom`은 arity 2에서만 규칙의 `decision_key`를 존중하고 **다른 모든 arity에서
  `{dt_eqp, product}`를 하드코드로 냈다.** 운영 규칙은 컬럼을 **하나** 선언하므로 값이
  브라우저를 떠난 적이 없고, 서버는 `빠진 결정키: dt_job_id`라고 보고했다 —
  **페이로드에 대해서는 참이고 원인에 대해서는 오도하는 문장.**
- 채택 실패가 **침묵**이었다. `alignment`를 선언한 규칙이 0건이거나 여럿이면
  `refreshWorklist()` 앞에서 반환해 **요청이 발행된 적이 없었다.** 목록이 로딩에
  실패한 게 아니라 시작하지 않았고, 침묵은 로딩과 구별되지 않는다.

순서가 중요했다는 사실이 이 커밋의 기록 가치다 — 워크리스트가 있으면 `__key`가 서빙된
행에서 오므로 **채택을 먼저 고쳤다면 arity 결함이 통째로 가려졌을 것이다.**

### `2fb1c44` — 그 하드코드가 충실히 옮긴 문장을 지운다

**교정 방향이 여기서 뒤집힌다.** `docs/spec/MAP_ALIGNMENT_SPEC.md` §5가
`decision_key: ['dt_eqp','product']`를 **계약인 것처럼** 적고 있었다. 삭제된 코드는 그
문장의 **충실한 전사(轉寫)**였다. 코드가 스펙을 어긴 게 아니라 스펙이 틀렸다 —
설정 값을 스키마처럼 제시한 것. 같은 실패 계급을 파일 전체에서 훑었고 다른 사례는 없었다.

### `c4a3159` — 넷 중 셋에 있던 가드, 목록만 없었다

수리 모양을 결정한 판단: **단위 키를 조립하는 네 자리 중 셋이 이미 빈 결정키를
막고 있었다**(`dt_alignment_metadata_mapper.py:46`, `core_alignment_mapper.py:41`,
`dt_inventory_metadata_mapper.py:96`). 넷 중 셋에 있는 가드는 **정책이 아니라 누락**이므로,
새 기구를 만들지 않고 있던 패턴을 완성했다.

```python
        try:
            u["unit_key"] = frame_confirmation.compose_unit_key(rule, u["key"])
        except frame_confirmation.ConfirmationRefused:
            # 어느 컬럼이 비었는지는 **거절한 쪽과 같은 술어**로 묻는다
            # (`contracts/blank_predicate`로 등가성이 고정돼 있다).
            u["unit_key"] = None
            unit_key_blank_cols.update(
                c for c in decision_key if crud.is_blank_value(u["key"].get(c)))
```

나쁜 행은 **빼지 않고** `state: unscorable` / `reason_code: unit_key_incomplete` /
`unit_key: null`로 **보이게** 남긴다. 조용히 사라지는 단위는 이 프로젝트가 반복해서 값을
치른 실패 모양이다.

그리고 가드는 하나가 아니라 **둘**이었다. 변이 검사가 그것을 말했다.

```python
        # 🔴 정렬은 `unit_key`가 문자열이라고 가정한다 ... 이름 없는 단위가 하나라도
        #    섞이면 `None < str` 비교가 `TypeError`로 터져 목록이 **다시** 500이 된다.
        uk = u["unit_key"] or ""
```

조립 가드만 넣었으면 500이 **한 줄 아래로 옮겨갔을 뿐**이고, 조립만 단언하는 테스트는
그것을 초록으로 출하했을 것이다.

## 아키텍처 영향

- 「한 항목의 결함이 목록 전체를 죽이지 않는다」가 재사용 가능한 형태로
  `PRIMITIVES.md` §7에 올라갔다(`32da009`) — **가드가 둘이라는 부분까지 포함해서.**
- 사유에 붙는 것은 두 번째 어휘가 아니라 **컬럼 이름**이다. 집계가 사유마다 한 줄이므로
  실리는 것도 컬럼 이름의 합집합 하나뿐이고 크기는 `decision_key` 길이로 닫혀 있다.
- 「비었다」의 판정은 목록과 확정이 **같은 술어**를 쓴다. 여기서 다시 정의하면 두 화면이
  서로 다른 행을 빈 행이라 부를 수 있다.

인시던트가 끝나고 보드에 올라간 것은 결론만이 아니라 **하루가 실제로 어떻게 흘렀는가**의
기록이다. 다섯 항목 전부 「믿었던 것 → 잰 것」의 형태다.

1. 느린 핸들러 하나가 앱 전체를 멈추게 하지 **않는다.**
