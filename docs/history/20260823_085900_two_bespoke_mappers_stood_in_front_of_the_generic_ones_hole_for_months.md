## 배경 — 게이트 ①의 마지막 한 칸

소유자가 `transfer_event`를 **작성 폼만으로** 완성하고 시험 실행을 눌렀다. `invalid_time_role`로
거절됐다.

`declarative-role` 매퍼는 **모든 바인딩을 프레임 셀 그대로** 읽는다. 그런데 그 컬럼은
**varchar** 이고 `_validate_role_value`는 tz-aware datetime 을 요구한다. 그래서
**varchar 시각 컬럼은 검증기를 절대 만족시킬 수 없다.**

🔴 **이 경로가 오늘 처음 돈 이유:** 기존 소스 둘은 **맞춤 매퍼**를 쓰고 각자 값을 스스로
변환한다. **그 둘이 이 칸 앞을 가려 주고 있었고, 맞춤 매퍼 없는 소스가 존재하는 날까지
구멍이 안 보였다.** 「폼으로 소스를 선언한다」가 새로운 일이었기 때문에 오늘 드러났다.

## 답은 엔진이 이미 계산해 두고 있었다

준비 경계가 해석한 순간(instant)이 **엔진 소유 이름으로 이미 찍혀** 있었다. 수리는
**다시 파싱하는 것이 아니라 거기서 읽는 것**이다.

```python
if role is not None and role.kind == "time":
    # A TIME Role is filled from the instant the preparation boundary
    # already interpreted (`SOURCE_OCCURRED_AT_COLUMN`), never from the
    # frame cell the binding names. ...
```

**설계하지 않고 맞춤 매퍼 둘에서 복사했다** — 둘 다 같은 값을 같은 줄에서 취한다. 범위는
**time 역할 하나**이고 그게 정확하다: claim 컴파일러는 `occurred_at`에만 kind `time` 을 주고
다른 무엇에도 주지 않는다. 나머지 역할 kind 는 자기 바인딩을 그대로 평가하고, **맞춤 매퍼는
둘 다 손대지 않았다.**

다시 파싱하지 않는 이유가 주석에 남았다 — **`source_event_identity`가 바로 그 값에서 이벤트
id 를 만든다.** 다른 것에서 시각을 딴 원자는 **자기가 속한 이벤트의 id 와 어긋난다.**

## 🔴 총괄이 「아무도 이걸 안 읽는다」고 보고했고, 틀렸다

지시서 `b6a67d28`은 **「해석된 순간은 `__occurred_at`으로 이미 발행돼 있고 전체 grep 에서
읽는 곳이 없다」**고 적었다.

`15876157`이 정정했다: **맞춤 매퍼 둘이 각각 한 줄에서 읽고 있다.**

> **실측(사후 확인):** 리터럴 `__occurred_at`은 그 시점 트리에서 `server/ledger/roleframe.py`의
> **상수 정의 한 줄에만** 나타났다. 두 매퍼는 `server/mappers/`에서 **상수 심볼
> `SOURCE_OCCURRED_AT_COLUMN`을 import 해서** 읽는다. 즉 **리터럴을 찾는 grep 은 범위를 트리
> 전체로 넓혀도 그 둘을 못 찾는다** — 놓친 축은 디렉터리가 아니라 **「리터럴이냐 심볼이냐」**였다.

그리고 그 오독이 결과적으로 방향을 맞게 만들었다는 것도 기록해 둘 값어치가 있다 —
**베끼는 것이 설계하는 것을 이긴 이유가 정확히 「이미 둘이 그렇게 하고 있었다」**였다.

## 남아 있던 갈래 하나가 «판정»으로 닫혔다

착지 시점의 주석은 **「바인딩이 다른 컬럼을 이름 대는 경우는 여기서 결정하지 않는다」**고
열어 뒀다. 몇 분 뒤 판정이 났고 `52a1ffdd`가 **설계가 아니라 사실로** 주석을 다시 썼다.

```
dt_job 은 origin 을 «ingested basis» 로 선언하고 컬럼을 이름 대지 않는다
그런데 그 소스의 문장들은 occurred_at 에 컬럼을 «바인딩하고 있다»
그리고 그 원자들은 «ingestion 스탬프»를 달고 있다
-> 즉 그 바인딩은 «돌고 있는 커서 위에서, 소스가 쓰인 이래로 아무것도 결정한 적이 없다»
```

그래서 판정은 **「시각 역할은 바인딩의 컬럼을 언제나 무시한다」** — 우연히 일치하는 경우에만이
아니라. 열린 질문을 닫힌 채로 남겨 두면 **다음 독자에게 이미 닫힌 질문을 열린 것으로 넘긴다.**

같은 호흡으로 **열려 있는 것**을 이름 댔다: **폼이 아무것도 결정하지 않는 컬럼을 계속 물어야
하는가.** 그것은 라이브 선언 둘을 다시 쓰고 **지문 둘을 움직이므로** 이 라운드의 일이 아니다.

## 🔴 게이트 ① 완주 — 소유자가 «직접» 한 것

```
+ New -> relation · identity · 시각 · 준비기 · 매퍼 · unit
-> 매핑 만들고 낱말 transfer@1 -> subject / target / occurred_at
-> die@1 키에 mat_type 을 더해 «한 엔터티로 두 세계»(Wafer 자리 / DT 자리)를 갈랐다
   응용 세션이 제안한 갈래 둘(자리를 신원으로 / dt_id 채우기)보다 «나은 셋째 길»이었다
-> 저장 -> 시험 실행 -> 원자 199
```

가는 길에 막힌 다섯 — **하나도 소유자 탓이 아니었다.**

```

3  매핑 삭제가 «안 보인다»           지워지는데 계획이 이름을 계속 댔다            (0a44069c)
4  컬럼 칸이 «뭘 원하는지» 안 말한다   잠긴 것을 눌린 채, 나머지는 전체 선택         (a13eeed4·e21e990f)
5  일반 매퍼가 시각 역할을 못 채운다   맞춤 둘이 가려 주고 있었다                    (189193a4)
```

넷은 작성 화면 경로의 결함이고, **다섯째는 화면이 아니라 서버 매퍼(`roleframe.py`)에
있었다.**

## 아키텍처 영향

- `DeclarativeRoleMapper`가 **역할 kind 로 분기**한다 — time 은 엔진이 찍은 순간, 나머지는
  바인딩 평가.
- 「선언만으로 소스를 만든다」가 **맞춤 매퍼 없이 처음 끝까지 돌았다.**

## 그때 남아 있던 것

- **`bind.occurred_at`의 `column`이 아무 일도 하지 않는다.** 자유도 0인 선언이고 그날 지운
  세 칸과 같은 부류인데, 지금 건드리면 라이브 선언 둘의 지문이 움직인다. 보드에 올라갔다.
- `prepare.output_columns` 후보 **0**.
- **「+ New 뒤 첫 저장 전」에는 계획 행이 0** — 잠금·전체 선택은 첫 저장 뒤부터 보인다.
- 🔴 **수리는 착지했는데 «한 시간 동안 서빙되지 않았다»** — 서버 프로세스가 그 수리보다
  앞섰다(`984b5ffc`). 재기동 뒤에야 세 소스가 전부 통과하고 소유자가 확인했다.
- `5f556cfc`가 손대지 않고 기록한 것: **모듈 접두어 필터 덕분에만 무해한 파일 하나** —
  남겨진 매퍼가 라이브 구현 id 를 version 없이 선언하고 있어서, **스캔 대상 공간으로 개명되는
  날 빌드에서 레지스트리를 통째로 죽인다.**
