# The write path can now say what it threw away, and stops fabricating the row

**Date:** 2026-08-11 18:25 · **Domain:** Server (write path / layering core) · **Status:** 착지 `94954cb`

> 이 항목은 **커밋 전에** 쓰였고 원래 「implemented, not committed」로 열려 있었다. 총괄이 착지 후 해시를 찍었다. **커밋 전에 쓴 이력 항목은 해시가 없어 아무도 그 커밋에서 도달할 수 없다** — 오늘 같은 항목이 둘이었고, 그래서 하루 전체 해시 스윕이 필요했다.

## 현상

`crud.apply_batch_updates`에는 **부분 실패를 말할 어휘가 없었다.** 성공을 반환하거나
예외를 던지거나 둘 중 하나였고, 「1,000개 중 900개를 받았고 나머지는 이래서 버렸다」를
말할 방법이 없었다. 그래서 모든 부분 폐기는 **터지거나 거짓말하거나**를 골라야 했고,
계속 거짓말을 골랐다.

2026-08-11 인시던트가 그 문장 그대로다.

```
config는 dt_job / 운영 컬럼은 dt_job_id
  -> 키가 column_types에 없으므로 드롭
  -> 200 SUCCESS 반환
  -> dt_inventory에 신원 없는 행이 착지
  -> 정렬 워크리스트가 그 행에서 unit key를 조립하다 요청 전체를 500
```

사슬의 어느 고리도 실패를 보고하지 않았다. 하루가 걸렸고, 결국 사람이 화면에서 봤다.

`347de78`이 드롭을 **셀 수 있게** 만들었다(`undeclared_column_drops()` + 하트비트
`note=`). 그것은 `/health`를 보는 **운영자**의 침묵을 고쳤지 **호출자**의 침묵은
고치지 못했다 — 프로세스 수명 계수기에는 배치도, 행도, 트랜잭션도 없다.

## 근본 원인

폐기가 일어나는 자리가 전부 **조용한 `continue`**였고, 그 사실을 호출자에게 옮길
통로가 애초에 설계되지 않았다. 그리고 신원 확정(`_get_or_create_row`)이 **컬럼 루프보다
먼저** 돌기 때문에, 모든 키가 드롭돼도 행은 이미 세션에 들어가 있었다.

## 무엇을 했나

### 1. `drop_report` — `replace_report`와 같은 out-parameter 계약

4-튜플 반환 시그니처는 운영 호출 지점 ~10곳과 테스트 수십 곳이 언패킹한다. 반환값에
실을 수 없으므로 **이미 이 함수에 존재하던 전례**(`replace_report`)와 같은 모양을 썼다.
새 기구를 만들지 않았다. 사유는 이름으로 온다 — `undeclared_column`(config 편집)과
`system_column`(발신자 버그)은 **고치는 사람이 다르므로** 한 숫자로 접지 않는다.
버전 게이트의 행 단위 거부는 `rows_refused`로 같이 실린다.

상세(행 샘플·컬럼 인구조사)에는 캡이 있고 **건수에는 캡이 없다.** 이름이 전부
페이로드에서 오기 때문이고, 보고서는 자기가 얼마나 감췄는지(`rows_omitted`,
`columns_omitted`) 스스로 말한다.

### 2. 유령 행 억제

**버린 입력이 존재 이유의 전부인 행은 거부보다 나쁘다 — 하류가 믿을 행이 생기기
때문이다.** 조건 셋을 모두 만족할 때만 `expunge`한다(신규 행 · 내용 0 · 키가 실제로
드롭됨). 기존 행은 절대 손대지 않고, `updates={}`를 일부러 보내는 호출자는 종전 동작
그대로다 — 내용 없는 insert 전반을 거부할지는 **별개의 정책 판정**이라 손대지 않았다.

`delete`가 아니라 `expunge`인 이유: 루프가 `no_autoflush` 안에서 돌아 아직 flush 전이므로
`session.new`에서 빼면 INSERT문도, `auto_stage_database_outbox`의 CREATE 이벤트도
애초에 나가지 않는다.
