## 인덱스 절반 (`4ed34a9`) — 하루를 재편성시킨 귀속이 측정으로 반증됐다

「missing index: 78%」는 측정 당시 참이었고 이제 죽었다: `_count_cells_bulk`가 그새
착지해 후보별 스캔이 아예 발행되지 않는다. `core_wafer_map` 문 하나. S0 0.184 s,
S1 0.182 s — **아무것도 안 해서 빠른 라우트의 1%짜리 인덱스.**

그리고 **드리프트를 고치면 라우트가 느려진다**: 0.184 → 1.128 s(+513%) — 거절되던
200층이 실제가 되어 각자 셀을 읽으므로. 남은 유일한 정직한 프레이밍: 드리프트 수리는
**정확성**(층 선택기 11 → 209), 인덱스는 그것을 **감당 가능하게** 하는 것(1.128 →
0.332 s, 소유자 실데이터 1.993 → 0.481 s, 76%). 소유자 박스가 더 나쁜 셀인 이유도
기록됐다: 밑줄 없는 map id 셋에 `_count_cells_bulk`가 **표 전체**의 벌크 경로를
접는다 — id가 전부 갈라지는 픽스처는 절대 못 보였을 모양.

순서가 이 커밋의 요점이다: `load_overlay_config`는 매 호출 재읽기 + gitignore라
레인의 워킹트리 편집이 **재기동도 커밋도 없이** 소유자의 도는 스택에 라이브로 갔다
(:8080 실측 928 ms → 2601/3211/3290 ms — 반쪽 수리가 닿아 가장 느린 셀에 앉아
있었다). 그래서 인덱스가 소유자 DB에 먼저, config는 뒤 — 마이그레이션 파일 헤더가
그 순서를 스스로 말한다. 하네스 결함 둘을 수 보고 전에 잡았다: 여덟 셀 전부 0.000 s
/0문(모델 미초기화 = CATALOG_UNAVAILABLE — 「수리가 됐다」와 구별 불가), 그리고
`cell()`이 자기가 만들 인덱스만 드롭해 623문 셀이 418문 셀보다 빨랐다.

## config 절반 (`1f1b700`) — 그리고 통계가 없던 테이블

`core_wafer_map.key_columns`가 데이터가 실제로 해소되는 복합키가 됐다(라이터
`map_meta_registrar`는 줄곧 복합으로 쓰고 리더 `resolve_binding`은 대부분 NULL인
컬럼으로 읽었다 — :8081이 200층, :8080이 11층이던 이유). `.sample`만 커밋에 나타난다
— 라이브는 설계상 gitignore.

마이그레이션이 알 수 없었던 것: **`core_wafer_map`은 ANALYZE된 적이 없었다.**
`last_analyze`·`last_autoanalyze` 둘 다 NULL, `n_live_tup` 0 — 플래너는 표가 비었다고
믿었고 빈 표 위의 새 인덱스는 선택할 가치가 없다. ANALYZE 후 24,749행. **존재하고
유효한데 선택되지 않는 인덱스는 밖에서 보면 도움이 안 된 인덱스와 정확히 같다.**
라우트 실측 2.6–3.3 s(인덱스 전) → 1.1–1.6 s → 0.6–0.9 s(ANALYZE 후) — 셋 다 최종
수가 아니다: 100랏 픽스처가 같은 DB에 쓰는 중이었고 **오염으로 기록됐다.**
