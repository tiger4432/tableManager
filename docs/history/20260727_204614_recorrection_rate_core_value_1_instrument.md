## 배경 — 1순위 가치가 무계기였다

핵심가치 #1 "최소 공수 교정"에는 계기가 하나도 없었다. #3은 테스트 스위트·`/health`·계약
벡터·실측 드릴까지 갖춘 것과 대조된다. 대가는 이 주에 그대로 나타났다 — 그리드 행 복사와
헤더 토글이 **모든 환경에서** 죽어 있었고, 사내망에서 Ctrl+C가 며칠 깨져 있었는데,
**움직였을 숫자가 어디에도 없었다.**

## 변경 내용

### ① 재교정률 — audit_logs에서 파생, 신규 로깅 코드 0줄

정의: 창 안에서 사람이 쓴 셀 중, 사람이 **두 번 이상** 쓴 셀의 비율. 같은 셀을 두 번
만졌다는 것은 첫 시도가 먹히지 않았다는 직접 증거다. 정의 결정 네 가지를 **가정이 아니라
실측으로** 내렸고, 근거를 코드 주석에 남겼다:

```python
# server/database/crud.py — 이 커밋 시점
RECORRECTION_WINDOW_DAYS = 7
# 감사 로그는 프루닝되지 않는다(outbox의 7일 보존은 database_outbox 전용).
# 창을 7일로 고정하는 것은 보존 한계 때문이 아니라 **지표를 현재 마찰에 반응하게** 하기 위해서다.

def get_recorrection_stats(db, window_days=RECORRECTION_WINDOW_DAYS) -> dict:
    """반환: {window_days, measured_cells, recorrected_cells, rate_pct}
    `rate_pct`는 분모가 0이면 None — 표본이 없을 때 0%로 위장하지 않는다."""
```

- **자동 소스 제외는 `source_name = 'user'` 양성 매칭.** 블랙리스트는 원리적으로 불가능했다 —
  파서가 인제션 파일명을 소스명으로 쓰므로 라이브에 distinct 소스명이 **10,750개**였고,
  필터 없이는 지표가 사람 공수가 아니라 인제션 물량을 따라 움직인다.
- **한 `transaction_id`는 한 번의 사람 행위.** 엑셀 붙여넣기 한 번이 같은 셀을 두 번 건드릴
  수 있다(실측 643그룹/1,286행). 행으로 세면 3.88%, 트랜잭션으로 접으면 2.96%였다.
- **동일값 재기록은 표현 불가능한 것으로 판명.** `has_changed` 가드가 바뀐 값만 로깅하고,
  동일해 보이던 4,290건은 전부 행 생성의 null→null(사람이 비워 둔 컬럼)이라 분모에서 빠진다.
  JSON 컬럼의 "값 없음"은 SQL NULL과 JSON `'null'` **양쪽**을 검사해야 했다(한쪽만 보면
  조용히 빗나간다 — 실측 `IS NULL` 0행 vs `::text='null'` 4,290행).
- **분모 없는 비율은 내보내지 않는다.** 표본 0이나 실패에서 0%가 아니라 null — 분모 없는
  숫자에 데어 온 프로젝트라서.

### ② 측정이 스스로 낳은 경고 — 그리고 **의도적으로 안 돌린 노브**

라이브 실측: 전체 **2.01%**(51,217셀). 그런데 200행 초과 트랜잭션을 제외하면 **13.13%**(3,381셀).
1000+행 트랜잭션 15개(맵 에디터 푸시 — 한 번의 사람 행위가 수천 셀을 쓰고 다시 안 만진다)가
손편집 신호를 **6.5배 희석**하고 있었다. 테이블별 격차도 극명했다: `core_wafer_map` 36.4%,
`inventory_master` 26.9%, `bonding_map` 2.3%. 즉 Ctrl+C가 다시 깨져 사람들이 재타이핑해도
전체 숫자는 2.01%→약 2.1%라 **아무도 못 본다.**

그럼에도 트랜잭션 크기 필터를 **일방적으로 넣지 않았다** — 임계값 200이야말로 그럴듯해
보이는 틀린 숫자를 제조하는 자의적 노브다. 가장 덜 자의적인 정의로 출시하고, 선택지는
보드에 사용자 결정 대기로 기록됐다.

### ③ 비용 방어와 소비처

쿼리는 1.6GB 순차 스캔에 512ms. 사람이 쓴 2.8% 행만 덮는 partial covering index를
`setup_db_performance.py`에 넣었지만 **적용은 못 했다**(검수자가 read-only 접근) — 그동안
60초 캐시 + 1500ms statement timeout이 방어하고, 타임아웃 경로는 라이브 데이터로 실측했다.

`/dashboard/summary`에는 **클라이언트 소비자가 하나도 없었다**(구 PySide6 대시보드가
유일한 소비자였다). 그래서 한 줄은 어드민 Overview 탭으로 갔고, 그 엔드포인트가 이미
~1.5s를 물기 때문에 자동 갱신 폴에서 **의도적으로 뺐다**(별도 5분 간격, 본문 렌더를
기다리게 하지 않음).

### ④ 문서 동기화 — diff를 따라갔으면 틀린 앵커에 도장을 찍었다

보안 라운드(`90e284f`) 반영을 4-에이전트로 돌렸는데, CODE_MAP의 최악 드리프트는 **이 커밋
범위가 건드리지도 않은 파일**에서 나왔다 — `process_supervisor.py` 선언 431줄 vs 실제 709줄,
`heartbeat.py` 174 vs 303, 메커니즘 두 개가 통째로 누락. 85줄 어긋난 앵커가 그럴듯한 맥락의
실제 함수에 착지해 있었고, 이 사례가 코드맵의 허용오차 노트에 박제됐다. FEATURE_CHECKLIST의
traversal 점검은 `curl --path-as-is`가 필수임이 기록됐다 — curl과 브라우저는 `../`를 클라에서
접어 버려서, 그 없이는 점검이 서버에 도달조차 못 하고 404를 "닫혔다"로 오독하게 된다.

## 검증

| 무엇을 | 어떻게 | 결과 |
|---|---|---|
| 서버 스위트 | `pytest server/tests/` | **720 passed** (기준선 699, +21) |
| 뮤테이션 | 결함 7종 주입 | 전부 검출 — 단 **첫 실행은 거짓말이었다**(아래) |
| 타임아웃 경로 | 라이브 데이터로 1500ms 초과 유도 | null 반환 확인 |

첫 뮤테이션 하네스는 아무것도 돌리지 않고 통과처럼 보였다 — pytest는 usage error에 exit 4를
내는데, Windows `shell=True`에서 `-k 'a or b'`가 usage error였다. 종료 코드를 다시 읽고서야
7종 검출이 실제로 확인됐다.

## 그때 남아 있던 것

- **트랜잭션 크기 임계 문제는 미해결이었다** — 2.01% vs 13.13%의 선택은 보드에
  **사용자 결정 대기**로 기록된 상태였다. 코드는 필터 없는 정의로 출시됐다.
- partial covering index는 **파일에만 있고 라이브에 적용되지 않은** 상태였다(read-only 접근).
- `/dashboard/summary` 자체의 ~1.5s 비용(테이블별 count(*))은 그대로였다 — 이 커밋은
  소비 주기를 늦춘 것이지 엔드포인트를 싸게 만든 것이 아니다.
