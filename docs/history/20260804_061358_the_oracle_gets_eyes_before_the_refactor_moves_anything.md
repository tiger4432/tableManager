# 리팩터가 무엇을 옮기기 전에, 채점기가 먼저 눈을 뜬다

> **일자:** 2026-08-04 새벽 | **관련 커밋:** `b322267`(라운드 0 하네스 3건) · `c0a3715`(포매터 리플로) · `2664004`(리플로가 옮긴 변이 앵커 2개 수리)
> **담당:** 총괄(순서 판정) · client/map 구현 · 하네스 자체 채점
> **대상:** `client2/scripts/check_harnesses.mjs` · `client2/tests/undeclared_identifier_harness.mjs` · `client2/tests/startxy_probe.mjs` · `client2/src/map_editor.js`(리플로만) · `client2/map_editor.html` · `client2/tests/company_roundtrip_harness.mjs` · `client2/tests/geometry_origin_reseat_harness.mjs`
> **후속 항목:** `20260804_065028_...`(R1~R6 이음새 라운드)

## 배경 — 9,632줄짜리 파일을 열기 전에 물어야 할 것

`map_editor.js`를 쪼개는 작업이 예정돼 있었다. 이 저장소의 하네스는 대부분
**소스 텍스트를 함수 이름으로 잘라내(`extractFunction`) `vm`에서 돌린다.** 즉
리팩터가 옮기는 것과 채점기가 보는 것이 **같은 텍스트**다. 그래서 실패가
「코드가 깨졌다」인지 「채점기가 못 찾았다」인지 구분이 안 되는 상태로 들어가면
라운드 하나가 통째로 귀속 불가가 된다.

라운드 0은 코드를 한 줄도 옮기지 않는다. **채점기 쪽만 손본다.**

## 수리 ① — 러너가 「0개 단언으로 초록」과 「많은 단언으로 초록」을 구별하게

각 하네스가 **자기 카운터에서** 기계 한 줄을 찍는다. 러너는 **읽기만 하고
절대 세지 않는다.**

```
ASSERTIONS <ran> <failed>
```

차단 조건: 초록인데 이 줄이 없거나 · `ran`이 0이거나 · `failed > 0`.
`KNOWN_RED` 항목은 기록된 `ran` 바닥 아래로 내려가거나 `failed` 천장을 넘으면 차단.
`ran 0`으로 기록된 항목은 **「이 하네스는 죽어 있다」는 정직한 자백**으로 남긴다.

러너 규칙 열 개 전부를 샌드박스 변이 테스트로 적·녹 채점했다.

## 수리 ② — 텍스트를 자르는 하네스는 「이름이 사라진 것」을 볼 수 없다

`undeclared_identifier_harness.mjs`가 `validDieListCache` 부류를 닫는다.
이 하네스만은 텍스트 슬라이스가 아니라 **번들러 자신의 파서**(vite가 이미
싣고 있는 `rolldown/parseAst`, 신규 의존성 0)로 파일 전체를 파싱하고,
참조되는 모든 식별자가 선언·임포트·플랫폼 전역 중 하나임을 요구한다.

**파일 단위 합집합을 일부러 택했다** — 오탐 0이어야 차단기로 쓸 수 있기 때문이다.

## 수리 ③ — 리플로를 따로 커밋한 이유

에디터 포매터가 탐색 작업 중에 `map_editor.js`와 맵 에디터 HTML을 다시 감았다.
이것을 이음새 추출 **아래에 깔아 두면** 실패한 라운드를 귀속할 수 없다.

측정하고 나서 「무행위」라고 말했다(이 항목 작성 시 재측정, 두 수 모두 일치):

| | |
|---|---|
| `map_editor.js` 변경 줄 | **223** (`+122 / -101`) |
| 공백 무시(`git show -w`) 시 남는 줄 | **73** — 전부 객체 리터럴이 여러 줄로 쪼개진 것 |
| HTML에서 추가된 `id` 집합 vs 제거된 `id` 집합 | **완전히 동일** — 아무것도 추가·삭제되지 않고 이동·재들여쓰기만 |

`client2/dist`는 **일부러 넣지 않았다.** `dist/map_editor.html`은 새 마크업을 담게
되는데 `dist`가 참조하는 번들은 이 편집 이전에 빌드된 것이라, 같이 커밋하면
**새 마크업에 옛 스크립트**를 출하하게 된다. 그렇다고 지금 다시 빌드할 수도
없었다 — 클라 레인들이 `client2/`에서 살아 있어서 빌드가 그 미완 작업을 번들에
말아 넣는다.

## 그리고 정확히 그 리플로가 하네스 둘을 죽였다 — H1이 그것을 잡았다

리플로는 **변이 앵커가 글자 그대로 매칭하던 두 자리**를 다시 감았다. 두 하네스는
베이스라인을 초록으로 통과한 뒤 **변이 단계에서 exit 2**로 죽었다. 이것이 H1이
잡으라고 만들어진 위장이고, H1이 잡았다.

수리는 **앵커를 다시 감기지 않는 형태로** 다시 잡는 것이다.

- `geometry_origin_reseat` / `orientation-guard-removed`: 리플로가 이어지는 한 줄을
  두 칸 옮겼다. 가드의 **모양**(`/if \(was\.rotation[\s\S]*?return null;/`)에 다시
  앵커했고, `once()`의 규율을 유지하는 `onceRe` 헬퍼를 새로 뒀다 — 0회 매칭이든
  2회 이상 매칭이든 죽는다. **조용히 적용을 멈춘 변이는 무장 해제된 검사**이기 때문이다.
- `company_roundtrip` / `P0-2: absent notch fingerprint`: 리플로가 거절 객체를 여러
  줄로 쪼갰다. 앵커의 꼬리는 애초에 **중의성 해소용**이었고 `if (!notchOnGrid) {`가
  이미 파일에서 유일하므로, 앵커를 그 한 줄로 줄였다 — 아래 객체가 어떻게 감기든
  무관하고 CRLF 처리도 필요 없다.

**약화가 아니라는 것을 증명하고 넘어갔다**: 수리 **전** 하네스를 리플로 **전**
소스에 물려 물린 자국을 비교했더니 두 경우 모두 동일했고(`orientation-guard-removed`
→ 새 실패 1건, `P0-2` → 같은 두 탐지), 수리된 앵커는 **같은 코드의 서로 다른 세
가지 포매팅**(리플로 전 · 리플로 후 HEAD · 일부러 만든 제3의 재감기)에서 모두
만점 변이 점수로 초록이었다.

## 이 라운드가 남긴 문장

> 텍스트를 잘라 채점하는 도구를 가진 저장소에서는, **포매터도 변경 이력의 일부**다.

그리고 순서가 그것을 감당하는 방법이었다 — 채점기 정비(라운드 0) → 리플로 단독
커밋 → 앵커 수리 → 그 다음에야 이음새를 옮긴다.
