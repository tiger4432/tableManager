## ① 왜 — 선언을 «행마다» 다시 읽고 있었다

```python
for payload in payloads:                                   # ← 그룹의 «행»마다
    filters = _payload_filters(db, rule, payload, source_table)
        for rule_name in (CONFIRMED_JOIN_RULE, FRAME_JOIN_RULE):   # ← 그 안에서 둘
            vj = derivation.join_rule(db, rule_name)               # ← 선언을 «다시 읽는다»
```

그리고 그 로더에는 **자기 캐시가 없다** — `virtual_join/executor` 의 TTL 은 그 파일의 것이고, 이 길은 `load_verified_rules` 를 «직접» 부른다. 로더는 부를 때마다 선언 파일을 다시 읽고 **선언마다 유일성 질의를 하나씩** 돈다.

## ② 구현자가 «멈추고 수를 냈다» — 그것이 이 라운드의 분기점이었다

판정 416 은 원래 다른 것을 시켰다(`join_rule` 이 세션을 안 받게). 그 지시에 「그 헬퍼가 그룹당인가 행당인가」를 «재서 답하라»는 물음이 붙어 있었고, **행당이면 캐시를 짓지 말고 멈추고 수를 가져오라**고 적혀 있었다. 구현자가 정확히 그렇게 했다.

```
판정 416 이 «더하는» 것    2,000 × 0.41 ms  ≈  0.8 s
«이미 있는» 것            2,000 × 3.4 ms   ≈  6.9 s        <- 8배
```

🔴 **수가 순서를 뒤집었다.** 로더를 먼저 고치면 416 은 「2 × 0.41 ms」가 되어 «잴 수 없는 수»가 된다. 거꾸로 했으면 416 이 「비싼 변경」으로 기록됐을 텐데 그건 사실이 아니다.

구현자가 캐시를 «안 지은» 사유를 스스로 적었다 — 「TTL 이 만료될 때마다 로더가 다시 돈다」가 2026-09-14 장애의 한 축이었다고 **그 파일이 스스로 적어 두었기** 때문이다.

## ③ 🔴🔴 이 라운드의 수는 «구조»의 수다 — 오늘 아낀 시간이 «아니다»

```
derivation.join_rule 중앙값      3.71 ms      (이 박스 · 라이브 선언 «2건»)
1,000행 그룹   전  2,000 x   =  «7.41 s»
              후      2 x   =  «7.4 ms»
소유자 규격    그룹 1,000행 «≤ 5 s»(판정 258)  ->  이 헬퍼 «하나»가 예산을 혼자 넘고 있었다
```

**⚠️ 그런데 이 박스에서 그 맵퍼는 «안 돈다».** 총괄이 판정 418 에서 재서 적었다 — 그 맵퍼를 이름 대는 규칙은 `dt_log_to_dt_map` «하나»이고 `enabled=False` 다. 구현자도 같은 정정을 자기 보고에 남겼다:

> 「7.41 s → 7.4 ms」는 «구조»의 수이지 이 박스가 오늘 아낀 시간이 아닙니다. 제가 잰 것은 「그 코드가 1,000행 그룹에 대해 무엇을 할 것인가」이고, 「오늘 여기서 무엇을 아꼈나」가 «아닙니다».

🔴 **커밋 메시지(`d6eb3dc1`)에는 그 문장이 없다.** 채널의 정정이 정본이고, 이 항목이 그것을 옮긴다.

### 그리고 이 수가 «어떻게» 만들어졌는지 — 기록자가 커밋을 열어 확인한 두 가지

```
㉠ 벽시계는 «두 반쪽»을 따로 쟀다
   본보기가 이름 대는 두 선언이 이 박스에선 «내려져» 있어(virtual_join_rules.json.sample 이
   2026-08-14 에 그렇게 적어 뒀다) end-to-end 로는 join_rule 이 «던진다».
   -> 호출 수는 «템플릿을 돌려서», 한 번의 값은 «살아 있는 다른 선언»으로 쟀고, 곱은 «산술»이다
   구현자가 그 사실을 보고에 적었다
㉡ 「2,000 -> 2」는 «천장»이고, 하니스가 «실제로» 센 것은 «1,000 -> 1» 이다
   루프가 첫 이름에서 맞으면 거기서 반환한다. 픽스처가 그 경우다:
     assert len(template._s276_asked) == 1
     assert len(template._s276_asked) <= 2          # 천장은 따로 단언
   -> 7.41 s 는 «천장 2,000»에 중앙값을 곱한 것이다. 첫 이름이 맞는 배치라면 절반이다
```

⚠️ 그리고 **같은 커밋 안에 중앙값이 둘이다** — 커밋 메시지는 `3.71 ms / 7.41 s`, 본보기 docstring 과 시험 docstring 은 `3.4 ms / ≈6.9 s`. 측정을 두 번 돌린 것이고 둘 다 「이 박스」다. 어느 쪽도 운영에 대해 말하지 않는다.

⚠️ **선언 «수»로도 커진다.** 로더가 선언마다 유일성 질의를 하나씩 하므로 조인이 많은 카탈로그에서는 «곱»으로 커진다. **운영 선언 수는 잴 수 없다** — 구현자가 그렇게 적었고 판정이 그 경고를 같이 남기라고 지시했다.

## ④ 답은 «캐시가 아니라 끌어올리기»였다 — 그 구별이 판정이다

```python
# 🔴 [S-276, 판정 417] THE DECLARATION IS RESOLVED ONCE, OUTSIDE THE LOOP. It does not
# change while this group runs, so its lifetime is the loop's - a MOVE, not a cache,
# and therefore no 「when is it stale」 question is created.
vj = _matching_join_rule(db, rule, source_table)

scopes = []
for payload in payloads:
    filters = _payload_filters(vj, payload)
```

**끌어올리기는 「언제 무효화하나」라는 물음을 만들지 «않는다»** — 값의 수명이 루프의 수명이고 그게 전부다. 캐시는 그 물음을 만들고, 그 물음이 09-14 의 한 축이었다. 일반화·설정 축을 «하나도» 안 만들고 값을 옮기기만 한 판이다.

그리고 **행당 절반이 DB 에 «닿을 수 없게» 됐다**:

```python
def _payload_filters(vj, payload: Dict[str, Any]) -> Dict[str, Any]:
    """⚠️ TAKES THE RESOLVED DECLARATION, NOT A SESSION (S-276). This is the per-row half,
    and a per-row function that can reach the database is a per-row function that will."""
```

```python
assert list(inspect.signature(template._payload_filters).parameters) == ["vj", "payload"]
assert "db" not in inspect.signature(template._payload_filters).parameters
```

나중에 이 틀을 고치는 사람이 루프 안에 질의를 되돌려 넣으려면 **인자부터 되살려야 한다** — 조용한 변경이 아니라 눈에 띄는 변경이 된다.

🔴 하니스는 **본보기를 «import» 한다** — `.py.sample` 은 이름으로 import 가 안 되므로 경로에서 «파일 전문»을 로드한다. 잘라쓰기가 아니다.

## ⑧ 아키텍처 영향

- 본보기가 가르치던 모양이 하나 고쳐졌다 — 「루프 안에서 선언을 다시 읽어도 된다」에서 「선언은 루프 밖의 값이다」로. **다음에 복사하는 사람에게 참이다.**

## ⑨ 그때 남아 있던 것

- 🔴 **판정 416/418 은 커밋이 «없다».** 되돌린 상태가 최종이고, 저장소에 그 흔적은 채널 기록뿐이다. 코드에서는 이 라운드의 어떤 줄로도 그 판정을 찾을 수 없다.
- `join_rule` 은 이 시점에 **여전히 `db` 를 받고, 여전히 호출자의 세션을 `load_verified_rules` 에 넘긴다.** 노출 시간이 그룹당 2,000회에서 «2회»로 줄었을 뿐 기제는 그대로다.
