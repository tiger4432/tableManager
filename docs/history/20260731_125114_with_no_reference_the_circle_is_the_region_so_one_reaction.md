## 배경 — 세 라운드가 이것을 두 개의 결함으로 취급했다

셀이 자기 **캔버스 칸**을 붙들고 있는데 원점 상자가 그 밑에서 움직이면, 셀이 읽는 번호가
바뀌고 ⚡ Push가 그 새 번호를 쓴다. 화면은 한 픽셀도 움직이지 않은 채 DB의 좌표가 갈린다.
이 주에 그 부류가 **세 자리**에서 나왔다 — 참조 전환 · 영역 변경 · 기하 편집.
수리는 매번 같았다: **DB 좌표가 불변량이고 캔버스 위치는 파생이다.**

그런데 앞선 세 라운드(2026-07-30 저녁 · 07-30 밤 · 07-31 오전)의 반응은 전부
`resolveValidDie`의 `set()` **안에만** 있었다. 기하 편집 경로에는 반응이 아예 없었다 —
이 커밋 직전까지 물리 규격 입력의 리스너는 이랬다.

```js
input.addEventListener('change', () => scheduleRenderGridCanvas());
input.addEventListener('input',  () => scheduleRenderGridCanvas());
```

**다시 그리기만 한다.** 그리는 사이에 좌표계가 바뀌었다는 사실에 아무도 반응하지 않는다.

## 라운드를 닫은 것은 사용자의 한 문장이다

> **「유효 다이가 없으면 유효 다이 영역이 곧 웨이퍼 원이다」**
> (커밋에 인용된 형태: 「유효 다이 없이 기하 프리셋 변경도 유효 다이 영역을 원 기하 내부로
> 변경하므로」)

참조 선언이 없는 맵에서 **유효 다이 영역은 곧 웨이퍼 원**이다. 그러면 기하를 바꾸는 것은
그 영역을 바꾸는 것이고, **참조를 지정하는 것과 닮은 연산이 아니라 같은 연산**이다.
두 개의 결함이 아니라 하나였다.

> **나는 원 기준 경로를 별개의 결함으로 취급하고 있었고, 그 오해 위에서 이 발견이 세 라운드를
> 살아남았다.** 문장 하나가 들어오자 코드의 반응 지점이 **둘에서 하나로** 줄었다.

## 수리 — 반응 함수 하나, 새 컨트롤 0개, 새 확인창 0개

```js
function reseatCellsToStoredCoords(was) {
  const now = seatingSnapshot();
  if (now) cellsSeatedUnder = now;
  if (!was || !now) return null;
  // [규칙 5] 방향과 START는 반대 연산이다 ― 다이를 붙들고 번호를 옮긴다. 하나라도 다르면
  // 이 반응은 아무것도 하지 않는다.
  if (was.rotation !== now.rotation || was.side !== now.side || was.invertY !== now.invertY
      || was.startX !== now.startX || was.startY !== now.startY) return null;
  …
  // (1) 각 셀이 **옛 좌표계에서** 말하던 저장 좌표를 되찾는다.
  withPhysFrame(was, () => { … held.set(k, getDbCoords(at.c, at.r, was.cols, …)); });
  // (2) 그 저장 좌표가 **새 좌표계에서** 가리키는 칸으로 다시 앉힌다.
  held.forEach((v, k) => { … getCanvasCellFromDb(v.x, v.y, now.cols, …) … });
}
```

- **새 변환식이 한 줄도 없다.** 옛 좌표계는 `withPhysFrame`으로 다시 열고, 안에서 도는 것은
  로드·렌더가 쓰는 바로 그 네 함수다.
- **거절 조건이 규칙 5의 정의다** — 방향(회전·반전·Y반전)과 START는 다이를 붙들고 번호를
  옮기는 연산이므로, 기하 반응이 거기서 뜨면 규칙 4가 규칙 5를 덮어쓴다.
- `serverCellKeys`도 함께 옮긴다. 안 옮기면 서버에서 온 셀이 「보낸 적 없음」으로 읽혀 정리
  경로가 실재하는 행을 지우자고 제안한다.

### 리스너가 「변경 전」을 잡을 수 없다 — 그래서 좌석 기록이 생겼다

`input`/`change`는 **DOM 값이 이미 바뀐 뒤에** 뜬다. 그래서 옛 좌표계는 직전 렌더가 남긴
기록에서 온다.

```js
// renderGridCanvas() 최상단
cellsSeatedUnder = seatingSnapshot() || cellsSeatedUnder;
```

🔴 이것은 상자에 대한 **두 번째 진실이 아니다.** 상자가 무엇인가는 `getWaferBoundingBox`
하나만 답하고, 여기 담기는 것은 그 함수가 이미 내놓은 답이다. 뜻은 「무엇이 옳은가」가 아니라
**「셀이 마지막으로 어디에 앉았는가」**다.

기록을 쓰는 자리가 딱 둘이고 그중 하나가 렌더 최상단인 것이 안전의 근거다 — **좌표계를
바꾸는 모든 경로는 렌더로 끝나므로**, 다음 기하 편집은 언제나 직전 화면과 대조된다.

⚠️ 호출자가 기록을 **미리 잡아 두면 안 된다.** 한 번의 조작이 반응을 두 번 탈 수 있고
(규격 교체 → 파생 치수, 그다음 마스크 적합 확장), 두 걸음이 이어 붙어야 저장 좌표가 보존된다.
옛 기록을 두 번째 걸음에 넘기면 같은 이동을 두 번 적용한다.

### 프레임 창이 자기 상자를 싣고 다닌다

```js
if (physFrameOverride && physFrameOverride.box && !(opts && opts.circleOnly)) {
  return physFrameOverride.box;
}
```

읽는 지점을 갈아끼우는 것이지 두 번째 상자 정의가 아니다 — 창에 실리는 상자는 **이 함수가
앞서 만들어 낸 바로 그 상자**다. 다시 계산해서 얻을 수 **없는** 이유가 있다: 창 안에서는
`isValidDieAt`이 원으로 답하므로 옛 마스크 상자는 원리적으로 재구성되지 않는다.
`circleOnly`가 이 창보다 세다 — 노치 지문은 마스크와 무관한 물리 특징이어야 한다.

> 즉 타이핑 케이스는 **그 유일한 호출자를 내가 지워도 하네스가 눈치채지 못할 함수**를

> 이 주의 `copy_header_count`·`company_roundtrip`과 **같은 모양**이다 — 하네스가 더 이상
> 닿지 않는 코드에 대해 녹색을 보고한다.

수리는 **DOM 이벤트에서 시작**하게 하는 것이다. `initDOMElements`를 슬라이스해 실행하고,
노드가 진짜 리스너 레지스트리를 갖게 하고, 케이스는 `.value`를 쓰고 제스처를 쏜다.

```js
function fire(node, type, what) {
  const n = node.dispatchEvent({ type });
  if (n === 0) throw new Error(`nothing is listening for '${type}' on ${what} — the wiring is `
    + 'gone, and a fixture that called the handler directly would still have been green');
  return n;
}
```

⚠️ `initDOMElements`가 부르는 함수 약 25개는 **하나씩 개별로** 스텁했다 — 개명이 조용한
no-op이 아니라 `ReferenceError`가 되게 하려고. 규칙 5 케이스만 직접 호출을 유지한다:
회전에는 리스너가 반응까지 닿지 않으므로 **가드 자신에게 거절을 물어보는 쪽이 더 강한 검사**다.

새로 잡히게 된 변이 둘 — `#preset-select`의 `change`에 아무도 안 듣는 경우, `#phys-chip-x`의
`input`에 아무도 안 듣는 경우. **5/5 → 7/7.**

프리셋 픽스처도 합성을 그만두고 실제 `server/config/maps.json`의 `BASE_OFFSET`을 쓴다
(offset 10, rotation 270). 종전 픽스처는 offset 0 → 0이라 `getScreenShift` 축을 통째로
