## ① 「파서가 안 맞았습니다」가 **아홉 갈래**에서 똑같이 나왔다

`d7592211`. 거절문 하나가 구조적으로 다른 자리 여러 곳에서 올라오는데 **글자가 같았다.**

```
scripts 폴더가 «없다»                 라우팅 문제
BasePipelineParser 를 «임포트 못 한다»  플러그인 적재 실패
폴더에 .py 가 «하나도 없다»            라우팅 문제
```

운영자는 아홉을 구별할 수 없었는데 **고치는 방법이 서로 반대**다 — 하나는 파서 버그이고
나머지는 라우팅이다.

바뀐 것은 **메시지가 «해석이 실제로 본 것»을 싣는다**는 것이다: 풀린 표 이름, 워크스페이스,
scripts 경로와 그 존재 여부, 플러그인 파일 수, 파서 클래스, 어느 클래스가 거절했고 어느 것이
던졌는지, 표준 폴백이 왜 비켰는지. **제어 흐름은 안 건드렸다** — 같은 호출들 사이로 out-dict
하나를 꿰었고, 모든 반환 계약이 같으며, **문장의 접두는 그대로 뒀다**(시험 넷이 그 접두로 매칭한다).

세 워크스페이스에서 실증됐다: 폴더 없음은 `MISSING` + 스캔 `NOT RUN`, 폴더는 있고 비었으면
플러그인 파일 0, `False` 를 돌려준 플러그인은 **이름이 declined 밑에** 찍힌다.
이 경로를 덮는 다섯 파일 **93 통과**.

## ② 「구멍을 메우는 추가 기능」이 실은 **원점을 고정하고** 있었다 — 소유자 판정

`bcc7fc2b`. 맵 메타 자동 등록기는 **absent-only · priority 99** 라서 순전히 덧붙이기만 하는
것처럼 보였다. 아니었다.

```
합성 행이 grid_start_x/y 를 «배치의 min x/y» 로 세운다
맵 에디터에서 start x/y 는  «좌표의 기준(BASIS)» 이지
                          유효 다이 기준과 저장 좌표 «사이의 시프트»가 아니다
=> 그 행은 구멍을 메우는 것이 아니라, 이후 «모든 편집이 읽히는 원점»을 고정한다
   그리고 에디터는 그것을 되돌릴 수 없다
```

**absent-only 는 «행»을 지켰다. «원점»을 지킨 것은 아무것도 없었다.**

기제를 걷어내지 않고 **기본값만 뒤집었다.** `auto_registered` 는 스위치가 아니라 여섯 phys 키
위의 **표지**이고, 이미 `grid_start_*` 를 들고 있는 행들의 출처를 설명하는 유일한 것이다
(`map_alignment` 의 `[D8]` 주석이 그렇게 적고 있다). 지우면 그 행들의 출처가 `declared` 가
되는데, 그것은 데이터가 뒷받침하는 것보다 **강한 주장**이다.

```python
# server/map_meta_registrar.py
- Knob: `auto_register_map_meta` in ingestion_settings.json (default ON).
+ Knob: `auto_register_map_meta` in ingestion_settings.json (default OFF since
+  2026-08-30; see DEFAULT_ENABLED for why).
```

🔴 **여기서 나온 시험 판정이 이 커밋의 값이다.** 기본값에 기대던 시험이 여덟이었고, 그중 **넷은
「아무것도 안 써진다」를 단언**한다 — 기능이 꺼지는 순간 그 넷은 **공짜로 통과**한다.
빨개진 넷만 고치지 않고 여덟을 다 확인한 이유가 그것이다:
**실패할 수 없는 가드 시험은 그것이 대체한 실패보다 나쁘다.** 여덟 전부 등록기를 명시적으로
켜고 이유를 적는다. 기본값 자체를 단언하던 시험은 **자기 주제를 따라 옮겨졌다** —
사라진 기본값에 대고 살려 두지 않았다.

라이브 설정은 여기에 아무것도 선언하지 않고 **없는 키가 기본값**이라, 라이브 파일은 안 건드렸다.

## ③ 작업목록의 «정렬이 잘라내기보다 먼저» 와야 했다

`147d3ef5`. 소유자 요청 — 정렬 작업목록이 **가장 최근에 적재된 단위**부터 열린다.
순서는 파생 표에서 그 단위 행들의 `MAX(updated_at)` 이다(업서트 경로가 매 쓰기에 찍는다).
`created_at` 은 **모든 동적 표에서 의도적으로 인덱스가 없고**(`models.py [F6]`),
어차피 묻고 있는 질문은 「이 단위가 마지막으로 데이터를 받은 게 언제인가」다.

두 줄짜리 변경이 아닌 이유가 여기 있다.

```python
# server/map_alignment.py
# 🔴 THE SORT IS RESOLVED BEFORE THE CUT, not after it.  [R7] below is the reason:
# which units survive `unit_cap` decides which units an operator can even SEE, so
# the cut must run in the SAME order the page is then shown in.  Ordering the cut
# alphabetically and re-sorting by time afterwards would show 'the newest among the
# first N unit keys', which is not the newest.
```

`unit_cap` 이 **SQL 에서** 걸리므로, 결정 키로 자른 뒤 화면에서 시각으로 재정렬하면
**「앞쪽 N 개 단위 키 중에서 가장 새것」**이 나온다 — 그것은 가장 새것이 아닌데
**화면에서는 정확히 가장 새것처럼 읽힌다.** `DISTINCT` 는 같은 컬럼들에 대한 `GROUP BY` 로
바뀌었고, 그 이유는 오직 `MAX` 가 함께 타기 위해서다. 그 컬럼이 없는 파생 표는 적재 시각이
**없는 것**이지 0 이 아니고, 키 순서로 폴백한다.

배선하다 둘이 드러났다:
```
빌더의 기본값과 라우트의 기본값이 «달랐다»   -> 한 동작에 기본값이 둘. 지금은 같은 상수를 읽는다
동률 타이브레이크가 «복합 정렬 키 안»에 타 있었다
   -> reverse=True 가 그것까지 뒤집어서, 값이 같은 단위들이 «역알파벳» 순으로 돌아왔다
```
🔴 두 번째는 **기본값이 `unit_key` 오름차순인 동안에는 안 보인다.** 기본값이 «시각»이 되는
순간 보이게 된다 — 한 배치가 1초 안에 적재되면 모든 행이 동률이고, **그때는 타이브레이크가
곧 운영자가 읽는 순서**다. 기존 시험 둘이 잡았고, 그게 그 시험들이 쓰인 이유다.

새 시험은 **알파벳 순서를 적재 순서와 반대로** 심어서, 「정렬된 것처럼 보이는」 결과가
통과할 수 없게 했고 **잘라내기까지** 단언한다.
