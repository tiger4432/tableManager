# 하니스가 CRLF 에서 «불활성»이 되고, 파일을 세면 «반쯤 정규화된» 것들이 숨는다

## 증상: 그 줄을 «건드리지도 않은» 변경에서 앵커가 사라졌다

같은 날 두 번 났다 — 커밋이 그렇게 적었다: 「the map one this morning, the retroactive one
at eleven」. 두 번 다 같은 것이었다.

```
하니스가 자기 «주제 파일»을 읽는다  ->  줄바꿈을 «정규화하지 않고»
그 하니스의 앵커는 \n 으로 «쓰여 있다»
=> CRLF 체크아웃에서
     여러 줄에 걸친 앵커  «절대 매칭 안 됨»
     한 줄짜리 앵커      «계속 매칭됨»
```
🔴 **대부분의 변이를 잡았다고 보고하면서 나머지에서 «불활성»이 되는 하니스는,
그냥 실패하는 하니스보다 나쁘다.**

## 🔴 ① 총괄이 «재지 않고» 원인을 붙였다 — 그리고 레인이 세 번 돌려 반박했다

`205eace7`. 총괄은 「그 변경에서 앵커가 드리프트했다」고 적었다. **아니었다** —
그 커밋은 열두 줄을 더하고 하나도 안 지웠으며 `countView` 를 건드린 적이 없다.

```
CRLF 소스 · 정규화하는 하니스   exit 0   304/0, 29/29
CRLF 소스 · 옛 하니스          exit 2   ANCHOR LOST
LF   소스 · 옛 하니스          exit 0   304/0, 29/29
=> 같은 코드가 «체크아웃에 따라» 다른 답을 냈다
```
총괄 자백: **「증상에 가장 가까운 변경을 골라 원인을 «재지 않고» 붙였다」** —
이 저장소가 이미 기록해 둔 「가설은 진단이 아니다」 그대로다.
레인은 총괄이 맞힌 것(던져서 잡힌 변이 둘)을 고치고, 틀린 것을 세 번의 실행으로 반박했다.

그리고 그 순간 **부류**가 됐다 — 같은 날 두 번째라서.

## ② 스윕은 «한 줄»씩만 더했다. 그리고 «기록»이 증거다

`c819cdb0`. 스물세 파일이 소스 읽기에 `.replace(/\r\n/g, '\n')` 를 얻었고 **그 외에는
아무것도 안 바뀌었다.** LF 체크아웃에서는 전부 no-op 이고, **요점은 LF 가 아닌 체크아웃**이다.

🔴 **「아무것도 안 바뀌었다」는 주장이 아니라 «기록»이다.**

```
스물넷 전부를 «스윕 전»과 «스윕 후»에 돌려서
   exit code · ASSERTIONS 줄 · 실패를 이름 대는 첫 줄  을 캡처했다
결과: «다른 기록 0»
```
이미 빨간 셋은 **같은 이유로 그대로 빨갛고, 안 건드렸다** — 다른 라운드 소관이다.

```
alignment_verdict_harness      exit 1   163/6
split_registry_harness         exit 1   (ASSERTIONS 줄 «없음» — 추출 단계에서 던진다)
valid_die_authoring_harness    exit 1   100/1
```
**빨강은 빨강으로 두고, 목록만 기록했다.**

수가 24 인데 바뀐 것은 23 이다. `map2_authoring_harness` 는 `readFileSync` 를 **주석 안에서만**
말하고 파일을 읽지 않는다 — 그 수를 만든 낱말 단위 스캔의 **위양성**이고,
**조용히 빼지 않고 여기 기록**했다(수가 이제 기록에 남았으므로).

🔴 **첫 시도가 정규식이었고 바로 그 파일에서 멈췄다.** 그리고 그 정규식은
`map_editor2_shell`(호출이 **두 줄에 걸쳐 쓰여 있다**)도 놓쳤을 것이다.
**괄호를 균형 맞춰 걷도록 다시 썼다 — «호출의 «모양»이 그것이 발견되는지를 정하면 안 된다».**

## 🔴 ③ 그리고 진짜 수는 23 이 아니었다 — «파일»이 아니라 «읽기»를 세야 했다

`c04f8fa2`. 읽기를 세니 **셋이 더** 나왔다. 그것들이 첫 통과에서 안 보인 이유가 기록할 값이다:

```
각 파일이 «이미 어딘가에» \r\n 을 들고 있다 —
   두세 개의 읽기 중 «하나는 이미 정규화»됐고 «다른 하나는 아니다»
=> 「이 파일이 \r\n 을 언급하나」로 묻는 시험은
   «정확히 반쯤 끝난 파일들»을 «배제»한다

frame_declaration_harness        2 중 1 이 맨몸
geometry_origin_reseat_harness   2 중 1
reposition_regime_probe          3 중 2
```
게이트는 스윕과 같다 — 전에 돌리고, 적용하고, 후에 돌리고, 대조. **다른 기록 0.**
`frame_declaration` 4079/0 과 `geometry_origin_reseat` 62/0 은 초록 유지,
`reposition_regime_probe` 는 ASSERTIONS 줄 없이 빨간 채로 남았다(알려진 상태, 이 레인 소관 아님).

**이 답을 낸 검출기는 «답을 이미 아는» 대조군 둘을 통과했다.**

```
valid_die_dirty_guard   «정규화됨»으로 읽힌다
                        (정규식이 맨몸이라 불렀던 파일 — `import { readFileSync }` 줄을 «호출»로 셌다)
map2_authoring          «진짜 읽기 없음»으로 읽힌다 (유일한 언급이 주석)

전체 하니스: 진짜 utf8 읽기 «57» · 정규화 «57» · 맨몸 «0» · 읽기 없음 «6»
```

## 🔴 ④ 총괄이 «독립적으로» 세려다 자기 대조군에 걸렸다 — 그날 열한 번째 계측 오류

`2dc2126c`. 총괄의 스캔이 **레인이 방금 고친 파일**을 신고했다 —
**맨몸 import 줄을 «호출»로 읽고, 두 줄 아래의 정규화를 못 봤다.**

> 대조군에 실패했다는 것은 **그 수를 버린다는 뜻**이다. 그 수로 레인의 수를 반박할 수 없다.
> 그날의 **열한 번째** 계측 오류였고, 발표 전에 잡힌 유일한 이유는
> **레인이 시연한 절차**였다 — **답을 이미 아는 파일을 먹여 본다.**

그래서 세 번째 계측기를 만드는 대신 **수 하나를 물었다**: 괄호를 세는 검출기가 지금 뭐라고
답하나. 23 이면 스윕이 닫히고, 더 나오면 정규식이 놓친 것이고 **차이만** 쓸면 된다.

- 클라 하니스 **57 개 전부**가 소스를 읽을 때 줄바꿈을 정규화한다. LF 체크아웃에서는 no-op.

  남는 형태가 이 라운드에서 쓰였다.
