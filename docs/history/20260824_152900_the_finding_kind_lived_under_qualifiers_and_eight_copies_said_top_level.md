## 배경 — 맵은 50%, 트렌드는 0%

같은 웨이퍼를 맵은 「절반 발견」으로, 트렌드는 「0」으로 그리고 있었다. 원인을 실측으로 갈랐다:

```
「종류는 최상위에 있다」고 적힌 사본       «8»
최상위에서 실제로 답하는 원자             «15»
답하지 않는 원자                       «103,841»
```

v5 런타임이 payload 를 `{"value":…}` + `{"qualifiers":{…}}`로 고정해 만들기 때문에,
재번역된 void **103,729**개가 `run_uid` 없이 `"defect"`로 투영되고 있었다(`658514bb`).

`4f0605f3`이 **두 언어 모두를 위해 한 번만** 적었다:

```python
# server/ledger_api/finding_kinds.py
def payload_field(payload, name):
    """The field from the payload top level, else from `qualifiers`, else None."""
    if not isinstance(payload, dict):
        return None
    if name in payload:
        return payload.get(name)
    return (payload.get("qualifiers") or {}).get(name)
```

## 접힘이 호출자의 collect 에 «양보»한다

## 🔴 「128과 64」는 결함이 아니라 «grain»이었다

이 시점의 진짜 결함은 위의 최상위-전용 읽기였다. 128/64 쪽은 다르다:

```
SYN-CX-BW-001   스캔된 다이 128 = 본딩 레그 둘에 «64 + 64»
맵    웨이퍼를 센다        -> 128
트렌드 실험 단위 하나를 센다  -> 64   (WaferLeg = wafer · bonding_leg)
=> «둘 다 맞다»
```

그래서 수리는 「하나를 고치는 것」이 아니라 **셋을 말하게 하는 것**이었다:
`511f53c4`가 비율을 만든 **두 수를 드러내고**(분자는 일부러 `—`, 절대 0이 아니다),
`6e1f86f3`이 `found_chip_count`를 이음매 건너로 실어서 hover 가 「64 스캔 0 발견」이라고
말할 수 있게 했으며(없으면 `null`, 절대 0이 아니다), `d6b17c92`가 **어느 grain 에서 센 수인지**를
붙였다. **요청은 0건** — grain 은 이미 클라에 선언돼 있었다.

## 아키텍처 영향

- payload 접근자가 **최상위 → `qualifiers` 순으로** 한 번만 적혀 있고 서버·클라 양쪽이
  같은 규칙을 쓴다.
- 접힘이 **호출자의 collect 에 양보**한다.
- 화면의 수가 **자기 grain 을 말한다.** 없음은 `—`이고 0이 아니다.
