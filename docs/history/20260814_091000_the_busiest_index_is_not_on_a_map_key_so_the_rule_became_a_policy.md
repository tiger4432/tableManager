# The busiest index is not on a map key, so the rule became a policy

**Date:** 2026-08-14 09:09 / 09:10 · **Domain:** DB (인덱스 조사 F5) · **Status:** 기록만 — `a256eca`, 판정 `321a91e`

## 조사 (`a256eca`) — 절반만 메커니즘이다

「감사 컬럼은 전부 인덱스, 질의 술어는 아님」의 배후 규칙을 물었다. 절반은 실재한다:
`init_dynamic_models`가 모든 동적 표에 하드코드 인덱스 집합을 붙이고 선언은 안 읽는다
— 한 곳의 리터럴 목록. 나머지 절반은 메커니즘이 아니다: 술어 인덱스 16개가 셋업
스크립트 둘 + 마이그레이션 넷에 손으로 흩어져 있고 **두 dev 박스의 손추가 집합이
서로소다**(교집합 공, 16 중 9는 어느 쪽에도 없음). 자동적인 것은 그 모양을 만들지
않는다.

예측은 맞았다가 중요한 방식으로 틀렸다: 17표 중 14가 그 모양을 보이지만 — 가장 뜨거운
술어 인덱스를 든 두 표에서 커버되는 술어는 `map_key_columns`가 **아니다**.
`wafer_map_metadata`는 시스템에서 가장 바쁜 인덱스(32,046 스캔)를 들고
`map_key_columns`를 선언조차 안 하며 `(target_table, map_id)`로 읽힌다. 「모든 표의
map_key_columns를 인덱싱하라」는 canon 규칙은 시스템 최열 읽기를 놓치고 필요 없는 표
열을 과세했을 것이다 — **조사가 자기가 찾으러 간 규칙의 반례를 들고 왔다.**

역방향도 같은 값이다: `ix_<t>_created_at`은 17표 전부 스캔 0에 매 insert 지불,
`idx_<t>_bk`는 17 중 16에서 0. `core_wafer_map`의 인덱스 열 중 다섯은 스캔된 적이
없고 아침에 추가된 하나가 4,949를 받았다. 비용도 수가 됐다: +13.1% 중위 insert,
+74.8 B/row WAL(반복 간 바이트 동일 — 결정 가능한 수), +8.1 B/row 저장.

**표 전체보다 위인 발견**: `assy_manager` 17표 어디에도 비즈니스 키 UNIQUE 인덱스가
없다 — `models.py` 자신의 주석이 «unprotected»라 부르는 상태. 성능이 아니라 정체성
무결성.

  (오버라이드를 다스리는 그 규율).
