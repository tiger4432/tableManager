## ① `follow_up` 종류가 «길 하나»가 됐다 (S-195)

```
c4aeb56c 15:11  ⓐ 디스패처가 «드레인 배치마다 규칙 파일을 다시 읽는» 것을 그만뒀다
92257825 15:20  ⓑ 자동 확정이 `builtin:` 표에 들어오고, «둘째 길»이 사라졌다
```
🔴 **일은 «안 바뀌었다» — 바뀐 것은 「어떻게 찾히나」다.** 인리치 스윕은 `_auto_confirm_followed_rows` 에서
«이 디스패처 옆»에서 «직접» 불리고 있었다. 즉 `follow_up` 한 종류에 **도는 길이 둘**이었고,
그것을 금지하던 규칙이 «이름 붙은 임시방편»을 이고 있었다. 이제 표 하나, 길 하나다.
🔵 **그리고 규칙이 «선언»에서 온다** — `AutoConfirmCollector` 는 이미 `rules` 를 받는데, 안 주면
`load_enrichment_rules` 로 «다시 찾았다». 합성된 규칙이 «이미 들고 있는» 것을.
📐 **ⓐ 는 성능이 아니라 «수명»의 수리다** — 그 목록이 이제 «리로드당 한 번» 실린다
(`_followup_builtin_rules` :1682). ⚠️ **무효화를 «다른 워커 캐시와 같은 자리»에 뒀다** —
**리셋 없는 캐시는 「리로드가 아무 뜻도 없게 되는」 이유**이고, 이 프로세스엔 그 자리가 이미 하나 있었다.

## ② 「`input_columns` 가 담아야 할 것」의 «열거 하나» (S-196)

```
aa0f1217 15:37  유도된 `input_columns` 가 단위의 «그룹 컬럼»을 든다 — 단위를 읽는 함수는 «하나»
6692ae9f 15:49  그 열거를 «하나»로: `required_mapper_input_columns` :2535, 검증기와 유도가 «같이» 부른다
```
🔴 **검증기는 빠진 것을 거절하고 작성 폼은 «같은 목록»을 유도한다 — 즉 둘이 «한 질문»에 답해야 한다.**
그런데 아니었다: 유도가 「준비된 프레임 «빼기» `read` 가 이미 읽는 것」이었고, 그 뺄셈은
**그룹이나 바인딩이 필요로 하는 컬럼을 정확히 지운다**. 그렇게 다시 지은 번들을 **자기 검증기가 거절했다.**
⛔ **그리고 수리가 «손으로 적은 목록»이면 안 됐다** — 첫 수리는 그룹 컬럼만 더했고, 다음 소스가
«바인딩» 컬럼에서 넘어졌다. **손으로 늘린 목록은 「다음 선언이 쓰는 것」을 놓친다.**
그래서 이 함수는 «종류»를 열거한다 — 새 종류는 여기 «하나»에 더하고 두 호출자가 «같이» 배운다.
⚠️ **경로가 값과 «같이» 실린다** — 거절문이 「어디서 요구하는지」를 이름 대야 하기 때문이다.
「Profile column 'base_id' at …bind.subject.keys.x.column is missing」이 운영자를 «그것을 원하는 선언»으로
보내고, 「없다」만으로는 못 보낸다.
🔵 **행 단위는 그룹 컬럼을 «요구하지 않는다»**(판정 306) — 행 단위라는 선언이 곧 「그룹이 «없다»」이므로.
📎 이 줄기의 시작(픽스처 낱말 하나가 시험 열둘을 죽인 것, `c91b2800`)은 [09-12 오후 항목](./20260912_145500_the_join_started_writing_and_a_lifecycle_learned_to_ask_a_document.md) §④ 에 있다 — 여기서 다시 적지 않는다.

## ③ 정리의 «나머지 절반»이 세 파일 건너에서 터지고 있었다 (S-191 `1f730cc9`)

```
pop 하면    `DYNAMIC_TABLES` 에서 클래스가 빠진다
남는 것     `Base.metadata` 는 «같은 싱글턴»이라 `Table` 과 `Index` 가 «살아남는다»
다음 빌드    클래스가 없으니 새로 짓는 팔을 타고 **같은 이름의 `Index` 를 하나 더** 붙인다
터지는 곳    «그 뒤에» `create_all` 을 부르는 «첫 파일»이 「index … already exists」로 죽는다
            — 샌 파일도, 그렇게 만든 픽스처도 «이름 대지 않고»
```
📐 **이 세션 실측: 그런 픽스처 «하나»에서 오류 1,008 건**(`ea1e8ec2`). 좌석 «넷»이 양쪽 절반을 손으로 했고
«넷»은 안 했다 — 그래서 함수 «하나»(`conftest.retire_dynamic_model` :75)로 접었다.
⛔ **그리고 「저장했다 되돌리기」는 «예외»이고 소스가 세 좌석을 이름 대어 적는다** — 거기서는 pop 이
restore 의 «역»이라, `Table` 까지 떨어뜨리는 헬퍼를 쓰면 짝이 깨진다(restore 는 «클래스»를 돌려놓지
`Table` 을 돌려놓지 않는다). 📌 **적어 둔 이유가 「다음 독자가 일을 마저 끝내지 않게」다.**
🔵 반환이 «물린 클래스», 없던 이름이면 `None` — 호출자가 「있었다」와 「애초에 없었다」를 «구별»할 수 있다.

## ④ 노트북이 «자기가 발행한 것»을 증명한다 (S-197)

```
bcde6af3 20:56  ⓐ 벤치가 «운영이 넘기는 입력»을 그대로 건네고, «못 읽음»이 값이 된다
8ec6bf4a 21:07  ⓑ 워크벤치 노트북 «둘»이 저장소에 들어오고, 발행이 «스스로를 증명»한다
```
### ⓐ 「못 읽었다」가 «예외»가 아니라 «답»이다
`raw_for_parser` 가 원문 몇 줄과 «인코딩 사다리»(`utf-8-sig` → `utf-8` → `cp949` → `latin-1`)의 결과를 주고,
실패는 `UNREADABLE`(「DataFrame 으로 못 읽음」)이라는 **값**이다.
🔴 **파서 작업은 「이 파일이 무엇인가」를 «모르는 데서» 시작한다** — 그 자리에서 예외를 던지는 도구는
바로 그 첫 걸음에서 쓸모가 없다.
🔵 그리고 `claimers` 가 「이 파일을 «누가» 무는가」를 제품과 «같은 방식»(각 파서의 `match()`)으로 묻는다.

### ⓑ 발행의 요점은 «파일»이 아니라 «대조»다
```
publish_mapper / publish_parser  ->  파일을 쓰고 -> «다시 import» 해서 -> «같은 프레임/파일»에 돌려
                                  -> 같은 결과일 때만 «남는다». 어긋나면 «지우고» 이름 대어 거절
```
🔴 **왜 필요한가:** `inspect.getsource` 도 복붙도 **「마지막으로 «실행된» 셀」**을 내보내지
**「화면 위의 셀」**을 내보내지 «않는다». 둘이 갈린 채로 발행되면 노트북에서 본 것과 파일이 «다른 것»이
되고, 아무도 그것을 모른다. 다시 돌려 보는 것이 «유일한» 보장이다.
⚠️ **프레임을 «넘겨받지 다시 유도하지 않는다»** — 다시 유도하면 창(`rows=`/`where=`)이 다시 돌아
«다른 창 = 다른 답»이 되고, 그러면 대조가 «본문과 무관한 이유»로 실패한다. 실패의 이유가 틀리면
그 게이트는 없느니만 못하다.
🔵 노트북은 «부품을 새로 만들지 않는다» — `server/tests/test_the_workbench_notebooks_call_production.py`
가 그것을 채점한다(셀이 컴파일되나 · 벤치 «말고» 다른 것을 import 하지 않나 · 벤치가 하는 일을 다시
구현하지 않나 · 이 박스의 이름이 실려 있지 않나 · `autoreload` 가 걸려 있나).

⚠️ **지시서의 전제 하나가 거짓이었다(기록):** 지시는 `server/parsers/notebooks/parser_workbench.ipynb` 를
「미추적 … 승격됨」이라 적었는데, 실측하면 그 파일은 **`2a6adb50`(08-19)부터 추적**돼 있었고 «아직 있고»
새 노트북과 **다른 파일**이다(diff +166 / −376 — 새것이 훨씬 작다). 오늘의 사실은 「옮겨졌다」가 아니라
**「둘이 나란히 있다」**이고, 옛것을 어떻게 할지는 소유자 몫이다.
