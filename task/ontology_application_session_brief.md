# 온톨로지 «응용» 기획 세션 — 인수 지시문 (2026-08-20 개설)

**이 파일이 그 세션의 출발점이다. 대화 없이 이것만 읽고 시작할 수 있어야 한다.**

---

## 0. 당신은 무엇을 하는 사람인가

**원장에 쌓인 «원자»로 사람이 무엇을 할 수 있는지를 기획한다.**

```
하는 것    응용의 «질문»을 정한다 — 누가, 무엇을 알고 싶어서, 무슨 화면을 여는가
           이미 있는 응용이 그 질문에 답하는지 먼저 «재고», 안 답하는 만큼만 새로 세운다
           소유자 판정이 필요한 자리를 골라 올린다

안 하는 것 설정 스키마 · 검증기 · 작성 화면 — 그건 «온톨로지 설정» 포크(별도 세션)의 소관이다
           직접 구현 — 지시서를 쓰고 구현자에게 넘긴다
```

🔴 **설정을 고치고 싶어지면 멈추고 말한다.** 오늘(2026-08-20) 설정 모양이 세 번 바뀌었다.
그 라인은 다른 세션이 잡고 있고, 두 세션이 같은 파일을 만지면 라이브 설정이 깨진다.

## 1. 🔴 착수 전 관문 — 예외 없음 (`CLAUDE.md` 상설)

```
① 최소 수정      바뀌는 층만. 주변 인터페이스·호출자·이름은 그대로
② 단순 로직      지금 필요 없는 일반화·추상·설정 축을 만들지 않는다
③ 무분별한 기능 추가 절대 금지    지시받지 않은 것은 만들지 않는다. 필요해 보이면 «말하고 기다린다»
```

**그리고 소유자 정정:** ①②③은 **코드 관점**이지 «요구사항을 자르는 근거가 아니다».
목표는 소유자가 말한 도착지 그대로이고, 관문은 거기에 **가장 적은 코드로** 가라는 뜻이다.
**「목표달성 못하면 말짱꽝」** — 도착 못 하는 수정은 작은 게 아니라 0이다.

## 2. 지금 «이미 있는» 것 — 여기서 시작하지 않으면 다시 만들게 된다

🔴 **이 목록이 이 지시문의 핵심이다.** 오늘 하루의 가장 큰 낭비가 「있는 것을 없다고 읽는 것」이었다.

## 3. 원자가 실제로 무엇인가 — 응용의 재료

```
한 원자 = 「누가 · 무엇을 · 언제 · 무엇에 대해」
   subject_type · subject_keys      누가          예: Lot / {lot: "A12"}
   predicate                        무엇을         예: has_wafer@1
   object_payload                   무엇에 대해
   occurred_at                      언제
   source_translator_ver            «어느 선언 세대»가 만들었나
   source_raw_ref                   어느 원본 행에서 나왔나
중복 판정 (uq_ledger_atom)  occurred_at · predicate · subject_type · subject_keys ·
                            object_payload · source_translator_ver · source_raw_ref
```

🔴 **`source_translator_ver`가 중복 판정에 들어간다.** 선언이 바뀌면 같은 사실이 «새 행»으로
쌓인다. 소유자 판정(2026-08-20): **「원장이니 append가 맞다. 갈아치우는 건 아니다.」**
응용은 **같은 사실의 여러 세대가 공존한다**는 전제로 설계해야 한다.

⚠️ **오늘 시점에 원장은 «안 나가고 있다».** 설정 모양이 바뀌면서 커서가 무효화됐고,
리셋 명령이 아직 없다. 보드의 「커서」 항목을 볼 것. **응용을 「지금 데이터가 있다」는 전제로
기획하기 전에 실제 행 수를 세라.**

## 4. 채널

```
소유자     한국어로 직접 지시한다. 양쪽 세션에 각각 말할 수 있다
총괄(온톨로지 설정 포크)   설정·화면 라인. 같은 파일을 만질 일이 생기면 «먼저 확인»
구현자      지시서를 받아 구현한다. 파일이 정본이고 메시지는 알림일 뿐이다
```

🔴 **파일이 정본, 메시지는 «샌다».** 오늘 채널이 세 번 샜다. 판정은 반드시 파일에 박는다.
🔴 **보고는 자연어로.** 코드명(T1·F2 같은 라벨)은 에이전트끼리만. 소유자에게는
**목표 → 필요 → 문제 → 완료** 서사로.

## 6. 첫 걸음 — 이것부터 하고 소유자에게 물어라

```
1  §2의 다섯 모듈과 다섯 화면을 열어 «각각 무슨 질문에 답하는지» 한 줄로 적는다
2  SCENARIO_CONSOLE_BRIEF 를 읽고 소유자가 이미 정의한 응용의 «도착지»를 적는다
3  원장 실제 행 수와 predicate 분포를 «센다» (없으면 없다고 적는다 — 추정 금지)
4  그 셋을 놓고 소유자에게 «한 장»으로 보고한다:
     있는 것 · 도착지 · 그 사이의 간격
5  간격을 좁히는 첫 응용 하나를 «소유자가 고르게» 한다. 골라 주지 말 것
```

**⚠️ 1~3을 건너뛰고 응용을 제안하지 말 것.** 이 프로젝트에는 이미 응용이 다섯 개 있고,
그것들이 무엇을 답하는지 모르는 채로 여섯 번째를 세우는 것이 오늘까지 가장 비쌌던 실수다.
