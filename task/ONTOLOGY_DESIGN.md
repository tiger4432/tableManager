## Ⅰ. 설계 원칙 «여섯» — 전부 소유자 상설이고, 판별식이 있습니다

```
① 마킹은 질의의 «주어»다
   「마킹한 노드의 하위 그래프를 데이터로 들고 온다」 · 「마킹은 결국 서브그래프 탐색」
   판별식  부품이 «거르나» 걷나 -> 거르면 어긴 것. collect 를 고쳐라

② 술어가 «아닌» 것은 표면적으로 «노드»다                          (2026-08-27)
   판별식  이게 술어인가? -> 엣지.  아니면 -> 노드.  제3의 축을 만들지 마라
   경계    표면 = 고르고 찍는 자리. 응답의 배관 칸은 표면이 아니다

③ 선언이 «정본»이다 — 코드는 «문법»만
   판별식  이 값이 바뀌면 «답»이 바뀌나 -> 선언.  «쓸 수 있는 것»이 바뀌나 -> 검증기

④ 라우트를 더 파지 마라 — 늘어야 하는 것은 «선언»이지 갈래가 아니다
   판별식  이 라우트가 «키»를 받나 «마킹»을 받나 -> 키를 받으면 그 키마다 한 번씩 불린다

⑤ walk 통일 = 모든 부품이 «한 로직»                                (소유자 2026-08-27)
   판별식  `bindLoaders` 에 «부품 이름을 보는 분기»가 있나 -> 있으면 아직 한 로직이 아니다

⑥ 부재는 «셋»으로 말한다
   아직 안 골랐다 · 서버가 못 답한다 · 걸었는데 없다.  한 낱말로 합치면 화면에서 못 읽는다
```

## 🔴 원칙 ②의 «목적» — 걷기로 «확장»하기 위해서다 (소유자 2026-08-27)

> 「너가 포인트로 말한 디펙도 **디펙의 종류 모델링 등 다른 관계 및 노드, 물리적 모델링이 붙을 수 있음**」
> 「**이 모든 것은 걷기 알고리즘을 통한 확장성을 위한 것**」

```
노드면    걸어서 «나갈 수» 있다 -> 나중에 무엇이든 «붙일 수» 있다
종점이면   거기서 «끝»이다 -> 붙일 자리가 없다. 붙이려면 «구조를 바꿔야» 한다
```

### 실측 — 물리 모델이 «이미 일곱» 있는데 «수식어»로 눌려 있다
```
선언   observed@1 목적어 = {kind:"value",
       qualifiers.optional: [gate · unit · run_uid · inchip_x · inchip_y · radius_y · finding_kind]}
원자   {"value": 7.691,
        "qualifiers": {"gate":7.0, "unit":"um", "run_uid":"sat|SYN-AUG-BW-001-01|10|10|7|…",
                       "inchip_x":7475.16, "inchip_y":4857.94, "radius_y":7.591,
                       "finding_kind":"void"}}
투영   schema_kind = «"terminal_finding_point_projection"»
       🔴 코드가 자기 이름에 «terminal» 이라고 적어 두었다
```

### 그 일곱이 «전부» 붙을 수 있는 것들이다
```
finding_kind        -> 「종류」 노드 (void · delam · non_wet). 종류에 «판정 기준»이 붙는다
run_uid             -> 「스캔」 노드 (언제 · 어느 장비 · 어느 레시피로 봤나)
inchip_x/y · radius · gate · unit  -> 「물리 모델」 (칩 안 좌표 · 크기 · 게이트 · 단위)
```
발견이 «노드»면 이렇게 걷힌다:
```
마킹1 웨이퍼 ─walk→ 발견들 ─찍기→ 마킹2
마킹2 발견   ─walk→ 종류 · 스캔 · «같은 스캔의 다른 발견» · «같은 종류의 다른 발견»
```
지금은 «마킹2 에서 나갈 곳이 없다». 그래서 「보이드 있던 wf 의 cmp rcp 로 진행한 wf 의 보이드」
같은 질문이 «웨이퍼를 거쳐서만» 돌아간다.

### 그래서 원칙 ②는 «이름 바꾸기»가 아니다
```
❌ 작은 판    type: "Finding Point" -> "void"     (화면 낱말만 바뀐다. 종점은 그대로다)
✅ 진짜 판    발견이 «주어가 될 수 있는 노드»가 된다
             -> 선언에 발견 엔터티 · observed 의 목적어가 entity_ref
             -> 수식어 일곱이 «엣지와 속성»으로 풀린다
             -> 그때 「종류에 무엇이 붙는다」를 «선언 한 줄»로 더할 수 있다  <- 이것이 확장성이다
```
⚠️ 크기가 커집니다. 그래서 계획 2단계의 «멈춤 조건»이 그대로 유효합니다 —
   발견 종류가 선언에 없으므로, 거기서 멈추고 «무엇을 선언에 넣을지»를 올리는 것이 먼저입니다.
   다만 목적지는 이제 분명합니다: **종점을 없애는 것**이지 이름을 고치는 것이 아닙니다.
