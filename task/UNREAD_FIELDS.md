# 폼이 «그리는데» 읽는 쪽도 받는 쪽도 없는 칸 — 전수

총괄 지시(`f4214a26`). 소유자가 «화면에서 직접» 보신 것에서 나온 부류입니다.
**부류 이름은 CODE_MAP 이 먼저 붙였습니다** — 「문법은 살아 있는데 «읽는 쪽»이 없다」.

```
먼저 본 것   상설(`f93bca47`)대로 `docs/architecture/CODE_MAP.md` §5-H-bis 를 «먼저» 열었습니다
            (스켈레톤 절 · 구현 발견자 절 · §5-H 의 `references` 문단)
그다음 잰 것  스켈레톤의 choice 슬롯 «여섯» + 씨앗 둘. 칸마다 «세 줄»로
증거의 성질   스켈레톤·검증기·실행은 «커밋된 코드»입니다 -> 운영에도 참입니다
            출하 샘플은 «모양»으로만 인용합니다
```

---

# 🔴 답 — **여섯 중 «넷»은 깨끗합니다. 걸린 것은 «셋»이고, 셋이 «서로 다릅니다»**

| 칸 | ① 폼이 그리나 | ② 검증기가 받나 | ③ 읽는 쪽 | 판정 |
|---|---|---|---|---|
| 중첩 식별키의 `entity` | ✅ (재귀) | ✅ «좁힘 없음» | ⚠️ 있는데 «더 좁다» | 🔴 부류 |
| `predicate_status` | ✅ | ✅ | ✅ 있음 | ✅ 깨끗 |
| `object_kind` | ✅ | ✅ | ✅ 있음 | ✅ 깨끗 |
| `source_unit` | ✅ | ✅ | ✅ 있음 | ✅ 깨끗 |
| `mapper_unit` | ✅ | ✅ | ✅ 있음 | ✅ 깨끗 |
| `occurred_at_basis` | ✅ | ✅ | ✅ 있음 | ⚠️ «다른» 결함 |
| `references` (씨앗 ①) | ✅ | ✅ | ❌ «0» | 🔴 부류 |

---

## ✅ 깨끗한 넷 — «왜» 깨끗한지 적습니다 (안 재고 넘기지 않았습니다)
```
predicate_status  값 둘(활성 · 은퇴). 🔵 읽는 쪽이 «있습니다» — 은퇴한 술어를 매핑이 쓰면
                 그 매핑이 «거절»됩니다. 즉 「은퇴」를 적으면 «무언가 달라집니다»
                 출하 샘플의 모양: 전부 활성 -> 은퇴가 «안 쓰인 것»이지 «안 읽히는 것»이 아닙니다
object_kind      값 넷. 샘플이 «셋»을 쓰고, 넷째도 값을 나르는 역할로 «매핑돼» 있습니다
source_unit      값 둘. 샘플이 «둘 다» 씁니다
mapper_unit      값 셋. 샘플이 «셋 다» 씁니다
```
🔴 **여기서 「샘플에 안 쓰였다」를 「읽는 쪽이 없다」로 읽지 않았습니다.** 그 둘은 다른 문장이고,
   ③은 «코드»에서 봤습니다.

---

# 🔴 걸린 것 셋 — 셋이 «다른 병»입니다

## ① `references` — 「뒤가 «없다»」
```
① 폼    ✅ 그립니다 (엔티티 밑 · 최근에 생겼습니다)
② 검증기 ✅ 받습니다 (전건 검사까지 합니다)
③ 읽는 쪽 ❌ «0» — 걷기가 이름을 못 대고, 투영의 합성 엣지도 없습니다
모양    출하 샘플의 엔티티 아홉 중 이것을 «선언한 것 0»
```
📎 CODE_MAP 이 이미 다섯 층으로 적어 뒀습니다 — 「폼이 묻는다」를 「돌아간다」로 읽지 말라고.
   **제가 더할 것이 없습니다.** 이 줄은 «확인»입니다.

## ② 중첩 식별키의 `entity` — 「뒤가 «좁다»」  🔴 이게 소유자가 보신 것입니다
```
① 폼    ✅ 그립니다. 🔴 그리고 «재귀»입니다 —
        엔티티 바인딩의 식별키 하나하나가 «또» 바인딩이고, 그 칸이 «안 좁혀진» 목록을 받습니다
        -> 「엔티티의 키가 또 엔티티」가 «끝없이» 뜹니다
② 검증기 ✅ 받습니다. 역할별 좁힘은 «역할 자리»에만 걸리고 «중첩 키»에는 «안» 걸립니다
③ 실행   ⚠️ 있는데 «더 좁습니다» — 엔티티 참조를 만들 때 키를 «하나»만 씁니다
        (CODE_MAP 이 그 「키 하나」 계약을 이미 적어 뒀고, 그 때문에 옛 뷰가 필요했다는 사연까지 있습니다)
모양    출하 샘플의 바인딩: 컬럼 다수 · 상수 소수 · 엔티티 «0»
```
🔴 **그래서 이건 「아무 일도 안 일어난다」가 아니라 «더 나쁩니다»** — 폼이 권하고 검증기가
받아 준 것을 «실행이» 못 씁니다. 거절이 «가장 늦게», 가장 먼 자리에서 납니다.

## ③ `occurred_at_basis` — 「고를 것이 «없다»」
```
① 폼    ✅ 고르개로 그립니다
② 검증기 ✅ 받습니다
③ 읽는 쪽 ✅ «있습니다» — 이 칸은 제대로 읽힙니다
🔴 그런데  닫힌 목록의 값이 «하나»뿐입니다. 고르개가 «선택지 하나»를 내밉니다
```
=> 부류가 «아닙니다». 그런데 화면에서는 부류와 «똑같이» 보입니다 — 이상한 고르개입니다.
   고치는 값이 다릅니다: 여기는 「읽는 쪽을 만들라」가 아니라 「이게 고르개여야 하나」입니다.

---

# ⚠️ 덤 — 코드가 «자기 주석에» 적어 둔 넷째
검증기 안에 「이 가지는 발화할 수 없다」고 «스스로» 적힌 조건이 하나 있습니다(어떤 목록이
은퇴하면서 항상 비게 됐다는 사유). 🔴 **제가 «직접 재지는 않았습니다»** — 주석은 의도의 증거이지
동작의 증거가 아니라서, 「있다」가 아니라 「코드가 그렇게 적고 있다」로만 답니다.
그 가지는 폼에 «안 나옵니다». 그래서 소유자가 보신 부류와는 다른 자리입니다.

---

# 🔴 마지막 한 줄 — **셋은 «같은 부류가 아닙니다»**

```
references        문법 ✅ · 폼 ✅ · 읽는 쪽 «없음»      -> 「뒤가 없다」   고칠 것: 읽는 쪽 or 폼에서 내리기
중첩 식별키        문법 ✅ · 폼 ✅ · 실행이 «더 좁음»     -> 「뒤가 좁다」   고칠 것: 좁힘을 «중첩에도»
occurred_at_basis  셋 다 ✅ 인데 선택지가 «하나»         -> 「고를 것이 없다」 고칠 것: 고르개인지 자체
```
🔴 **화면에서는 셋이 똑같이 「이상한 목록」으로 보입니다. 그런데 고치는 값이 셋 다 다릅니다.**
그래서 하나로 묶어 티켓 하나로 내면, 둘은 고쳐지고 하나는 «다른 것이 고쳐집니다».

## 이 문서가 «안 한» 것
```
⛔ 고치지 않았습니다 · UI 설계 없음 · 이 박스의 «행 수» 없음 (샘플은 «모양»으로만)
🔴 ③(읽는 쪽)은 전부 «코드»에서 봤습니다. 「샘플에 안 쓰였다」를 「안 읽힌다」로 쓰지 않았습니다
⚠️ record 필드 중 «선택»인 것 전부를 훑지는 «못했습니다» — choice 슬롯 여섯과 씨앗 둘까지입니다.
   남은 것은 「선택 필드 전수」이고, 그건 다음 라운드 크기입니다
```
