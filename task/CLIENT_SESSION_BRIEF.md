## 2. 🔴 일하는 순서 — **목업 먼저, 코드는 그다음**

```
1  대상 화면을 «직접 본다»      실제로 열어 본다. 스크린샷·DOM 실측
2  무엇이 불편한지 «적는다»     추측 말고 관측. 「~할 때 ~가 안 보인다」
3  목업을 만든다                HTML/CSS 한 파일. task/design/<화면>_<주제>.html
4  소유자에게 «보여주고 기다린다»  Artifact 로 띄우거나 브라우저로 연다
5  승인 후에만 client2/src 를 고친다
6  빌드 -> 총괄에게 재기동 요청 -> «직접 걸어서» 확인 -> 보고
```

🔴 **4번을 건너뛰지 마십시오.** 승인 전 코드 수정은 되돌리는 비용이 훨씬 큽니다.
그리고 목업은 **한 번에 하나의 결정만** 묻습니다 — 다섯 개를 한 장에 담으면 아무것도 못 정합니다.

### 목업에 담을 것 / 안 담을 것
```
✔  실제 데이터 모양 (진짜 컬럼명 · 진짜 길이의 로트 번호 · 진짜 개수)
✔  «전»과 «후»를 나란히
✔  좁은 화면에서 어떻게 되는지
✖  lorem ipsum · 가짜 숫자 · 실제로 없는 기능
✖  「나중에 이렇게도 할 수 있습니다」  <- 지시받지 않은 것
```

## 3. 🔴 소유자 상설 — UI 원칙. 이게 이 세션의 «헌법»입니다

```
🔴 절대 복잡하면 안 된다
      새 영역 · 새 모드 · 모달 «금지».  읽기는 무마찰, 쓰기는 «1회 확인»
🔴 가독성이 «기능»이다
      작은 글씨는 «없느니만 못하다».  줄이려고 작게 만들지 말 것
🔴 문구는 번역체 금지
      기호 · 짧은 영어 · 명사형.  「~를 지지합니다」류 금지
      전체 문장은 «확정하는 한 곳»에만
🔴 칸 옆 문구는 «무엇을 하면 되는지»만
      설계 근거 · 미결 판정 · 파일 경로 · 에러 코드 원문 -> 화면에 내지 않는다
```

### 오늘(2026-08-21) 소유자가 실제로 겪은 것 — 같은 실수를 반복하지 마십시오
```
「이럴 거면 드롭박스를 하지, column 을 나열하는 게 무슨 의미」
   -> 후보가 «보이는데 못 고르는» 칸.  나열은 선택이 아니다
「dt_cell_key 쓰라는 거면 그냥 미리 넣어두면 되지, 뭐 저래 모호하게 적어놨어」
   -> 기본값은 «보여주는» 게 아니라 «들어가 있어야» 한다
      「덮어쓸 수 있음」은 채워진 칸에 붙는 말이지 빈 칸에 붙는 말이 아니다
「구조를 못 외우겠다」 · 「값이 없으면 빈 폼으로 하위 구조가」
   -> 사람이 밖에서 알아야 하는 것이 있으면 그건 화면이 덜 된 것이다
```

🔴 **그리고 이것 — 오늘 총괄이 밤을 태운 오독입니다:**
```
「접힌 컨트롤은 «없는» 컨트롤이 아니다」
   폼이 못 푸는 칸이라고 판정했는데 «두 겹 접힘 아래» 있었다
   -> 「없다」고 적기 전에 «다 펼쳐 보고» 적는다
```

## 5. 🔴 공유 트리 — 오늘까지 이걸로 사고가 «여섯 번» 났습니다

세션 여럿이 **하나의 working tree**를 공유합니다.

```
✔  git add <경로>            경로를 «하나씩»
✔  git commit ... -- <경로>  🔴 commit 에도 경로를 붙인다
                             안 붙이면 «인덱스 전체»가 간다 — 실제 사고 있었음
✔  커밋 전 git diff --cached --name-only 로 «담길 것»을 눈으로 센다
✔  백틱이 있는 커밋 메시지는 `-F` 파일로 (셸이 백틱을 «실행»한다)

✖  git add -a / -A / 디렉터리째
✖  git stash · checkout -- · reset --hard · clean
      🔴 «트리 전체»를 건드립니다. 남의 미착지 작업이 사라집니다
      빨강의 주인을 가릴 땐 git diff -- <파일> 로 «읽습니다». 아무것도 안 건드립니다
```

🔴 **파일을 프로그램으로 자르거나 갈아 끼우면 «바뀐 줄 수»를 찍고 예상과 대조하십시오.**
오늘 총괄이 78줄 교체를 하려다 **643줄을 지웠습니다.** `git status` 는
「M 하나」로 똑같이 조용했습니다. `--name-only` 도 못 잡습니다 — 파일이 하나니까요.

> 소유자 지시: 「세션 간 메시지가 에러를 유발하는 것 같다. **지시문 커밋 기반으로** 통신 돌려」

```
총괄 → 당신    task/DESIGN_ORDERS.md            «지금 할 것»만
당신 → 총괄    task/design_session_report.md     보고 · 질문 · 판정 요청
공통           일 시작 전 git pull → 쓴 뒤 commit + push
               🔴 커밋이 «초인종»입니다
```
- 착수 전·보고 전에 `DESIGN_ORDERS.md` 를 다시 읽습니다.
- 판정 요청은 보고 파일 **맨 위**에 「🔴 판정 요청」.
- 두 파일이 아직 없으면 **보고 파일을 만들면서 시작**하십시오.

## 9. 🔴 착수 전 관문 — 소유자 상설, 예외 없음

```
① 최소 수정      바뀌는 층만. 주변 인터페이스·호출자·이름은 그대로
② 단순 로직      가장 단순하게 도는 것. 지금 필요 없는 일반화·추상·설정 축 금지
③ 지시 안 받은 것 만들지 않기   가드·테스트·헬퍼·「나중을 위한」 훅 전부 포함
```
🔴 **셋은 «코드» 관점입니다. 요구사항을 깎는 근거가 아닙니다.**
목표는 소유자가 말한 도착지 그대로이고, 관문은 **거기에 가장 적은 코드로** 가라는 뜻입니다.
소유자 원문: **「목표달성 못하면 말짱꽝」.**

**필요해 보이는데 지시받지 않았으면 — 만들지 말고 «말하고 기다립니다».**

🔴 **디자인 세션이 특히 조심할 것:** 「이왕 하는 김에」가 이 세션의 가장 큰 위험입니다.
한 화면을 고치러 들어가서 **옆 화면까지 손대지 마십시오.** 부류로 판정하되,
**고치는 것은 지시받은 범위**입니다. 같은 병이 옆에 넷 더 있으면 **보고에 적고 기다립니다.**

## 10. 시작하는 법

```
1  이 파일과 CLAUDE.md 를 읽는다
2  git pull
3  task/DESIGN_ORDERS.md 가 있으면 읽는다. 없으면 총괄의 첫 지시를 기다린다
4  task/design_session_report.md 를 만들고 「인수 완료 · 대기 중」 한 줄을 적고 push
   -> 그 커밋이 총괄에게 «당신이 살아 있다»는 신호입니다
```

**첫 라운드 전에 무엇을 할지 확인하십시오. 스스로 일감을 만들지 않습니다.**
화면이 여럿이라 「개선할 것」은 무한히 보입니다 — **순서는 소유자와 총괄이 정합니다.**
