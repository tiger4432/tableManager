# 체인 통합 계획안 — 「가상 조인·enrich 는 체인을 «선언하는 한 방법»」

## 0. 명제 — 「**행 하나는 사실 하나**」 (소유자 2026-09-15)

> 「결국 최종 목표는 하나야 — **행 하나는 사실 하나**」
> 「난 항상 단순한 설계를 지향해. 그래야 고장도 안 나고 빠르거든」

이 한 줄이 아래 전부의 «이유»다. 통합도, 유일 키도, 실물화도 이 문장의 «따름정리»다.

```
행      «사실» 하나. 그 사실이 무엇인지 말하는 것이 «신원»(키)이다
칸      그 사실에 대한 «주장». 주장마다 «누가 말했나»(source layer)가 붙는다
원장    그 사실들을 원자로 번역한다 — 그러려면 사실이 «어딘가 행으로» 있어야 한다
```

### 0.1 이 문장이 «금지»하는 것 넷 — 그리고 넷 다 오늘 실물로 있다

```
① 두 행이 한 사실           = 사본. 신원이 «없거나 좁다»
   실물: 평키 표가 business_key_val 을 안 채워 매 실행마다 사본이 앉았다 (S-226)
② 한 행이 두 사실           = 신원이 «사실보다 좁다»
   실물: dt_log 의 400 행이 같은 dt_job_id 를 쓰면서 셀 좌표가 다르다.
        카탈로그는 신원을 (dt_job_id, b_wx, b_wy) 로 적는데 조인은 dt_job_id 하나로 물었다
        -> 그 유일 인덱스는 «영원히» 안 선다. 접어도 안 된다 — 접으면 셀 399개가 사라진다
③ 어느 사실도 아닌 행        = 신원이 «비어 있다»
   실물: 한 컬럼의 빈 키가 수십만 행. 중복이 아니라 «부재»다 (상설: 길이 0 문자열은 NULL)
④ 행이 없는 사실            = 읽을 때만 존재하는 값
   실물: 가상 조인 컬럼. 원장이 «볼 수 없어서» 번역 대상이 못 되고, 그래서 walk 의
        주어도 마킹도 이력도 없다. 이것이 「원장 번역을 복잡하게 만든다」의 실체다
```
🔴 **①~④ 가 다른 사고로 보였는데 한 문장의 네 가지 위반이다.** 그래서 수리도 하나다 —
   «사실의 신원을 제대로 세우고, 사실을 행으로 있게 한다».

### 0.2 그래서 따라오는 것 (새 규칙이 아니라 «따름정리»)

```
유일 키를 기계가 세운다 (S-235)    ①②③ 을 «구조적으로 불가능»하게 만드는 장치다.
                                 그리고 못 세우면 그것은 「데이터가 더럽다」가 아니라
                                 **「신원 선언이 틀렸다」**는 신호다 — 그래서 접기 전에 가른다
실물화를 기본으로                  ④ 의 해소. 값이 행의 칸이 되고 «누가 말했나»가 층으로 붙는다.
                                 층이 있으므로 실물화가 「한 행에 두 사실」이 되지 «않는다» —
                                 행은 여전히 한 사실이고, 칸은 그 사실에 대한 출처 붙은 주장이다
선언 표면이 하나                   같은 사실을 세 문법이 각자 만들면 「누가 그 행의 저자인가」가 셋이 된다
```
⚠️ 그리고 이 명제가 **쓰기 가상화를 이미 기각한다**(§6) — 읽기 시점에만 있는 값은 ④ 그 자체다.

## 1. 도착지 — 한 줄

> **제품에 있는 것은 «체인 규칙» 하나다. `enrichment_rules.json` 과 `virtual_join_rules.json` 은
> 그것을 «적는 다른 문법»이지, 별도 생성기도 별도 수명주기도 아니다.**

🆕 **[2026-09-15 소유자 판정] 가는 «길»이 바뀌었다 — 「이행」이 아니라 「하나씩 새로」.**
```
종전 계획   옛 세 문법을 «새 문법으로 옮긴다»(이행) -> 옛 껍데기를 은퇴
오늘 판정   통합 선언에 «종류를 하나씩 새로» 넣는다 — join 먼저, enrich·mapper 는 그 뒤
           옛 껍데기는 그 종류가 «다 옮겨진 뒤» 통째로 버린다
🔴 차이가 «이행 도구»다: 기계가 옛 선언을 새 문법으로 써 주는 4단계(3단계)가 «필요 없어진다».
   대신 각 종류마다 「새 자리가 옛 자리와 같은 답을 내나」를 한 번씩 증명한다
⛔ 그리고 이번 라운드에 «가상 조인은 무접촉»이다 — 짓는 것은 통합 선언 쪽 join 종류뿐(S-237)
```

🔵 **새 발명이 아니라 «미완의 통합을 끝내는 것»이다.** 오늘도 두 파일은 체인 규칙을 «만들어» 낸다
(`chain/builtins.synthesize_chain_rules` → `enrichment.config.load_enrichment_chain_rules` +
`virtual_join.config.synthesized_join_chain_rules`). 갈라진 것은 **생성 이후**다 — 이름·끄기·거절·순서·로그가 각자 논다.

## 2. 모양 (제안)

셋을 가르는 것은 «종류»가 아니라 칸 **둘**이다 — 「값을 어떻게 얻나」와 「어디에 앉나」.
그리고 후자는 **이미 값이다**: 가상 조인의 `materialize` 가 읽기 조인을 쓰기로 바꾼다.

```jsonc
{
  "name": "dt_log_frame",
  "enabled": true,

  "on":     { "table": "dt_log", "columns": ["b_wx","b_wy"] },   // ③ 컬럼 트리거는 «이미 있다»(S-140)

  "derive": { "mapper": "frame_map", "params": { } },
  //        | { "join":   { "table": "...", "on": {...}, "take": [...], "fold": {...} } }
  //        | { "decide": { "key": [...], "contract": "..." } }

  "into":   { "table": "dt_inventory" },     // 저장
  //        | { "read": true },              // 읽기 시점 (옛 가상 조인)

  "key":    { "columns": ["dt_job_id","b_wx","b_wy"], "unique": true },

  "limits": { "group_by": null, "max_group_rows": null,
              "max_group_attempts": null, "idempotent": true }
}
```

| 오늘 | 새 모양 |
|---|---|
| 체인 규칙 | `derive.mapper` + `into.table` |
| 가상 조인 | `derive.join` + `into.read` |
| 가상 조인 + materialize | `derive.join` + `into.table` ← **한 칸만 다름** |
| enrich (dedup · auto_confirm) | `derive.decide` + `into.table` |

### 완성의 정의 시험 (임의 스키마, 두 줄)
> 「**<이 표>에 쓰기가 나면 <이 방법>으로 값을 얻어 <여기>에 앉힙니다. 신원은 <이 컬럼들>입니다.**」

박스 컬럼 이름이 안 들어가고, 절차가 아니라 두 줄이다. **통과.**

## 3. 사라지는 것 (더해지는 것이 아니라)

```
충돌 검사기 «둘»   enrichment_name_collisions · join_name_collisions  -> «삭제»
                 (겹침을 «단속하는 기계»가 있다는 것이 곧 겹치면 안 되는 것이 겹쳤다는 자백)
enabled          세 곳 -> 한 곳          「다 껐는데 왜 나냐」가 «참일 수 없게» 된다
거절 어휘         셋 -> 하나
부팅 로그         둘 -> 하나 (규칙 목록 «하나»)
순서(S-156)      일부 -> «전부»에 걸림
```

🔴 **이 목록이 이 라운드의 «증거»다.** 통합이 끝났는데 저 둘이 남아 있으면 통합이 안 된 것이다.
🆕 **[2026-09-15] 목록은 그대로 유효하고 «시점»만 뒤로 간다** — 위 판정대로 옛 껍데기는 종류가 «다 옮겨진 뒤» 통째로 버리므로, 이 다섯은 join·enrich·mapper 셋이 다 새 자리에 선 «그날» 한꺼번에 사라진다. 중간에 하나씩 사라지지 않는다는 뜻이고, 그래서 **중간 상태에서는 이 목록으로 진척을 재지 못한다**.

## 4. 단계 — 각 단계는 «동작 0» 이고, 각 단계에 되돌리기가 있다

> ⚠️ 2026-09-14 의 사고 넷은 **전부 「급하게 지은 엄격함」**이었다. 그래서 이 계획의 0단계는 기능이 아니다.

### 0단계 — 호환성 하니스 «먼저» (기능 0)
「어제 돌던 선언이 오늘도 **같은 결과**를 낸다」를 자동으로 재는 것.
```
입력  선언 스냅샷(세 파일)
출력  규칙 목록 · 이름 · trigger/target · 순서 · enabled 상태
게이트 변경 전후가 «같음». 다르면 그 줄을 이름 대어 보여 준다
```
🔴 **이것이 없으면 1~5단계 전부가 오늘의 재현이다.** 먼저 짓는다.

### 1단계 — 읽기 통합 (문법은 그대로, 파일도 셋 그대로)
로더 하나가 세 출처를 읽어 **하나의 목록**을 낸다. 이름공간·`enabled`·거절 어휘·로그를 통일.
**게이트**: 0단계 비교가 「같음」 · 부팅 로그가 규칙 목록 하나를 찍음.

### 2단계 — 모양 통일 (새 문법을 «읽을 수 있게»)
새 문법(§2)과 옛 세 문법을 **둘 다** 읽어 «같은 내부 규칙»을 만든다.
**게이트**: 같은 선언을 옛 모양/새 모양으로 적으면 내부 표현이 «동일».

### 3단계 — 이행 (기계가 «써 준다»)
옛 세 파일을 읽어 새 한 파일로 **제품이** 옮긴다. 원본은 보존(되돌리기).
🔴 운영자는 손으로 옮기지 않는다 — 소유자 판정 ②의 적용.
**게이트**: 이행 전/후 규칙 목록·순서·대상이 동일.

### 4단계 — 한 파일만 (옛 문법 은퇴) — «통째로» 착지
충돌 검사기 둘 **삭제**. 옛 로더 은퇴.
**게이트**: 그 두 함수가 사라지고 전 스위트 초록 · §3 목록이 실제로 비었음.
⚠️ 이 단계는 쪼개 착지하면 그 사이가 «거짓»이다(관통 변경은 통째로).

### 5단계 — 유일 키를 «기계가» (S-235)
선언이 `key.unique` 라고 말하면 제품이 그 유일성을 **성립시킨다**.
```
① 인덱스를 제품이 만든다 (CONCURRENTLY · 멱등 · 취소 잔해 INVALID 는 스스로 걷어냄)
② 중복이 막으면 «접는다» (소유자 판정 ③) — 기준은 선언 가능하게, 기본은 updated_at 최신 → row_id
③ 접은 것을 «보고»한다. 조용한 삭제 금지. 되돌릴 수 있게 남긴다
④ 그래도 실패하면 운영자에게 «DDL 이 아니라 사실»을 준다 (무슨 키가 몇 건)
```
**게이트**: 중복 있는 표에서 인덱스가 서고 · 접은 목록이 보고되고 · 아무것도 조용히 사라지지 않음.

## 6. 쓰기 가상화 검토 결과 — **안 한다**

| | |
|---|---|
| 가상화가 주는 것 | 소급 비용 0 · 오늘 사고 부류(유일 키·사본·배치 사망·큐 막힘)가 «불가능» |
| 그런데 비용이 비대칭 | `join` 은 **SQL** 이라 DB가 한다. `mapper` 는 **파이썬**이라 읽기마다 돈다(맵 20×20 · 동시 10명) |
| 더 큰 것 | **원장이 못 본다.** 원장은 «표»를 읽는다 → 읽기 시점에만 있는 값은 walk 의 주어가 못 되고 마킹·이력이 없다. 「종점을 없앤다」와 정반대 |

**노린 효과는 따로 얻는다**
```
소급이 비싸다        -> 바뀐 것만 다시 돌기(rescope)   ✅ 이미 있음 (제품 6파일)
커밋 전에 보고 싶다   -> «미리보기»                    🔴 없음 (어제 은퇴한 dry-run 은 「양쪽 다 거절」이라 미리보기가 아니었다)
```
📌 그래서 후속 안건: **미리보기**(선언을 켜면 몇 행이 어떻게 바뀌나를 «쓰지 않고» 보여 준다).
   그것이 2026-09-14 사고의 «예방책»이기도 하다 — 어젯밤 저는 「어제 돌던 게 오늘도 도나」를 볼 자리가 없었다.

## 8. 2단계 설계안 — 「내부 표현 하나」 (2026-09-14 밤, 짓기 «전» 검토용)

### 8.1 문제를 정확히

0·1단계를 지으면서 드러난 것: **조인의 내부 표현은 오늘 «체인 규칙 dict 가 아니다».**

```
체인 규칙   워커 루프가 걷는 dict  — trigger_table · target_table · mapper · params · limits
가상 조인   실행기가 걷는 dict     — left/right_table · right_columns · right_folds ·
                                cardinality · expose · materialize · unique_index
enrich     이미 «체인 규칙으로 합성»된다 (load_enrichment_chain_rules)
```

그래서 「새 문법을 읽으면 옛것과 같은 내부 규칙이 나온다」를 증명하려면 **그 «같은 것»이 무엇인지부터**
정해야 한다. enrich 는 이미 접혔고(#3 → #1), 남은 것은 **조인**이다.

### 8.2 관찰 — 두 소비자가 «같은 객체»를 다른 칸으로 고른다

조인이 체인과 다른 것은 «종류»가 아니라 **어디에 앉느냐**뿐이다. 그리고 그 축은 이미 값이다
(`materialize` 가 읽기 조인을 쓰기로 바꾼다). 그러므로:

```jsonc
{
  "name": …, "enabled": …,
  "on":     { "table": …, "columns": [...] },
  "derive": { "kind": "mapper" | "join" | "decide", …종류별 짐… },
  "into":   { "table": … }  |  { "read": true },
  "key":    { "columns": [...], "unique": true },
  "limits": { … }
}
```
```
워커 루프    into.table 이 있는 규칙을 «고른다»
읽기 경로    into.read 이고 derive.kind == "join" 인 규칙을 «고른다»
=> 한 객체, 두 소비자. 「종류」가 아니라 «칸»으로 갈린다
```
🔵 이미 그 축을 읽는 함수가 있다 — `chain/rule_census.derive_kind` 가 세 문법을 «한 낱말»로 읽는다
(0단계에서 지었고 시험이 있다). 그것이 이 표현의 씨앗이다.

### 8.3 🆕 **[2026-09-15 판정으로 다시 씀] 안전한 순서 — «새 종류 먼저, 옛 껍데기는 마지막에 통째로»**

```
① 통합 선언에 join «종류»를 새로 짓는다 (S-237). 옛 가상 조인은 «무접촉»
② 게이트 = 「같은 뜻을 새 자리에 적으면 옛 자리와 «같은 답»을 낸다」
   -> 왕복 동일성(옛 dict 로 되돌리기)이 «아니라», 두 선언의 «답»을 견준다
③ enrich·mapper 종류도 같은 방식으로 하나씩
④ 셋이 다 선 뒤에 옛 껍데기 셋을 «통째로» 버린다 — 그때 §3 의 다섯이 한꺼번에 사라진다
```
🔴 **종전 8.3 의 어댑터 왕복은 «이행»을 전제한 설계였다.** 이행을 안 하므로 옛 dict 로 되돌릴 이유가 없고, 증거의 자리가 「같은 dict 인가」에서 **「같은 답인가」**로 옮겨간다.
⚠️ 그래서 «잃는 것»이 하나 있다: 왕복 동일성은 «기계가» 채점했는데, 「같은 답」은 **픽스처가 그 답을 부르는 자리까지 걸어야** 채점된다. 그 픽스처가 이 단계의 첫 산출물이다.

### 8.4 이 설계가 «안» 하는 것

```
⛔ 조인 실행기의 SQL 을 건드리지 않는다 — 팬아웃 가드(유일 인덱스)는 그대로다
⛔ 소비자를 «같이» 옮기지 않는다 — 하나씩, 각각 census 게이트
⛔ 새 문법을 «강제»하지 않는다 — 옛 세 문법은 3단계 이행이 끝날 때까지 계속 읽힌다
```

### 8.5 남은 판단 (소유자·총괄)

```
① `expose`(조인이 «어느 컬럼을» 올리나)는 derive.join 의 짐인가, into 의 짐인가
   -> 제안: derive.join. 「무엇을 가져오나」는 값을 얻는 방법의 일부다
   ✅ **[2026-09-15] 답: `derive.join.take`** (8.6 ㉠)
② 유일 인덱스 이름(`unique_index`)은 선언의 칸이 아니라 «제품이 채우는 사실»이다
   -> 그러므로 내부 객체의 «파생 칸»이지 문법의 칸이 아니다 (S-235 가 그것을 세운다)
③ `materialize` 는 into.table 로 접히는가, 별도 칸으로 남는가
   -> 제안: into.table 로 접는다. 그것이 「한 칸만 다르다」의 실체다
   ✅ **[2026-09-15] 답: 접는다 — `materialize` 는 «칸 자체가 없다»** (8.6 ㉠)
```

### 8.6 🆕 통합 `join` 선언이 «들어야 하는 칸» — 오늘 가상 조인에서 (2026-09-15, D-37 ②)

> **이 표가 구현자 ㉠ 번역의 «입력»이다.** 출처는 둘뿐이다 — 출하 선언
> `server/config/sample/virtual_join_rules.json.sample` 과 정규화기 `server/virtual_join/config.py`.
> 🔵 **«선언 칸»과 «파생 칸»을 먼저 갈랐다** — 정규화 결과 dict 는 칸 «열여덟»인데
> 검증기가 날것에서 «읽는» 칸은 «아홉»이다(`_validate_join` 의 `raw.get` 전수). 나머지 아홉은
> 제품이 채우는 사실이므로 **새 문법의 칸이 아니다**(8.5 ② 와 같은 부류).

#### ㉠ 선언 칸 «아홉» + 이름

| 옛 칸 | 새 자리 | 근거 |
|---|---|---|
| (dict 키) | `name` | 오늘도 규칙 이름은 «키»이지 칸이 아니다 |
| `enabled` | `enabled` | §3 의 「세 곳 → 한 곳」이 이 칸이다 |
| `left_table` | `on.table` | 「이 규칙이 «어느 표에» 걸리나」 — 트리거 쪽 |
| `join_key[].left` | `on.columns` **와** `derive.join.on` 의 왼쪽 | 🔴 **한 값이 두 자리에 쓰인다** — 트리거 컬럼이면서 조인 키다. 오늘은 그 둘이 같은 것이 «우연히» 참이고, 새 문법은 그것을 «말하게» 된다 |
| `right_table` | `derive.join.table` | 값을 얻어 오는 쪽 |
| `join_key[].right` | `derive.join.on` 의 오른쪽 | |
| `expose` | `derive.join.take` | 8.5 ① 의 제안대로. 「무엇을 가져오나」는 값을 얻는 방법의 일부 |
| `join_cardinality` (오늘 값은 `"one"` «하나») | `key.unique: true` | 정규화기가 `"one"` 이 아니면 «거절»한다(:411) — 즉 오늘 이 칸은 «상수»다 |
| `unresolved_label` (기본 `"미상"`) | **«없다»** | 🔴 못 찾은 값은 **null 이 null 이다**. 라벨은 «표시»이지 사실이 아니고, 그것을 선언에 두면 저장된 값이 「미상」이라는 문자열과 구별되지 않는다 |
| `materialize` (기본 false) | **칸 자체가 «없다»** | 8.5 ③ 대로 `into` 로 접힌다 — `into.read` 면 안 씀, `into.table` 이면 «항상» 씀 |
| `max_rewrite_rows` (materialize 일 때만 읽힘) | ⚖️ **판정 필요** — `limits` 인가, 페이싱으로 충분한가 | 오늘은 이 칸이 «거절의 근거»다(`no_rewrite_cap`: materialize 인데 상한을 안 적으면 규칙을 버린다). 페이싱으로 접으면 그 거절이 «사라지는» 것이라 동작이 바뀐다 |
| `__comment` | (버림) | 밑줄 접두는 로더가 «주석»으로 본다 |

#### ㉡ 파생 칸 «아홉» — 새 문법의 칸이 «아니다»

```
left_columns · right_columns          join_key 에서 뽑은 투영
right_folds · folded                  🔴 오늘 «선언이 아니다» — notation_norm.join_pair_rules 가 계산한다(:451)
collide · virtual_only                expose 중 왼쪽에도 있는 것 / 조인만 만드는 것
required_left_index · required_index · required_index_ddl    운영자가 만들 인덱스 (S-235 가 세운다)
```

#### ㉢ 🔴 이 표가 «드러낸» 것 둘 — 둘 다 새 문법의 «빈칸»이다

```
① §2 모양의 `derive.join.fold` 는 «옛 짝이 없다»
   오늘 fold 는 선언이 아니라 «계산»이다. 새 문법에 칸으로 두면 그것은 «새 축»이고,
   두지 않으면 새 문법이 오늘의 동작을 그대로 적을 수 있다. -> 판정 필요
② 가상 조인 선언에는 «알 수 없는 칸을 거절하는 자리»가 없다
   실측: `virtual_join/config.py` 전체에 허용 목록 0 — 오타 칸은 «조용히» 무시된다.
   S-152 가 맵퍼 인자에 세운 「선언 있으면 오타 거절」이 여기엔 «없다»
```
⚠️ **출하본이 `materialize` 를 «한 번도 안 쓴다»** — 출하 선언 둘 다 그 칸이 없어 기본값 false 다.
   즉 `materialize` 경로의 근거는 «출하본»이 아니라 «코드»다(S-189 ⓐ, `config.py:552~554`).

## 9. 마지막 단계 — 체인 선언 **UI** 에 새 모양 반영 (소유자 2026-09-14 「마지막으로 넣어」)

### 9.1 왜 «마지막»인가 — 순서가 규칙이다

```
✅ 모양이 서고 -> 폼이 «그 모양을 그린다»
❌ 폼이 먼저 그리고 -> 읽는 쪽이 나중
```
🔴 후자가 이 저장소의 «단골 결함»이다 — 「폼이 그리는데 읽는 쪽이 «없다»」(S-184 가 오늘도 그 상태).
선언 칸이 화면에 있는데 아무도 안 읽으면, 운영자는 «적었는데 아무 일도 안 일어나는» 경험을 한다.
그것이 S-221 이었고 S-152 였다. 그래서 UI 는 2~5단계가 착지한 «뒤»다.

### 9.2 어떻게 — 폼을 «짜지 않는다». 스켈레톤이 그린다

이 제품의 선언 폼은 **스켈레톤이 정한다**(작성 표면의 정본). 그러므로:

```
① 스켈레톤이 새 모양을 «선언»한다   on · derive(3중 택1) · into(2중 택1) · key · limits
② 폼은 그것을 «따라» 그린다        새 칸을 위한 화면 코드는 «0줄»이 목표
🔴 게이트: 새 칸을 그리려고 client2 에 «손으로 그린» 입력이 생기면 그 단계는 실패다
```
⚠️ 예외가 필요하면 그것이 «발견»이다 — 스켈레톤이 표현 못 하는 모양이 있다는 뜻이고,
   그때는 폼을 짜는 게 아니라 «스켈레톤의 빈칸»을 보고한다.

### 9.3 화면이 새로 말해야 하는 것 «셋»

```
① derive 는 «셋 중 하나»   mapper | join | decide — 고르면 아래 짐이 «바뀐다»
   (한 화면에 셋을 다 펼쳐 놓으면 운영자가 「무엇을 적어야 하나」를 못 고른다)
② into 는 «둘 중 하나»     표에 앉힘 | 읽기 시점 — 여기가 「한 칸만 다름」이 «보이는» 자리
③ 이 규칙이 «어느 문법»인가  옛 셋 중 하나인가, 새 모양인가 (이행 중에는 둘 다 열린다)
```

### 9.4 게이트

```
① 옛 문법으로 저장된 선언을 «열고 저장»하면 바이트가 그대로다 (왕복 무손실)
② 새 모양으로 적은 선언이 «같은 내부 규칙»을 만든다 (8.3 ④ 와 같은 단언, 화면 경유)
③ 새 칸을 위한 손그림 입력 «0»
④ 🔴 «실제 페이지 경로»로 연다 — 하니스가 선언을 직접 주입해 초록인데 화면은 빈 폼인
   경우가 이 저장소에 있었다. 라운드는 «그 경로를 걸어» 닫는다
⑤ 편집 중 자동 갱신이 폼을 갈아 끼우지 않는다 (C-95 가 그 사고였다)
```
