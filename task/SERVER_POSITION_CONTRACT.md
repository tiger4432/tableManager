## 1. 재료는 «이미 있습니다» — 실측

```
observed 원자                      114,510
  object_payload.die.x AND .y      114,483 / 114,510   (99.98%)   ✅ 여기 있습니다
  object_payload.run_uid           114,510 / 114,510   (100%)     ✅ 백업 경로
  🔴 object_payload.position            27 / 114,510   (0.02%)    ← 지금 «읽는» 자리
  🔴 object_payload.map_id               9 / 114,510   (0.01%)
```
```
finding_kind 별 좌표 보유
  void      102,937 중 102,922        (15 없음)
  delam      11,567 중  11,561        ( 6 없음)
  non_wet         6 중       «0»      ← 이 종류는 «전부» 없습니다
```

**그래서 새로 만들 것이 없습니다.** `die.{x,y}` 를 `position` 으로 내보내면 됩니다.
`run_uid` 는 `"sat|<wafer>|<x>|<y>|<gate>|<time>"` 이라 파싱 백업이 되지만, **먼저 `die` 를 쓰십시오** —
문자열 자르기는 구분자가 바뀌는 날 조용히 틀립니다.

## 2. 🔴 좌표«만» 내면 안 됩니다 — 기준계를 같이 내야 합니다

**실측 — 같은 표 안에 좌표계가 «둘»이고 범위가 «같습니다»:**
```
bonding_log 의 bx/by        범위 0..13
bonding_log 의 bond_x/bond_y 범위 0..13
두 쌍이 «같은 행» :  0 / 141        ← 한 행도 안 겹칩니다. 다른 좌표계입니다
```
**그리고 매칭 수로는 못 가릅니다:**
```
관측 자리 39개를 대 보면   bx/by 로 38개 맞음  ·  bond_x/bond_y 로 37개 맞음
-> 둘 다 0..13 을 촘촘히 덮어서 «어느 쪽이든 거의 맞습니다». 매칭은 «증거가 아닙니다»
```
🔴 **그러므로 클라가 추론하면 안 됩니다.** 서버가 «선언»해야 합니다.

```
낼 것   position: { x, y, frame: "<이 좌표가 속한 기준계 이름>" }
        frame 이름은 lot_map 의 projection axis 와 «같은 낱말»이어야 합니다 (bond · dt · core)
        그래야 부품이 「이 점을 이 맵에 얹어도 되나」를 «비교»로 답합니다
```
📎 회전도 여기 걸립니다 — `frame.grid.rotation` 이 본딩 «180» · DT 0 · 코어 0 이고
   클라는 지금 그것을 «0회» 읽습니다. 기준계 이름이 없으면 회전을 적용할 «대상»이 없습니다.

## 6. 수락 단언 — 이것으로 합격을 판정합니다

```
A  finding point 응답에 position {x, y, frame} 이 «있다» — 좌표 있는 원자 99.98% 에서
B  좌표 없는 27건이 position «null»(또는 absent)로 온다 — (0,0) 이 «아니다»
C  frame 낱말이 lot_map projection 의 axis 낱말과 «같다» (bond · dt · core)
D  collection 의 bbox 가 자기 point 들의 «최소·최대»와 맞는다.  없으면 null
E  접힘 수리와 «같은 커밋»에 있다

   경유지가 사라집니다. 칸이 노드를 «무는» 것이 아니라 walk 이 낸 point «그 자체»가 칸입니다.
   마킹 계약 §4 의 게이트가 통과하기 시작하는 지점은 «같습니다»
```

# 8. 🔴 lot_map 이 «혼자» 들고 있던 여섯 — walk 이 실어야 합니다

> 총괄 지시 `a86dea5b`. §2 의 기준계가 그중 ①이고, 나머지 다섯을 여기 흡수합니다.

```
①  프레임          grid_cols·rows · start_x/y · y_invert · rotation · side · phys_*
                   실측: 본딩 rotation «180» · DT 0 · 코어 0.  클라는 «0회» 읽습니다
                   🔴 그리고 «어느 컬럼으로 세운 격자인가»가 «선언에 없습니다» (위 정정)

②  valid_die_ref   프레임이 {relation, present, map_id} 로 달고 옵니다
                   「이 자리가 진짜 다이 자리인가」의 유일한 근거.  walk 이 안 실으면
                   point 가 «격자 밖»인지 «격자 안인데 빈 칸»인지 못 가릅니다

③  칸 상태 «셋»    found · scanned · unscanned.   실측(슬롯 07 본딩축):
                   found 13 · scanned 16 · unscanned 112
                   🔴 둘로 접지 마십시오 — 112 를 scanned 로 태그하면 «112자리에 대한 거짓»입니다
                   (모듈이 스스로 적어 둔 규칙입니다)

④  분모            scanned.  「발견 13」이 «무엇의» 13인지가 여기서만 나옵니다
                   🔴 그리고 이름이 정확해야 합니다 — 지금 라벨은
                   「검사 29 · bonding_log ∩ inspection_run 기준」입니다. 그 «기준»을 walk 이 이어받아야 합니다

⑤  맵 밖(unplaced) 좌표가 없어 «어느 칸에도 못 앉는» 검사 자리.
                   실측: 웨이퍼당 1 (slot 01 은 3) · 이 랏 25슬롯 합 «27» · 전체 «2,527자리 · void 2,525»
                   🔴 0 과 «모른다»를 가르십시오. 지금 lot_map 은 행 축이 웨이퍼가 아니면
                   «unknown» 을 냅니다 — 그런데 슬롯이 지정되면 셀 수 있습니다 (제 재대조 참조)

⑥  겹침            한 칸에 point 가 «둘 이상» 앉는 것.  실측(같은 웨이퍼, 축만 바꿔서):
                   본딩축  sum(n) 13 / 칸 13  ->  겹침 «없음»
                   DT축    sum(n) 13 / 칸  «8»  ->  겹침 «있음» (5개가 겹칩니다)
                   🔴 투영을 바꾸면 겹침이 «생깁니다». 칸이 노드가 되는 순간
                   「이 노드는 point 하나인가 다섯인가」를 walk 이 말해야 합니다
```

## 9. 수락 단언 — §8 에 대해
```
G  point 가 «격자 밖»인지 «격자 안 빈 칸»인지 구분돼 온다        (② valid_die_ref)
H  칸 상태가 «셋»으로 온다 — 둘로 접히지 않는다                  (③)
I  분모가 «무엇의 분모인지» 이름과 함께 온다                      (④)
J  못 앉힌 자리가 «수»로 온다.  셀 수 없을 때만 「모른다」        (⑤)
K  한 노드에 앉은 point 수가 온다 (겹침이 «가려지지» 않는다)      (⑥)
```
