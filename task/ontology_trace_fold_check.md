# 추적을 걷기로 접을 수 있나 — 실측 판정

> 총괄 지시 `ontology_application_ruling.md` 22:0x
> 소유자: 「frame 노드도 있어야 하나 너무 복잡하네 전략 세워보자 이러면 하드코딩 점점 많아질듯 추적할때」
> **이 문서는 읽기 전용 실측입니다. 코드 0줄.**

## 🔴 결론 먼저

**「접을 수 있다」는 오늘 데이터로는 «거짓»입니다. 그런데 그 이유가 walk 이 약해서가 아닙니다.**

```
predicate      object_kind    원자 수    walk 이 엣지로 보나
─────────────────────────────────────────────────────────────
transferred    value          72,964     ✗   ← 추적 SQL 이 읽는 것
transfer       entity_ref      1,405     ✓
```

`transferred` 중 `entity_ref` 인 것: **0개.**
그리고 두 술어는 **주어를 하나도 공유하지 않습니다** — `transfer` 의 주어는 `die` 뿐(wafer 0),
`transferred` 의 주어 wafer 3,426. **교집합 0.**

즉 **전사 이력 전부가 「값」으로 선언돼 있어서 그래프에 «선이 없습니다».**
SQL 이 손으로 payload 를 따라가는 것은 게을러서가 아니라 **그 길밖에 없어서**입니다.
고칠 자리는 walk 이 아니라 **선언**입니다.

---

## ① 그 SQL 이 «답하는 사실»

`_traceability_sql()` 은 트렌드 표의 «행 하나»(= grain unit, 지금은 wafer + bonding_leg)마다
아래를 답합니다. 열이 아니라 사실로 적습니다.

```
F1  이 leg 에 «어떤 최종 부품»들이 올라갔나         final_components
F2  그게 «몇 개»인가  (= 분모)                     components
F3  부품마다 «코어 웨이퍼»가 밝혀졌나               core_components
F4  부품마다 «DT 를 지났나»                        dt_components
F5  F3 · F4 각각의 «근거 원자 id»                  core_evidence · dt_evidence
F6  그래서 이 leg 의 추적 상태는 셋 중 무엇인가      absent · partial · ready
```

**F4 는 혼자 서지 못하고 F4a 를 먼저 만듭니다:**

```
F4a  «부품 하나의 생애» — 같은 (component_id, final_chip_id) 를 가진 전사 원자 전부
     SQL 의 component_events CTE 가 이걸 «그 자리에서 조립»한다
```

🔴 **F6 이 이 판정의 급소입니다.** `absent`(없음) 와 `partial`(일부만) 을 가르는 것은
**분모 F2** 입니다. 분모가 없으면 화면은 「추적 안 됨」과 「반만 추적됨」을 구분하지 못합니다.

## ② walk 이 낼 수 있나 — «불러서» 잰 것

씨앗 넷을 실제로 호출했습니다. 전부 `hops` 를 올려가며 포화까지 확인했습니다.

```
씨앗                                       홉    노드   엣지   개체   낸 사실
─────────────────────────────────────────────────────────────────────────────
WaferLeg{BW-001, HBM-B_LOW-P}  ← 표의 행    1     6      5      1     없음
   (= 추적이 붙는 바로 그 단위)             2    12     11      1     없음
                                            4    31     30      1     없음
                                            6    34     33      1     없음  ← 포화
                                           12    34     33      1     없음  ← 안 늘어남
Wafer{SYN-CX-BW-001}          baseline     12     3      2      1     없음
Wafer{SYN-CX-BW-001} incoming              12     1      0      1     없음
Wafer{SYN-CX-CW-HBM-B-03}     코어 쪽       6    400*   402     14     간접(아래)
```
`*` 노드 상한(400)에 걸림.

**결과를 그대로 옮깁니다:**

```
행에서 걸으면      개체가 «자기 자신 1개»에서 «끝까지» 안 늘어난다.
                   홉 6에서 포화하고 12까지 그대로다. 늘어나는 건 mechanism quantity 뿐.
                   -> F1 · F3 · F4 · F5 «전부 0»
코어에서 걸으면    개체 14개에 닿는데 «전부 코어 웨이퍼와 랏»이다.
                   base wafer 는 «없다». 방향이 반대여도 못 건넌다.
```

**유일하게 근접한 갈래** — 코어 씨앗 + `collect="value"`, hops 2:
```
value 노드 43개 · 그중 component payload 를 통째로 안은 것 12개
propagation.state = "ranked" · ranked 43 · top_set 43 · 전부 rank 1 · contrast = "unexamined"
```
🔴 **닿기는 하지만 이건 「낼 수 있다」가 아닙니다.** 이유 둘:
① 값 노드의 **payload 를 손으로 파싱**해야 합니다 — 지금 SQL 이 하는 일과 «같은 일»입니다.
② 씨앗 하나로는 **43개가 전부 rank 1** 입니다. `collect` 는 모집단을 고르지 줄을 세우지 않습니다.

## ③ 🔴 못 내는 것 — 이름을 댑니다

### (a) 전사가 «엣지가 아니다» — F1 · F3 · F5 가 여기서 죽는다

`transferred` 원자 **72,964개가 전부 `object_kind='value'`**.
walk 은 `object_kind == "entity_ref"` 일 때만 개체→개체 엣지를 만듭니다.
그래서 코어 웨이퍼와 베이스 웨이퍼 사이에 **선이 없습니다.**

지금 실제로 걸을 수 있는 술어는 **넷뿐**입니다:
```
has_wafer   -> Wafer   1,645
transfer    -> die     1,405
slot_map    -> Lot       443
derived_from-> Lot       101
```

⚠️ **픽스처 탓이 아닙니다.** `transferred` 를 내는 여섯 소스 중 운영 계보에 가장 가까운
`dt_log` (4,669원자) 도 **value 로 냅니다.**

### (b) 부품(component)이 «노드가 아니다» — F4 · F4a 가 여기서 죽는다

```
주어가 component 인 원자: 0건
원장에 실재하는 주어 타입: Wafer 219,727 · Lot 2,281 · die 1,405 · DTJob 792 · Recipe 44 · WaferLeg 42
```
SQL 은 `component_id + final_chip_id` 로 원자를 묶어 **그 자리에서 노드를 만듭니다.**
walk 에는 그 노드가 없습니다. **(a) 를 고쳐도 (b) 는 남습니다.**

🔴 **소유자의 frame 판정 시험을 여기 대면 부품은 frame 과 «반대쪽»에 떨어집니다.**
「이 부품은 저 코어에서 왔다」·「이 부품은 DT 를 지났다」 — **부품에 대해 주장을 합니다.**
좌표계에 대해서는 아무도 주장하지 않습니다. 같은 시험이 frame 은 빼고 component 는 넣습니다.

### (c) 분모가 «그래프 밖»에 있다 — F2 · F6 이 여기서 죽는다

walk 은 **닿은 것을 세지, 「닿았어야 할 것」을 세지 않습니다.**
`_trace_state(count, total)` 의 `total` 은 그래프가 모르는 수입니다.

🔴 **이것이 「접는다」와 「잃는다」를 가르는 자리입니다.** 분모 없이 접으면
`absent` 와 `partial` 이 **같은 화면**이 됩니다 — 이 프로젝트가 반복해서 맞은 그 결함
(「없는 것을 고장이나 진행 중으로 읽는 것」)이 추적 열에 그대로 들어옵니다.

**그리고 (c) 는 제가 이 라운드에서 «못 푼» 것입니다.** (a)(b) 는 갈 자리가 분명한데
(c) 는 아직 자리가 없습니다.

## ④ 성능 — 한 줄이 아니라 두 줄이 필요합니다

```
지금    추적 SQL     «페이지당 1회»    13 unit -> 183 ms
접으면  walk         «unit 당 1회»     13회   -> 188 ms  (unit 당 14 ms)
                                       페이지 상한 100 이면 100회 ≈ 1.4 s
```

🔴 **그런데 저 14 ms 는 walk 이 «아무것도 못 찾은» 시간입니다.**
(a)(b) 를 고쳐 실제로 건너기 시작하면 unit 당 시간은 **올라갑니다.**

성능은 걸림돌이 아니지만, **「페이지 단위 한 번」이라는 성질은 잃습니다.**

## ⑤ 전략 판정 — 「추적 = 걷기 선언 하나」는 «조건부로» 참입니다

조건이 셋이고 **셋 다 선언 쪽**에 있습니다. 코드 쪽이 아닙니다.

```
조건 1   transferred 를 entity_ref 로 낸다        매핑     -> (a) 해소
조건 2   component 를 개체로 선언한다              어휘     -> (b) 해소
조건 3   분모를 «선언»에서 읽는다                   ???     -> (c) 미해결
```

### 조건 1 이 참이면 walk 이 실제로 건너나 — «대리 측정»했습니다

걸을 수 있는 전사가 원장에 하나 있습니다(`transfer`, entity_ref). 같은 walk, 같은 날:

```
씨앗 die{SYN-XFER-CORE-W07}   hops=1   노드 2 · 개체 1
                              hops=2   노드 4 · 개체 2 · preds [asserts, subject, transfer]
                                       -> die(Wafer) 에서 die(DT) 로 «건넜다». collect=entity ranked 2
```
**「DT 를 지났나」(F4 모양)를 payload 를 한 글자도 안 읽고 2홉에 답했습니다.**
개체→주장→개체이므로 **1홉이 아니라 2홉**입니다.

⚠️ 이것은 조건 1 의 **대리 증거**이지 조건 1 을 적용한 측정이 아닙니다.
72,964 원자에 적용한 뒤가 어떨지는 **안 재봤고, 재려면 선언을 바꿔야 합니다 — 제 레인이 아닙니다.**

---

## ⑥ 그래서 하드코딩은 «어디로» 가나

`_traceability_sql()` 의 문자열 리터럴 **14개**를 뽑아 행선지를 붙였습니다.

```
조건 1 이 없앤다   to · from · keys · type · base_wafer_id · bonding_leg · bond_layer · wafer
조건 2 가 없앤다   component · component_id · final_chip_id
어휘가 이미 가짐   transferred                (술어 이름 — 선언된 이름이지 하드코딩이 아니다)
🔴 남는다          dt_slot · dt_lot
```

**남는 둘의 정체:** 「어느 종류의 자리를 지났나」입니다.
조건 1 이 되면 `to` 가 개체가 되므로 이 둘은 **«선언된 개체 타입 이름»**으로 바뀝니다.
그게 **화면에서 고르는 값이면 하드코딩이 아니고, 코드에 박히면 이름만 바뀐 같은 결함입니다.**

## ⑦ 제가 «못 잰» 것 — 먼저 적습니다

```
1  조건 1·2 를 적용한 뒤의 walk         선언을 바꿔야 해서 못 쟀다. ⑤ 는 «대리» 측정이다
2  조건 3(분모)의 자리                  못 찾았다. 이 라운드의 미해결이다
3  운영 환경                            여기 숫자는 이 박스의 픽스처다. 다만 (a) 는
                                        dt_log 에서도 참이므로 «픽스처 한정 결함이 아니다»
4  성능의 «고친 뒤» 값                   ④ 의 14 ms 는 못 찾은 상태의 시간이다
```

## ⑧ 정리 — 소유자 질문에 대한 답

**「이러면 하드코딩 점점 많아질듯」 — 맞습니다. 그리고 원인이 잡힙니다.**
추적 질문이 하나 늘 때마다 SQL 이 하나 늘어나는 이유는 **전사가 값으로 선언돼 있어서**입니다.
값은 걸을 수 없고, 걸을 수 없으면 손으로 따라가야 하고, 손으로 따라가면 낱말이 코드에 박힙니다.

**「frame 노드도 있어야 하나」 — 아니오, 그리고 그 판정이 다음 것도 정합니다.**
`주장의 대상인가`로 자르면 frame 은 밖, **component 는 안**입니다.
그리고 지금 늘어나는 복잡도는 **노드 종류가 아니라 (a) 에서 옵니다.**
