# 명세 — walk 의 `collect` : **도착 엔티티 타입**

> **Status:** 초안 · 소유자 승인 대기 · **Owner:** 총괄
> **소유자 정의 (2026-09-06):** 「내가 말한 collect 는 **목적지를 die 로 할지 rcp 로 할지** 이런 거 정하는 건데」

---

## 0. 왜 이것이 «빠진 것»인가

CLAUDE.md 데이터 상설(소유자, 2026-08-24):
```
부품   선언하는 것은 «둘»뿐 — { start = 읽을 마킹,  collect = 무엇을 걷나 }
```
**그 둘 중 하나가 walk 에 없습니다.**
```
start    ✅ 있습니다 — `id` (+ positive/negative)
follow   ✅ 있습니다 — 어느 «술어»로 걷나
collect  ❌ 없습니다 — 「무엇을 «받을» 것인가」
```
⚠️ 한때 `collect` 이라는 인자가 있었으나 **다른 물건**이었습니다 — 투영이 지어낸
«노드 종류»(entity·point·claim·collection·quantity·event) 중 하나를 고르는 것.
소유자가 2026-08-27 에 그것을 잡으셨고(「사용자가 claim, point, collection 이런 걸 어케 암」),
종류가 «하나»가 되면서 정당하게 은퇴했습니다(`9f0d964d`).
🔴 **그런데 그 자리에 «도착 타입» 축이 들어서지 않았습니다.** 이 명세가 그 자리입니다.

---

## 1. 무엇인가

```
collect = 걷기가 «돌려줄» 엔티티 타입의 목록
예       start=wafer@1 · follow=… · collect=recipe@1     -> 「이 웨이퍼가 닿는 레시피」
         start=wafer@1 · follow=… · collect=die@1        -> 「이 웨이퍼의 다이」
         collect 없음                                     -> 오늘과 같음 (닿는 것 전부)
```

## 2. 무엇을 «범위»로 갖나 — 🔴 선언에서 나옵니다
```
✅ 선언된 엔티티 타입   wafer@1 · die@1 · recipe@1 · defect@1 …
⛔ 배관 낱말 «금지»     kind·point·collection 류. 그것이 2026-08-27 의 결함입니다
=> 폼은 «선언을 읽어» 채웁니다. 사람이 외울 것이 없습니다
```

## 3. 🔴 «거르개»가 아니라 «목적지»입니다 — 이 명세의 핵심

이 구분이 이 항목의 전부입니다.
```
❌ 거르개   전부 걷고 «응답에서 뺀다»
           -> 예산(node_limit)이 «버릴 노드»에 먼저 쓰입니다
           -> 예산이 다하면 「레시피 0」이 나오는데, 그건 «없어서»가 아니라 «못 가서»입니다
           -> 그 둘이 화면에서 «같아 보입니다» (이 저장소의 「다섯 개의 0」 부류)
✅ 목적지   걷기가 그 타입을 «향해» 예산을 씁니다
           -> 지나가는 노드는 «길»이고, collect 타입은 «답»입니다
           -> 예산·절단을 «답» 기준으로 보고합니다
```
📎 실측 근거(2026-09-05 클라 라운드): `direction=both` 로 걸으면 예산이 «남의 웨이퍼 다이»에
   먼저 쓰여 defect 270 중 149 가 형제였고 **절단이 걸렸습니다.** outgoing 으로 좁히니 절단이
   사라졌습니다. 즉 «예산을 어디에 쓰나»가 답을 바꿉니다 — 거르개로는 그걸 못 고칩니다.

## 4. 답이 «셋»입니다 — 하나로 접지 않습니다
```
① 닿았다      collect 타입 노드 N 개.  N 이 0 이어도 «닿았고 없었다»면 그렇게 말합니다
② 예산에서 끊겼다  🔴 「0」이 아니라 «끊겼다»라고 말합니다 — 무엇이 몇 개 남았는지와 함께
③ 선언에 길이 없다  start 타입에서 collect 타입으로 가는 «술어 경로»가 선언에 없습니다
                 -> 이건 «걷기 전에» 알 수 있습니다. 걷지 않고 답합니다
```
⚠️ ②와 ①(N=0)이 «같아 보이면» 이 명세는 실패입니다. 그것이 이 항목의 존재 이유입니다.

## 5. `follow` 와의 관계 — 두 갈래. 총괄 추천은 ㉮
```
㉮ 추천   collect 을 주면 follow 를 «선언에서 계산»합니다
          「start 타입에서 collect 타입까지 닿는 술어들」은 선언이 압니다
          -> 사람이 고를 것이 «둘 -> 하나»로 줍니다 (도착지만 고르면 됩니다)
          -> 「두 줄로 말해진다」에 가까워집니다
㉯        collect 과 follow 를 «둘 다» 받습니다 (follow 는 지금처럼 손으로)
          -> 지금 화면과 호환. 다만 사람이 여전히 술어를 알아야 합니다
🔵 ㉮ 로 하되 follow 를 «주면 그것이 이깁니다» — 계산은 «기본값»이고 잠그개가 아닙니다
```

## 6. 하지 «않는» 것
```
⛔ 마킹 체인·이력·「결과에서 줍기」  — 이 명세와 무관합니다. 별건입니다
⛔ 순위 매기기(_rank_layers)      — 옛 collect 이 하던 둘째 일. 되살리지 않습니다
⛔ 노드 «종류» 축                  — 은퇴 그대로. 되살리지 않습니다
⛔ 새 라우트                       — `GET /api/ledger/subgraph` 에 인자 «하나»가 붙습니다
```

## 7. 착수 전 재야 할 것 «둘»
```
① 선언이 「타입 A 에서 타입 B 로 가는 술어 경로」를 «낼 수» 있나
   -> ㉮ 가 성립하는지가 여기서 갈립니다. 못 내면 ㉯ 입니다
② 목적지 지향이 «예산 배분»을 어떻게 바꾸나
   -> 지금 루프가 너비 우선이면, 목적지 타입을 만나는 가지를 «먼저» 펴야 합니다
   -> 그 변경 크기를 재고 나서 짓습니다
```

## 8. 게이트
```
① collect=recipe@1 로 「웨이퍼 -> 레시피」가 «나온다»
② collect 없이 부르면 «오늘과 같은 답» (무회귀)
③ 🔴 예산을 낮춰 끊기게 만들면 «끊겼다»가 나온다 — «0» 이 아니라
④ 선언에 길이 없는 조합은 «걷지 않고» 거절하고, 그 사유가 화면에 뜬다
⑤ 폼이 선언에서 타입 목록을 «읽어» 채운다. 손으로 적는 칸 «0»
```

# ⛔⛔ **철회 — 이 명세가 제안한 것은 «이미 있습니다»** (총괄 2026-09-06 09:4x)

> 소유자: 「원래 «가»였고 가에서 여러 갈래 후보에서 선택할 수 있었는데」
> 소유자: 「**왜 다 만들었다고 보고된 기능을 처음부터 다시 하는 거지?**」

## 실측 — ㉮ 는 «출하된 설계»입니다. 제 추천이 곧 그것이었습니다
```
client2/src/rnd_board/api.js:1586  typeGraph(declaration)          선언 -> 타입 그래프
                            :1611  pathsBetween(decl, from, to)    「두 타입 사이 «모든 단순 경로»」
                                                                   반환이 {hops, follow, chain}
walk_box_panel.js:38   import { typeGraph, pathsBetween }
                 :377  도착 타입 «목록»을 선언에서
                 :383  routes() — 시작 -> 도착 «경로들»
                 :387  useRoute(index) 「경로 하나를 «쓴다» — follow 와 hops 가 그 경로에서 나옵니다」
```
🔴 **§5 의 「㉮ 추천: 도착지를 주면 follow 를 선언에서 계산」이 «이미 돌고 있는 코드»입니다.**
   그리고 「여러 갈래 후보에서 고르기」도 `routes()` + `useRoute()` 로 «있습니다».
   그 코드에 소유자 정정(2026-08-29, 자기 고리는 경로의 한 칸)까지 주석으로 박혀 있습니다.

## 그래서 이 명세에서 «살아남는» 것과 «죽는» 것
```
⛔ 죽습니다   §1 · §2 · §5 — 전부 이미 있습니다
⚠️ 미확인    §3(목적지 vs 거르개 — 예산이 목적지를 향하나) · §4(답 셋 가르기)
             -> 이건 «클라가 계산한 follow 로 서버를 부르는» 구조라, 예산 질문이 남아 있을 «수»는 있습니다
             -> 다만 그것도 «제가 확인하기 전엔 없다고 말하지 않겠습니다»
```

## 🔴 제 실패 — 이틀에 «세 번», 전부 같은 모양
```
① 「map_editor 는 CSS 때문에 import 안 된다」   실제: 됩니다 (그 금지의 1단계가 22분 뒤 고쳤음)
② 「걷기 검색창은 follow 를 손으로 적는다」      실제: 선언에서 온 체크박스 14
③ 「collect(도착 타입)이 없다」                 실제: typeGraph + pathsBetween + useRoute
```
**공통 원인:** 제가 «제가 예상한 이름»을 «제가 예상한 층»에서 찾고, 없으면 «기능이 없다»고 결론냅니다.
`collect` 은 «서버 인자»로 죽었지만 그 «기능»은 처음부터 «클라의 선언 계산»으로 살아 있었습니다.
🔴 그리고 ③ 은 **오늘 아침 제 grep 출력에 `pathsBetween` 이 이미 찍혀 있었는데** 안 읽었습니다.
