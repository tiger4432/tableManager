# 지시서 — 트렌드 축: 소유자가 «화면에서 골라» 그린다

> 소유자 지시 (2026-08-23) · 총괄 전달 `ontology_application_ruling.md` 14:4x
> 🔴 **도착지: 소유자가 화면에서 축을 골라 트렌드를 얻는다. JSON 을 쓰지 않는다.**
> 고를 수 있는 것이 무엇인지, **못 고르는 것이 «왜» 못 고르는지**가 화면에 보인다.

---

## 1. 왜 이게 «차트 설정»이 아닌가

소유자 원문: **「진정한 “온톨로지”가 들어가는 트렌드지」.**

축을 고르는 것은 색을 고르는 것이 아니라 **«어느 관계를 타고 갈지»를 고르는 것**입니다.
「DT 로 그릴까, DT 인데 추적된 웨이퍼로 변환해서 그릴까」는 **홉 하나 차이**입니다.
그러므로 이 라운드가 만드는 것은 차트 옵션이 아니라 **걷기의 다섯 자리**입니다.

---

## 2. 🔴 다섯 축이 «한 연산»이다 — 이게 이 설계의 전부다

```
축      뜻                     연산
─────────────────────────────────────────────────────────────
point   점 하나가 무엇인가       접는 단위를 «고른다»
x       가로                   걸어가서 «시각»을 읽어 온다
y       세로                   여기서 «값»을 읽거나, 두 종류를 세어 «비율»
color   색                     걸어가서 «속성»을 읽어 온다
shape   모양                   걸어가서 «속성»을 읽어 온다
```

**`x` · `color` · `shape` 는 서로 다른 기능이 아닙니다.** 셋 다
「어느 관계를 타고 가서, 거기서 무엇을 읽나」 하나이고 **자리만 다릅니다.**

    축 = (걸음, 읽을 것)

**그래서 만들 것은 축 다섯 개가 아니라 «걸어가서 읽어 오기» 하나입니다.**
이걸 다섯 자리에 꽂으면 다섯 축이 됩니다. 자리마다 코드를 나누면 이 라운드는 실패입니다.

---

## 3. 바뀌는 층 / 그대로인 것

```
바뀐다   server/ledger_subgraph.py    collect 가 «개체 타입»까지 받는다 (§4)
                                     + 「걸어가서 읽어 오기」 한 자리
바뀐다   화면 (트렌드 축 고르는 곳)     후보 목록 + «못 고르는 사유» 표시 (§5)
그대로   원장 스키마 · 어휘 · 설정 형식   원자도 선언도 «안 늘린다»
그대로   얼린 여덟 (은퇴 구역)          손대지 않는다
```

---

## 4. 공사 1 — `collect` 가 «타입»까지 받는다

지금 `collect` 는 노드 «종류» 여덟(entity · event · claim · collection · point · value ·
quantity · action) 중 하나만 받습니다. 실측:

```
collect="entity" 로 랏을 걸으면   Lot 5 · Wafer 25 가 «같이» 나온다
```

**소유자가 고르려는 것은 「Wafer 냐 die 냐 DT 냐」 — 한 단 아래인 «타입»입니다.**

```
지금    collect: "entity"
필요    collect: "entity/Wafer"  또는  {kind:"entity", type:"Wafer"}
        (형식은 구현자가 기존 규약에 맞춰 고른다. 여기서 정하지 않는다)
```

🔴 **`collect` 의 계약을 넓히는 것뿐입니다.** 걷기·전파·순위는 안 바뀝니다 —
그 함수의 독스트링이 이미 「`collect` 는 POPULATION 만 고른다」라고 못 박아 두었습니다.

---

## 5. 공사 2 — 화면이 «후보»를 주고, 0 이 곧 «사유»다

소유자 ④: **「내가 사용하기 편하게. AI들만 쓸 줄 알면 의미없음」.**

**후보 개수를 세는 그 숫자가 그대로 거절 사유입니다.** 총괄 실측:

```
Wafer        114,492   ✅ 고를 수 있음
WaferLeg          18   ⚠️ 고를 수 있으나 «어디에도 선언 안 됨» — 그 표시를 같이
die                0   ⛔ 「이 종류에 붙은 관측이 0건」
DT                 0   ⛔ 같은 사유
DT -> 추적 코어     0   ⛔ 「출발점이 0건」  (지도는 있음 — 전사 원자 1,405)
```

화면 문구는 **개수와 사유 한 줄**이면 됩니다. 예:

```
Wafer      114,492
WaferLeg        18   선언 없음
die              0   이 종류에 붙은 관측 없음
DT               0   이 종류에 붙은 관측 없음
```

🔴 **회색으로 «지우지» 마십시오.** 소유자가 「왜 DT 가 없지」를 물어야 하는데,
없으면 물을 수 없습니다. **보이되 못 고르고, 옆에 사유.**
(이건 이 프로젝트 상설입니다 — 「없는 것을 고장이나 진행 중으로 읽지 않는다」.)

---

## 6. 🔴 판정 요청에 답합니다 — 시각 «기본값»은 계측 시각입니다

총괄 질문: 「스텝 시각이 «선택지»가 아니라 «기본값»이어야 하는지 판단해 주십시오.」

**아니오. 기본값은 «계측 시각»이고, 스텝 시각은 «선택지»입니다.**

```
근거 1   커버리지가 «전부»가 아니다
         불량 있는 웨이퍼 2,631 중 스텝 시각을 가진 것 2,606 -> «25장이 없다»
         기본값이 스텝이면 그 25장이 «조용히» 사라진다.
         빠진 것이 안 보이는 기본값은 기본값이 아니다

근거 2   계측 시각은 원자가 «자기 안에» 든 사실, 스텝 시각은 «조인해서» 얻은 것
         기본값이 조인이면 조인이 깨지는 날 «빈 화면»이 기본이 된다

근거 3   「막대가 60개뿐」은 데이터의 «사실»이다 (실측 1,962 원자 · 서로 다른 시각 60)
         기본값을 바꿔 가리면 「계측을 더 자주 해야 하나」라는 «옳은 질문»이 안 나온다
```

📎 다만 **스텝 시각이 «한 번의 클릭»이어야** 합니다 — 선택지로 두되 숨기지 말 것.
쓸 수 있는 스텝 여덟은 총괄이 이미 쟀습니다(BONDING · MOLDING · PLASMA_CLEAN · DT ·
POST_BOND_QUEUE · DIFFUSION · MI_THICKNESS · DEPO).

## 7. y 축 — 값과 비율 «둘만». 편차는 이번에 «안 만듭니다»

```
✅ 비율   불량.  분자 = observed · 분모 = inspection_run · absence_is_zero: false
✅ 값     물리량. 물리 단위 그대로 (MPa · °C · h)
⛔ 편차   «이번에 안 만든다»
```

**왜 안 만드나 (총괄 실측 인용):** 실측과 설정값이 «다른 원자»에 있고 같이 든 원자가 0입니다.
그러므로 「편차 = 실측 − 설정」은 뺄셈이 아니라 **조인**입니다. 게다가 설정값이
웨이퍼마다 다릅니다(0.35 · 0.35 · 0.22) — **레시피 상수가 아닙니다.**
조인 규칙을 이 라운드에서 지어내면 그게 새 축입니다. **적어만 두고 넘어갑니다.**

## 8. 수락 단언 — 이것으로 합격을 판정한다

```
A  소유자가 «화면에서만» 트렌드 하나를 끝까지 만든다.  JSON 을 «한 글자도» 안 쓴다
B  못 고르는 항목이 «보이고», 옆에 사유가 한 줄로 붙는다 (die/DT 에 「관측 없음」)
C  point 를 Wafer -> WaferLeg 로 바꾸면 «코드 변경 없이» 다시 그려진다
D  x 를 계측 시각 -> BONDING 스텝 시각으로 «한 번의 클릭»으로 바꾼다
   그리고 그때 «빠지는 25장»이 화면에 숫자로 나온다
E  color 와 shape 가 x 와 «같은 코드»를 쓴다 — 자리만 다르다는 것의 확인
```

## 10. 순서

