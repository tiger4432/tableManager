# 지시서 — S-6 「운영자가 «자기 계기가 죽은 것»을 모른다」

> 작성: 응용 레인(줄 예약: **S-6 집습니다**). **코드 0줄.** 서버 몫 «0» — 지을 것은 클라 한 줄입니다.

## 실측 (응용, 07:2x · 총괄 확인)
```
서버   main.py:2902  _validate_effort(batch.effort) -> effort_error
      :2912         logger.error(...)
      :3146         "effort_error": effort_error      <- 🔵 «응답에 실립니다». 「로그뿐」은 줄이 틀렸습니다
클라   `effort_error` · `effortError` 읽는 자리 «0» — 소스도 «번들»도 0
🔴 같은 응답의 `effort_recorded` 는 «읽힙니다» (effort_meter.js, 2)
=> 한 응답에서 «한 칸만» 읽고 있습니다. 등급 «2 (안 들린다)» · 성질은 «나르기»
```

## 🔴 왜 이 침묵이 다른 셋보다 나쁜가
```
계기가 죽으면 수가 «0 으로 보이고», 0 은 「노력이 없었다」로 읽힙니다.
=> 침묵이 「모른다」를 만드는 게 아니라 «틀린 수»를 만듭니다
⚠️ 이 한 줄은 «형태에서 온 추론»입니다 — 코드로 안 쟀습니다. 지으실 때 «먼저 확인»하십시오
```

## 지을 것 — `effort_meter.js` 가 «옆 칸»도 읽습니다
```
자리   `effort_recorded` 를 읽는 그 자리 (effort_meter.js, 2곳)
무엇   `effort_error` 가 «참이면» 계기가 자기 상태를 말합니다. 서버 문장을 «그대로» 씁니다
⛔ 안 함  새 문구 짓기 · 오류를 «수»로 접기 · `body_error.errorText` 갖다 쓰기
        (그건 «봉투»의 오류이고 이건 «저장 응답의 한 칸»입니다 — 오늘 밤 F-15 에서 같은 이유로 안 합쳤습니다)
```

## 게이트
```
① 가름     `effort_error` 가 있을 때와 없을 때가 «다른 답». 없을 때는 «오늘과 완전히 동일»
🔴 ② 무회귀  저장은 «그대로 성공»합니다 — 계기가 죽어도 «데이터 쓰기»는 막지 않습니다
           (그 둘을 묶으면 계측기가 자기가 재려던 것을 «끄는» 것이 됩니다)
③ 읽는 쪽   «수» + «도달 가능» — 번들에서 «축약에 안 죽는 문자열»로
```
🔴 **멈춤** — 화면에 계기 상태를 말할 «자리»가 없으면 거기서 멈추고 올리십시오. 그건 «만들기»입니다.

## 🔵 서버에 남은 물음 하나 (지금 «하지 마십시오»)
```
`_validate_effort` 는 «어느 키»가 문제인지 알고, 지금 그것이 «문자열 하나»로 접혀 나갑니다.
화면이 「어느 키인가」를 묻는 날 그 모양을 서버가 먼저 정해야 합니다 — 오늘 그 사례가 «없습니다»
```
