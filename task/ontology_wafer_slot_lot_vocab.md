# 2. 🔴 자리는 신원이 아니다 — 소유자 상설 규칙이 이 소스에서 «측정으로» 확인된다

소유자 상설: **「랏이란 단위를 잊으라」 — 단위는 웨이퍼, 랏은 값.**
`dt_log` 34,939행에서 그게 참인지 직접 쟀다.

## 먼저 틀릴 뻔한 것 — 철자가 「이동」처럼 보인다

원본 그대로 세면 **웨이퍼 136장이 자리를 2~5곳 옮긴 것처럼** 보인다. 표본을 꺼내니:

```
WF.010101 -> CL-2601-001/01 · CL-2601-001/1 · CL_2601_001/01 · CL_2601_001/1 · None
```

**이동이 아니라 `-`/`_` 와 `01`/`1` 이다.** 규모:

```
core_lot   714 -> 699 (변형 15)      core_slot  61 -> 52 (변형 9)
dt_lot     696 -> 696 «드리프트 0»    dt_slot    50 -> 50 «드리프트 0»
```

**core 쪽만 흔들리고 dt 쪽은 깨끗하다.** 그리고 `(core_lot,core_slot)` 이 `(None,None)` 인
자리 하나에 **웨이퍼 117종**이 몰려 있다 — 이건 자리가 아니라 결측이다.

## 정규화하고 결측을 뺀 «뒤»에도 자리는 신원이 아니다

```
한 웨이퍼가 붙은 자리 수      1곳 932장 · «2곳 20장»
한 자리가 가진 웨이퍼 종수    1종 968곳 · «2종 2곳»
```

**그러므로 키는 `wafer`, 자리(`lot`,`slot`)는 한정어다.**
지금 `has_wafer@1` 이 정확히 그 모양이다 — 바꿀 것 없다.

# 3. 어휘 세트 제안 — **새 술어 0개**

`dt_log` 가 말하는 문장은 넷이고, 넷 다 기존 어휘로 적힌다.

```
문장                                   어휘                      상태
─────────────────────────────────────────────────────────────────────
core 웨이퍼가 이 랏 이 슬롯에 있었다     has_wafer  Lot->Wafer+{slot}   그대로 쓴다
core 웨이퍼·dt 스트립이 처음 보였다      register                       그대로 쓴다
die 가 core (x,y) 에서 dt 자리로 갔다   transfer   die->die            🔴 §4 참조
이 전사가 어느 잡·장비였나              transfer 의 «한정어»            선언 확장 (새 술어 아님)
```

**전사의 문맥(`dt_job` · `dt_eqp`)은 새 술어가 아니라 `transfer@1` 의 한정어다.**
지금 `required: [] · optional: []` 로 비어 있다. 여기에 이름을 넣는 것이
「기존 키 확장」이고, 그게 최소 수정이다.

⚠️ 시각은 한정어가 아니라 원자의 `occurred_at` 이다 — `read.occurred_at` 이 이미
`{"column":"event_time","timezone":"Asia/Seoul"}` 로 잡혀 있다. **중복 선언하지 말 것.**

# 4. 🔴 진짜 막힌 자리 — dt 쪽에 «신원»이 없다

> 🔴 **이 절은 만료됐다 (2026-08-22 23:38, 소유자가 풀었다). §14 를 보라.**
> 아래의 「dt_id 가 비어서 막혔다」와 갈래 (가)/(나) 는 **더 이상 선택지가 아니다.**
> 소유자가 `die@1` 의 키를 바꿔서 **셋째 길**로 풀었다.


`transfer@1` 은 `die -> die` 이고 `die@1` 의 키는 `{substrate_id, x, y}` 다.

```
core 쪽    substrate_id = core_wafer   ✅ 있다 (81% 채움 · 953종)
dt 쪽      substrate_id = ???
```

**`dt_id` 컬럼이 있는데 채움이 «0%» 다.** 그래서 dt 쪽엔 자리밖에 없다:

```
(dt_lot, dt_slot)          928종 · 드리프트 0 · 채움 90%
dt_x, dt_y                 FULL
dt_cell_key                34,939종 = 행 수  -> 이건 «행 id» 지 개체가 아니다
```

## 갈래 둘 — 소유자 판정이 필요하다

```
가  자리를 신원으로 쓴다     substrate_id = dt_lot|dt_slot 를 prepare 에서 만든다
    지금 되나              된다. dt 쪽 드리프트 0
    언제 틀리나            자리가 «재사용»되는 날. core 쪽이 이미 그 병을 보여준다
                           (정규화 뒤에도 자리 2곳이 웨이퍼 2종을 갖는다)
    부작용                 원장 안에만 있는 이름이 생긴다 — 밖에서 그 id 를 못 부른다

나  dt_id 를 채운다         소스가 이미 그 칸을 «가지고» 있다. 채우면 core 와 같은 모양
    비용                   원장이 아니라 «인제션» 쪽 일
```

**저는 (나)를 권합니다.** (가)는 지금 데이터에서만 참인 가정 위에 신원을 세우고,
그 가정이 깨지는 날 **이미 쌓인 전사 원자 전부**가 틀린 곳을 가리키게 됩니다.
다만 dt_id 를 채우는 게 이번 범위 밖이면, **(가)로 가되 「자리를 신원으로 썼다」를
설정에 적어 두는 것**이 차선입니다.

# 6. 판정 요청 — `slot_map` 이 지금 아무것도 말하지 않는다

라이브 원자로 쟀습니다.

```
서로 다른 slot_map 사실 226   -> has_wafer 두 개로 재현되는 것 «226» (100%)
서로 다른 (랏,랏) 짝    40    -> derived_from 이 이미 덮는 것 «40» (100%)
from == to              226/226 (100%)   슬롯 이동이 «한 건도» 없다
한 웨이퍼의 서로 다른 슬롯 수  전부 1 (125/125)
```

그리고 이건 **데이터가 아니라 «선언» 때문입니다** — `slot_map@1` 은 한정어 `wafer` 를
**required** 로 요구합니다. 웨이퍼를 이름 대는 순간, 그 문장은 양쪽 `has_wafer` 가
이미 말한 것 이상을 말할 수 없습니다. **자유도가 0입니다.**

⚠️ **지우자는 제안이 아닙니다.** `ledger_trace._map_slot` 이 이걸 읽습니다(은퇴 대상이지만
아직 돕니다). 그리고 저는 같은 날 「도출되니 지워도 된다」로 축 하나를 죽인 적이 있습니다.
**판정만 요청드립니다** — 슬롯이 «바뀌는» 전사가 실제로 있습니까? 있다면 `wafer` 를
required 에서 빼야 이 술어가 일을 합니다. 없다면 은퇴 라운드 재료입니다.

# 7. 남는 구멍 하나 (적어만 둡니다)

`transfer` 는 `die -> die` 인데 **웨이퍼에서 다이로 가는 «엣지»가 없습니다.**
`die@1` 의 `substrate_id` 가 웨이퍼 이름을 «담고» 있을 뿐이라, 관계가 아니라 «키 접두»입니다.
walk 은 키 접두를 못 넘습니다. 「이 웨이퍼의 다이들이 어디로 갔나」를 그래프로 물으려면
그 자리가 필요합니다 — **다만 새 술어가 답인지 조회가 답인지 아직 안 쟀습니다.**

# 8. 「본질적인 이벤트면 원장에 채우는 게 맞나」 — 맞습니다, 판별식 하나를 붙여서

소유자 질문 (2026-08-22 밤). 판별식이 실제로 판별하는지 **라이브 원자에 먹여** 봤습니다.

## 판별식 — 「이 원자를 만들 때 «규칙»을 썼나」

```
본 것      행을 그대로 읽었다                 재해석에 «재저장 불필요»
결론       규칙을 적용해서 냈다               규칙이 바뀌면 «조용히 틀린다»
```

**`bind.mappings` 의 이름이 이미 그걸 말합니다** — `in_slot`(읽기) 對
`merge_slot_join`·`split_slot_carry`(규칙).

## 지금 6개를 그 시험에 태운 결과

```
술어                시험                                          판정
────────────────────────────────────────────────────────────────────────
has_wafer          slot 을 말하는 «유일한» 술어. 사실 238          🟢 본 것 — 남긴다
transfer           그 시각에 일어난 이동                            🟢 본 것 (아직 원자 0)
has_netdie         잡의 die 수                                     🟢 본 것
────────────────────────────────────────────────────────────────────────
slot_map           226/226 이 has_wafer 두 개로 재현                🔴 결론
derived_from       40/40 이 slot_map 과 «상호» 재현                 🟡 둘 중 «하나»면 족하다
register           Wafer 125/125 · Lot 25/25 가 다른 원자에 이미 있다 🟡 아래
```

## `register` 는 지우면 안 됩니다 — 지금 «구별할 것이 없을» 뿐입니다

`register` 의 일은 walk 에서 `[root]`(등록됐고 부모가 없다 = 진짜 꼭대기)와
`[dead_end]`(등록도 없고 부모도 없다 = 그냥 못 본 것)를 가르는 것입니다.

지금 데이터엔 **등록 없이 등장하는 개체가 하나도 없어서** 그 구별이 이미 무너져 있습니다.
이건 「필요 없다」가 아니라 **「아직 그럴 일이 없어서 안전해 보인다」**입니다.
소스가 늘면 그날 살아납니다.

## 그래서 셋업할 때의 규칙

```
채운다      소스 행이 «말한» 것.  주어·목적어·한정어·시각을 행에서 그대로 옮긴다
안 채운다   규칙을 돌려서 «낸» 것. 대응·병합·분기·정규화 결과
```

⚠️ **결론을 원자로 쌓아도 «되돌릴 수는» 있습니다** — 실측: v2 원자 2,115개 전부가
`source_raw_ref` 와 `source_event_id` 를 가지고 있고, 원본 행 키가 그 안에 들어 있습니다.
**문제는 되돌릴 수 있느냐가 아니라, 규칙이 바뀐 날 «어느 원자가 낡았는지 아무도 안 알려준다»는
것입니다.** 그래서 결론은 원자가 아니라 읽는 쪽에 두는 편이 쌉니다.

## 그리고 이건 「무엇을 못 쓰게 한다」가 아닙니다

목적어가 **개체 참조**로 남아 있으면 낱말이 바뀌어도 그래프는 안 죽습니다.
실측 — v2 원자의 목적어 종류:

```
entity_ref  1,173   낱말을 다시 읽어도 «걸을 수» 있다
(none)        546   register
value         396   has_netdie — 걸을 수 없다. 값이면 값으로 충분한 것만 value 로
```

**`has_wafer` 를 나중에 다른 뜻으로 읽고 싶어도 재저장이 필요 없는 이유가 이것입니다** —
주어·목적어가 개체로 남아 있어서, 바뀌는 것은 «그 엣지를 뭐라 부르는가»뿐입니다.

# 9. 「GROUP 으로 읽는 건 본질이 아닌가」 — GROUP 이 아니라 «그룹이 낳는 것»이 갈린다

소유자 질문. §8 판별식을 GROUP 에 대 보니 **제 채점 하나가 틀렸습니다.**

## 판별식 — 「그룹에서 행 하나를 빼면 이 원자가 바뀌나」

라이브 소스 둘이 **둘 다 `unit: "group"`** 인데 서로 다른 일을 합니다.

```
lot_event   group_by event_group_key    안 바뀐다   되붙이기
   142행 -> 40분자.  has_wafer 원자 907개는 각각 «그 행의 그 웨이퍼»가 낸 것.
   그룹 크기가 값에 «안 들어간다». 행 분할은 저장 사정이지 세상이 아니다

dt_job      group_by dt_job             바뀐다      세기
   mappers/ledger_v2_dt_job_mapper.py:60   count = len(unit)
   매퍼 독스트링이 스스로 말한다 — "the count only exists once the rows are grouped"
```

## 실측 — `has_netdie` 값은 «행 수»다

```
저장된 값 == 그룹 행 수        396 / 396   (100%)
저장된 값 == max(dt_index)     171 / 396   ← 우연히 겹치는 것뿐
선언은 value = column dt_index  그런데 이 잡들에서 dt_index 는 «전부 null»
```

⚠️ `dt_index` 가 다른 데 쓰이는지는 «안 쟀습니다». 잰 것은 둘뿐입니다 —
저장된 값이 행 수와 396/396 일치한다는 것, 그리고 매퍼가 `len(unit)` 을 쓴다는 것.

## 그래서 §8 정정

```
§8 에서   has_netdie   🟢 본 것        <- 틀렸다
지금      has_netdie   🔴 결론 (집계)
```

## 결과가 무엇인가

**늦게 온 `dt_log` 행 하나가 저장된 72 를 조용히 낡게 만듭니다.** 그리고 지금:

```
잡당 has_netdie 원자   1개씩 (396/396)
supersedes 채워진 원자  «0» / 2,115      정정 경로가 아직 한 번도 안 쓰였다
```

새 원자가 73 으로 쌓이면 **72 와 73 이 둘 다 「사실」로 남습니다.** 무엇이 맞는지는
시각으로만 갈리고, 읽는 쪽이 그걸 알아서 해야 합니다.

## 소스 플랜 규칙

```
그룹이 «되붙이기»면   unit: group 이 맞다 — 본질.  흩어진 조각을 원래 한 사건으로 되돌린다
그룹이 «집계»면       그 값은 원장 밖에서 세는 편이 싸다 — 본질 아님
```

**왜 밖이 싼가:** 집계는 원본이 있는 한 언제든 다시 낼 수 있습니다(실측 — v2 원자
2,115개 전부가 `source_raw_ref` 를 들고 있습니다). 원자로 굳히면 다시 낼 수 있다는 이점은
그대로인데, **늦게 온 행이 그것을 낡게 만드는 위험이 새로 생깁니다.**

🔴 **「`has_netdie` 를 지워라」가 아닙니다.** 세어 둔 값이 빨라서 필요할 수 있습니다.
말씀드리는 것은 **그게 어느 부류인지 알고 두자**는 것입니다 — 결론을 원자로 둘 거면
낡는 날의 처리(`supersedes`)가 같이 서 있어야 하고, 지금은 안 서 있습니다.

# 10. GROUP 이 «본질»인 예시 — 셋은 이 시스템에 이미 있다

§9 의 판별식을 더 날카롭게 하면 이렇습니다:

```
집계 그룹    행을 빼면 «남은 원자의 값»이 바뀐다        72 -> 71
되붙이기     행을 빼면 «원자가 하나 없어질» 뿐,
             남은 원자의 «내용»은 그대로다              <- 이게 본질
```

## ① 참여자마다 한 행 — 양쪽이 서로를 가리킨다 🟢 v2 에서 «지금 도는» 것

`lot_event` 의 split 하나를 행 그대로 꺼내면:

```
행1   lot_id=NAB115     child=NAB115TA   slots=01:02:04:05:06:07:09:...  (19장 «남은 것»)
행2   lot_id=NAB115TA   parent=NAB115    slots=03:08:12:21:22:24         (6장 «간 것»)
```

**행 하나만 보면 「NAB115 가 19장을 갖는다」** — 그건 사건이 아니라 **사건 «후»의 상태**입니다.
두 행이 있어야 「25장 중 6장이 갈라져 나갔다」가 됩니다.

그리고 계보 엣지는 **행1 의 `child` 와 행2 의 `parent` 가 서로를 가리켜야** 나옵니다.
merge 도 같은 모양입니다:

```
행1   lot=DT-2601-003   parent=DT-2601-004   child=None
행2   lot=DT-2601-004   parent=None          child=DT-2601-003
행3   전부 None                                              <- 빈 행도 그룹 안에 있다
```

**한 행만 쓰면 같은 엣지를 두 번 쌓거나, 어느 행이 정본인지 사람이 골라야 합니다.**
그룹이 그 선택을 없앱니다. 규모: split 78행/39사건 · merge 58행/29사건.

## ② 항목마다 한 행 — 묶음이 곧 그 개체다 (모양은 있고, v1 이 만든 것)

```
{recipe: SYN-RCP-BOND, rev: 4} -> {param: pressure_MPa,  value: 0.35, unit: MPa}
                               -> {param: temp_C,        value: 145.0}
                               -> {param: purge_delay_s, value: 0}
       has_param 원자 35 · 레시피 7 -> 레시피당 5줄
```

**「레시피 rev 4」는 다섯 줄 «전부»입니다.** 한 줄은 레시피가 아닙니다.
rev 가 5로 올라가면 다섯 줄이 «같이» 바뀝니다 — 그래서 그 묶음이 사건입니다.

🟢 그런데 **그룹이 낳는 건 여전히 원자 다섯 개지 「5」가 아닙니다.** 판별식 통과.

## ③ 좌표마다 한 행 — 맵 한 장이 «한 번의 측정» (본질인데 «안 쓰고 있는» 자리)

```
observed 원자 114,510 · 서로 다른 run_uid 58,947 · 웨이퍼 2,631
한 (런, 웨이퍼) 가 가진 칸 수  최대 13
```

지금은 **그룹 없이 칸마다 원자**입니다. 그게 틀린 건 아닙니다 — 칸 하나의 관측은
그 자체로 사실이니까요. **문제는 「이 런에서 이 웨이퍼를 쟀다」는 사건이 원장에 없다는
것입니다.** `run_uid` 가 payload 안의 «값»이라 개체가 아니고, 그래서

```
「같은 런에서 무엇을 더 쟀나」          그래프로 못 묻는다
「이 런이 어느 장비·레시피였나」        걸 자리가 없다
```

**§8 의 「value 로 두면 걸을 수 없다」가 여기서 실제로 물립니다.**
run 을 개체로 올리면 그룹이 그 개체를 낳고, 칸 원자들은 그 아래 붙습니다.

## ④ 시작/끝 두 행 — 구간이 사건 (⚠️ 지금은 «여럿이 아니다»)

`track_in` 5행. `track_out` 은 **없습니다.** 모양은 알아볼 만하지만
**지금 층을 만들면 소비자 0인 축입니다.** 적어만 둡니다.

## 한 줄 요약

```
그룹이 «흩어진 조각을 원래 한 사건으로» 되돌리면      본질 — unit: group 이 맞다
그룹이 «여러 사건에서 새 값을 만들면»                 집계 — 원장 밖에서 세는 편이 싸다
```

**구별하는 법은 그룹의 크기가 원자의 «값»에 들어가는지 보는 것입니다.**
①②는 안 들어갑니다(원자 수만 늡니다). `dt_job` 의 `has_netdie` 는 들어갑니다.

# 11. 「집계면 원장에 안 올려도 되나」 — 앞의 반만 맞다. §9 가 조건을 빼먹었다

소유자 확인 질문. **제 §9 문장이 그대로는 위험해서 정정합니다.**

```
그룹 크기가 원자의 «값»에 들어간다   ->  집계다                    ✅ 확실
집계다                              ->  원장에 안 올려도 된다      ⚠️ «조건부»
```

## 빠진 조건 — 「그 수를 원장 «안»에서 다시 셀 수 있나」

집계를 안 올려도 되는 이유는 「언제든 다시 낼 수 있으니까」입니다.
**그런데 다시 세려면 «세어질 것»이 원장 안에 있어야 합니다.** 실측으로 갈립니다:

```
has_netdie 의 72
   그 잡을 주어로 가진 원자     has_netdie 1 · register 1  «그게 전부»
   predicate='transfer' 원자    0        subject_type='die' 원자   0
   dt_log 실제 행                72
   -> 원장 안에 그 잡의 die 가 «하나도 없다». 72 는 원장 밖에서만 셀 수 있다
      🔴 지금 지우면 그 사실은 «어디에도 없다» — 올려야 한다

랏의 웨이퍼 수 25
   has_wafer 원자로 세면        25
   -> 원장 «안»에서 세어진다. 이걸 has_netdie 처럼 값으로 또 올리면 «사본»이다
```

## 그래서 판별식은 두 단이다

```
1  그룹 크기가 값에 들어가나          들어가면 집계
2  그 수를 원장 «안» 원자로 다시 세나  세어지면 «올리지 않는다» (사본)
                                    안 세어지면 «올린다» (그것 말곤 없다)
```

## 이게 `has_netdie` 에 뜻하는 것

**지금은 올려야 맞습니다. 그리고 `transter_event` 가 착지해 die 원자가 쌓이는 날
같은 원자가 «사본»이 됩니다.** 그러니 —

```
지금        지우지 않는다
그날        다시 판정한다.  판정 근거는 「die 원자로 72 가 세어지나」 하나뿐이다
```

⚠️ 그리고 그날이 오면 **낡은 `has_netdie` 원자들이 조용히 남습니다.** §9 에서 말씀드린
`supersedes` 가 0/2,115 인 것이 여기서 다시 걸립니다.

## 예외 하나 — 사람이 «주장한» 수

누가 「이 잡은 72개였다」고 **보고한** 것이라면, 그건 도출이 아니라 **관측**입니다.
원장이 다시 셀 수 있어도 그 주장 자체가 사실이므로 올립니다.
**기계가 센 것과 사람이 말한 것은 같은 모양이지만 다른 것입니다** —
지금 `has_netdie` 는 기계가 센 것(`len(unit)`)이라 이 예외에 해당하지 않습니다.

# 12. 「즉 현재 원장 구성으로 파생 가능하냐 아니냐」 — 맞다. 「현재」가 두 가지인 것만

소유자 압축 (2026-08-23). **맞습니다.** 다만 그 한 줄로 채점하면 제가 §8 에서
「도출됨」이라 적은 넷 중 **셋이 잘못 걸립니다.** 갈라야 할 것은 이것입니다:

```
선언상 파생 가능      그 값이 다른 값을 «가질 수가 없다» (자유도 0)   -> 사본. 안 올린다
데이터상만 파생 가능   지금 우연히 겹칠 뿐, 선언은 안 막는다          -> 올린다
파생 불가            셀 재료가 원장에 없다                          -> 올린다
```

**이건 소유자가 이미 세운 잣대와 같은 것입니다** —
「이 칸이 서로 다른 두 값을 가질 수 있나. 하나만 나오면 사본이다.」
술어에 대고 물으면 「이 술어가 다른 원자들과 «어긋날 수» 있나」가 됩니다.

## 넷을 다시 채점 — 검증기와 walk 코드를 읽어서

```
slot_map      한정어 `wafer` 가 «required».  웨이퍼를 이름 대는 순간
              양쪽 has_wafer 이상을 말할 수 없다                    선언상    🔴 사본

register      `registration_probe` 는 문법상 «required: false».
              검증기 주석 그대로 — "one that emits no register needs no probe"
              (ledger/config_authoring.py:1538)
              -> «미등록 개체가 생길 수 있다». 지금 0인 건 우연        데이터상만 🟢 올린다

derived_from  slot_map 이 40/40 짝을 덮지만 «방향»을 안 말한다.
              walk 이 양방향을 뒤지는 이유가 그것 (ledger_trace.py:1456)
              -> 방향은 derived_from 에만 있다                       데이터상만 🟢 올린다

has_netdie    die 원자 0 · transfer 원자 0                          파생 불가  🟢 올린다
```

## 결론

**네 개 중 «진짜 사본»은 `slot_map` 하나입니다.** 나머지 셋은 오늘의 우연이거나
아예 파생 불가입니다.

그리고 이게 소유자 압축이 옳은 이유이기도 합니다 — **판정은 「지금 원장에 무엇이 있나」가
아니라 「지금 원장 «구성»(=선언)이 무엇을 허용하나」로 합니다.** 데이터를 세는 것은
후보를 «찾는» 방법이고, 확정은 선언을 읽어야 납니다.

# 13. 설비 노드를 넣으면 walk 이 wafer 문맥을 어떻게 유지하나

소유자 질문 (2026-08-23). **설비는 이미 원장에 있습니다 — 다만 «값»으로.**

```
processed_with / measured 의 payload 키   eqp 24,320 · chamber 11,645 · recipe · step · job 2,575
설비 34종 · 그 원자들이 닿는 웨이퍼 5,210장
```

⚠️ 처음에 `equipment` 라는 키로 찾아서 **「설비는 원장에 없다」고 읽을 뻔했습니다.**
키 이름은 `eqp` 입니다.

## 팬아웃 실측 — walk 이 통과하면 몇 장이 되나

```
SYN-DIF-01   2,575장      SYN-STK-B  1,288장     SYN-MI-02  913장
평균 601장 / 설비
```

## 🔴 한정어로 좁히려 했고, 실측이 그 생각을 죽였습니다

```
eqp + step        평균 309.8      eqp + chamber   평균 475.6
eqp + recipe      평균 538.1      eqp + 시(hour)   평균 198.4
eqp + job         평균   7.8   <- 77배!  ... 인 줄 알았다
```

**`job` 의 7.8 은 «가짜»입니다.** `job` 을 가진 원자는 24,320 중 2,575개(11%)뿐이고,
나머지 89% 는 `job = null` 로 **한 덩어리에 묶여** 평균을 끌어내린 것입니다.
`job` 이 있는 원자만 놓고 다시 재면:

```
eqp + job (job 있는 것만)   최대 1 · 평균 1.0 · 묶음 2,575
```

**웨이퍼당 하나입니다. 아무것도 안 묶습니다.** (`dt_log` 의 `dt_job` 과 이름만 같고
다른 것입니다 — 저기선 잡이 배치인데 여기선 웨이퍼 하나입니다.)

## 그리고 «안 좁혀지는» 설비를 열어 보니 — 그게 답이었습니다

```
SYN-DIF-01   원자 2,575 · 웨이퍼 2,575 (1:1) · job 0종 · step 1종 · 날짜 1종
payload      {"eqp":"SYN-DIF-01","step":"DIFFUSION","basis":"recipe_setpoint",
              "recipe":{"id":"SYN-RCP-DIFF","rev":"2"},"chamber":"CH-B","inferred":true, ...}
```

**`inferred: true` · `basis: recipe_setpoint`** — 「이 설정이 전부에 걸렸다」가
그 원자들이 «말하는 사실»입니다. 팬아웃 2,575는 결함이 아니라 **내용**입니다.
좁히려 드는 게 틀린 것이었습니다.

## 그래서 답은 두 겹입니다 — 새 선언 0개

### ① 통과는 «노드»가 아니라 «원자» 단위로 — 문맥은 원자가 들고 있다

walk 의 상태가 「지금 노드」면 설비에서 문맥이 사라집니다. 「지금 «원자»」면 안 사라집니다:

```
들어옴   W --processed_with--> {eqp:E, step:DIFFUSION, recipe:{id,rev:2}, chamber:CH-B}
나감     E 를 지나 나갈 때, «그 원자가 들고 있는 키들»과 같은 값인 원자로만
         -> chamber CH-B 로 좁히면 2,575 -> 1,288
```

🔴 **이 제한은 사람이 엣지별로 짜는 정책이 아닙니다.** 나가는 쪽을 고르는 것은
**들어온 원자가 이미 들고 있는 한정어**이고, 그건 선언에서 옵니다.
소유자 상설 —「특정 엣지를 걸어서 뽑아라 같은 하드 constraint 를 사람이 일일이
지정하면 안 됨」— 을 어기지 않는 유일한 모양입니다.

### ② 그래도 안 좁혀지면, «질량»이 알아서 죽입니다

이 세션 앞에서 잰 것 그대로입니다 — 슈퍼노드에서

```
질량   차수로 나뉘어 1/2575 로 «스스로» 죽는다      막을 필요가 없다
도달   «포화»한다 — 설비가 모든 것을 연결해 버린다   막아야 한다
```

**「순위만 내는 걸로 가자」고 하셨으니 질량 쪽이고, 그러면 설비 슈퍼노드는 따로 막을
장치가 필요 없습니다.** ① 은 도달로 물을 때를 위한 것입니다.

## 설비를 «개체»로 올릴 것인가

```
지금       eqp 는 payload 안의 «값».  §8 대로 — 값이면 걸을 수 없다
올리면     「이 설비가 무엇에 닿았나」를 그래프로 물을 수 있다.  그리고 팬아웃이 «답»이다
```

**§12 로 채점하면: 원장에 새로 쓸 원자는 없습니다.** `eqp` 는 이미 원자 안에 있고,
설비 노드는 **투영이 그 값을 노드로 내면** 생깁니다 — 재저장이 아니라 읽기입니다.
(이게 `APPLICATION_PROPAGATION_BRIEF` 공사 1 과 같은 자리입니다.)

**판정이 필요한 것 하나:** 「이 설비가 무엇에 닿았나」를 **그래프로** 물을 일이 있습니까?
있으면 투영이 `eqp` 를 노드로 내고, 없으면 값으로 두는 것이 맞습니다.

# 14. 🔴 소유자가 §4 를 풀었다 — 그리고 제 갈래 둘보다 낫다 (2026-08-22 23:38)

라이브 설정을 다시 읽었습니다. **제가 §4·§5 를 쓴 뒤 소유자가 이어서 작업하셨습니다.**

## 바뀐 것

```
die@1 키    {substrate_id, x, y}          ->  {mat_id, x, y, «mat_type»}
소스 이름    transter_event                ->  transfer_event   (오타 고쳐짐)
선언        bind.mappings {}  (빈 빨강)    ->  «다 참»
dt_log      34,939행                      ->  36,344행 (전사 씨앗 1,405행이 들어옴)
새 테이블    —                             ->  dt_transfer_log «있음» (아직 0행)
```

## 소유자 해법 — 엔터티를 안 늘리고 «한 타입을 두 세계»로 갈랐다

```
subject   die@1 { mat_id: core_wafer_id · mat_type: "Wafer" · x: c_wx · y: c_wy }
target    die@1 { mat_id: dt_job_id     · mat_type: "DT"    · x: b_wx · y: b_wy }
```

# 15. 허브에 안 휘둘리고 «자재» 문맥을 유지하는 법

소유자 질문 (2026-08-23). §13 은 «설비»였고 이건 «자재»입니다 — 답이 다릅니다.

## ① 허브의 대부분은 «투영이 만든 것»입니다 — 키를 접지 마십시오

**같은 원자 1,405개를 두 가지로 투영해서 차수를 쟀습니다:**

```
노드 = die «전체 키» (mat_id, mat_type, x, y)   1,405 노드 · 차수 최대 «1» · 평균 1.00
노드 = mat_id «만»                                 10 노드 · 차수 최대 «261» · 평균 140.5
```

**허브는 데이터에 없습니다. 키를 접는 순간 생깁니다.** 그리고 문맥이 사라지는 지점이
정확히 거기입니다 — DT 한 장에 코어가 «10장» 섞입니다(10장 섞인 DT 9개 · 7장 1개).

🔴 **이 원칙은 이 코드베이스에 «이미» 있습니다** — `ledger_subgraph.quantity_node_id` 독스트링:
모델 이름을 신원에 넣는 것은 «의도»이고, 공유 노드 하나면 두 모델러의 주장이
「아무도 안 한 제3의 것」으로 접합된다. 자재도 같습니다.

## ② 진짜 허브(설비·레시피)에서는 «재시작»이 문맥입니다

설비는 접기와 무관하게 진짜 허브입니다(§13 — `eqp` 평균 601장).
거기선 자재를 «들고» 갈 수 없고, **그게 맞습니다** — W → E → W′ 에서 W 가 사라지는 것은
「W 와 W′ 가 E 를 공유했다」가 대칭적 사실이기 때문입니다.

**유지되는 것은 «씨앗»입니다.** 개인화 페이지랭크의 재시작 벡터가 곧 자재 문맥이고,
허브를 건너 멀어진 것은 재시작 확률만큼 «자동으로» 약해집니다. 질량은 1/deg 로 스스로 죽습니다.

## ③ 접기는 «출력»에서 하고 «그래프»에서 하지 않습니다

「이 코어 웨이퍼가 어느 DT 들로 갔나」는 **결과를 `mat_id` 로 묶으면** 나옵니다.
그래프에서 접으면 차수 261 짜리 허브가 생기고, 그건 되돌릴 수 없습니다.

# 16. 초기 설비는 «약한 허브»가 아니라 «강한 다리» — 그리고 경로가 그걸 드러낸다

소유자 (2026-08-23): 「설비 도입 초기에는 설비가 슈퍼노드가 아니라서 설비 매개해서 섞이지
않을까? collect 후 결과에서 걸은 경로도 나와?」 — **§13 ② 가 규모가 클 때만 참이었습니다.**

## 지적이 맞습니다 — 1/deg 는 «커야» 방어가 됩니다

```
설비 차수     2 -> 이웃 하나가 0.5000      직접 이웃(1.0) 의 절반
             3 -> 0.3333                 «강한 다리»
            10 -> 0.1000
           601 -> 0.0017                 여기서야 무시된다 (지금 eqp 평균)
          2575 -> 0.0004
```

## 그런데 그건 «결함이 아닙니다»

차수 정규화는 허브 방어가 아니라 **「이 공유가 얼마나 특별한가」**를 재는 것입니다.
정말 3장만 그 설비를 거쳤다면 「그 셋이 공유한다」는 **강한 정보**이고 높은 질량이 맞습니다.

## 🔴 진짜 위험은 다른 데 있습니다 — 「희귀해서 3」과 「덜 들어와서 3」

```
희귀해서 3      그 설비를 실제로 3장만 거쳤다        높은 질량이 «옳다»
덜 들어와서 3   500장을 거쳤는데 3장만 기록됐다      그 셋이 «근거 없이» 강해진다
```

**순위만 보면 둘이 같습니다.** 그리고 이건 임계값으로 못 가릅니다 — 임계값은
「희귀해서 3」인 진짜 신호도 같이 죽입니다.

## 그래서 답은 «경로»입니다 — 실행해서 확인했습니다

`subgraph(..., collect="Entity")` 를 케이스 1 · 컨트롤 2 로 직접 불렀습니다:

```
walk.start       {"positive": 1, "negative": 2}
propagation      state "ranked" · contrast «"contrasted"» · ranked 42 · top_set 1
```

rank 1 이 실제로 낸 경로:

```
씨앗 부호 +   CL-2601-002  ->  claim:slot_map  ->  CL-2601-002-A4
씨앗 부호 −   CL-2601-005  ->  claim:slot_map  ->  CL-2601-005-A5
                           ->  claim:derived_from  ->  CL-2601-002-A4
```

**같은 후보에 케이스와 컨트롤이 «둘 다» 닿았고, 각각 어느 길로 왔는지가 나옵니다.**
홉마다 `atom`(원자 id)과 `ref`(원본 행)까지 붙습니다.
소유자가 말씀하신 리포트 모양 — 섞여 나오되 «이건 디펙 없는 쪽» 이라고 말해 주는 것 — 이
바로 이 구조입니다.

## 🔴 다만 지금은 «1등 층만» 경로를 답니다

```
ledger_subgraph.py:947    for item in layers[0]:  item["evidence"] = _evidence(...)
실측                      ranked 42 · evidence 를 가진 것 «1»
```

rank 2 이하는 **경로도 부호도 없습니다.** 그래서 「이 wf 는 디펙이 없습니다」를
**말할 수가 없습니다** — 1등이 아니라는 것만 압니다.

📎 **부호는 이미 계산돼 있습니다.** `:940` 이 후보마다
`"reach": [from_positive, from_negative]` 를 들고 있는데, `:950-954` 의 산출 dict 에
**안 실립니다.** 즉 「섞였다는 것을 말하기」에 필요한 값이 이미 있고 안 나갈 뿐입니다.

🔴 **제안이 아니라 보고입니다.** 공사 1 → 3 라운드가 그 파일에서 돌고 있어
지시서에 안 넣었습니다. 넣을지는 총괄·소유자 판단입니다.

⚠️ 곁가지 — 제 첫 출력에서 「부호 없음」을 `-` 로 찍는 바람에 «음의 부호»로 읽을 뻔했습니다.
표시 문자를 갈라서 다시 쟀습니다.

# 17. 「walk 이 진짜 쓸만한가」 — 소유자 상설 질문. 지금까지의 정직한 채점

소유자 (2026-08-23): 「아무튼 walk 이 진짜 쓸만한지 스스로 계속 생각해봐야 해」.
**판정을 내리지 않고, 실측으로 갈린 것과 안 갈린 것을 적습니다.**

## 🟢 실측이 «쓸만하다»고 말하는 것

```
1  대조가 답을 «좁힌다»        컨트롤 없음 -> top_set 12 (전부 동점 = 답이 없는 것과 같다)
                              컨트롤 둘   -> top_set «1»
   순수 순위가 못 하는 일이고, 이 세션에서 유도한 「대조 = 전파의 1차 절단」이 실제로 돈다

2  답이 아니라 «근거»가 나온다   경로가 홉마다 atom(원자 id) + ref(원본 행)
                              씨앗마다 갈라지고 부호(+/−)가 붙는다

3  응용이 «설정»으로 갈린다      collect: Entity / Quantity — 코드 분기 없이
```

## 🔴 실측이 «아직 못 미덥다»고 말하는 것

### ① 홉을 늘려도 «안 좁혀진다» (오늘 새로 잰 것)

```
hops    2      3      5      8     12
nodes   67    119    309    400    400      <- 8 부터 노드 상한(400)에 걸려 «안 늘어난다»
ranked  13     13     28     54     54
top_set 12     12     12     12     12      <- «한 번도 안 줄어든다»
```

**깊이는 후보를 늘릴 뿐 답을 좁히지 못합니다.** 좁히는 것은 대조뿐입니다.
그리고 hops 8 부터는 «상한이 먼저» 옵니다 — 실제 팹 규모에선 훨씬 일찍 올 것입니다.

### ② 경로가 «1등 층만» (§16) — 42 중 1. 「이 wf 는 깨끗합니다」를 못 말한다
### ③ 자재 라벨이 좌표로 나온다 (§15) — 사람이 결과를 읽을 수 없다
### ④ 초기 설비에서 「희귀해서 3」과 「미기록이라 3」을 못 가른다 (§16)

### ⑤ 🔴 가장 큰 것 — «진짜 질문»에 아직 안 태웠다

제가 돌린 것은 합성 랏의 계보입니다. 소유자의 실제 질문(「이 디펙의 원인」)은
**관측 원자가 필요한데 `observed` 술어가 v5 어휘에 없습니다** (§12).

## ⚠️ 그리고 오늘 구현자가 스스로 잡은 것이 제 ①번을 «누릅니다»

구현자 보고(총괄 인용): 첫 홉 규칙을 **변이시켰는데 테스트 16개가 전부 초록**이었고,
규칙이 맞아서가 아니라 **「지배 비교가 같은 부호끼리만 하고, 픽스처가 그 경우를 못 만들어서」**
였습니다.

**제가 방금 잰 「대조가 12 → 1 로 좁힌다」도 같은 위험 위에 있습니다** —
좁혀진 것은 봤지만 **그 좁힘이 «옳은» 좁힘인지는 안 봤습니다.**
좁아졌다는 사실은 맞다는 증거가 아닙니다.

## 그래서 — 판정을 미루고, «무엇이 판정할지»만 못 박습니다

```
결정적 시험    불량 원인 질문 하나를 «사람이 답을 아는» 케이스/컨트롤로 태운다
              top_set 이 작고 1등이 «아는 원인과 맞으면»      -> 쓸만하다
              top_set 이 크거나 1등이 엉뚱하면                -> 안 쓸만하다.  깊이로 못 고친다
막는 것        v5 어휘에 관측 술어가 없다.  그게 먼저다
그때까지       「대조가 좁힌다」는 것만 참이고, 「맞게 좁힌다」는 «미확인»으로 둔다
```
