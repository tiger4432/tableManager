# 점검 — 공정 컨텍스트(재료 상태)가 «추적으로 유도»되나

> 소유자: 「공정 컨텍스트는 온톨로지 추적으로 불가한지 점검」 · 총괄 20:3x
> 🔴 읽기 전용 · 코드 0줄 · 선언 안 씀. 아래는 전부 실행해서 나온 숫자입니다.

---

# 0. 답 — **지금은 «유도 안 됩니다». 26%만 됩니다**

그리고 **모자란 것은 «새 필드»가 아니라 «재료»입니다.**

---

# 1. 시험한 것

「공정 원자(`processed_with`)마다, 그 웨이퍼의 «직전 전사»가 도착한 곳을 보면
그때의 재료 상태가 나오나」 — 전사의 `to.type` 이 이미 상태 이름을 답니다:

```
package_gate 64,375 · dt_job 4,640 · dt_slot 3,775 · bond_layer 174
```

공정 원자 25,120 과 전사 원자 72,964 를 시각순으로 «맞붙여» 봤습니다.

---

# 2. 결과

```
전사 기록이 «아예 없는» 웨이퍼       18,601   74.0%   🔴 유도 «불가»
공정이 «첫 전사보다 앞»               3,944   15.7%   ✅ 「아직 웨이퍼 상태」로 유도됨
package_gate 뒤                       2,575   10.3%   ✅ 유도됨
────────────────────────────────────────────────────
유도되는 것 합계                      6,519   26.0%
```

🔴 **그리고 유도된 상태가 «한 종류»뿐입니다.** `dt_job` · `dt_slot` · `bond_layer` 전사가
원장에 8,589건 있는데, **그 뒤에 공정 원자가 «하나도» 안 옵니다.**
즉 소유자가 가르고 싶어 하시는 축(웨이퍼 / 본딩 / DT)이 **데이터에 아직 없습니다.**

---

# 3. 🔴 왜 안 되나 — 두 쪽이 «다른 웨이퍼»를 다룹니다

소스별로 갈라 보면 원인이 분명합니다:

```
소스                     공정 원자    그중 «전사 기록 없는» 웨이퍼
syn_recipe_book           10,442        7,867   (75%)
syn_eqp_log                6,378        6,378   «100%»
syn_mes_queue              2,575        2,575   «100%»
syn_mi_gauge               1,781        1,781   «100%»
syn_fab_mes                3,000            0   (0%)   ✅
syn_complex_composite        944            0   (0%)   ✅
```

**`syn_eqp_log` 이 결정적입니다** — 이 소스는 전사 원자를 «67,240건» 내면서,
자기 공정 원자 6,378건은 **전혀 다른 웨이퍼**에 붙입니다.
같은 소스 안에서도 두 집단이 갈립니다.

---

# 4. 그래서 «무엇이 모자란지» 이름을 댑니다

```
1  공정 원자가 붙는 웨이퍼에 «전사 기록»이 없습니다  (74%)
   -> 선언 문제가 «아닙니다». 인제션이 그 웨이퍼의 이동을 안 싣고 있습니다

2  선행하는 도착 종류가 package_gate «하나»뿐입니다
   -> dt_job · dt_slot · bond_layer 뒤에 공정이 «안 옵니다»
   -> 소유자가 원하시는 세 상태 중 «둘»은 데이터에 사례가 0 입니다
```

**둘 다 «필드를 더해서» 풀리지 않습니다.** 선언을 늘려도 그 웨이퍼엔 여전히 이동 기록이 없습니다.

---

# 5. ⛔ 하면 안 되는 지름길 — 스텝 «이름»으로 가르기

`BOND_PREP` · `PRE_BOND_MI` · `PLASMA_ACTIVATION` 처럼 **이름에 상태가 보입니다.**
그래서 이름으로 가르고 싶어집니다. **그건 하드코딩입니다** —
다른 팹에서 그 낱말이 다르면 조용히 틀립니다. 소유자 DoD(「코드 0줄, 선언 교체만」)에 어긋납니다.

---

# 6. ③ step_family 없는 956건 — 따로 셌습니다

```
전부 «한 소스»입니다     syn_complex_composite
step 이름은 «있음»       BOND_PREP · PHOTO_COAT_01 · INGOT_RELEASE · PRE_BOND_MI …
다른 축                  recipe 956 · eqp «0» · chamber «0»
```

**결측이 아니라 «그 소스가 step_family 를 안 내는 것»입니다.**
단계로 묶으면 이 소스가 «통째로» 빠지고, 화면엔 그냥 안 보입니다.

---

# 7. 🔴 이 점검이 §12 규칙의 사례입니다

「지금 26%가 유도된다」는 **「유도 가능하다」는 뜻이 아닙니다.**

```
유도되는 26%    재료(전사 기록)가 «마침» 있는 것
안 되는 74%     재료가 «없는» 것.  그리고 선언은 그 재료를 «보장하지 않습니다»
```

**선언을 늘리기 전에 물어야 할 것이 「필드가 있나」가 아니라 「재료가 있나」였습니다.**
이번엔 재료가 없습니다.

---

# 8. 소유자 질문 — 「챔버가 DT 공정 챔버였으면 DT 쪽 PC 계측으로 연동되나. 유니버셜한 API 로 되나」

목업 카드(`챔버 파티클 / SYN-BD-02 · CH-A / 8/19 03:20 · BONDING 겹침`)에 대한 질문입니다.
**두 질문이고 답이 다릅니다.**

## 답 1 — 지금 «연동 안 됩니다». 셋이 없습니다

```
① DT 쪽에 chamber 가 «0»
   dt_log · dt_transfer_log · transfer_event · dt_job — 원자도 컬럼도 «없음»
   (chamber 를 내는 것은 syn_recipe_book 7,867 · syn_eqp_log 3,778, 둘 다 processed_with)

② 파티클 계측이 «없습니다»
   measured 의 metric 은 넷뿐: etched_cd · photo_overlay_error
                              post_clean_surface_roughness · post_cmp_film_thickness
   각 36건 · 설비 1종.  파티클 계측 원자 «0»

③ 챔버가 «비교 축으로 선언 안 됨»
   bonding_log 축 일곱   wafer · bond_eqp · bond_lot · dt_lot · core_lot · b_bn · stack_height
   inspection_run 축 둘  scan_recipe · scan_eqp
   -> 챔버가 «어느 쪽에도 없습니다»
```

⚠️ **그래서 목업의 「CH-A」가 어디서 오는지 제가 «못 찾았습니다».**
비교 축 선언에도 없고 그 테이블들의 컬럼에도 없습니다. 원자 payload 에는 있습니다(11,645).
**목업이 지금 데이터 경로보다 «앞서» 있을 수 있습니다** — 그린 사람에게 확인이 필요합니다.

## 답 2 — 🟢 「유니버셜한 API 로 되나」는 **네. 이미 그 모양입니다**

비교 축이 코드가 아니라 **선언 파일**에서 옵니다:

```
server/config/siblings_axes.json      (지금은 sample 폴백 중)
  attribution: [ { relation · about · label · key_column · join · axes:[{name,label,column}] } ]
```

**DT 챔버 축을 만들려면 그 파일에 항목 하나를 더하면 됩니다 — 코드 0줄.**
조건은 「그 컬럼이 실제로 있을 것」이고, 지금은 «없습니다»(답 1의 ①).

## 🔴 다만 — 선언이 «두 군데»이고, 축은 온톨로지를 «안 봅니다»

```
원장 어휘   server/config/ontology/ledger_config.json    원자를 «만드는» 선언
비교 축     server/config/siblings_axes.json             원자를 «가르는» 선언
                                                        -> «소스 테이블»을 봅니다
```

축 선언이 relation + join + column 입니다. **즉 「온톨로지로 연동」이 아니라
「테이블 조인 선언」입니다.** 유니버셜하기는 한데 **온톨로지 축은 아닙니다.**

```
그래서   챔버로 잇는 두 길이 있습니다
  가  테이블 축으로      siblings_axes 에 선언.  코드 0줄.  «단, 컬럼이 있어야»
  나  온톨로지 노드로     챔버를 개체로 올린다 (설비와 같은 부류 — 소유자가 「설비는 노드」라 하셨음)
      -> 그러면 걷기로 이어지고, 축 선언 없이 «어느 화면에서나» 붙습니다
```

**「DT 상 PC 계측으로 연동」처럼 «다른 공정 단계의 계측»까지 이으려면 (나)여야 합니다** —
(가)는 한 테이블의 조인 규칙이라 단계를 건너뛰지 못합니다.

---

# 9. 🔴 정정 — 「DT 상태 사례가 0」인 이유가 «집단»이 아니라 «순서»였습니다

배경으로 돌려 둔 SQL 판이 끝났고 **제 파이썬 결과와 정확히 일치**합니다:

```
SQL     직전 전사가 있는 것 2,575 (10.3%) · package_gate 만
파이썬   package_gate 2,575 + 「전사 없음」 18,601 + 「첫 전사 앞」 3,944 = 25,120
        18,601 + 3,944 = 22,545  <- SQL 의 「직전 전사 없음」과 «같은 수»
```

**두 방법이 같은 답을 냈습니다.** 그런데 SQL 판이 제가 안 뽑았던 열을 하나 더 냈습니다:

```
to.type=dt_slot   원자 3,775 · 웨이퍼 «2,650»   <- package_gate(2,575)보다 «많다»
```

## 그래서 다시 재 봤더니 — 겹칩니다

```
dt_slot 전사 웨이퍼 2,650 · 공정 원자 웨이퍼 5,210 · «겹침 2,609» (98.5%)
```

**제 §3 이 「두 쪽이 다른 웨이퍼를 다룬다」고 했는데, dt_slot 에 대해서는 «틀렸습니다».**
거의 다 겹칩니다.

## 그러면 왜 「DT 상태의 공정」이 0 인가 — 순서입니다

겹치는데도 **dt_slot 전사 «뒤»에 오는 공정 원자가 0** 입니다. 즉:

```
이 데이터에서 순서가 «항상» 공정 -> DT 입니다.
웨이퍼가 DT 자리로 간 «뒤»에는 processed_with 가 «한 건도» 안 기록됩니다
```

**그래서 「DT 상태에서의 공정」이 없는 것은 집단 문제가 아니라 «순서» 문제입니다.**
그리고 이건 둘 중 하나입니다 — 제가 «못 가릅니다**:

```
가  실제 공정이 그렇다        DT 가 하류라 그 뒤에 공정이 «없다»  -> 결측이 아니라 사실
나  기록이 거기서 끊긴다      DT 뒤 공정이 있는데 원장에 «안 들어온다» -> 인제션 구멍
```

**소유자만 답할 수 있습니다: 「DT 자리에 올린 뒤에도 공정이 있습니까?」**
있으면 (나)이고 인제션을 봐야 합니다. 없으면 (가)이고 **소유자가 가르고 싶어 하신
「DT 상태 공정」이라는 축 자체가 이 팹에 «없는» 것입니다.

## §3·§4 에 대한 정정 범위

```
그대로   74%(18,601)가 «전사 기록이 아예 없다»       — 소스별 실측 그대로입니다
정정     「두 쪽이 다른 웨이퍼를 다룬다」는 dt_slot 에 «안 맞습니다» (98.5% 겹침)
정정     DT 상태 사례 0 의 원인은 «순서»이고, 그 순서가 사실인지 구멍인지는 «미확인»
```
