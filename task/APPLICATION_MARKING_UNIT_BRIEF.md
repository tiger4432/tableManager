# 설계 — 마킹의 단위: 「노드 또는 노드의 집합」

> 소유자 판정 (2026-08-23 16:0x): **「온톨로지 상 “노드 또는 노드의 집합”이 그림의 한 점이
> 되어야 하고 그것이 마킹의 단위」** · 총괄 전달
> 🔴 설계만. 코드 0줄. 라이브 config 읽기만. 아래 숫자는 전부 직접 재거나 실행한 것입니다.

---

# 0. 결론 넷 — 먼저 놓습니다

```
①  마킹 객체는 «한 타입»입니다 — 그리고 «이미» 한 타입입니다. 새로 만들 것이 없습니다
②  집합의 신원도 «이미» 있습니다.  collection 을 넓히지 마십시오
③  트렌드 축의 point 는 이것과 «같은 것»입니다. 흡수됩니다 — 축이 아니라 «계약»입니다
④  🔴 그런데 맵 위 다이는 «지금 마킹이 안 됩니다». 오늘 찾은 그 벽의 네 번째 얼굴입니다
```

---

# 1. ① 마킹 객체의 정의 — **「하나 | 집합」이 아니라 그냥 «노드 id»**

노드 id 체계를 열어 봤습니다. 여덟 종류가 **전부 같은 모양**입니다:

```
ledger-entity:v1:<b64>              개체 하나 (Wafer · Lot …)
ledger-finding-point:v1:<b64>       맵 위의 한 칸 = 발견 하나
ledger-finding-collection:v1:<b64>  발견들의 «묶음»
ledger-event / claim / value / quantity / enrich-action : v1 : <b64>
```

**「집합」도 id 가 있습니다.** 그러므로 「노드 하나」와 「노드의 집합」은 **두 타입이 아닙니다** —
둘 다 노드 id 하나입니다.

```
마킹 = 노드 id 하나.   끝입니다.
```

🔴 **그래서 «마킹 객체»라는 새 타입을 만들지 마십시오.** 만드는 순간 정본이 둘이 됩니다.

---

# 2. ② 집합의 «신원» — **판정: 넓히지 않습니다. 이미 됩니다**

총괄 질문: 「집합을 마킹했다가 다시 풀 때 같은 집합이 나와야 한다.
지금 collection 은 발견 묶음 전용인데 소유자가 말한 «노드의 집합»이 더 넓다 — 넓힐까?」

## 지금 collection 이 신원을 «어떻게» 갖는지 열어 봤습니다

```
id 안에 든 것   ["Wafer", {"wafer":"W1"}, "void", "SEM", "MAP7"]
                즉 (타입 · 키 · 불량종류 · 방법 · 맵)
```

**멤버 목록이 아니라 «질의»입니다.** 그래서 다시 풀면 그 질의를 다시 돌려
**같은 집합이 나옵니다** — 신원이 «도출»됩니다. 저장할 것이 없습니다.

## 그리고 «넓힐 필요»가 없는 이유 — 접힌 노드 «자신»이 신원입니다

소유자가 말씀하신 「노드의 집합」을 두 갈래로 갈라 보면:

```
접기로 생긴 집합   「이 웨이퍼의 다이들」    = 접기 규칙 + 키
                   -> 그 집합의 신원은 «그 웨이퍼 노드 id» 자신입니다.
                      「그 아래 다이들」은 걷기가 풀어 줍니다. 새 id 가 필요 없습니다

임의로 고른 집합   「이 다이 다섯 개」(올가미)
                   -> 질의로 못 씁니다. 열거해야 하고, 신원이 «없습니다»
```

**소유자 원문이 「그림의 한 점」이라고 했으므로 마킹 단위는 «항상» 첫째입니다** —
차트의 점은 무언가가 접혔기 때문에 «존재»합니다.

```
판정   collection 을 넓히지 «않습니다».  별도 신원도 «만들지 않습니다»
       점이 Wafer 로 접혀 있으면 -> 마킹 = 그 Wafer 노드 id
       점이 die 로 접혀 있으면   -> 마킹 = 그 die 노드 id
       점이 발견 묶음이면        -> 마킹 = 그 collection 노드 id  (이미 있음)
```

⚠️ **임의 집합(올가미)은 이번 범위가 아닙니다.** 지금 그 요구가 «하나도» 없고,
미리 층을 만들면 소비자 0 인 축이 됩니다. **필요해지는 날 다시 올립니다.**

---

# 3. ③ 트렌드 축의 `point` 와 같은 것인가 — **같습니다. 흡수됩니다**

앞서 낸 트렌드 축 지시서에서 `point` 를 「점 하나가 무엇인가 — 어느 노드 종류로 접는가」라고
적었습니다. **그게 바로 마킹 단위입니다.**

```
전     축 다섯:  point · x · y · color · shape       (다섯 다 «축»)
후     계약 하나 + 축 넷
       point  = «이 점이 어느 노드인가» — 축이 아니라 «마킹 계약»
       x·y·color·shape = 그 노드에서 «걸어가서 읽어 오는» 것
```

🔴 **이 정정이 중요한 이유:** `point` 를 축으로 두면 「차트 설정」으로 읽히고,
마킹은 «따로» 만들게 됩니다 — 정본이 둘이 됩니다.
`point` 를 계약으로 두면 **점을 클릭하는 것이 곧 그 노드를 마킹하는 것**이고,
클릭한 것을 그대로 다음 걷기의 «씨앗»으로 넘길 수 있습니다.

📎 트렌드 축 지시서 §2 의 「축 = (걸음, 읽을 것)」은 그대로 유효합니다.
바뀌는 것은 **point 가 그 다섯에서 빠져 위로 올라간다**는 것뿐입니다.

---

# 4. ④ 🔴 알려진 벽 — 맵 위 다이는 «지금 마킹이 안 됩니다»

노드 id 를 실제로 디코드해 봤습니다:

```
Wafer        ✅ 씨앗 가능
Lot          ✅ 씨앗 가능
collection   ✅ 씨앗 가능
die          ⛔ 「subject type 'die' is not a declared entity type」
DTJob        ⛔ 같은 거절
WaferLeg     ⛔ 같은 거절
```

**소유자 원문 ①이 「맵 위의 좌표 등을 모두 한 객체로 인식하게」인데,
맵 위의 그 다이가 지금 «풀리지 않습니다».**

그리고 이건 오늘 이미 세 번 만난 벽의 **네 번째 얼굴**입니다:

```
1  씨앗 검증     die 를 씨앗으로 못 준다
2  노드 라벨     die 이름 대신 «좌표»가 뜬다
3  걷기 축       traversable 이 v1 에만 있다
4  «마킹»        die 노드를 마킹 대상으로 못 만든다      <- 이번에 드러난 것
```

**원인은 하나입니다** — 검사가 라이브 선언이 아니라 v1 하드코딩 목록을 봅니다.
`die@1` 은 라이브에 «선언돼 있고» 원자 1,405개가 그 선언으로 쓰였습니다.

```
그러므로   이 설계는 «완성»되지만, 맵 다이 마킹은 ③(은퇴)이 열려야 «발화»합니다
           설계를 미룰 이유는 없습니다 — Wafer · Lot · collection 은 지금도 됩니다
```

# 5. 그래서 남길 것 / 갈아엎을 것 (총괄 구분에 답합니다)

```
🟢 남긴다   노드 id 체계 여덟 종류
            근거: 「집합」의 신원이 «그 안에» 이미 있습니다 (§2 실측).
                  버리면 마킹 정본이 둘이 됩니다
🔴 교체     축 아홉짜리 평평한 마킹
            근거: 그 목록에 «맵 위 다이»가 없습니다. 노드 모델에는 있습니다(point 종류)
```

# 6. 수락 단언

```
A  차트의 점을 클릭하면 «그 노드 id» 가 나온다.  새 마킹 타입이 «없다»
B  그 id 를 그대로 다음 걷기의 씨앗으로 넣으면 «돈다» (Wafer·Lot·collection 으로 확인)
C  집합을 마킹했다 풀면 «같은 집합»이 나온다 — 저장한 멤버 목록 «없이»
D  point 를 Wafer -> collection 으로 바꿔도 마킹 코드가 «안 바뀐다» (둘 다 노드 id 라서)
E  die 로 바꾸면 «거절되고», 거절문이 「v1 목록에 없다」가 아니라
   사람이 읽을 사유를 말한다
```
