# 🔴 맨 앞 — 체인이 «못 하는 것» 다섯 (총괄이 받을 목록)

전략은 「체인이 표를 만들고 원장이 그대로 읽는다」입니다. 아래 다섯은 **표를 아무리 잘 만들어도
남습니다** — 체인의 능력 밖이거나, 애초에 체인의 문제가 아닙니다.

## ① 🔴 목적어의 «값»은 «수»여야 합니다 — 글자는 값이 될 수 없습니다
```
setup_bundle.predicate_claim    object.kind "value"  ->  역할 종류 "quantity"
roleframe._validate_role_value  quantity  ->  JSON 수 · 유한 · «bool 도 거절»
=> 표의 그 칸이 글자면 술어의 목적어로 «못» 실립니다
회피로  글자는 «수식어»로 실립니다 (수식어 역할은 attribute -> `_scalar` 가 문자열을 받습니다)
```
🔴 **이건 체인이 못 고칩니다.** 표를 바꿔도 값의 «종류»가 안 바뀝니다.
남는 선택은 셋이고 셋 다 «체인 밖»입니다 — 값을 수로 바꾸거나, 글자를 수식어로 옮기거나,
목적어 종류를 늘리거나(어휘 결정).
📌 **총괄 판정이 필요한 자리는 여기입니다.** 나머지 넷은 작업입니다.

## ② 바인딩된 컬럼은 «모든 행»에서 비어 있으면 안 됩니다 — 선택 수식어도 그렇습니다
```
roleframe._evaluate_binding                     kind "column" 의 값이 결측이면
                                                `missing_binding_value` 로 «던집니다»
roleframe.DeclarativeRoleMapper.interpret_unit  선언된 바인딩을 «전부» 평가합니다
=> 「선택」은 «바인딩을 안 하는 것»이지 「비어 있어도 되는 것」이 아닙니다
```
체인은 채우거나 그 행을 «안 내보낼» 수 있습니다. 그런데 —
🔴 **이미 내보낸 행을 «거둬들이는» 길이 체인에 없습니다** (`mapper_sdk.df_to_updates` 는
`{"updates": [...]}` 만 만듭니다 — 삭제 항목이 없습니다). 그래서 「나중에 무효가 된 행」은
표에 남고, 원장 쪽에서 매번 거절로 나타납니다.

## ③ 표와 그 «키»는 체인이 만들지 않습니다 — 먼저 선언돼 있어야 합니다
```
mapper_sdk.df_to_updates    crud.TABLE_CONFIG 에서 composite_key_source / business_key 를 읽습니다
그 표가 TABLE_CONFIG 에 «없으면»  둘 다 None -> 검사가 하나도 안 걸리고
                                business_key_val 도 안 붙습니다 -> «식별자 없는 쓰기»
```
그 함수의 주석이 그 결과를 이미 적어 두었습니다 — 「행은 들어가고, upsert 가 다시 못 찾고,
매 실행이 사본을 하나 더 넣는다」. 🔴 **조용합니다.** 그러니 이 페이즈의 표는
「체인이 만든다」가 아니라 **「선언해 두고 체인이 채운다」**입니다.

## ④ 시각 컬럼의 «타입»은 체인이 정하지 못합니다
```
roleframe._validate_role_value   time  ->  «타임존이 붙은» datetime 이 아니면 `invalid_time_role`
roleframe.DeclarativeRoleMapper  time 역할은 «준비 경계가 해석한 순간»에서 채웁니다.
                                 바인딩이 가리키는 칸은 «읽지 않습니다» (2026-08-23 판정)
```
체인은 값을 넣을 뿐이고, 그것이 무엇으로 «읽히는지»는 표의 컬럼 타입과 준비 경계가 정합니다.
⚠️ **미검증 하나:** 시각 컬럼을 타임존 있는 타입으로 두면 준비 경계까지 타임존이 살아 오는지
저는 실행으로 확인하지 «않았습니다». 명세로는 답할 수 없는 것이라 그대로 올립니다 —
확인 방법은 「그 타입의 컬럼 하나로 소스를 세워 원자가 서는지」이고, 그건 구현자 자리입니다.

## ⑤ 한 행이 «한» 원자가 되려면 선언 쪽에서도 셋을 지켜야 합니다
체인의 일이 아니라 «선언의 일»인데, 표를 그렇게 만들어도 이 셋이 어긋나면 한 행이 여러 원자가
됩니다.
```
map.unit.kind = "row"           아니면 한 단위가 여러 행입니다 (선택지 event · row · group_by)
bind.mappings 가 «하나»          매핑 하나가 문장 하나이고, 엔진은 매핑마다 한 번 방출합니다
read.registration_probe 없음     탐침이 있으면 등록 원자가 «따로» 더 섭니다
```

# ① 원자는 «무엇»으로 이루어지나 — 선언에서 뽑은 것

## 봉투 (`ledger/envelope.py`)
원자가 저장되는 칸은 `ROW_COLUMNS` 가 정본입니다. 그중 **번역이 채워야 하는 것**과
**엔진이 스스로 채우는 것**이 갈립니다.

```
번역이 채운다   subject_type · subject_keys · predicate · object_kind · object_payload
              occurred_at · source_who · source_translator_ver · source_raw_ref
엔진이 채운다   id (uuid7, 쓰기 직전) · source_event_id · source_event_state
여기서 안 쓴다  supersedes (정정 경로) · occurred_at_basis (시각의 «성격»을 원자가 스스로 말할 때)
```
🔴 `check_envelope` 가 «내용과 무관하게» 묻는 것 넷: 세계 시각이 있나(타임존 포함) · 출처가 있나 ·
번역기 판이 있나 · 원문으로 돌아갈 길이 있나. **이 넷이 없으면 그 원자는 서지 않습니다.**
그리고 `freeze_payload` 가 목적어 값을 봅니다 — 유한하지 않은 수와 문자열이 아닌 키는 거절입니다.

## 선언 (`ledger/ledger_skeleton.json` · `ledger/setup_bundle.py`)
운영자가 «소스 하나»에 대해 채우는 칸은 이렇습니다. (스켈레톤이 폼을 만들고, 시험이 검증기와의
차이를 «0» 으로 셉니다 — 두 쪽이 어긋날 수 없는 구조입니다.)

```
relation                         표 이름
read.unit                        row | group
read.identity                    컬럼 목록 — 원문으로 돌아가는 길
read.order_by                    컬럼 목록 — 커서가 여기서 «파생»됩니다
read.group_by                    컬럼 목록
read.occurred_at.timezone        필수
read.occurred_at.column | basis  🔴 «정확히 하나». 표에 세계 시각이 있으면 column,
                                 없으면 basis (닫힌 목록)
prepare.*                        구현 id · 판 · 입력 컬럼 · 출력 컬럼 · 조인 규칙
map.implementation_id            바인딩을 실행할 엔진
map.unit.kind                    event | row | group_by
bind.mappings.<이름>.predicate    어휘의 술어 하나
bind.mappings.<이름>.bind.<역할>  역할마다 바인딩 하나
```

## 역할과 바인딩 — 여기가 «표와 원장이 만나는 자리»입니다
술어 하나가 «강제하는» 역할은 `setup_bundle.predicate_claim` 이 만듭니다. 사람이 고르는 것이
아니라 술어에서 «나옵니다».
```
subject       항상 · 엔티티
occurred_at   항상 · 시각
target        목적어가 엔티티 참조일 때 · 엔티티
value         목적어가 값 / 사건 참조일 때 · 수(quantity) / 식별자(identity)
<수식어 이름>  술어가 선언한 필수·선택 수식어마다 하나씩 · 속성(attribute)
```
바인딩은 «세 종류»뿐입니다 (`binding_kinds`):
```
column     그 행의 컬럼 하나를 읽는다
constant   고정 값
entity     {엔티티 타입, 식별키마다 «또 바인딩»}   <- 엔티티 역할은 이것만 허용됩니다
```
🔴 **식이 없습니다.** 이어붙이기도, 자르기도, 계산도 없습니다. 그래서 조립된 식별키는
**표에 컬럼으로 «이미» 있어야 합니다** — 전략이 「체인이 만들어 둔다」고 말한 바로 그 자리입니다.

# ② 그 각각이 «표의 무엇»이 되어야 하나

「한 행 = 원자 하나」인 표의 컬럼을 종류별로 적습니다. **스키마 이름은 빈칸입니다** — 어느
도메인에서도 같은 표가 나와야 합니다.

| 원자의 자리 | 표에서 | 개수 | 비어도 되나 | 값의 종류 |
|---|---|---|---|---|
| 주어의 식별키 | 키 조각마다 «컬럼 하나» | 엔티티가 선언한 조각 수 | ❌ (엔티티가 null 허용을 선언하지 않는 한) | 유한한 JSON 스칼라 |
| 세계 시각 | 컬럼 하나 | 1 | ❌ | 타임존이 붙은 시각 |
| 목적어(엔티티 참조) | 상대 엔티티의 키 조각마다 컬럼 하나 | 상대가 선언한 조각 수 | ❌ | 유한한 JSON 스칼라 |
| 목적어(값) | 컬럼 하나 | 1 | ❌ | 🔴 «수». 유한. bool 아님 |
| 수식어 | 수식어마다 컬럼 하나 | 술어가 선언한 수 | ❌ (바인딩했다면) | 유한한 JSON 스칼라 |
| 원문으로 가는 길 | `read.identity` 가 가리키는 컬럼 | 1 이상 | ❌ | — |
| 커서 | `read.order_by` 가 가리키는 컬럼 | 1 이상 | ❌ | 순서가 있고 «수정에도» 단조여야 함 |

## 이 표가 «말하지 않는» 것 — 그리고 그게 맞습니다
```
술어 이름        컬럼이 «아닙니다». 선언의 매핑 하나가 술어 하나입니다
주어의 타입       컬럼이 «아닙니다». 바인딩의 entity_type 이 정합니다
출처 · 번역기 판  컬럼이 «아닙니다». 소스 선언에서 나옵니다
```
🔴 그래서 **「한 행 = 원자 하나」인 표는 «술어 하나짜리» 표입니다.** 한 표에 여러 술어를 담고
싶으면 술어마다 매핑을 더하는 것이고, 그러면 한 행이 여러 원자가 됩니다 — 그건 「한 행 = 여러
원자」이고 이 명세의 표가 아닙니다. **표를 술어별로 «가르는» 것이 이 전략의 값어치입니다.**

## 비어 있는 칸의 처리 — 「채운다」가 아니라 「선언하지 않는다」
선택 수식어를 «어떤 행에서는» 못 채운다면, 그 수식어는 그 표에서 «바인딩하지 않습니다».
바인딩해 두고 비워 두면 그 행의 원자가 통째로 거절됩니다(맨 앞 ②). 즉 —
```
값이 늘 있다     -> 컬럼을 두고 바인딩한다
값이 가끔 있다    -> 🔴 표를 «가른다». 있는 것만 모은 표에서 바인딩한다
값이 아예 없다    -> 컬럼도 바인딩도 두지 않는다
```

# ③ 그래서 «두 줄»이 이렇게 나옵니다

```
① 「<이 표>의 한 행이 «한 문장»이 되게, 주어 식별키 · 시각 · 목적어 · 수식어를
    «각각 한 칸»으로 채우십시오」
② 「선언에서 <그 표>를 소스로 잡고, 술어 하나를 골라 그 칸들을 역할에 «짝지으면» 됩니다」
```

🔴 **판별식을 제 명세에 대고 돌려 봅니다** (`CLAUDE.md` 완성의 정의):
```
✅ 두 줄이 나온다
✅ 그 안에 이 박스의 «컬럼 이름»이 없다 — 도메인 낱말도 없다
✅ 절차가 아니다 — 「먼저 A 하고 B 만들고」가 아니라 «채우고 · 짝짓는» 둘이다
🔴 다만 «전제»가 하나 붙습니다: 그 표가 이미 «선언»돼 있어야 합니다 (맨 앞 ③)
   그 전제가 안 깔리면 두 줄이 «세 줄»이 됩니다 — 「먼저 표를 등록하고」가 앞에 붙습니다
```
⚠️ 그래서 이 명세의 완성은 「표 등록이 운영자의 한 걸음 안에 들어오나」에 걸려 있습니다.
그건 화면의 일이고, 페이즈 ①(「활성화하면 원장이 선다」를 믿을 수 있게)과 «같은 자리»입니다.

# ④ 체인이 «무엇을 할 수 있어야» 하나 — 지금 할 수 있는 것과 대조

## 지금 할 수 있는 것 (`server/mapper_sdk.py`, 커밋됨)
```
payloads_to_df   원천 행을 «평평한 프레임»으로 (행 식별자를 달고)
sql(db, ...)     «같은 세션»에서 다른 표를 읽는다 — 이 배치가 방금 넣은 것까지 보인다.
                 파라미터는 «묶어서» 넘긴다 (문자열 조립 아님)
(df, db) -> df   저자가 쓰는 «유일한» 단계. pandas 로 무엇이든 계산한다
df_to_updates    프레임을 대상 표의 갱신으로. 결측은 None 으로 «되돌리고»,
                 키는 «선언에서» 정한다 (조립 키 / 단일 키)
```

## 그래서 위 표의 각 칸을 만들 수 있나
```
✅ 조립된 식별키 컬럼     pandas 에서 만들어 컬럼으로 내보내면 됩니다 — 전략의 핵심이고 «됩니다»
✅ 다른 표에서 끌어온 값   같은 세션 읽기가 있습니다
✅ 결측을 채우거나 행을 뺌  프레임에서 하면 됩니다
⚠️ 시각 컬럼의 «타입»      맨 앞 ④ — 미검증. 값은 넣을 수 있으나 타입은 표의 선언이 정합니다
❌ 표 자체와 그 키의 «등록» 맨 앞 ③ — 체인 밖입니다
❌ 이미 넣은 행의 «회수»    갱신만 있고 삭제가 없습니다
❌ 목적어 값을 «글자로»     맨 앞 ① — 표를 바꿔도 안 됩니다. 어휘 · 판정의 자리입니다
```

## 그래서 다음 라운드가 될 것 — 순서대로
```
1  표와 키를 «운영자의 한 걸음»으로 등록되게 (없으면 두 줄이 세 줄이 됩니다)   -> 화면
2  시각 컬럼 타입이 준비 경계까지 살아 오는지 «실행으로» 확인                  -> 구현자
3  목적어 값이 «글자»여야 하는 경우를 어떻게 할지                              -> 🔴 총괄 판정
4  무효가 된 행을 표에서 «내리는» 길 (지금은 남아서 매번 거절로 나타납니다)     -> 판정 후 구현자
```

## 이 명세가 «하지 않은» 것 — 밝혀 둡니다
```
⛔ 코드를 쓰지 않았습니다. 필요한 것은 위 네 항목으로 «지시서»에 넘어갑니다
```
