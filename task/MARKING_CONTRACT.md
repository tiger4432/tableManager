# 마킹 계약 — 한 장. 서버·클라가 «같이» 보는 정본

> 소유자 상설: 「**마킹한 노드의 하위 그래프를 데이터로 들고 오는 거야**」
> 소유자 지명: 「서버랑 클라 다 아는」 -> 응용 세션이 이 계약의 소유자입니다.
> 이 파일이 정본입니다. 서버·클라 지시서는 여기를 가리킵니다.

---

## 1. 마킹이란 무엇인가 — 한 줄

**마킹은 «부호 붙은 노드 집합»이고, 질의의 «주어»입니다.** 화면 상태가 아닙니다.

```
값        { node_id -> sign }        sign ∈ { +1 케이스, -1 컨트롤 }
그 외     «없습니다». 좌표도, 라벨도, 색도 마킹에 들어가지 않습니다
쓰임      walk({ start: <마킹 이름>, collect: <무엇을 걷나> })
```

🔴 **부호 셋을 구분합니다** — 이 구분이 이 제품의 핵심입니다.
```
+1   여기서 났다              마킹에 «있음»
-1   봤는데 안 났다 (대조군)   마킹에 «있음»
없음  «미검사»                 마킹에 «없음»  ← 0 이 아니라 «목록에 없는 것»
```

**실측 (`main.js` 의 부품 선언):**

부품                읽는 마킹      쓰는 마킹
main-trend          marking:0      marking:0     ← 점을 찍으면 여기 들어갑니다

```
🔴 **`marking:0` 을 읽는 부품이 «하나도 없습니다».**
트렌드에서 점을 찍으면 값은 들어가는데 **아무도 안 봅니다.** 그래서 맵이 안 바뀝니다.

## 3. 계약 — 마킹은 «둘»입니다

소유자 도식대로 접습니다. **트렌드가 찍는 것이 «곧 마킹1»입니다.**

> 🔴 **정정 (12:5x).** 아래 표가 «코어 맵»을 두 줄에 다 적고 있었습니다 — 제 실수입니다.
> `task/CHART_DESIGN.md`(정본, 코드와 일치)에 맞춰 고칩니다: **본딩 맵은 1, 코어 맵은 2.**
> 그리고 `marking:3` 은 «판정 대기»가 아니라 «은퇴»입니다 (§6 에서 닫혔습니다).

```
마킹 이름     뜻                    쓰는 곳                       읽는 곳
marking:1    지금 보는 대상         메인 트렌드(점 찍기) ·          본딩 맵 · 구성 · 머리 요약 ·
             = walk 의 start        본딩 맵(칸) · 구성(층)          칩 확대 · composite
marking:2    후보 선택             후보 목록 · 순위표 · 코어 맵      후보 트렌드 · 코어 맵
marking:3    —                    «은퇴». 교집합은 «읽는 자리에서 계산» (§6 판정)
```
```
🔴 바뀌는 것 «하나»   main-trend 의 writes: 'marking:0'  ->  'marking:1'
                     그 한 줄이 트렌드 -> 맵 사슬을 잇습니다
🔴 마킹이 «아닌» 것    axis:y · axis:group 은 «축 선택»이지 마킹이 아닙니다.
                     저장소를 같이 쓰더라도 이름 규칙을 나눕니다 (`axis:` 접두)
```
⚠️ `marking:0` 은 «은퇴»입니다. 남겨 두면 다음 사람이 또 여기에 씁니다.

## 4. 🔴 게이트 — «서버가 준 node id» 만 마킹이 됩니다

```
허용     서버 응답이 준 node id            (ledger-entity:v1:… · ledger-quantity:v1:… 등)
거절     클라가 지어낸 id                  (`unresolved-die:<axis>:<frame>:<x>,<y>`)
판정     `nodeIdResolved` 가 이미 «진짜/가짜»를 구분합니다. 그걸 그대로 게이트로 씁니다
```
**왜:** 지어낸 id 로 마킹하면 walk 이 «없는 노드»에서 출발합니다. 빈 결과가 나오는데
그 빈 것이 「없다」인지 「씨앗이 가짜다」인지 구분이 안 됩니다.

```
거절될 때 화면이 하는 일   그릴 수는 «있습니다». 마킹만 «안 됩니다».
                          그리고 «왜 안 되는지»가 보여야 합니다 —
                          「이 칸은 아직 원장 노드가 아닙니다」
```
⛔ 조용히 무시하지 마십시오. 안 되는 것과 안 눌린 것은 다릅니다.

## 5. 🔴 좌표는 «어느 기준계»의 것인가 — 안 적으면 또 어긋납니다

**실측 (`lot_map` 의 `frame.grid`):**
```
본딩축   rotation «180»   grid_y_invert false
DT축     rotation 0       grid_y_invert false
코어축   rotation 0       grid_y_invert false
클라     rotation 을 «0회» 읽습니다 (grep 결과 없음)
```
🔴 **그래서 본딩 (3,4) 와 코어 (3,4) 는 «다른 물리 자리»입니다.**
마킹이 맵을 건너다니는 순간 어긋납니다.

```
계약   마킹에 들어가는 것은 «노드 id» 뿐이므로 좌표 기준계 문제는 «마킹에는 없습니다».
       기준계는 «그리는 쪽»의 문제입니다 — 셀을 노드로 바꾸는 그 자리에서 rotation 을 적용합니다
       그리고 «어느 기준계로 만든 노드인지»를 노드 id 가 스스로 지녀야 합니다
```
🔴 **추가 (2026-08-30, 총괄 판정과 합침) — 이 규칙은 «문이 둘»입니다. 한쪽만 고치면 반쪽입니다.**
```
소스(번역)      원장에 «기록»할 때 표준 좌표로 적는다        총괄 2026-08-30 판정
화면(사람 클릭)  노드 id 를 «만들» 때 표준 좌표로 만든다      이 절이 원래 적어 둔 것
=> 규칙은 하나입니다: 「원장에 들어가는 «모든 문»에서 표준으로」. 문이 둘일 뿐입니다
```
경위: 총괄이 같은 문제를 서버 쪽에서 처음부터 다시 유도했고 설계가 «두 번» 뒤집힌 뒤
이 절과 같은 결론에 도착했습니다. 다음에 이 자리를 고치는 사람은 «둘 다» 보십시오.

📎 §4 의 게이트가 서면 이 문제가 «자동으로» 좁아집니다 —
   지어낸 id 가 마킹에 못 들어가므로, 기준계가 다른 두 칸이 같은 마킹에 섞일 일이 없습니다.

# 10. 🔴 소유자 판정 (2026-08-24 18:4x) — **키는 «노드 id + 노드 타입»**

> 소유자 원문: 「**키는 노드 아이디와 노드 타입**, 2번 b, 3번 예」

🔴 **그래서 트렌드에서 찍은 것과 맵에서 찍은 것이 «같은 노드여도» 절대 안 만납니다.**
   오늘 「트렌드 점을 찍으면 맵이 바뀌는가」가 게이트인 이유가 이것입니다.

## 10.2 계약 — §1 을 «고칩니다»

```
전   마킹 = { node_id -> sign }
후   마킹 = { (node_id, node_type) -> sign }
```
```
값        { id, type, sign }        sign ∈ { +1 케이스, -1 컨트롤 }
type      «서버가 준 노드 타입» 그대로 (entity 종류가 아니라 노드 종류: entity·point·quantity·…
          그리고 entity 면 그 개체 타입까지 — 선언 낱말로)
동치      두 마킹 항목이 같다 = id «와» type 이 «둘 다» 같다
저장소    키가 «쌍»입니다. 한 문자열로 접을 때는 «정본 형식»을 하나만 정하고 그것만 씁니다
```
⛔ **`experiment-unit:v1:…` 은 은퇴합니다** — 그것이 트렌드만의 다섯째 id 공간이었습니다.
   트렌드 점의 키는 «그 점이 가리키는 노드»의 (id, type) 입니다.

## 10.3 그래서 §4 게이트가 «더 강해집니다»
```
