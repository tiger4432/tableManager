# 임의 질문 응용 — 여섯 응용이 «프리셋»이 되는 토대

**소유자, 2026-08-20: 「사용자의 임의의 질문에 답할 수 있게」**

여섯 응용(`ontology_application_algorithm.md` §12) 중 하나를 고르는 대신, **그 여섯이
프리셋이 되는 «질문 하나»**를 세운다. 이 프로젝트의 상설 순서 그대로다 —
「기본 단위 → 함수 → config → 프리셋」. **프리셋은 편의층이지 토대가 아니다.**

---

## 1. 한 문장

**임의 질문 = 손잡이 다섯의 임의 설정. 그리고 여섯 응용은 그중 여섯 점이다.**

---

## 2. 손잡이 다섯

### ① 씨앗 — 어디에 자극을 주나

    값역   노드 집합 × 부호 × 가중
           개체 집합        사람이 표시한 웨이퍼·랏
           조건으로 뽑은 집합  기간 · 주장 조건 · 계측값 구간 · 맵 영역
           물리량 노드       「압력이 원인이라면?」
           액션 노드         「이 액션을 했다면?」

    🔴 부호가 손잡이의 일부다 (§S2)
           +  관측됐다
           −  «봤는데 안 났다»   ← 미검사(씨앗 없음)와 구별된다

### ② 매질 — 어떤 간선 위에서 도나

    개체 간선     원자 중 `object_kind = entity_ref` 인 것
    기전 엣지     선언된 인과 방향
    바인딩        필드 → 물리량  ·  🔴 관장 엣지(공정 → 물리량, 미설계)
    액션 영향     액션 → 물리량

    부분집합 지정 가능 — **정책이 고르는 것이 이 손잡이다** (소유자: 「걸을 엣지를
    지능적으로 뽑는 거지」)

### ③ 방향 — 시간의 어느 쪽으로

    거스름   원인 쪽      「왜 났나」
    따라감   영향 쪽      「어디까지 위험한가」

    🔴 무방향은 «금지». 섞이면 결과를 원인으로 착각한다 (§4)

### ④ 반환 — 무엇을 세나 (대수)

    (ℝ, +, ×)          질량       구조적 근접도
    (2^S, ∪, ·)        이진 도달   공유 «분율»
    ([0,1], max, min)  퍼지 도달   «등급이 실린» 공유 분율
    (ℕ, +, ×)          계수       경로 가짓수 — DAG 전용

    🔴 **읽는 응용이 대수를 고르는 것이, 가치 ③(같은 원자를 다르게 해석)의
    가장 구체적인 형태다.**

### ⑤ 읽기 — 무엇이 켜졌는지 보나

    물리량 노드    원인 후보
    액션 노드      행동 후보
    개체 노드      영향 반경 · 혈통 공통점
    결측 노드      워크리스트
    선언 노드      죽은 선언

## 3. 3단 구조 — 그리고 두 단은 «이미 있다»

    1  선택   임의 조건 -> 노드 집합        ledger_selection.py (73KB, 존재)
    2  전파   손잡이 ②③④ 로 흘린다          🔴 «없다». 이번에 세울 것
    3  읽기   손잡이 ⑤ + 최상위 집합 산출     부분적으로 존재 (대조·걷기의 산출층)

### 이미 있는 것 — 실측

    ledger_selection.py    「UI 마킹을 원장 근거로 해소」
                           서버가 아는 kind: entity_set · map_cells · map_die · time_range
    ledger_trace           걷기 (1홉 이상, 단 술어 이름 하드코딩 · Lot 고정)
    ledger_walk_contrast   대조 = 전파의 k=1 절단 (§15.2)
    mechanism_gate         기전 그래프 + 바인딩 (23노드 22엣지, 라이브)

### ⚠️ 확인된 간극 (내 소관 아님, 지적만)

    claim_filter · metric_region   클라는 보내는데 `ledger_selection` 에 없다
                                   (다른 모듈일 수 있어 단정하지 않는다)
    ledger_selection.py:542        `finding_kind == "void"` 하드코딩
                                   `SCENARIO_CONSOLE_BRIEF` §0 일반화 규율 위반
    관장 엣지                       공정 → 물리량. 선언 자체가 없다 (미설계)

## 4. 🔴 합격 조건 — 여섯 응용이 «코드 0줄»로 나와야 한다

이것이 이 설계의 수락 단언이다. 여섯 중 하나라도 특별 분기가 필요하면 손잡이가
불완전한 것이다.

    응용            ① 씨앗              ② 매질        ③ 방향   ④ 반환      ⑤ 읽기
    ─────────────  ────────────────   ──────────   ─────   ────────   ────────
    ① 원인 후보     표시한 웨이퍼 ±      전부          거스름   퍼지 도달   물리량
    ② 다음 행동     표시한 웨이퍼 ±      전부          거스름   질량        액션
    ③ 영향 반경     의심 원인 하나       전부          따라감   이진 도달   개체
    ④ 결측          표시한 웨이퍼 ±      전부          거스름   퍼지 도달   결측
    ⑤ 죽은 선언     질문 여러 개의 합     선언 엣지만   거스름   이진 도달   선언
    ⑥ 과거 유사     표시한 웨이퍼 ±      전부          거스름   퍼지 도달   («순위 상관»)

**여섯 줄이 전부 같은 함수의 인자다.** 새 코드가 아니라 새 «설정»이다.

⚠️ ⑥만 산출이 다르다 — 두 질문의 순위 벡터를 상관으로 비교하는 «후처리»가 붙는다
(§21.5-② 로 코사인에서 순위 상관으로 정정됨). 그 후처리는 손잡이가 아니라 산출층이다.

---

## 5. 자연어는 «나중»이고 손잡이가 먼저다

소유자: 「사람이 쿼리를 하면 그 쿼리를 기반으로 GNN이 컨텍스트 해석해가면서 …」

🔴 **순서가 중요하다.** 자연어 사상을 먼저 만들면 질문 «유형»이 코드에 박힌다 —
「왜 났나 질문이면 이렇게, 어디까지 위험한가 질문이면 저렇게」가 되고, 그것이
소유자가 기각한 「사람이 케이스별로 지정하는 것」의 기계 버전이다.

    먼저   손잡이가 «임의 설정»을 받는다        <- 표현력이 여기서 정해진다
    나중   자연어 -> 손잡이 사상               <- 표현 못 하는 질문은 애초에 없다

그리고 방향·반환은 질문의 «문법»에서 대체로 읽힌다:

    「왜 났나」          거스름 · 물리량 읽기
    「어디까지 위험한가」  따라감 · 개체 읽기
    「몇 %가 공유하나」   도달 반환
    「무엇과 닮았나」     순위 상관

---

## 6. 산출의 «고정된 모양» — 손잡이와 무관하게 항상 같다

    최상위 집합       1등이 하나가 아니다. 지배당하지 않는 것 «전부» (§21.3)
    비교 불가 표시     「이 둘은 정도가 아니라 종류가 다르다」
    근거 경로         홉마다 원자 ref · 발화자 · 선언 세대
    미계측 표시        상위인데 «잴 방법이 없는» 것은 그 자체가 액션 (§13)
    잘림 사유         degree_cap · cycle · depth — 기존 `truncation_reason`

🔴 **숫자는 나가지 않는다** (소유자 판정 §21). 순위와 최상위 집합만 나간다.

---

## 7. 선행조건과 순서

    지금 가능        ⑤ 죽은 선언 · §13 선언 진단 (선언 그래프만 있으면 된다)
    원장 필요        ①②③④⑥  <- 커서 전역 지문 -> 소스별 지문 (설정 라인 대기열)
    설정 라인 필요    `Action` 개체 (②) · 관장 엣지 (미계측 추론)

**순서 제안:** 손잡이 다섯을 받는 전파 «한 벌»을 먼저 세우고, 선언 그래프 위에서
⑤와 §13으로 검증한다. 원장이 흐르면 ①③④⑥이 «설정만»으로 열린다 — 그것이
합격 조건(§4)의 실증이 된다.

---

## 8. 판정 필요

    1. 이 3단 구조로 가는가 (선택 -> 전파 -> 읽기)
    2. 손잡이 다섯이 맞는가 — 빠진 축이 있는가
    3. 착수를 「전파 한 벌 + ⑤ 검증」으로 잡는가, 아니면 원장을 기다리는가
    4. `claim_filter`·`metric_region` 서버 부재는 설정 라인에 넘기는가

# 9. 질의 형태 확정 — 소유자 제안 (2026-08-20)

> 「walk  start: some node ids  ·  collect: another node types
>  이러면 해당 노드와 연관있는 지정한 노드 타입 모두 collect」

**채택.** §2의 손잡이 다섯보다 낫다 — 사용자에게 노출되는 것이 둘이고, 어휘 이름이
들어가지 않는다.

    walk
      start:    { + [node ids],  − [node ids] }
      collect:  <node type>

## 9.1 합격 조건 통과 — 여섯 응용이 두 필드로

    start: 표시한 관측 ±   collect: Quantity      ① 원인 후보
    start: 표시한 관측 ±   collect: Action        ② 다음 행동
    start: 의심 원인       collect: Wafer         ③ 영향 반경
    start: 표시한 관측 ±   collect: Lot           혈통 공통 조상
    start: 표시한 관측 ±   collect: Missing       ④ 결측
    start: 여러 질문       collect: Declaration   ⑤ 죽은 선언

§4의 수락 단언(코드 0줄)을 통과한다.

## 9.2 부호는 «필수» — 옵션이면 안 된다

실무가 「양호랏과 불량랏의 차이」(소유자)인데 부호 없이는 표현이 안 된다. 그리고
§15.2에서 **부호 있는 정규화 씨앗의 1홉이 비율 차와 항등**임을 확인했으므로,
대조가 별도 기능이 아니라 이 문법의 한 경우가 된다.

옵션으로 두면 안 쓰게 되고, 안 쓰면 공유 요인이 1등이 되어 매번 쓸모없는 답이 나온다.
**기본이 대조여야 한다.**

## 9.3 경계를 «두지 않는다» — 순위가 그 자리를 대신한다

홉 제한도 개수 제한도 임의 상수다(§21). collect 는 「연관된 것 전부」가 아니라
**「지배당하지 않는 최상위 집합」**을 낸다. 자르는 것이 아니라 정렬해서 위를 내는
것이므로 상수가 없다.

실행 예산(`ledger_subgraph` 의 노드·엣지 한도)은 남지만 그것은 **답의 경계가 아니라
요청의 경계**이고, 초과하면 기존 `truncation_reason` 으로 말한다.

## 9.4 방향을 감추되 시간은 지킨다 — 씨앗을 «관측»으로

무방향이면 결과보다 늦은 것이 원인 후보로 걸린다(시간 누수, §4). 방향 인자를 노출하면
손잡이가 셋이 된다.

🔴 **해결: 씨앗을 개체가 아니라 «관측»으로 둔다.** 마킹은 웨이퍼를 고르지만 문제인 것은
그 웨이퍼의 `observed` 원자이고, **그것은 `occurred_at` 을 갖는다.** 그 시각이 기준선이
되어 시간 필터가 저절로 걸리고 방향 인자가 사라진다.

씨앗이 시각 없는 개체면 필터가 안 걸린다. 그때는 **응답이 「시간 기준 없음」을 말한다** —
조용히 새게 두지 않는다.

## 9.5 감추는 것 셋

    매질   기본 전부. 정책이 나중에 좁힌다 — 사용자 손잡이가 아니다
    대수   퍼지 도달 기본 (collect 가 집합을 묻고 순위가 필요하므로)
    방향   §9.4 의 시간 기준으로 대체

# 10. 결측 노드 — 생성 «가능한가»

**소유자 질문: 「결측에 대한 노드 생성 가능?」**

결측에는 원자가 없다. 그러므로 «원자의 투영»으로는 노드가 안 나온다.
**다른 생성기가 필요하고, 브리핑이 이미 그 식을 적어 두었다:**

    결측 = 기대 − 실재                (`SCENARIO_CONSOLE_BRIEFING` §0-ter)
    기계는 삼각형   골격(걷기) · 주석(집계) · 기대(선언)

즉 결측 노드의 생성기는 **«선언 × 주체»의 곱에서 «원자»를 뺀 차집합**이다.
투영의 나머지가 「원자를 읽어 노드를 낸다」인 것과 근본적으로 다르다.

## 10.1 세 부류, 세 가지 답

### ① 신원 결측 — 🔴 «오늘 가능». 새 선언 0개

걷기가 이미 홉마다 상태를 낸다: `resolved` · `contested` · `candidate` · `unresolvable`.
`unresolvable` 인 홉은 **원자는 없지만 «자리»는 지목돼 있다** — `(주체, 술어, ⊥)`.

    노드     (subject, predicate, 미해소)
    생성기   걷기의 홉 상태. 이미 계산되고 있다
    선행조건 없음

「이 랏의 부모가 누군지 모른다」가 그대로 노드가 된다.

### ② 주석 결측 — 측정 계획 선언이 «선행»

    노드     (subject, 기대된 술어, 값 없음)
    생성기   측정 계획 선언 × 주체  −  실재 원자
    선행조건 🔴 «측정 계획 선언»이 없다. 브리핑: MI 번역 묶음과 함께 착지
             (소유자 「나중에」)

기대가 선언되지 않으면 「없어야 정상인 것」과 「있어야 하는데 없는 것」을 구별할 수 없다.
**선언 없이 만들면 모든 빈칸이 결측이 된다.**

### ③ 이벤트 결측 — 어렵다

「했는데 기록이 안 들어왔다」. 노드로 만들려면 탐지가 «앞서야» 한다(희귀 서열 서명 ·
층간 모순 · 기전 흔적 추론 — 브리핑 3단 사다리). **추론의 산물이지 차집합이 아니다.**
지금 범위 밖.

## 10.2 🔴 그리고 결측 노드가 «관장 엣지»를 대체한다 (부분적으로)

§(응용 방향 문서)에서 「미계측 물리량으로 가는 관장 엣지가 없다」고 적었다.
결측 노드가 그 일의 «정밀한» 절반을 한다:

    관장 엣지    「CMP가 두께를 관장한다」      공정 수준. 기대 선언 «불필요». 넓다
    결측 노드    「이 웨이퍼의 두께가 없다」     주체 수준. 기대 선언 «필요». 정밀하다

결측 노드는 바인딩을 타고 물리량에 닿으므로, 미계측 물리량이 후보로 collapse 되는
소유자의 추론이 **주체 단위로** 성립한다.

**둘은 대체재가 아니라 상보재다.** 기대가 선언된 곳은 결측 노드가 정밀하게, 선언이
없는 곳은 관장 엣지가 넓게 덮는다.

## 10.3 결측 노드의 그래프 성질

    들어오는 엣지   주체 → 결측 노드
    나가는 엣지     결측 노드 → 물리량 (바인딩 경유)
    활성            받고, 통과시킨다

전파에서 자연스럽게 순위에 오르고, **상위인데 결측이면 그 자체가 액션**이다
(「이걸 재기 시작하라」). §13 예시의 주체 단위 판이다.

⚠️ 카디널리티: 「선언 × 주체」는 원리상 크다. 다만 **걷기의 프런티어 안에서만 생성**되므로
질의당 유계다. 투영이 이미 유계 프런티어로 도는 것과 같은 규율이다.
실규모에서의 증가율은 **미측정**.

## 10.4 판정 필요

    1. ① (신원 결측) 만으로 먼저 여는가 — 선행조건 0
    2. ② 를 위해 «측정 계획 선언»을 이 세션에서 설계하는가, MI 묶음까지 기다리는가
    3. 관장 엣지를 ② 와 «함께» 볼 것인가 (상보재이므로 같이 보는 것이 자연스럽다)

# 11. 「무한 케이스」 규칙으로 자기 감사 (소유자 상설, 2026-08-20)

> 「항상 생각할 때 "무한대의 케이스를 커버하는지 고려할 것"」

**판정 방법: 설계 안의 «유한한 목록»이 곧 실패 지점이다.**

## 11.1 통과

    간선의 정의        `object_kind = entity_ref`      술어가 무한히 늘어도 무관
    부호 있는 씨앗      임의 노드 집합
    순위 · 지배 관계    후보 수 무관
    결측 = 모집단−실재  술어 무관 (§10 정정 후)
    응용 여섯          두 필드의 조합이므로 무한

## 11.2 🔴 실패 ① — `collect` 의 노드 «종류»가 코드에 있는 유한 목록

    구조에서 오는 것    Claim · Event · Value        원자 구조 고정. 유한이어도 «된다»
    선언에서 오는 것    Quantity · Action · …        🔴 선언 층은 무한히 늘 수 있다

**시정:** `collect` 가 받는 것은 「코드가 아는 이름」이 아니라 **「레지스트리에 등록된
노드 종류」**여야 한다. v3 `entities` 레지스트리가 이미 있으므로 합성 노드 종류도
거기서 오면 무한 확장된다.

## 11.3 🔴 실패 ② — 질의가 «합성 불가»

두 필드로는 「A 타입 중 B에도 닿는 것」을 못 쓴다. 필터를 더하면 손잡이가 늘고,
안 더하면 표현 못 하는 질문이 남는다 — 둘 다 유한이다.

**시정 (이미 설계에 있다):** `ledger_subgraph` 가 「노드 id를 **다음 씨앗으로 되먹일 수
있다**」고 적어 두었다.

    walk(start: A, collect: T)  →  결과를 다음 walk 의 start 로

**연쇄가 곧 합성이다.** `walk` 하나는 유한하지만 «연쇄는 무한»이다. 손잡이를 늘리는
것이 아니라 **되먹임이 보장되는지**를 확인하면 된다.

## 11.4 ⚠️ 경계선 — 「대수 넷」

    목록으로 구현되면        실패 (다섯째 대수가 오면 코드 수정)
    «반환을 꽂는 자리»면     통과

문서의 「대수 넷」은 **열거가 아니라 예시**로 읽어야 한다. 구현은 반환을 인자로 받는다.

## 11.5 이 규칙이 사후에 설명하는 판정

설계 문서의 「액션 종류 v0 는 되돌릴 수 있는 것만 (hold · priority_inspection ·
recipe_review)」이 정확히 유한 목록이었다. 소유자가 「모든 액션이 된다」로 이미
폐기했고(방향 문서 §14-②), **이 규칙이 그 판정의 근거를 준다.**

# 12. 🔴 설정 라인에 올린 판정 요청 — 원자에 «이름» 인가 «선언 id» 인가 (2026-08-20)

소유자 발화: 「원장에 has wafer 이런 도메인 어휘 안 들어가고 어떻게 할수 있을지 전략」
-> 소유자 지시로 온톨로지 설정 총괄에게 올림. **파일이 정본이므로 여기 박는다.**

## 12.1 왜 저장이 필요한가 — 판별자

`Lot → Lot` 은 `derived_from` 이기도 하고 `slot_map` 이기도 하다. **모양으로 구별되지
않는다.** 그러므로 판별자는 필요하고, 질문은 그것이 «읽히는 이름» 이냐 «안정된 id» 냐다.

## 12.2 실측 — v3 는 이미 안정 주소를 만들고 «버린다»

    선언         emit.predicate: "register@1"
    _runtime_id  @1 을 떼어냄                    (roleframe.py:987, 적용 1137/1167/1169)
    원자         predicate = "register"

코드가 이유를 스스로 적었다 — 「physical predicate/entity spellings stay compatible with
the existing LedgerStore and read APIs」. **원칙이 아니라 호환 결정으로 읽힌다.**

## 12.3 선언 id 저장이 «개명 자유보다» 크게 얻는 것

    개명         선언의 label 한 줄. 원자 0건
                 (지금은 `predicate` 가 dedupe 컬럼이라 개명 = 재저장 = 두 배)
    이름 다원성   공장·팀마다 다르게 부르는 «같은 관계» 가 하나의 id 를 공유
                 -> 🔴 둘째 가치(여러 사람의 지식 통합)가 «데이터 층» 에서 실현된다
    응용별 해석   같은 id 를 읽는 쪽이 다른 label·역할로
                 -> 셋째 가치

지금까지 둘째·셋째 가치는 «선언 층» 얘기였다. id 저장은 그것을 데이터 층으로 내린다.

## 12.4 🔴 시점 — 이것이 올린 이유다

    원장이 지금 안 흐른다      커서가 전역 지문에 묶임 (총괄 통보)
    재백필이 어차피 대기 중     소스별 지문 판정 후 재실행 예정

**재백필을 어차피 해야 한다면 그때 모양을 바꾸는 추가 비용이 0이다.** 데이터가 쌓인
뒤에는 실비용이 되고, 그것은 넷째 가치(마이그레이션 free)를 정면으로 무는 자리다.

**「나중에 할 수 있는 일」이 아니라 「지금 아니면 비싸지는 일」로 보인다.**

## 12.5 id 의 조건 — 「무한 케이스」 규칙 적용

**생성되면 불변**이어야 한다. 이름에서 유도되거나 파일 내 위치에 묶이면 개명·재정리
때 깨진다.

⚠️ **`register@1` 형태는 조건 미달이다** — 이름을 포함하므로 개명하면 주소가 바뀐다.
별도 불변 id 가 필요하다.

## 12.6 대가 셋 (내가 아는 한)

    ① 사람이 DB 를 직접 못 읽음    뷰로 해소. 진단 동선이 한 겹 늘어남
    ② 일회성 마이그레이션         재백필과 합치면 0, 따로 하면 실비용
    ③ 구 read 경로가 깨짐         `ledger_trace` 등이 이름으로 묻는다.
                                 다만 어차피 고칠 것(축 B)이라 «새» 비용은 아님

## 12.7 내 입장

**판단하지 않는다.** 저장 모양은 설정 라인 소관이고, 내가 모르는 제약(구 read 경로의
소비자 수 · 마이그레이션 스크립트의 현재 범위 · `setup_version 4` 라운드와의 충돌)이
있을 수 있다. **시점 때문에 「나중에」가 선택지가 아닐 수 있다는 점만 올렸다.**

회신 대기 중.

# 13. §12 정정 + 응답 — 총괄 회신을 받고 (2026-08-21)

총괄 회신 정본: `task/ontology_predicate_id_ruling.md`. 아래는 **내 쪽 정정과 추가 제안**이며,
채널이 세 번 샜으므로 파일에 박는다.

## 13.1 🔴 내 시점 논거는 틀렸다 — 전제가 하루 안에 뒤집혔다

§12.4는 「원장이 안 흐른다 → 재백필 어차피 대기 → 추가 비용 0」이었다.
**그 전제가 `b100fb2a`(2026-08-21 11:26, 소스별 지문)로 해소됐고, 내 메시지는 그 뒤에
나갔다.** 커밋과 `ledger_restamp_cursor.py` 존재를 직접 확인했다.

    dt_job     재스탬프 완료 — 막혀 있지 않다
    lot_event  v1 모양이라 이쪽만 막힘
    이미 쌓인   ledger-v2 원자 792행 (총괄 실측)

    정정된 셈   지금 하면   792행 재처리 (또는 옛 모양 방치)
               나중 하면   그때까지 쌓인 전량
               -> 「나중보다 싸다」만 남고 «0» 은 사라진다

**교훈:** 다른 세션이 알려 준 사실에는 유통기한이 있다. 그것을 논거의 «핵심»으로 쓸 때는
쓰기 직전에 다시 재야 한다. 오늘 그러지 않았다.

## 13.2 총괄의 반론 — 「원장이 자기 완결성을 잃는다」

    지금   원자 하나만 보면 predicate = "register" — 뜻이 그 «안» 에 있다
    id면   원자는 id 만, 뜻은 «살아 있는 설정 파일» 에
           -> 선언이 지워지면 과거 원자가 안 읽힌다
           -> 🔴 뷰로 해소 «안 된다» (뷰도 지금 설정을 보므로)

**이 반론은 옳고, 내 §12.6 대가 목록에 없었다.** 핵심가치 ⑤(이력)의 근거가 가변 파일에
기대게 되는 문제다.

## 13.3 실측 — v3 에는 «이름 층» 이 아예 없다

우회로(「label 을 지문에서 빼면 개명이 공짜」)가 있는지 쟀다. **없다.**

    v3 vocabulary 항목    layer · object · status · subjects     이름 필드 없음
    v3 entities 항목      keys                                   이름 필드 없음
    _semantic_plain       `_` 시작 필드와 config_path 만 제외      label 을 뺄 수가 없다

🔴 **v3 에서는 id 가 곧 이름이다** (`register@1`). 둘이 같은 것이므로
**개명 = id 변경 = 지문 변경 = 커서 리셋 = 재저장**이다. 뺄 label 이 없다.

## 13.4 제안 정정 — 「이름을 없애자」가 아니라 «셋으로 나누자»

총괄의 자기 완결성 반론은 세 번째 조각으로 답한다:

    predicate_id         불변 · 판별자 · dedupe 컬럼        개명해도 안 바뀐다
    label                선언에만 · 자유 변경               🔴 v3 에 «없는 층»
    predicate_at_write   쓸 때의 이름 · 원자에 · «비-dedupe»  자기 완결성

**세 번째가 반론의 답이다:**

    선언이 지워져도 읽힌다     「그때 이걸 register 라 불렀다」가 원자 «안» 에 있다
    이력상 오히려 옳다        append-only 원장에서 «쓸 때의 이름» 이 정확하다.
                            지금 이름으로 소급 해석하는 것이 오히려 이력 왜곡이다
    행이 안 늘어난다          비-dedupe 이므로 이름 때문에 중복이 생기지 않는다

**「뷰로 해소 안 된다」는 지적이 맞기 때문에 원자 «안» 에 넣는 것이다.**
그리고 총괄이 붙인 조건(「선언은 은퇴만, 삭제 금지」)은 이 조각이 있으면 **필수가 아니라
바람직**으로 내려간다 — 삭제돼도 원자가 자기 이름을 갖고 있다.

## 13.5 여전히 내 판단이 아니다

저장 모양은 설정 라인 소관이고 판정은 소유자께 올라가 있다. 위는 **선택지를 하나 더
놓는 것**이지 결론이 아니다. 특히 `predicate_at_write` 한 컬럼의 실제 비용(행 크기 ·
인덱스 영향)은 **내가 재지 않았다.**
