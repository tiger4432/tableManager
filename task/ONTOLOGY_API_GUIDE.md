```

                                  |
   「이건 어디서 왔나」  ────────  원장  ──────── 「무엇과 이어져 있나」
    trace · explore                                subgraph · subgraph/table
    explore_entity                |
                                  |
   「왜 이건 나고 저건 안 났나」    |     「무엇으로 만들어졌나」    composition
    siblings · journey            |     「추세가 어떤가」          trends
    selection/resolve             |     「표로 보자」              lots · lot_map
```

## 🔴 지금 상태를 한 줄로

**아홉은 돌고, 여섯은 안 돕니다** (하나는 제가 «안 쟀습니다» — `selection/resolve`). 그리고 안 도는 이유가 **전부 같습니다** —
**원자를 «쓴» 선언과 원자를 «읽는» 선언이 다른 파일입니다.**

```
쓰는 쪽    server/config/ontology/ledger_config.json     <- 대표님이 폼으로 만드신 것
읽는 쪽    server/config/ledger_config.json              <- «이 파일이 없습니다»
           그래서 config/sample/…json.sample 로 흘러가고, 그 샘플이 깨져 있습니다
```

이게 이 문서의 결론이기도 합니다. 아래 각 갈래의 「유니버셜한가」가 거의 다 이 한 줄로 갈립니다.

# 1. 「이건 어디서 왔나」 — 계보

**주소** `trace` · `explore` · `explore_entity`

**R&D 가 묻는 것:** 「이 랏이 어느 랏에서 갈라져 나왔나. 이 웨이퍼가 몇 번 슬롯에 있었나.」
불량이 났을 때 **거슬러 올라가는** 자리입니다.

**부르는 법:** `trace?lot=NAB539TA` — 랏 이름 하나.
`explore_entity?id=<개체 id>` — 개체를 클릭했을 때.

**어떻게 도나:** 원장에서 「어느 랏에서 나왔다」·「이 웨이퍼를 담고 있다」 같은 문장을
재귀로 따라 올라가며 홉마다 상태를 붙입니다.

```
유니버셜   🔴 아닙니다.  실행해 봤고 «지금 안 돕니다»
           거절: 「원장 소스 선언을 읽을 수 없다」 -> §0 의 그 파일 문제
           그리고 도더라도 이 코드는 「랏」이라는 낱말과 술어 이름 넷이 «코드에 박혀» 있습니다
           (has_wafer · derived_from · slot_map · register + 주어가 Lot 인지 검사)
           다른 팹에서 그 낱말이 다르면 «조용히 빈 답»이 나옵니다
```

# 2. 「무엇과 이어져 있나」 — 증거 그래프

**주소** `subgraph` · `subgraph/table`

**R&D 가 묻는 것:** 「이 웨이퍼(또는 이 사건) 주변에 무엇이 붙어 있나.
여기서 걸어 나가면 무엇이 나오나.」 **원인 후보를 «퍼뜨려» 찾는** 자리입니다.

**부르는 법:** `subgraph?node_id=<노드 id>&hops=3`
`subgraph/table?…&format=csv` 이면 엑셀·Spotfire 가 바로 먹습니다.

**어떻게 도나:** 원장 원자를 그대로 두고 «투영»만 합니다 — 사건·주장·개체를 노드로 펴고,
선언된 물리 기전(`mechanism_models.json`)을 얹어 물리량 노드까지 냅니다.
씨앗을 **케이스(+)/컨트롤(−)** 로 줄 수 있고, 결과에 **어느 씨앗에서 어떤 길로 왔는지**가
경로로 붙습니다.

```
유니버셜   🟡 반쪽.  «돕니다» (직접 불러 확인)
           선언 구동인 부분   기전 모델은 파일에서 읽습니다. 노드를 더해도 코드가 안 바뀝니다
           박혀 있는 부분     씨앗으로 줄 수 있는 «개체 타입 목록»이 옛 코드 목록입니다
                             -> 대표님이 어제 만드신 `die` 는 «씨앗이 안 됩니다» (거절 납니다)
                             -> 노드 이름표도 그 목록을 봐서, die 는 이름 대신 «좌표»가 뜹니다
```

⚠️ **이게 지금 제일 아픈 자리입니다.** 어제 넣으신 전사 원자 1,405개가 **여기로 못 들어옵니다.**

# 3. 「왜 이건 나고 저건 안 났나」 — 대조

**주소** `siblings` · `journey` · `selection/resolve`

**R&D 가 묻는 것:** 이 시스템에서 **가장 본질적인 질문**입니다.
「불량 난 웨이퍼들이 «공통으로» 지난 것은 무엇인가. 안 난 쪽과 «무엇이» 다른가.」

**부르는 법:** `siblings?finding=void&window=90d`
`journey?scope=…` — 웨이퍼 두 장의 공정 서열을 위아래로 나란히.

**어떻게 도나:** 불량 종류별로 「난 집단」과 「안 난 집단」을 잡고, 두 집단이 지난
공정·장비·레시피를 견주어 **차이 나는 축**을 올립니다.

```
유니버셜   🟡 반쪽.  불량 종류·비교 축이 «선언 파일»에서 옵니다 (좋은 쪽)
           journey 는 옛 해결기를 함께 읽어서 §0 문제에 걸립니다
           siblings 는 축 선언이 «읽힙니다» (확인함).  전체 응답은 «안 쟀습니다»
```

# 4. 「추세가 어떤가」 — 시계열

**주소** `trends`

**R&D 가 묻는 것:** 「이 불량이 최근에 늘고 있나. 어느 시점부터인가.」

**부르는 법:** `trends?kinds=void,delam&window=180d`

**어떻게 도나:** 불량 종류별 시계열과 표를 한 번에 냅니다. 화면에서 구간을 칠하면
그 마킹이 그대로 다음 질문(대조)으로 넘어가게 설계돼 있습니다.

```
유니버셜   🟢 좋은 편.  «돕니다» (직접 불러 확인)
           불량 종류를 코드가 아니라 «선언»에서 읽습니다 — 종류를 늘려도 코드가 안 바뀝니다
           옛 어휘 목록·옛 해결기를 «안 읽습니다» (코드에서 확인)
```

# 6. 「무엇을 물을 수 있나」 — 카탈로그

**주소** `kinds` · `entities` · `coverage` · `structure`

**R&D 가 묻는 것:** 「이 원장이 지금 무엇을 알고 있나. 무엇을 물어볼 수 있나.」
화면이 처음 뜰 때 한 번 묻는 자리이고, **대표님이 「무엇을 채워야 하나」를 보는 창**입니다.

```
kinds      🟢 돕니다.  불량 종류 목록 + 종류마다 원자 수까지 나옵니다
           ⚠️ 다만 지금 「번역기 선언을 못 읽는다」 경고를 달고 답합니다 — §0 문제
           그래서 「원장에 있음/없음」 표시가 «전부 없음»으로 나옵니다. 개수는 맞습니다

entities   🟡 돕니다.  register 된 개체를 타입별로 나열합니다
           ⚠️ 타입 목록이 옛 코드 목록이라 «장비·제품» 같은 안 쓰는 것이 뜨고,
              대표님이 새로 선언한 타입은 «안 뜹니다»

coverage   🔴 안 돕니다.  §0 의 그 거절이 그대로 납니다
structure  🔴 안 돕니다.  같은 이유 (옛 해결기를 읽습니다)
```

# 8. 🔴 유니버셜 총평 — 대표님이 가장 물으신 것

**기준: 다른 스키마의 팹에 가져갔을 때, 코드 0줄 고치고 선언만 바꿔서 도는가.**

```
🟢 그렇다        trends · composition · kinds            (3)
🟡 반쪽          subgraph 둘 · siblings · entities · lots 둘  (6)
🔴 아니다        trace · explore · explore_entity
                 coverage · structure · journey          (6)
   (selection/resolve 는 «안 쟀습니다» — 입력 형식을 제가 못 만들었습니다)
```

## 그리고 🔴 여섯이 «여섯 가지 문제»가 아닙니다 — 한 가지입니다

```
읽는 쪽이 «원자를 쓴 그 선언»을 안 봅니다.

  ① 옛 해결기가 없는 파일을 찾다가 «샘플»로 흘러가고, 그 샘플이 깨져 있다
     -> trace · explore · explore_entity · coverage · structure · journey  «여섯»
  ② 개체 타입 검사가 «옛 코드 목록»을 본다
     -> die 가 씨앗이 안 된다 (subgraph)
  ③ 이름표 순서도 같은 옛 목록에서 온다
     -> die 이름 대신 좌표가 뜬다
```

**그래서 고칠 것도 하나입니다.** 다만 «고치는 방향»을 소유자가 정하셨습니다:

> **소유자 (2026-08-23): 「v1 해결기들은 가급적 «은퇴»시키는 방식으로 하는 게 좋겠어.」**

그러면 질문이 「어떻게 고치나」가 아니라 **「없애면 무엇을 잃나」**가 됩니다. 재 봤습니다 — §8-bis.

# 8-bis. 🔴 「없애면 무엇을 잃나」 — 여섯을 하나씩 재 봤습니다

## 계보 셋 — **잃는 것이 «표현»뿐입니다. 사실은 이미 다른 데 있습니다**

`subgraph` 를 랏 하나로 직접 불러 봤습니다:

```
씨앗 Lot=NAB539TA · 4홉 -> 노드 254 · 엣지 621
담긴 주장   derived_from 8 · has_wafer 131 · slot_map 50 · register 27
담긴 개체   Lot 5 · Wafer 25      부모 랏이 «노드로 나옵니다»
```

**계보 셋이 쓰는 낱말 넷이 `subgraph` 안에 그대로 있습니다.**
다른 것은 «모양»입니다 — 저쪽은 홉 사슬(1홉·2홉·…)로 주고, 이쪽은 그래프로 줍니다.

```
trace · explore · explore_entity   은퇴해도 «사실»은 안 잃습니다
                                   잃는 것: 「1홉·2홉…」으로 줄 세운 «표현»
                                   그 표현이 필요하면 subgraph 결과를 정렬하면 됩니다
```

## `journey` — **대체가 «없습니다»**

「웨이퍼 두 장이 지난 공정을 «서열»로 나란히」는 다른 어느 것도 안 합니다.
`siblings` 는 «차이 나는 축»을 주지 «순서»를 안 줍니다.

```
은퇴하면   이 질문 자체를 잃습니다.  v5 쪽에 다시 만들어야 합니다
```

## `coverage` — **대체가 «없습니다» (운영 건강)**

응답에 담긴 것: 소스별 원자 수 · **번역기 커서 위치** · 파티션 · 마지막 원자 시각.
「어느 소스가 어디까지 썼나」를 보는 유일한 창입니다. `kinds` 는 «종류별 개수»만 줍니다.

```
은퇴하면   백필이 어디까지 갔는지 볼 창이 없어집니다.  v5 쪽에 작게 다시 필요합니다
```

## `structure` — **반쪽 대체**

「선언된 개체·관계를 그래프로 + 어디에 데이터가 얼마나」입니다.
선언 자체는 설정 화면이 폼으로 보여 주지만, **«그래프 모양»과 «데이터 분포»는 여기뿐**입니다.

```
은퇴하면   선언을 «한눈에» 보는 그림을 잃습니다.  급하지는 않습니다
```

## 정리 — 은퇴 순서

```
바로 은퇴 가능   trace · explore · explore_entity      subgraph 가 사실을 덮습니다 (실측)
                 structure                             급하지 않습니다
v5 에 «작게» 다시  coverage                            커서·소스 현황 (작습니다)
                 journey                              두 웨이퍼 서열 대조 (이건 기능입니다)
```

🔴 **그리고 은퇴하면 §8 의 ①이 통째로 사라집니다** — 없는 파일을 찾다 샘플로 흘러가는
그 문제가 «그 코드와 함께» 없어집니다. 남는 것은 ②③(옛 타입 목록)뿐이고,
그건 `subgraph` 쪽이라 따로 다뤄야 합니다.

## 🟢 셋이 왜 좋은지도 한 줄로

`trends` · `composition` · `kinds` 는 **옛 어휘 목록을 아예 안 읽습니다.**
필요한 것을 «선언 파일»에서 읽고, 없으면 «없다»고 답합니다.
**새 API 를 만들 때 이 셋의 모양을 따르면 됩니다.**

# 9. 제가 «안 잰» 것 (추측하지 않았습니다)

```
selection/resolve   입력이 화면 마킹 형식이라 손으로 못 만들었습니다

```
