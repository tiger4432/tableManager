# 지시서 — 어느 화면에서든 클릭한 글자가 씨앗이 된다

> **작성:** 응용 기획 세션 (2026-08-21) · **수신:** 총괄 (착수 판정) → 서버·클라
> **소유자 발화:** 「내가 웹에서 어떤 화면을 보고 있든 lot_id 스러운 글자를 클릭하면
> 그게 walk 으로 연동되서 확장 프로그램 view 에 바로 그 lot 정보가 주루륵 뜨는거지」
> 「lot 이라 하였지만 **우리가 가지고 있는 엔티티로 추정되는 것**이라고 보면 됨」

## 0. 착수 전 관문 (`CLAUDE.md` 상설)

    ① 최소 수정 · ② 단순 로직 · ③ 안 시킨 것 금지

**이 지시서에도 걸린다.** §6 「하지 말 것」을 지시의 일부로 읽는다.

## 1. 🔴 재고 — 백엔드가 «거의 다» 있다

    GET /api/ledger/entities?type=&q=      register 된 개체를 «부분 문자열» 로 찾는다
                                           전용 trigram 인덱스 있음 (REGISTER_SEARCH_INDEX)
    GET /api/ledger/explore_entity?id=     그 개체의 주장과 전방 참조를 «그래프로»
                                           id 는 불투명·타입 있음

**소유자가 말한 동선이 `클릭 → entities → explore_entity` 이고, 둘 다 이미 돈다.**

## 2. 막는 것 — 「타입을 지정해야 한다」 하나

```python
# ledger_trace_router.py, /entities
subject_type: str = Query("Lot", alias="type", ...)     # 🔴 단일 타입 «필수», 기본값이 Lot
```
「우리 엔티티로 추정되는 것」이면 **타입을 모른 채** 물어야 한다.
그리고 기본값 `"Lot"` 은 어휘 하드코딩이다.

`explore_entity` 에도 `if subject_type == "Lot"` 분기가 하나 더 있다.

---

## 3. 🔴 설계 판단 — 패턴으로 «추정»하지 않고 원장에 «확인»한다

    ✗ 패턴 방식   `^[A-Z]\d+$` 류 정규식으로 「lot 처럼 생겼나」 판별
                 공장마다 다르다 = 하드코딩. 무한 케이스 규칙 실패.
                 그리고 오탐이 난다 (같은 모양의 남의 코드)

    ✅ 조회 방식   원장의 `register` 원자에 물어본다
                 «실재하는 것» 만 걸린다. 오탐 0. 어휘 중립.
                 새 개체 타입이 «선언되면» 자동으로 인식 대상이 된다 — 코드 0줄

소유자 표현 「엔티티로 «추정»되는 것」의 구현은 **추정이 아니라 확인**이다.
원장에 없는 글자는 그냥 안 걸리고, 그것이 정답이다.

**비용:** `register` 원자는 O(개체) 이지 O(원자) 가 아니다(schema.py 의 부분 인덱스 주석).
싼 쪽이다.

## 4. 공사

### 공사 A — 서버: `resolve` 하나

    GET /api/ledger/resolve?q=<클릭한 글자>

    한다      «선언된 개체 타입 전부» 를 횡단해 register 원자를 찾는다
              타입 목록은 «선언에서» 온다 (하드코딩 금지)
    낸다      [{ type, id, keys }]  — id 는 기존 `/entities` 와 «같은 불투명 id»
    여럿이면   그대로 여럿을 낸다. «모호» 는 사용자가 고를 일이지 서버가 고를 일이 아니다
    없으면     빈 목록. 오류가 아니다 — 「우리 엔티티가 아니다」가 답이다

⚠️ **새 검색 기계를 만들지 않는다.** 기존 `entity_catalog` 를 타입마다 부르는 것으로
족하다. 한 질의로 합치는 최적화는 «느리다는 측정이 나온 뒤에» 한다.

### 공사 B — 서버: `/entities` 의 타입 강제 해제

    지금   type 이 단일 필수, 기본값 "Lot"
    뒤     type 이 «선택». 없으면 전 타입

기본값 `"Lot"` 을 지운다. `explore_entity` 의 `subject_type == "Lot"` 분기는
**이번에 건드리지 않는다** — 동작이 다른 이유가 있는지 확인되지 않았다(§6).

### 공사 C — 클라: 브라우저 확장

    잡는다   «클릭한 텍스트 선택 영역» 하나.  🔴 화면 전체 스캔은 «하지 않는다»
    보낸다   그 문자열만
    그린다   resolve 가 하나면 바로 패널, 여럿이면 고르는 줄 하나
    패널     explore_entity 의 그래프를 «주루륵» — 기존 뷰어 산출물을 재사용

🔴 **클릭한 것만 보내는 이유:** 전체 스캔은 보고 있는 화면 내용을 통째로 서버에 보낸다.
소유자 원문이 「클릭하면」이고, 밑줄 치기(전체 스캔)는 **필요가 확인되면 그때** 얹는다.

## 5. 수락 단언

    A  선언에 개체 타입을 «하나 추가»하면 그 타입의 id 도 «코드 0줄» 로 인식된다
    B  원장에 없는 글자를 클릭하면 «빈 목록». 오류도, 추측도 아니다
    C  같은 글자가 두 타입에 있으면 «둘 다» 나온다. 서버가 고르지 않는다
    D  기존 `/entities?type=Lot` 호출이 그대로 돈다

**A 가 이 라운드의 핵심이다.** 하나라도 타입 이름이 코드에 남으면 미완이다.

## 6. 하지 말 것

    ✗ 정규식·패턴으로 id 를 «추정»              §3
    ✗ 화면 전체 스캔 / 자동 밑줄                 §4-C. 데이터가 통째로 나간다
    ✗ `explore_entity` 의 Lot 분기 수정          이유 미확인. 별도 라운드
    ✗ 새 검색 엔진·인덱스                        기존 trigram 인덱스로 족하다
    ✗ 타입 «목록» 을 코드에 두기                  선언에서 온다
    ✗ 모호할 때 서버가 하나 고르기                사용자가 고른다

## 7. 이 응용과 `walk` 의 관계

    resolve   글자 -> «노드 신원»          이 지시서
    walk      노드 -> «주변»               `task/APPLICATION_PROPAGATION_BRIEF.md`

**둘은 직렬이고 독립이다.** `resolve` 는 `walk` 없이도 `explore_entity` 로 쓸모가 있고,
`walk` 가 서면 패널이 「주변」에서 「원인 후보와 다음 할 일」로 자란다.

**그래서 이 라운드는 `walk` 를 기다리지 않는다.**
