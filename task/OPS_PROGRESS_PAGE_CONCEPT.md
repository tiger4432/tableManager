# 진행 관리 화면 — 컨셉 문서 (목업용)

> 소유자 요청 (2026-08-30): 「원장 업데이트든 체인 리플레이든 파일 인제션이든
> 이런 것들 진행 관리를 좀 종합적으로 체계적으로 할 수 있는 페이지가 있으면 좋겠어」

이 문서는 **무엇을 보여줘야 하는가**를 적습니다. 색·레이아웃·컴포넌트는 디자인 쪽 판단입니다.
다만 §3 의 「섞이면 안 되는 상태」 두 표는 **디자인 요구사항**입니다 — 그게 이 화면의 존재 이유입니다.

---

## 1. 이 화면이 푸는 문제 하나

**지금은 「안 돌고 있다」가 「할 일이 없다」와 똑같이 보입니다.**

실제 사고 (2026-08-30):
- 원장 소스 하나(`lot_event`)가 재건 이후 **한 번도 안 돌았습니다.**
- 그 소스가 만들어야 할 원자 셋이 **전부 0**이었고, 아무도 몰랐습니다.
- 화면에는 그냥 **아무것도 없었습니다.** 오류도, 경고도 없이.
- 원인을 찾는 데 저녁 내내 걸렸고, 찾고 나니 **커서 표에 이미 적혀 있었습니다.**

그리고 같은 표에 지금도 이런 게 적혀 있는데 아무도 안 봅니다:

```
dt_log 소스   molecules_refused 96
             refusal_reasons = { no_identity: {count: 80, last_at: …},
                                 missing_occurred_at: {count: 16, last_at: …} }
```

> **이 화면의 한 줄 목표: 「무엇이 안 돌고 있고, 무엇이 왜 거절됐고, 어떻게 다시 돌리나」를
> 첫 화면에서 답한다.**

---

## 2. 화면의 여섯 영역

### ① 원장 번역 — 소스별 진행
데이터: `ledger_translator_cursor` (이미 있는 표, 새로 만들 것 없음)

| 칸 | 뜻 |
|---|---|
| `source` | 소스 이름 |
| `translator_ver` | 번역기 판. **커서는 (source, ver) 로 갈립니다** — 판이 바뀌면 처음부터 |
| `updated_at` / `started_at` | 마지막으로 «움직인» 시각 |
| `molecules_done` · `atoms_written` · `atoms_deduped` | 얼마나 했나 |
| `molecules_refused` · `incomplete_molecules` | 얼마나 «못» 했나 |
| `refusal_reasons` | **사유별 count 와 last_at** — 이 화면의 핵심 재료 |
| `source_head` | `groups_behind` / `rows_behind` = **지연** |

⚠️ 선언에 있는 소스인데 **커서 행이 아예 없으면** 「한 번도 안 돌았다」입니다.
그건 표에 «행이 없는» 상태라, 표만 그리면 **안 보입니다.** 선언 목록과 대조해서
「없는 것」을 별도로 세워야 합니다.

### ② 파일 인제션
데이터: `file_ingestion_checkpoints` · `file_ingestion_logs`
- 어디까지 읽었나, 최근 실패, 파서를 못 찾은 파일

### ③ 체인
데이터: `database_outbox`
- 밀린 건수, 가장 오래된 것의 나이

### ④ 소급 연산 — 실행 자리
데이터: `GET /admin/retroactive/operations` (이미 있음)

각 연산이 **스스로 선언**하는 것들을 그대로 보여줍니다:

| 필드 | 화면에서의 뜻 |
|---|---|
| `label` | 사람 이름 |
| `params` | 무엇을 받아야 하나 |
| `deletes` | **무엇을 지우나** (null 이면 안 지움) |
| `restartable` | 중간에 끊겨도 되나 |
| `cli` | 같은 일을 하는 명령줄 |
| `what_is_missing` | 이 연산이 «무엇이 없을 때» 쓰는 것인가 |

**실행은 항상 두 걸음:**
```
1  드라이런    GET /{op}/count   ->  「몇 건에 영향」
2  실행        run_id 를 받고 진행을 ①~③ 과 같은 자리에서 본다
```

### ⑤ 프로세스 상태 — 「지금 무엇이 살아 있나」
데이터: `server/config/supervisor_status.json` (감독자가 계속 갱신)

```
supervisor_pid · started_at · updated_at · stopping
children              자식 프로세스들 (이 시스템은 «다섯»입니다)
failed_children       🔴 죽은 것
correlated_children   묶여 있는 것
events                최근에 일어난 일
```
🔴 **`updated_at` 이 «멈춰 있으면» 감독자 자신이 죽은 것입니다.**
자식이 다 살아 있다고 그려 놓고 감독자가 10분 전에 멈췄으면, 그 화면은 «10분 전 사진»입니다.
그래서 **자식 목록보다 `updated_at` 의 나이가 먼저 보여야** 합니다.

### ⑥ 큐 — 「무엇이 밀려 있나」
데이터: `database_outbox`

```
status · retry_count      🔴 retry_count 가 높은 것 = «계속 실패하고 있는 것»
                          밀린 건수만 보면 「많다」로 보이고, 재시도 수를 봐야 「막혔다」가 보입니다
created_at · processed_at · broadcast_at
                          가장 오래된 «미처리»의 나이 = 실질 지연
event_type · table_name   무엇이 밀리나
```

데이터: `server/config/scheduler_status.json`
```
collectors[]   table_name · script_name · cron_expression
last_updated   🔴 이것도 «나이»를 봐야 합니다 — 스케줄러가 멈추면 이 값이 안 움직입니다
```

### 🔴 그리고 «없는» 것 하나 — 소급 연산의 실행 기록
```
/admin/retroactive/{op}/run 은 run_id 를 «돌려주는데», 그 run 을 적어 두는 표가 «없습니다»
=> 실행을 걸어 놓고 나면 「그게 지금 어디쯤인지」를 물어볼 데가 없습니다
=> 목업에는 «있는 것처럼» 그려 두시고, 서버 라운드에서 그 표를 같이 만들겠습니다
   (이건 화면 탓이 아니라 서버에 빠진 조각입니다)
```

## 3. 🔴 섞이면 안 되는 상태들 — 이게 디자인 요구사항입니다

**모두 「숫자가 0」이거나 「화면이 비어 있음」으로 나타납니다. 그래서 지금 구별이 안 됩니다.**
서로 다른 다섯이고, **사람이 할 일이 각각 다릅니다.**

| 상태 | 어떻게 아나 | 사람이 할 일 |
|---|---|---|
| **안 돌았음** | 선언엔 있는데 **커서 행이 없음** | 돌려라 |
| **돌았는데 0** | 커서는 있고 `atoms_written`=0 | 왜 0인지 봐라 (입력이 없나, 전부 거절인가) |
| **거절됨** | `molecules_refused`>0 + `refusal_reasons` | **사유를 읽어라** — 대개 고칠 수 있는 것 |
| **지연됨** | `source_head.groups_behind`>0 | 기다리거나 밀어라 |
| **정상·할 일 없음** | 지연 0 · 거절 0 · 최근 실행됨 | 없음 |

### 프로세스·큐 쪽도 같은 병이 있습니다
| 상태 | 어떻게 아나 | 사람이 할 일 |
|---|---|---|
| **감독자가 죽음** | `supervisor_status.updated_at` 이 «안 움직임» | 🔴 이 화면 전체가 옛 사진 |
| **자식이 죽음** | `failed_children` | 살려라 |
| **막힘** | `database_outbox.retry_count` 높음 | 사유를 봐라 |
| **밀림** | 미처리 중 «가장 오래된 것»의 나이 | 기다려라 |
| **스케줄러 멈춤** | `scheduler_status.last_updated` 나이 | 살려라 |

⚠️ **「밀림」과 「막힘」을 같은 숫자로 그리면 안 됩니다.** 밀린 건 기다리면 되고,
막힌 건 사람이 가야 합니다. 둘 다 「큐에 N건」으로 보입니다.

> 「없어서 0」과 「막혀서 0」과 「아직 안 해서 0」을 **같은 회색**으로 그리면
> 이 화면은 지금 있는 화면과 똑같아집니다. 그 셋을 가르는 것이 이 화면의 전부입니다.

**정렬은 「할 일 있는 것」이 위로.** 정상인 것은 아래로 접혀도 됩니다.

## 4. 실제 값 예시 (개발 박스 — 운영 수가 아닙니다)

목업에 넣을 «모양»으로만 쓰십시오. 운영 수치는 다릅니다.

```
정상        void_observation   원자 207,714 · 거절 0 · 지연 0 · 최근 실행 08-29 22:34
거절 있음    dt_log             원자 5,415 · 거절 96
                              no_identity 80 · missing_occurred_at 16
방금 살아남   lot_slot_wafer     원자 907 · 거절 0 · 최초 실행 08-30 21:27
안 돌았음    (오늘 이전의 lot_event — 커서 «행 자체»가 없었음)
```

## 5. 화면이 하지 «말아야» 할 것

```
⛔ 실행 버튼을 드라이런 없이 두지 말 것
   각 연산이 「몇 건에 영향」을 스스로 답합니다. 그걸 «보여주고» 나서 실행입니다
⛔ 숫자를 «서버가 붙인 꼬리표 없이» 그리지 말 것
   count 는 exact / sample / upper_bound 를 같이 옵니다. 표본이면 표본이라고 써야 합니다
   (서버가 이미 그 문장을 만들어 보냅니다 — 화면은 그대로 렌더하고 스스로 판정하지 않습니다)
⛔ 거절 사유를 접어 두지 말 것. 그게 유일하게 «고칠 수 있는» 정보입니다
⛔ 새 상태를 «지어내지» 말 것. 위 열 가지는 전부 데이터에서 나옵니다
```

## 6. 참고 — 서버 쪽에 이미 있는 것 / 없는 것

```
있음   ledger_translator_cursor · file_ingestion_checkpoints · file_ingestion_logs
      database_outbox · supervisor_status.json · scheduler_status.json
      /admin/retroactive/operations · /{op}/count · run_id
없음   위 여섯 영역을 «한 번에» 주는 라우트 (모으는 일)
없음   소급 연산 «실행 기록» 표 — run_id 를 돌려주는데 적어 두는 데가 없습니다
없음   「범위만 다시 하기」 — 별도 지시서: task/SCOPED_REDO_BRIEF.md
```

새로 모을 «데이터»는 없습니다. 이 화면은 이미 기록돼 있는데 아무도 안 보는 것을
**보이게 만드는** 일입니다.
