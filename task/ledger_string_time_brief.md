# 문자열 시각을 «선언»으로 읽는다 (소유자 판정 2026-08-21 09:5x 「2번 진행」)

> 소유자: 「문자열 타입 시각은 **마이그레이션 방법 찾아** — 문자열 형식이 운영에서는
> 일정하지 않아서 문자열로 둔 거임」 → 총괄이 방법을 올림 → 「2번 진행」
>
> 🔴 **순서: 이 라운드는 `ledger_per_source_version_brief.md`(소스별 지문) «뒤»다.**
> 이유는 그 지시서 §②에 적혀 있다 — 이 라운드는 원자의 «값»을 바꾸므로 전역 지문 아래서
> 착지하면 모든 소스의 커서가 동시에 막힌다.

## 🔴 도착지

```
varchar 에 든 시각을 «세상 시각»으로 읽는다. 그리고 그 해석 규칙이 «선언»에 있어서
다른 표·다른 형식이 와도 코드 0줄로 먹는다
```
소유자 DoD 그대로다: **다른 스키마 운영 환경에서 코드 0줄, 선언 교체만으로 발화.**

---

## 재 놓은 사실 — 여기서 시작한다 (다시 재지 말 것)

**구현자 실측 (`c6d9b587`), DB 전수:**
```
string 으로 선언됐는데 DB 가 timestamp   →  «0건». 선언은 정직하다
lot_event.event_time  선언 datetime · 실제 varchar     🟠 뒤집힌 것은 «여기 하나»
```
**총괄 실측 (형식 분포, 이 박스):**
```
dt_log.event_time   «3형식이 한 컬럼에 섞여 있다»
      2026-05-11 00:00:00          8,700   zone «없음»
      2026-08-10T00:14:00+09:00    6,733   KST
      2026-08-09T00:00:00Z         4,567   UTC
lot_event 2형식(둘 다 naive) · core_wafer_map 2 · map_split_registry 2(시가 한 자리)
wafer_process 1형식(분까지, 초 없음) · process_event 1형식(+09:00)
```

### 🔴 그래서 위험한 것은 «파싱»이 아니다
형식은 전부 ISO 계열이라 파서 하나로 읽힌다. **한 컬럼 «안»에 zone 있는 값과 없는 값이
같이 있는 것**이 문제다. 무턱대고 캐스팅하면 `…T00:00:00Z`(UTC)와 `2026-05-11 00:00:00`
(아마 KST)이 같은 줄에 서고 **한쪽이 조용히 9시간 밀린다. 거절도 안 난다.**

## 규칙 — 한 줄. 새 축을 «만들지 않는다»

```
명시 offset 이 있으면   그것을 쓴다        (+09:00 · Z)
없으면                  선언된 read.occurred_at.timezone 을 쓴다
```
✅ **`timezone` 은 이미 선언에 있다** — 총괄이 아침 걷기에서 `Asia/Seoul` 로 채웠고 검증기가 받았다.
**새 필드를 만들지 말 것.** 있는 칸의 «뜻»을 「naive 값의 시간대」로 확정하는 것이 이 라운드다.

⚠️ 그래도 형식이 안 읽히면 **조용히 넘기지 말고 거절한다.** 못 읽은 값을 적재 시각으로
대체하는 것이 오늘의 병이다.

## 바뀌는 층 · 그대로인 것

```
바뀐다   ① 읽기 경로의 occurred_at «해석»            naive ↔ aware 판정과 tz 적용
         ② 시각 피커의 «후보 규칙»                   config_authoring.py:1179 근처
              지금은 catalog 타입이 datetime 인 컬럼만 후보로 준다
         ③ compiler_contract_version                 값이 바뀌므로 «올라가야 한다»

그대로   선언 «형식»(새 필드 없음) · 스켈레톤 · 검증기 거절 코드 · 팩·클레임 ·
         setup_version · table_config.json 의 string 선언(소유자: 의도다)
```

🔴 **①과 ②는 «같이» 착지한다.** 읽기만 고치면 사장님이 화면에서 그 컬럼을 «고를 수 없고»,
피커만 고치면 고른 값이 안 읽힌다. 둘 중 하나만은 **둘 다 안 한 것과 같다.**
[[if-code-cannot-reach-it-neither-should-the-declaration]]

🔴 **③을 빼지 말 것.** 원자의 값이 바뀌는데 지문이 안 움직이면, 커서가 **「같은 셋업」이라고
믿고 새 해석으로 이어 쌓는다.** 옛 해석 원자와 새 해석 원자가 구별 없이 섞인다.

## ⛔ 착수 «전» 멈춤 조건 — «하나»다

> **라이브 읽기 경로가 이미 변환하고 있으면 → 멈추고 보고.**

구현자 하니스는 `bf._fetch_v2_lineage_page` 를 «직접» 불러 상위 경로를 건너뛴다. 거기서
`str` 이 나왔다는 것이 **「라이브에도 변환기가 없다」를 뜻하지 않는다.** 구현자 본인이
그 주의를 달아 뒀다. **라이브 경로로 한 번 재고 시작할 것.** 이미 변환한다면 이 라운드는
훨씬 작아지거나 필요 없어진다.

나머지는 진행하면서 재고, 숫자는 나오는 대로 한 줄씩. **「못 쟀다」도 답이다.**

## 🔴 받아들이는 시험 — **Z 값이 판별식이다**

```
1  dt_log 의 «세 형식»을 각각 태워 읽은 시각을 비교한다
      2026-08-09T00:00:00Z        →  KST 09:00 으로 읽혀야 한다
      2026-05-11 00:00:00         →  KST 00:00 으로 읽혀야 한다
      2026-08-10T00:14:00+09:00   →  KST 00:14 로 읽혀야 한다
2  화면: dt_log 소스의 시각 피커가 event_time 을 «후보로 준다»
3  라이브 설정 회귀 없음: 거절 0 · missing 0 · 「4 layers · complete」
4  픽스처 체크포인트                test_ledger_setup_boundary.py:218
      atom_count 10 · molecule_count 1 · incomplete 0 · 술어 4종
5  이미 쌓인 원자는 «안 건드린다». 과거는 옛 해석으로 남는다 (append 원칙)
```

⚠️ **naive 값만으로 재면 아무것도 증명 못 한다.** 「offset 우선」 규칙과 「무조건 declared tz」
규칙이 naive 값에서는 **같은 답**을 낸다. **`Z` 값이 둘을 가르는 유일한 표본이다.**
이 프로젝트가 이미 당한 모양이다 — [[a-fixture-both-rules-agree-on-decides-nothing]].

⚠️ **`wafer_process` 의 「분까지, 초 없음」과 `map_split_registry` 의 「시가 한 자리」도
한 번씩 태울 것.** 파서가 조용히 실패하기 좋은 자리다.
