# [Task] 셋업 마찰 — 관찰 결과와 «어떻게 고칠 것인가»

> **상태:** 관찰 완료, 착수 대기
> **측정:** 2026-08-18 밤 ~2시간. 소유자가 `dt_log`를 원장에 붙이는 전 과정에 동석하며
> 저장마다 실시간 검증. 저장 약 20회, 거절 약 40건. **실제로 일어난 것만** 적었다.
> **소유자 지시:** 「어디까지 간소화할 수 있는지」 + 「어떻게 할 건지도 적어라」

## 0. 결론

거절 40건 중 **사람이 판단해야 했던 것은 다섯 개 남짓**이다. 나머지는 이미 다른 곳에 적힌
것을 옮겨 적기, 필드 이름 외우기, 물리 표를 안 봐서 생긴 것이었다.

## 수단은 네 가지뿐이다 — 위에서부터 강한 순

| 수단 | 뜻 | 강도 |
|---|---|---|
| **① 구조적 제거** | 그 칸을 «없앤다». 틀릴 자리가 사라진다 | 가장 강함 |
| **② 유도** | 다른 선언에서 계산해 채운다. 사람에게 안 묻는다 | 강함 |
| **③ 제약 입력** | 드롭다운·실측값 표시. 틀린 값을 못 «고르게» 한다 | 중간 |
| **④ 진단 개선** | 거절문이 답을 같이 준다 | 가장 약함 |

**④는 최후 수단이다.** 오늘 ④를 개선해서 왕복이 줄었지만, 애초에 물어보지 않았으면 왕복이
없었다. 아래 각 항목은 **가능한 가장 강한 수단**으로 배정했다.

## 1. 🔴 `basis`를 쓰면 매퍼가 시각 컬럼 이름을 되물어야 한다 — **① 구조적 제거**

**증상.** 소스가 `occurred_at: { basis: "ingested" }`를 선언하면 계획이 물리 컬럼
`created_at`으로 해석한다. 그런데 매퍼는 시각을 **컬럼 이름으로** 읽는다:

```python
ProfileSentences(context, profile, occurred_at=unit.iloc[0]["event_time"])   # lot_event
```

`dt_job`에서는 답이 `created_at`이다. 그래서 오늘 매퍼가 이렇게 됐다:

```python
occurred_column = context.source_plan.driver.occurred_at.column      # ← 되묻는 중
sentences = ProfileSentences(context, profile, occurred_at=unit.iloc[0][occurred_column])
```

**소유자 판정: 「`basis`를 쓴다고 시각이 달라지면 안 되지, 다 `occurred_at`이어야지」.**

**어떻게.** `source_preparation`이 `__source_row_ref`를 얹는 바로 그 자리(`:777` 근처)에서
**`__occurred_at`도 얹는다.** 값은 이미 그 함수 안에 있다 — `occurred_values[0]`이 그것이고,
지금은 검증에만 쓰고 버린다. 컬럼에서 왔든 basis에서 왔든 매퍼는 한 이름만 안다.

```python
sentences = ProfileSentences(context, profile, occurred_at=unit.iloc[0][SOURCE_OCCURRED_AT_COLUMN])
```

**부수 효과 — 이게 진짜 이득이다.** 매퍼가 `context.source_plan`을 읽을 이유가 **완전히**
사라진다. 지금 남은 유일한 용처가 이것이다. 매퍼 계약이 `unit` 하나로 줄어든다.

**주의.** `lot_event` 매퍼도 같이 옮겨야 한다. 원자 디프 0으로 검증.

## 2. 🔴 컬럼 이름을 타이핑한다 — **③ 제약 입력**

**증상.** 소스 하나에 컬럼 이름을 적는 자리가 **최소 12곳**이다 — `identity`, `group_by`,
`order_by`, `cursor.columns`, `occurred_at.column`, `mappers.input_columns`,
`unit.columns`, 그리고 바인딩마다 `column`.

오늘 실제로 난 사고 둘:
- 엔터티 키를 `dt_job_id`로 지정 → **그 컬럼은 값이 0건.** 실제 값은 `dt_job`
- `order_by: [dt_job, dt_index]` → **중복 8,580건.** 백필 실행 중에 거절될 조합

**어떻게.** 컬럼 자리는 전부 `table_config.json`에서 읽은 **드롭다운**. 그리고 후보마다
**옆에 숫자를 붙인다:**

```
dt_job          34,939 / 34,939 값 있음
dt_cell_key     34,939 / 34,939 값 있음   ← 유일
dt_job_id            0 / 34,939 값 있음   ⚠ 비어 있음
```

**두 사고가 다 이 숫자 하나로 막힌다.** 오타 방지는 부수 효과이고, 본질은 「그 컬럼이 쓸 수
있는 컬럼인가」를 고를 때 보여 주는 것이다.

**구현 위치.** 후보와 개수를 내려 주는 API 하나. 화면 없이도 명령으로 먼저 쓸 수 있다.

## 3. 강제된 것을 사람이 받아쓴다 — **② 유도 (진행 중)**

검증기가 이미 **정확히 일치**를 요구하는 자리를 작성자가 다시 적는다. 자유도가 0이라
**틀릴 수만 있고 나아질 수 없다.**

| 받아쓰는 것 | 무엇이 강제하나 |
|---|---|
| 프로필 바인딩의 `keys` 이름 | 엔터티의 `keys` |
| `$role` / `$role?` 표기 | 그 역할의 `required` |
| claim의 `object.kind` | 낱말의 object kind |
| claim의 qualifier 집합 | 낱말의 required/optional |
| `group_by` ⊆ `identity` | 드라이버 규칙 |
| `unit.columns` ⊆ `input_columns` | 매퍼 규칙 |
| `mappers.input_columns` | 프로필 바인딩이 부르는 컬럼 전부 |

**어떻게.** 두 층으로 나눈다.

**지금(②):** 화면이 유도해 채우고, 사람에게는 **자유로운 것만** 묻는다. 엔터티 바인딩에서
키 «이름»은 유도, 「어느 컬럼이 그 키를 공급하나」만 질문.

**다음(①):** 유도되는 것은 **파일에서 아예 빼는** 것을 검토한다. `mappers.input_columns`가
후보다 — 프로필 바인딩에서 100% 계산되므로 선언할 이유가 없다. 다만 「매퍼가 받는 컬럼」이
계약으로서 눈에 보이는 값도 있으니, 없애기 전에 그 값을 따져야 한다.

## 4. 필드 이름을 외워야 한다 — **④ 진단 (구조적 해결이 어려움)**

같은 개념이 자리마다 다른 이름을 쓴다. **나조차 오늘 두 번 틀렸다.**

| 자리 | 맞는 이름 | 내가/스크립트가 틀린 것 |
|---|---|---|
| 프로필 | `packs` | `pack_ids` ← 소유자에게 잘못 알려 줌 |
| 엔터티 | `keys` | `identity_keys` ← 내 스크립트가 조용히 실패 |
| emit.object | `value` | `payload` ← 잘못 알려 줌. `payload`는 저장 컬럼 이름 |
| 소스 | `source` | `source_id` |

**어떻게.** 이름을 통일하는 것은 파괴적 변경이라 지금은 안 한다. 대신:
- 거절문이 **허용 목록**을 댄다 — **오늘 착지함**
- **오타 근접 제안** — 「`pack_ids`? `packs`를 뜻하셨나요」. `difflib` 기반 진행 중
- 화면이 있으면 이 항목은 **자동 소멸**한다(필드를 타이핑하지 않으므로)

## 5. 물리 표가 틀렸는데 손가락은 원장을 가리킨다 — **④ 진단 + ③ 가시화**

`dt_log` 실측:
- 선언 컬럼 **14개**, 실제 **31개** — 값이 있는데 선언 안 된 컬럼 9개
- 선언된 14개 중 **7개가 값 0건**
- 타입 불일치 **3건**
- `composite_key_source`가 **전부 빈 컬럼 3개**로 구성 — 아무것도 식별 못 함

거절문은 `bundle.sources.dt_job.driver.order_by`를 가리켰다. **원인은 카탈로그다.**

**어떻게.**
- 거절문이 원인 파일을 지목한다 — 「`table_config.json`의 `dt_log`가 유일 키를 선언하지 않음」
- 화면에 **카탈로그 상태 패널**: 선언/실물 컬럼 수, 값 0건 컬럼, 타입 불일치, 선언된 키가
  실제로 유일한지

## 6. 타입 불일치를 아무도 안 본다 — **④ 계측 추가**

`schema_drift`는 **이름만** 비교한다. 주석이 스스로 적어 뒀다 — 「타입 불일치는 이 모듈이
못 잡는 첫 번째 종류」.

`dt_log` 한 표에서 3건. **26개 표 전체가 같은 사각지대이고 지금 몇 건인지 모른다.**

**어떻게.** ① 전 표를 한 번 세어 개수를 먼저 안다(급한지 정하려면 숫자가 필요).
② 드리프트에 타입 비교를 **INFO 등급**으로 추가. 배포를 막지는 않되 **매일 보이게** 한다.

## 7. 자동 ALTER는 하지 않는다 — **판정 완료**

소유자 질문(「자동 type alter 안 되나」)에 대한 실측:

```
core_slot   숫자 아님 4,567건   예: C14, C23, C19
dt_slot     숫자 아님 4,567건   예: S18, S25, S13
event_time  파싱 실패 0건 — 그러나 형식 3종(20자/19자/그 외 21,150) + NULL 522
```

`C14`를 숫자로 캐스팅하면 실패하거나 **접두사를 떼고 `14`로 조용히 바꾼다.** `event_time`은
파싱은 되지만 타임존 기준이 섞여 있어 변환 후 **몇 시간씩 어긋난 값**이 자리잡는다.

**결론: `ADD COLUMN`만 자동, `ALTER TYPE`은 절대 자동 아님.** 현행 설계가 옳다.
**어떻게.** 이 근거를 `schema_drift` 주석에 남긴다 — 다음 사람이 「왜 타입은 안 고치지」라고
물을 때 답이 코드에 있어야 한다.

## 8. 유일성을 백필 전에 못 잰다 — **③ 제약 입력 + 계측**

`order_by`가 행을 유일하게 지목하지 못하면 **백필 실행 중에** 거절된다. 오늘은 내가 임시
스크립트로 미리 쟀다:

```
['dt_job','dt_index']      26,359 / 34,939   중복 8,580   ← 소유자가 처음 고른 것
['dt_job','dt_cell_key']   34,939 / 34,939   유일        ← 실측으로 찾음
```

컴파일 검사는 「카탈로그 키를 포함하는가」까지만 본다 — **실제 데이터의 유일성은 안 본다.**

**어떻게.** §2의 드롭다운과 같은 자리. 조합을 고르면 **즉시 실측 유일성**을 보여 준다.
화면이 없다면 명령으로 먼저: `check_source_ordering.py <source_id>`.

## 9. 첫 문제에서 멈춘다 — **④ 진단 (착지함)**

`load_setup`이 첫 거절에서 예외를 던진다. `validate_bundle_errors`는 **전부** 돌려주는데
쓰이지 않았다. 전수로 바꾸자 5번 저장할 것이 1번이 됐다.

**작성 경로는 전수, 실행 경로는 즉시 정지.**
