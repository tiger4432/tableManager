# 차트 설계 — 정본 (소유자 확정 2026-08-24)

> 소유자: 「그냥 «차트별로 내부 컨피그» 달면 될 텐데 — 사용 마킹 그룹, x, y, value」
> 소유자: 「차트별 컨피그랑 마킹 저렇게 해 두면 이제 «차트 확장이 계속 가능»해서
>  추가 기능 개발이 매우 쉬워져. **차트 설계 정본으로 박아**」
>
> 상위 정본: `task/MARKING_CONTRACT.md` (마킹이 무엇인가) · 이 문서 (차트가 무엇인가)

---

## 1. 한 줄

**차트는 «부품 종류»가 아니라 «선언 하나»다.**
같은 부품이 선언을 갈아입고 트렌드도 되고 맵도 되고 표도 된다.

```
chart = {
  marking : { reads, writes },   // 사용 마킹 그룹
  x       : …,
  y       : …,
  value   : …
}
```

🔴 **새 차트를 만든다 = 이 선언을 «하나 더 쓴다».** 코드는 안 는다.
그것이 이 설계의 «유일한» 합격 기준이다.

---

## 2. 네 축이 각각 무엇인가

```
marking.reads    어느 마킹에서 «출발»하나          -> walk 의 start
marking.writes   찍으면 어디에 «쓰나»               -> 클릭이 만드는 것
x                가로로 무엇을 «펼치나»             자재 · 시각 · 격자 x · inchip x
y                세로로 무엇을 «펼치나»             값 · 격자 y · inchip y · (표라면 행)
value            «무엇을 그리나»                    walk 의 collect + 그릴 값
```

**`marking` 이 「어디서 시작하나」이고 `x·y` 가 「어디에 놓나」이고 `value` 가 「무엇을」이다.**
셋이 갈리면 차트의 «종류»는 그 조합의 결과이지 미리 정할 것이 아니다.

## 2-bis. `value` 는 «엣지·개체 쌍»이다 — 소유자 확정 (2026-08-24 저녁)

> 소유자: 「**value 표현 좋다 `observed.die`, `inspected.die` 이렇게 타겟 edge, entity 쌍으로
> 한정하는거**」

```
value = <엣지>.<개체>        「어느 엣지로 닿은 · 어느 개체를 세나」
비율이면 «둘»               { numerator: 'observed.die',  denominator: 'inspected.die' }
```

**그 쌍이 하는 일은 «한정»이다.** 엣지 하나와 개체 하나를 지정하는 것으로
「무엇을 세는가」가 닫힌다 — 세는 법을 따로 적을 데가 없어진다.

```
observed.die     observed 로 닿은 die 를 distinct 로  ->  «난» 칩 수
inspected.die    inspected 로 닿은 die 를 distinct 로 ->  «본» 칩 수
```
🔴 **「한 칩에 보이드 여러 개여도 한 칸」이 `.die` 에서 «공짜로» 나온다** (소유자 원문).
오늘 실측된 485% 같은 수(칸당 7개)가 나올 자리가 사라진다.

### 그래서 트렌드의 walk 은 «하나»다

```
start     = marking.reads          (마킹 없으면 모집단 전체 = 소유자 도식의 「서버 walk」)
collect   = point / finding
분모      = 그 walk 에서 inspected.die
분자      = 그 walk 에서 observed.die
x         = 닿은 노드가 «든» 속성으로 group   (웨이퍼 · 레그 · 랏 · 설비 …)
y         = 분자 / 분모
```

### 세 상태가 «따로 만들 것 없이» 나온다
```
inspected 있고 observed 없음   ->  깨끗함 (대조군)
inspected 없음                 ->  «안 봤음» — 0 이 아니라 «부재»
```
지금은 이 셋을 별도 모집단 CTE 로 만들고 있다. 쌍 표기면 walk 이 그대로 답한다.

### 🔴 왜 이 표기가 필요했나 — 실측 (2026-08-24)
```
사고   void 트렌드 72점이 found_rate «전부 0». 맵은 같은 웨이퍼에서 «발견 28»
원인   ledger_trends 가 분자는 «자기 SQL»(object_payload->>'finding_kind'),
       분모는 «스캔 관계의 컬럼»(inspection_run) 에서 가져온다 — 둘이 «다른 곳»에 산다
       -> 원자가 그 이름을 qualifiers 밑에 들자 «분자만» 죽고 분모는 건강했다
       -> 103,841 중 «15개»만 세고 있었다
증거   그 파일이 «자기 주석에» 적어 뒀다:
       「전에도 이 라우트가 건강한 분모를 보고하면서 발견을 0으로 셌다」  = 두 번째다
```
**쌍 표기 + 한 walk 이면 이 사고가 «구조적으로 불가»하다** — 분자와 분모가 같은 걷기에서
같은 문법으로 나오므로 한쪽만 조용히 죽을 수 없다.

### 채택 전에 재야 하는 것 «둘» (추측하지 않는다)
```
① 예산   마킹 없는 기본 트렌드는 모집단 전체를 걷는다. 걷기 대조가 쓰는 것과 «같은 게이트»
         (max_atoms · 결정적 표본 · gate 를 응답에 적기)가 필요하고 비용을 재야 한다
② 도달   inspected 원자가 x축 그룹 키(레그·랏·설비)까지 «걸어서» 닿는가.
         walk 이 entity_ref 를 건너는 것은 실측됨 (코어 다이 -> DT 다이 «2홉»)
```

### 재료는 «이미 있다» (2026-08-24 실측)
```
inspected    die_inspection       117,662     <- 「봤다」도 원자다. 이게 분모의 재료다
observed     void_observation     103,841
             delam_obs             11,567
```

## 2-ter. 「차트는 «창»이다」 — 소유자 정식화, 그리고 지금과의 거리 (2026-08-24 저녁, 실측)

> 소유자: 「**마킹1 -> 마킹2 이렇게 이어지면서 서브그래프 탐색을 계속하는거야.
> 차트들은 그 서브그래프를 «보여주는 창»이고**」
> 소유자: 「우리 프로젝트는 **walk 제어가 핵심**인듯 — 어떻게 걸어서 연관 있는 거를
> 유기적으로 뽑아서 온톨로지 탐색을 가능하게 하느냐」

```
모델   마킹1 --walk--> 서브그래프 --찍기--> 마킹2 --walk--> 서브그래프 --...--> 계속
창     차트는 그 서브그래프를 «보는 창». 창은 «가져오지 않는다» — 고른다
```

### 🔴 지금은 창이 «아니다» — 한 번 켤 때 요청 «13개» (실측, 한 페이지 로드)
```
composition   ×2    같은 final_chip_id 로 «두 번». 인자 동일 = «중복»
trends        ×3    window=180d · kinds=void · kinds=delam
subgraph      ×1    collect=quantity        <- 🔴 «walk 은 이것 하나뿐»
lot_map       ×3    void ×2 «인자 동일 중복» · delam ×1     <- 소유자 「버려」 판정한 라우트
siblings      ×4    leg · bond_lot · scan_recipe · bond_eqp  <- «알약마다 하나»
─────────────────────────────────────────────────────────
라우트 5개 · 요청 13개 · «정확히 중복» 2개 · 그중 walk «1개»
```
**차트가 창이면 이 수가 「마킹 수」여야 한다.** 지금은 「차트 수」다.
그리고 `siblings ×4` 는 소유자 상설을 정면으로 어긴다 —
「화면이 하나 늘 때 fetch 함수가 하나 늘면 어긴 것」. 알약이 하나 늘면 요청이 하나 는다.

### 🔴 원인은 «인자의 모양»이다 — 소유자 진단: 「마킹 받게 했으면 없을텐데」

요청 13개가 «무엇을» 인자로 받는지 보면 원인이 한 줄로 나온다:
```
composition   ?final_chip_id=SYN-CX-CHIP-001        <- «칩 id»    (마킹 아님)
lot_map       ?row=SYN-CX-BW-001&by=wafer           <- «행 키»
siblings      ?scope=leg:HBM-B_LOW-P                <- «축:값»
trends        ?kinds=void&grain={…}                 <- «grain 선언»
subgraph      ?id=<노드>&collect=quantity           <- 🔴 유일하게 «노드»에서 시작
```
**subgraph 하나만 마킹의 언어로 묻는다.** 나머지 넷은 «도메인 키»로 묻는다.
```
칩 id 를 받는 라우트는  ->  «칩마다 한 번» 불릴 수밖에 없다
마킹을 받는 라우트는    ->  마킹 «전체»에 한 번 답할 수 있다
```
🔴 **그래서 요청 수는 화면 탓이 아니라 «인자 모양의 결과»다.** 중복 둘이 그 증거다 —
`composition?final_chip_id=X` 가 두 번인 것은 두 부품이 «각자 그 칩 id 를 풀었기» 때문이다.
둘 다 「마킹1」을 받았다면 walk 은 하나였다.

📎 이것은 CLAUDE.md 에 이미 적힌 위반 ②의 실물이다 —
   「라우트를 더 판다: 화면이 하나 늘 때 fetch 함수가 하나 는다.
    늘어야 하는 것은 «선언»이지 갈래가 아니다」

### 그래서 목표가 «수»로 적힌다
```
지금   요청 13 · 라우트 5 · walk 1 · 중복 2
목표   요청 = «마킹 체인의 길이».  라우트 = «walk 하나».  중복 = 0
       차트는 그 결과에서 «고르기만» 한다 (선언: start = 어느 마킹 · collect = 무엇을)
```
🔴 **이것이 「walk 제어가 핵심」의 실무 번역이다.** 핵심은 알고리즘이 아니라
**「무엇이 걸어서 닿는가」와 「닿은 것이 자기를 뭐라고 부르는가」** — 둘 다 «선언»의 성질이다.

### 오늘 실패 «전부»가 그 둘 중 하나였다 (2026-08-24)
```
① 닿지 못함   마킹이 질의에 «안 실림» (positive/negative 부재)        -> start 가 틀림
② 닿지 못함   transfer 72,964 가 «값»이라 엣지가 «없음»                -> 코어까지 못 걸음
③ 거리       die 주어가 wafer 주어보다 «2홉 멀다»                      -> 같은 술어, 다른 깊이
④ 못 부름     finding_kind 가 qualifiers 밑 -> 읽는 쪽이 «defect» 로   -> 닿았는데 이름을 잃음
⑤ 못 부름     트렌드가 최상위만 봐서 103,841 중 «15» 를 셈             -> 화면이 0% 를 답함
⑥ 예산       node_limit 400 에서 끊김을 «부재»로 읽을 수 있었음        -> 끊김 ≠ 없음
```
**알고리즘 결함은 «하나도 없다».** 전부 도달성·명명·예산이다.
그래서 walk 제어는 «코드를 고치는 일»이 아니라 «선언을 맞추는 일»이다.

### 마킹 체인의 길이는 «선언»이지 설계가 아니다
```
저장소   이름 붙은 마킹을 «여럿» 담는다 (이미 그렇다)
부품     marking:1 / marking:2 를 «선언»에 적는다
그래서   마킹3 은 «선언 한 줄». 코드가 아니다 -> 「탐색을 계속한다」가 구조적으로 가능하다
지금 2인 이유  부품 선언이 둘만 쓰기 때문. 한계가 아니다
```

## 2-quater. walk 이 «잘 도는» 토폴로지 조건 — 실측 기반 (2026-08-24 밤)

> 소유자 질문: 「수학적으로 walk 이 잘 동작할 토폴로지 조건」

```
모델   그래프는 사실상 «이분» — 개체 ↔ claim(원자). 개체→개체 한 홉이 «실제로는 2홉»
       실측 근거: 씨앗 하나에서 entity 129 · claim 257 (≈1:2)
       -> 🔴 «실효 깊이는 명목의 절반». 개체 거리 3을 원하면 hops ≥ 6
탐색   씨앗 집합에서 폭우선 · 예산 B(node_limit ≤ 1000) · 깊이 h · 목표 종류 K(collect)
```

### ① 거리 균일성 — `d(s,K)` 가 씨앗에 «무관»해야 한다
```
실측   void 원자   wafer 주어 «2홉»  ·  die 주어 «4홉»   (같은 술어, 다른 깊이)
결과   hops 는 상수인데 거리가 다르면 «같은 질문이 웨이퍼마다 다른 답»
대안   walk 이 「깊이」가 아니라 «그 종류까지의 거리»를 답한다
```

### ② 차수 예산 — `b^d ≤ B`
```
실측 차수   웨이퍼→die «128» · 레시피→웨이퍼 «600» · die→void ≈7      예산 B «1000»
감당 깊이   b=128 -> ≈1.4      b=600 -> ≈1.07
🔴 즉 «지금 이 그래프는 허브 방향으로 깊이 1 밖에 못 간다». 체인을 늘리면 여기서 막힌다
```

### ③ 🔴 허브는 «펼칠 노드»가 아니라 «분류 라벨»이다
멱법칙 그래프에서 BFS 는 두 홉 안에 허브를 만난다 — «만나는 건 못 피하고 펼치는 걸 피한다».
```
나쁨   레시피를 «통과» -> 600장을 실어 온다
좋음   레시피를 «라벨»로 -> 「이 둘이 같은 레시피인가」를 «펼치지 않고» 판정
```
📎 소유자 확정 표기 `value = <엣지>.<개체>` 가 정확히 이 모양이다 — 홉이 아니라 «이름».

### ④ 정밀도 — `|모은 것| / |밟은 것|`
```
실측   후보 «21» / 밟은 «435» = «4.8%»
원인   collect 가 순위·전파만 몰고 nodes[] 를 «안 자른다»
       -> 후보 21을 얻으려 claim 257·entity 129 를 실어 오고, 예산은 그것들이 먼저 쓴다
```

### ⑤ 🔴 «종류 몫그래프»의 연결성 — 가장 실용적인 조건
인스턴스(수십만)가 아니라 «종류로 나눈 몫그래프»를 본다. 노드 예닐곱이라 손으로 그려진다.
```
wafer ──inspected──▶ die ──observed──▶ point          ✅
wafer ──processed_with──▶ recipe                       ✅ (오늘 착지, 되돌아 나가는 변은 허브에 막힘)
die ──transfer──▶ die(DT)                              🔴 양끝이 «다른 DT job 이름»
wafer ──?──▶ chip                                      🔴 변 «없음»
quantity(클래스) ──?──▶ value                          🔴 변 «없음»
```
> **조건**: 제품이 묻는 (출발 종류, 도착 종류) 쌍 «전부»에 대해 몫그래프가 «연결»이어야 한다.
> 오늘 빠진 엣지 넷이 정확히 이 그림의 끊긴 변이다. 「어디까지 걸리나」는 인스턴스를 재는 문제가
> 아니라 «이 작은 그림을 보면 답이 나오는» 문제다.

### 지금 적합도와 «가장 싼 순서»
```
① 거리 균일성  🔴 위반    ② 차수 예산 🔴 깊이 1    ③ 허브 규칙 «없음»
④ 정밀도 «4.8%»           ⑤ 몫그래프 🔴 변 넷 끊김
```
**다섯 중 넷이 위반인데 화면이 도는 이유**: 지금 쓰는 경로가 전부 «깊이 2 이내»다.
체인을 늘리는 순간 다섯이 «동시에» 물린다.
```
순서   ④(collect 가 실제로 자르게) → ③(허브는 라벨) → ⑤(끊긴 변 넷) → ①(거리를 답하게)
       ②는 ③④가 서면 «저절로» 완화된다
⚠️ ④ 착수 전 측정 하나: 어느 node_kind 가 «증거»에 물려 있나.
   안 재고 자르면 후보의 「실측 21」이 「이름뿐 21」이 된다
```

## 3. 지금 화면의 여덟이 이 선언으로 «전부» 나온다

```
차트                marking.reads  writes    x            y            value
──────────────────────────────────────────────────────────────────────────────────
메인 트렌드          marking:1      marking:1  자재         비율/물리량   point (비율)
후보 트렌드          marking:2      marking:2  자재         물리량       point (그 물리량)
본딩 맵             marking:1      marking:1  격자 x       격자 y       die + point
코어 맵             marking:2      marking:2  격자 x       격자 y       die + point
칩 확대             marking:1      marking:1  inchip x     inchip y     point (+extent)
composite           marking:1      marking:1  inchip x     inchip y     point (여러 die)

⑦ 좌표는 «자리 목록»으로 온다 (placements)

```
