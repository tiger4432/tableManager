# [Task] 외부 경로도 워크스페이스 파서로 들어간다 — 해석 층 하나만 고친다

> **상태:** 착수 승인 대기
> **소유자 지적:** 「parser로 들어가는 입구는 외부든 내부든 같아야 해」 ·
> 「하드코딩을 왜 이렇게 해?」 (2026-08-18)
> **소유자 상설 규율:** 「최소 수정으로 레이어만 수정하고 다른 인터페이스는 건들지 마」

## 무엇이 막고 있나 — 실측

같은 파일 형식을 읽는데 **입구가 둘이고, 서로 만나지 않는다.**

| 경로 | 파서를 어떻게 찾나 | 소유자의 `void.py`가 쓰이나 |
|---|---|---|
| 내부 `<표>/raws/` | `<표>/scripts/`의 `.py`를 전부 올려 `BasePipelineParser` 하위 중 **`match()`가 True인 첫 번째** (`directory_watcher.py:2129-2178`) | **예** |
| 외부 `external_sources` | `parser` 문자열을 **코드에 박힌 화이트리스트**와 대조 → 내장 모듈 (`SUPPORTED_EXTERNAL_PARSERS = {"voids_json"}`, `:263`) | **아니오** |

결과: **「외부 폴더를 내 스크립트로 읽기」가 지금 코드로 표현 불가능하다.**
`parser: "void"`는 화이트리스트에 없다고 거절되고, `parser: "voids_json"`은 소유자 스크립트가
아니라 내장 모듈이 돌면서 `table_name: "void"`를 안 받는다고 또 거절한다.

## 왜 하드코딩됐나 (변명이 아니라 진단)

외부 소스 기능이 **하나의 피드(void)를 위해 나중에 붙었고**(`2dec4fb`), 「config가 임의
코드를 부르지 못하게」를 가장 싸게 지키는 방법이 화이트리스트였다. 경계 자체는 옳다 —
오늘 원장에서 `trusted_cutover_implementations()`를 두고 내린 판단과 같다.

**그리고 오늘 원장에서 이미 같은 문제를 고쳤다.** 손으로 관리하는 목록 대신 저장소에 실재하는
구현을 발견하게 했고(`ledger/implementations.py`), 목록이 사라져도 경계는 남았다.
여기서도 같은 답이 통한다 — **워크스페이스 `scripts/`에 실재하는 플러그인만 쓸 수 있다**는
것 자체가 경계다. config는 표 이름만 말하고, 코드 위치를 말하지 않는다.

## 바뀌는 것 — 해석 층 하나

`validate_external_source_specs`가 `parser`를 화이트리스트와 맞추는 **그 지점 하나**를 바꾼다.

- `parser`가 **비어 있으면** 내부와 같은 방식으로 찾는다 — `table_name`의 워크스페이스
  `scripts/`를 올려 `match()`가 True인 플러그인을 쓴다
- `parser`가 **적혀 있으면** 종전대로 화이트리스트를 본다 (아래 호환성 참조)
- 어느 쪽으로도 못 찾으면 **이름을 대고 거절**한다 —
  「`<표>/scripts/`에 이 파일을 받겠다는 플러그인이 없다」

## 🔴 그대로인 것 — 건드리지 않는다

소유자 규율에 따라 다음은 **손대지 않는다.** 지시서의 이 절이 합격 기준의 일부다.

| 그대로 | 왜 |
|---|---|
| `external_sources` 선언 모양 | 기존 항목이 계속 통해야 한다. `parser`를 **선택**으로 만들 뿐 없애지 않는다 |
| `SUPPORTED_EXTERNAL_PARSERS` 경로 | `parser: "voids_json"`을 적은 기존 선언은 **종전과 똑같이** 동작한다 |
| `BasePipelineParser` 계약 (`match()`·`parse()`) | 플러그인을 고쳐 쓰게 하지 않는다 |
| 내부 `raws/` 경로 | 한 줄도 바뀌지 않는다 |
| 표 핸들러·체크포인트·게이트 | 무관하다 |
| `table_name`이 `table_config`에 있어야 한다는 규칙과 키 요구 | 그대로다 |

## 합격 기준

- [ ] `parser`를 **비워 둔** 외부 선언이 그 표의 워크스페이스 플러그인으로 읽힌다
- [ ] `parser: "voids_json"`인 기존 선언이 **종전과 동일하게** 동작한다 (회귀 0)
- [ ] 플러그인을 못 찾으면 **어느 표의 어느 폴더를 봤는지** 대며 거절한다
- [ ] 내부 `raws/` 경로에 변경이 없다 — 그 테스트가 한 건도 안 바뀐다
- [ ] `external_sources` 선언 스키마가 바뀌지 않았다 (키 추가·삭제 없음)

## 덤으로 고칠 작은 것 하나

`enabled: false`인 항목은 지금 **통과도 거절도 아니고 조용히 건너뛴다**(`:310-311`).
그래서 「선언 안 함」과 「꺼 둠」이 화면에서 구분되지 않는다 — 소유자가 오늘 운영에서
「거절도 아니고 그냥 0으로 뜬다」를 만난 원인이다.
등록 시 **「N개 선언 중 M개 비활성」 한 줄**을 로그에 남긴다. 그 이상은 하지 않는다.

## 비범위

- 파서 구현 자체를 합치거나 옮기는 것. 정본은 **워크스페이스 스크립트**이고 소유자가 관리한다
- `void` 표의 키·스키마 결정. 소유자 판정 사항이다
- 외부 소스에 새 기능(재귀 깊이, 다중 파일명 등) 추가
